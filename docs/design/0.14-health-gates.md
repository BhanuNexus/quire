# Quire 0.14 health: three rules become tests

Status: current
Area: tests that enforce project rules (default shortcuts, agent visibility in MCP tools, dialog layout coverage); search and retrieval for callers that may not see every note
Code: `crates/quire-app/src/keymap.rs` (`every_default_shortcut_passes_the_conflict_checker`), `crates/quire-mcp/tests/visibility.rs`, `crates/quire-index/src/{lib,index,sections,hybrid,semantic}.rs` (`Keep`, `*_where`), `crates/quire-index/src/views.rs` (`parse_where`, `run_over`), `crates/quire-intel/src/ask.rs` (`retrieve_where`), `crates/quire-mcp/src/tools/{legacy.rs,read/ask.rs,read/search.rs,read/list.rs}`, `apps/quire-desktop/src/layout_check.rs` (`kind`, `every_kind_of_dialog_has_a_sample`), `apps/quire-desktop/src/overlays.rs` (`OverlayView::type_name`, `capture`)

Plan item 14 of the codebase-health pass. Three rules that `AGENTS.md` marked `[review only]` or "listed ones only" are now tests. Writing the tests found two defects; both are fixed, each in its own commit with a changelog bullet. Item 4 (a per-frame bench for the editor) was not done.

## 1. Default shortcuts and the conflict checker

**Before.** `defaults_work_everywhere` (`keymap.rs`) ran `Keymap::conflicts` over the defaults but skipped six commands and looked only at blocking conflicts (`Taken`, `Reserved`). AltGr and Option conflicts of a new default passed.

**Now.** `every_default_shortcut_passes_the_conflict_checker` checks every binding of `COMMANDS` (80 today) with the checker Settings uses for a person's own keys, for Windows, macOS and Linux at once. A default must have no conflict, or exactly the one its row in the test's table states; a key reserved on another platform does not count against it, because the test checks each platform's own defaults (`Keymap::for_platform`). The table lists the defaults with a warning, and a blocked default is always a failure:

- 6 were blocked on one platform: `Ctrl+Tab`, `Ctrl+Shift+Tab` and `` Ctrl+` `` (⌘ with them switches apps on macOS), `Ctrl+H` (⌘H hides the app), `Ctrl+Alt+Up`/`Down` (switch workspaces on many Linux desktops). The first pass left them; the 0.14 release replaced them (below), so the table has no blocked rows and the test fails on any blocked default.
- 18 warnings: 7 `Alt+<key>` defaults that type a character with Option on macOS, and 11 `Ctrl+Alt+<key>` defaults that are AltGr on Windows. The app lets typing win (`altgr_typed`) or drops the character.

A new default with any conflict fails, a changed conflict fails, and a row whose default is gone fails. Checked by adding `Alt+N` to `NewTask`: the test failed with `NewTask Alt+N: the checker says ["Option"], the table []`.

**Update: the six, per platform.** Each platform with an unfirable default has its own, in `MOVED` (`keymap.rs`); the others keep the old key.

| Command | Old | New | Platform |
|---|---|---|---|
| Next tab | Ctrl+Tab | ⌘⌥PageDown | macOS |
| Previous tab | Ctrl+Shift+Tab | ⌘⌥PageUp | macOS |
| Inline code | Ctrl+` | ⌘⇧C | macOS |
| Find and replace in note | Ctrl+H | ⌘R | macOS |
| Add cursor above | Ctrl+Alt+↑ | Alt+Shift+↑ | Linux |
| Add cursor below | Ctrl+Alt+↓ | Alt+Shift+↓ | Linux |

⌘⇧[ and ⌘⇧] (the Mac tab keys elsewhere) are not usable: ⌘⇧[ is taken by folding. ⌘⌥← and ⌘⌥→ would be the usual choice, but the checker reports every Ctrl+Alt+arrow as a Linux workspace key. ⌘R sits beside ⌘⇧R (replace in all notes) as ⌘F does beside ⌘⇧F. Ctrl+Alt+Shift+arrows move a window to another workspace on GNOME and KDE, so Linux gets Alt+Shift+arrows. Not pressed on a real Mac or Linux desktop: the keys come from the platforms' published shortcut lists and the checker.

Stored keys: `settings.toml` keeps only a command's own list when a person changed it, but Settings also writes a command's defaults into that list (adding a key beside them, or another command taking one). `Keymap::for_platform` replaces the old default in such a list with the platform's new one (no key twice); keys a person chose, and an empty list (unbound), stay as they are. Nothing is rewritten on disk, so a settings file copied back to an older Quire works as before.

**Editions.** `COMMANDS` has no edition-dependent rows (no `cfg` in `commands.rs`), so one table holds for both. The test lives in `quire-app`, beside the checker; `cargo test -p quire-app --no-default-features` runs it for Lite (see "What was run").

Other key handling is not in this test: the drawing editor's keys have their own (`keys_dont_conflict_with_quires`), and the fixed keys of dialogs (Escape, Enter, arrows) are not shortcuts a person can change.

## 2. MCP tools and hidden notes

**Before.** Four hand-written tests in `tests/security.rs` and a list of named calls in `tests/connections.rs`. A new tool was covered only if someone added it there.

**Now.** `tests/visibility.rs`, `read_tools_never_tell_a_vault_with_hidden_notes_apart`:

- Two vaults with the same visible notes, which link to the hidden ones by name, by typed link and in front matter. The second also has a `deny` zone (`Private/`, eleven notes, enough to fill a page of hits), hidden folders (`.obsidian/`, `.trash/`) and a locked folder (`Journal/`). It is served twice: locked (`Server::open_with`) and unlocked in the server's process. Each server's index also holds the text of PDF pages with the same words: a visible `wiki/scan.pdf` in both vaults, and `Private/diary.pdf` and `.obsidian/scan.pdf` in the second, so `search` with `kind: attachments` or `all` ranks pages a caller may not see.
- The tools are every tool of `ToolRegistry::standard()` with `Access::Read` or `Access::Ask` (25 today). A new tool is covered without editing the test.
- Arguments come from each tool's input schema: required properties get the first ordinary value that works in the plain vault; then each property in turn gets every hidden name (paths, titles, tags, property names, a view spec), every ordinary value, both booleans, a few numbers and every `enum` value; a property that is an object (`search`'s `filters`) gets each of its own properties in turn, with the same values. The hidden values include a `where` condition with a line break that adds `sort:` and `limit: 1`. 1,740 calls per run, about 20 seconds.
- A reply from the vault with hidden notes must equal the plain vault's, after taking out the strings the call itself sent and the vault's folder. Order is not compared (lists of equal rank come out of hash maps in any order, from run to run); with a limit under 10 only the shape is compared (how many items and lines), because which of several equal notes makes the cut also varies. Every hidden note carries `zq` in its title, body, tags, properties, link types and tasks; no reply may contain it, or `.obsidian/`, `.trash/`, `Journal/`, `.qenc` or `quire-lock`. Sources must be numbered from 1 without gaps.

**Defect found and fixed: ranked tools leaked that hidden notes matched.** `ask`, `ask_notes`, `search` and `search_notes` ranked the whole index, took the top k, then dropped what `common::visible` hides. A hidden note that ranked high took a place within the limit, and in `ask` a source number. An agent asking about a word found only in a deny zone (`secrettagzq`) got one visible passage numbered `[3]`, which says that two hidden passages matched first. The fix ranks only visible notes: `quire_index::Keep` is a predicate over note paths; `Index::search_where`, `Index::search_sections_where`, `IndexService::search_sections_where`, `IndexService::hybrid_search_where`, `SemanticIndex::search_where` and `quire_intel::retrieve_where` rank only what it keeps, and the four tools pass `|p| visible(cx, p)`. The old functions call the new ones with a predicate that keeps everything, so the app's own search and Ask are unchanged. Unit tests: `notes_the_caller_may_not_see_take_no_places` (`quire-index`), `retrieve_where_numbers_only_what_it_keeps` (`quire-intel`). Reverting the fix makes the generic test fail on `ask_notes` calls (for example `sources numbered [3, 4]`).

**Defect found by a later review and fixed: a `where` condition cut before hiding.** `list` and `search` (`filters.where`) spliced the agent's condition into `where: {w}`, ran it as a view over every note, and only then dropped hidden notes. A line break in the condition added view keys: `salary > 10\nsort: salary desc\nlimit: 1` kept one row, and when that was a hidden note the visible result came back empty, which says that a hidden note has a larger salary. Now `views::parse_where` refuses a condition with a line break (`invalid_args`), and keeps only the condition's filters of what it parses; `list` runs it with `views::run_over` and `visible`, and `search` passes its `keep` to `Index::allowed`, which does the same. `run_in` asks `keep` only about notes that pass the view's own tests (`from` and, for notes, `where`), so a condition costs one policy check per matching note, not per note of the vault. Unit tests: `a_where_condition_is_one_line` (`views.rs`), `the_where_filter_sees_only_what_keep_accepts` (`sections.rs`).

**Left, and still a leak: shared index statistics.** The server's index, its word statistics (IDF) and its meaning model (LSA vectors) are built from every note, hidden ones included. So what a hidden note says shifts which visible notes rank high enough to show "by meaning", and a word found only in hidden notes can bring up a visible note: in the test, `ask` for `secrettagzq` abstains in the plain vault but lists a visible "nearest passage" in the other, because the hidden notes put that word next to "shared words". No hidden text, path or title is returned; what leaks is that a word co-occurs with visible content somewhere hidden. A fix needs an index (or at least statistics and a meaning model) per visibility set; deny zones can differ per client, so this is a design change, not a test-pass fix. The test tolerates differences in these four tools (`RANKED`) as long as the reply names nothing hidden and numbers its sources from 1; it prints how many (58 per run today). For `search` and `search_notes` the number of hits found by keyword (and of PDF pages) must still equal the plain vault's whenever both replies have fewer hits than `limit`: a hidden note that took a place would push a visible one out. Hits found by meaning alone are not counted, because whether a passage is close enough by meaning depends on the meaning model. Checked by undoing fixes: without the `where` fix the test fails on `list` and `search` with the line-break condition; without the attachment fix (1c61e37) on `search` with `kind: attachments` and `all`; with `keep` ignored when ranking keyword parts, on `search` for `shared`, `Ideas` and `diary`.

**Not covered.** Write tools (`create`, `rename`, `delete`…) and resources (`resources/list`, `resources/read`) are not in the generic test; resources and some write paths are in `security.rs` and `connections.rs`. `AGENTS.md` says `[review only]` for write tools.

## 3. Every dialog in the layout check

**Before.** `layout_check` laid out the dialogs listed in `overlays()` and `registry::layout_samples`. Nothing failed for one left out. The research count (24 `impl OverlayView`, all listed) was right, but two `Overlay` variants had no sample: quick capture (`Overlay::Capture`) and the template picker (`Mode::Templates`).

**Now.**

- `kind(&Overlay)` names each variant, and each palette `Mode`, in a `match` without `_`: a new variant does not compile until it is named there. A dialog in its own file is named by its type (`OverlayView::type_name`, test-only, a default method using `std::any::type_name`).
- `every_kind_of_dialog_has_a_sample` reads the variants of `enum Overlay` and `enum Mode` from `overlays.rs` and every `impl OverlayView for <type>` in the crate's source, and fails for any without a sample, naming it. Checked by removing the template-picker sample: it failed with `["Templates"]`.
- Samples added: the template picker, and quick capture empty and with 40 lines.

**Defect found and fixed: quick capture with a long text ran off the window.** The text field grew with its text, so at 900×560 and 760×480 the dialog's top was above the window (`[183 -112] - [717 672]`) and its buttons out of reach. The field now scrolls inside a box at most 40% of the window high.

All dialogs and every `OverlayView` compile in both editions (none is behind a feature), so the same samples are checked in Lite.

## Other findings, not changed

- Hash-map order reaches tool output: `tasks`, `links`, `neighbors` and `properties` list notes of equal rank in an order that changes from run to run, so with a small `limit` the note that makes the cut is random. Not a leak; it makes replies non-reproducible (and caches keyed on a reply miss).
