# Quire 0.13: packaging

ARM64 Linux, a Flatpak, and `.md` file associations. Requests behind it: a Flatpak (Joplin's issue, 92 votes), ARM64 Linux (the requests for Obsidian's Snap on ARM64), and opening `.md` files from the file manager (555 votes for "open `.md` files outside the vault"; 0.12 added the command-line and drop paths in `quire_app::single_file`, 0.13 adds what the operating systems need to call it).

Nothing here changes the app's behaviour apart from one line: the window's application id (§5). Everything else is in `packaging/`, `.github/workflows/` and the docs. **Nothing was built in CI**: the workflow changes pass `actionlint` and `zizmor` and the pieces that can run on a Linux x86_64 box were run (what and how: §7).

## 1. ARM64 Linux

**What ships:** `Quire-<v>-linux-aarch64.tar.gz` and `.AppImage`, `Quire-<v>-linux-arm64.deb`, for both editions, with the engine bundled in the full edition's three packages exactly as on x86_64 (the engine job builds `aarch64-unknown-linux-gnu` too, its pin is `engine.sha256.aarch64-unknown-linux-gnu`, and Quire Lite downloads `quire-ai-engine-aarch64-unknown-linux-gnu.gz` on demand). File names follow each format's own word for the architecture, as the x86_64 ones do (`x86_64` and `amd64`).

**Native, not cross-compiled.** GitHub's arm64 Linux runners are free and unlimited for public repositories (generally available since August 2025; [runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners): `ubuntu-24.04-arm`, `ubuntu-22.04-arm`, `ubuntu-26.04-arm`; 4 CPUs, 16 GB RAM, 14 GB SSD for public repositories). The release uses `ubuntu-22.04-arm`, the arm64 twin of the x86_64 job's `ubuntu-22.04`, so the binaries need glibc 2.35 or newer on both. Native builds need no cross linker, no emulated tests and no second set of system libraries, and the smoke tests (install the `.deb`, run the AppImage and the engine, tamper with the engine) run on the machine they are for. The jobs are one matrix: `edition` × `arch`, with the runner and the Debian architecture name added per arch.

**What differs from x86_64**

- **No `--icf=all` on aarch64.** The flag (identical code folding, about 1 MiB per binary; [0.10 §2](0.10-perf.md)) works because Rust 1.97 links *x86_64* Linux with `rust-lld`. aarch64 Linux still links with the system's GNU `ld`, which doesn't know the flag, so passing it would fail the link. `package.sh` sets it only when building x86_64. (Installing `lld` and using `-fuse-ld=lld` would restore it; not done because the saving is small and unmeasured here.)
- **Size budgets are the x86_64 ones** (80 MiB full, 50 MiB Lite, 25 MiB engine; raised from 75/45 in 0.13, see below): `check-size.sh` takes the binary and the edition, nothing architecture-specific, and its "stripped" check uses `readelf`, which reads any ELF. aarch64 code is usually about as big as x86_64's; the first run gives the real numbers. Without ICF it can be about 1 MiB larger; the budgets have 7 and 4 MiB of headroom.
- **The sync server is x86_64 only**, as before. The same crates would build on aarch64; it wasn't asked for, and it adds a build to each release.
- **CI** also runs `cargo test --workspace` on `ubuntu-24.04-arm` for every pull request, so arm-only failures (SIMD code in candle and the vector crates, endianness assumptions) show before a release.

**Checked scripts.** `unpack-engine.sh` and `engine.sha256.<target>` take the target as an argument and in the file name, so they handle the new target as is; `packaging/test-unpack-engine.sh` gained a case that the aarch64 and x86_64 pins are kept apart. `pin-models.py` pins models, not engines, and doesn't mention targets. `build.rs` of `quire-ai` reads `engine.sha256.$TARGET`. `fetch-appimagetool.sh` takes the architecture and has the SHA-256 of the aarch64 `appimagetool-aarch64.AppImage` and `runtime-aarch64` of the same releases as the x86_64 ones (downloaded and hashed for this change; the x86_64 hashes were re-checked against the pinned ones).

## 2. Flatpak

**Which edition: the full edition only, one app id** (`io.github.bhanunexus.Quire`). Reasons: a Flatpak is a distribution channel with one listing per app; Lite exists for people who count download size, which a Flatpak with a shared runtime doesn't help, and a second listing would need its own id, review and updates. The two editions share settings and files, so people who want Lite use the `.deb`, AppImage or archive. Revisit if people ask.

**Built from source, offline** (the Flathub way): `packaging/flatpak/io.github.bhanunexus.Quire.yml`, freedesktop runtime 26.08 and its `rust-stable` extension (26.08's is Rust 1.98; the workspace needs 1.97, and an older extension would fail on `rust-version`, so the manifest prints `rustc --version` first). `flatpak-cargo-generator` (pinned commit and SHA-256) turns `Cargo.lock` into `cargo-sources.json`, 916 crates with checksums, which is generated by the release workflow and git-ignored. Inside the sandbox, `cargo --offline build --release --locked` builds the engine, then its SHA-256 is written to `crates/quire-ai/engine.bundled.sha256` and the app and `quire-cli` are built with it, which is what `package.sh` does for the `.deb`. `/app/bin` holds `quire`, `quire-cli` and `quire-ai-engine` side by side, where the app looks for the engine.

**Why not repackage the release binaries:** Flathub requires source builds, and one manifest then serves both CI and a later submission (the only change is the first source: `dir` to `git`, [packaging/flatpak/README.md](../../packaging/flatpak/README.md)).

**Permissions** (`finish-args`): Wayland, fallback X11, IPC and DRI for the window; the network (sync, AI providers, update check); PulseAudio (voice notes); the Notifications and Secret Service buses (reminders, API keys in the keyring); and **`--filesystem=home`**. The last is the one to defend: notes are in folders people choose and Quire watches them for changes by sync tools. The file-chooser portal gives access to one folder through a FUSE path where change notifications don't work, and it doesn't carry over to the next start. A narrower `xdg-documents` would not cover `~/Notes`, `~/Sync` and so on. It can be narrowed by users with `flatpak override`. Flathub will review it as an exception. File dialogs already use the portal (`rfd` with `xdg-portal`).

**AppStream and the desktop file.** The metainfo (`packaging/linux/io.github.bhanunexus.Quire.metainfo.xml`) now has four screenshots at the release tag, `<provides>` with `text/markdown`, `<url type="help">`, an empty OARS 1.1 rating (no content classes apply: no violence, no user-generated content shared with others, no purchases) and a release entry with the date, a link and the notes. `render-metainfo.py` makes the release entry from CHANGELOG.md: the date from `## [x.y.z] - date`, the notes from the section's opening paragraph. A version with no section gets "Release notes are on the release page." The `.deb`, the AppImage and the Flatpak all install the rendered file (the Flatpak does it with the same script). `appstreamcli validate --no-net` passes; `--pedantic` reports only that the id has a capital letter (`Quire`), as every reverse-DNS app id does.

**The app id's case.** The old id was `io.github.BhanuNexus.Quire`; it is now `io.github.bhanunexus.Quire`, as the request suggested and as `appstreamcli` prefers (a mixed-case developer id is a validation warning, and it fails the command). It renames the `.deb`'s and AppImage's desktop entry, icon and AppStream file; nothing else keyed on it. Flathub verifies the namespace and the id is permanent once published, so check its current rule on case before submitting.

**Not done, on purpose:** nothing was submitted to Flathub; `flatpak-builder-lint` wasn't run (it's in the CI image and runs as an informational step); the update check is left as it is (opt-in; shows a link to the GitHub release, which in a Flatpak is the file, not an update); no Flatpak for Lite; no `flathub.json`.

**Open items before a submission:** the first CI run's build time and disk use (§7); the linter's findings; whether Flathub wants `home` or accepts the override route; a decision on the update check (hide it when `FLATPAK_ID` is set?); an `xdg-desktop-portal`-based file-open path would be the way to drop `home` later.

## 3. `.md` file associations

**One rule on all systems: offer, never take.** Quire is added to the "Open with" list for `.md` files and never becomes the default. Linux packages don't write `mimeapps.list`, the macOS entry is `LSHandlerRank` Alternate, the Windows keys only add choices.

**Only `.md`, not `.markdown`.** `single_file::is_markdown` (and `NotePath::is_markdown` under it) accepts `.md` only. Registering `.markdown` would list Quire and then refuse the file with the "Quire opens Markdown (.md) files" notice, so it isn't registered. Supporting `.markdown` (and `.mdown`) is a change to what a note is across the vault crates, not a packaging one; it is deferred.

**Linux.** The desktop entry has `MimeType=text/markdown;text/x-markdown;` and `Exec=quire %f`. `%f` is one file: file managers start one Quire per selected file. `%F` would pass several files and the app opens only the first one (`main.rs` reads one argument), losing the rest without saying so. `%U` would pass `file://` URLs, which Quire doesn't parse. `inode/directory` isn't added: opening a folder as a vault works from the command line (`quire ~/Notes`), but listing Quire for every folder in every file manager's "Open with" is noise, and no other platform has the equivalent. `install.sh` (the archive) installs the same entry and runs `update-desktop-database`; the `.deb` relies on dpkg's desktop-file-utils trigger. `desktop-file-validate` passes (one hint: more than one main category, as before).

**macOS.** `Info.plist` has no document types and no UTI import: Quire is not listed in Finder's *Open With* for `.md` files (see the next paragraph for why). Both CI's `packaging` job and the release's macOS job check that `CFBundleDocumentTypes` is absent.

**The open-file Apple event is not handled, and can't be here.** A Finder double-click, *Open With*, a drop on the Dock icon and `open -a Quire file.md` don't put the file in `argv`: Launch Services sends the running (or starting) app an `odoc` Apple event, which AppKit hands to `application:openFile:` / `application:openURLs:` on the application delegate. Quire's windowing is eframe 0.37 over winit 0.30.13 (Cargo.lock). winit 0.30 has no event for it: a grep of its macOS backend finds only `WindowEvent::DroppedFile` (a drop *on the window*), and its `platform/macos.rs` documents that you have to define your own `NSApplicationDelegate` method with `objc2`'s `declare_class!`, which is `unsafe` code, and the workspace forbids `unsafe`, and it would add `objc2` as a direct dependency (it is in the tree through winit, at two versions). So the file is **not opened** when launched that way; AppKit shows its "cannot open files in this format" alert. What works: `open -a Quire --args notes.md` and `quire notes.md` (the argument path, tested on Linux through the same code), and a drop on the window. **Decided:** listing Quire in Finder's *Open With* only to show an error is worse than not listing it, so the `CFBundleDocumentTypes` and UTI keys were removed before release; the release check now makes sure they stay out until the event is handled. Ways to make it work later: a small crate or winit release that exposes the event (winit 0.31's `ApplicationHandler` is the likely route), or an exemption for one audited `unsafe` module.

**Windows.** The installer is NSIS (`packaging/windows/quire.nsi`). A new component, *Offer Quire for .md files* (on by default; `/S` installs get it), writes only HKCU keys: the `Quire.Markdown` ProgID with an open command `"quire.exe" "%1"` and an icon, an empty `Quire.Markdown` value under `HKCU\Software\Classes\.md\OpenWithProgids` (adds a choice to *Open with* without touching the default), `Applications\quire.exe` with `SupportedTypes`, and `Capabilities` plus `RegisteredApplications` so Quire shows in Settings → Default apps. It tells Explorer with `SHChangeNotify(SHCNE_ASSOCCHANGED)`. The uninstaller removes exactly these. Windows 10 and 11 don't let an installer set a default for the user (the hash check on `UserChoice`), and this doesn't try. The portable zip changes nothing. The script compiles (NSIS 3.08 on Linux, both editions) with stand-in files; that is all that was run.

**Opening a file while Quire is running: a second window.** There is no single-instance mechanism (a search of the apps and crates finds none), and adding one means a local socket or per-platform event handling plus rules about which vault the file belongs to, so each file opens in a **new Quire process**, in single-file mode when it is in no vault (`single_file::resolve`), or in its vault when it is in one. Starting Quire twice on one vault was already possible, so this adds no new case. A single running instance that receives files is deferred.

**To check by hand, on a Mac:** install the `.dmg`, then (1) *Open With* on an `.md` file does not list Quire; (2) `open -a Quire --args ~/x.md` and `/Applications/Quire.app/Contents/MacOS/quire ~/x.md` open it. **On Windows:** (1) install with the component on; right-click an `.md` → *Open with* lists Quire, and *Choose another app* too; (2) Settings → Default apps → Quire lists `.md`; (3) the default for `.md` is whatever it was; (4) choosing Quire opens the file; a file in a vault opens in the vault; (5) uninstall: the entries are gone (`reg query HKCU\Software\Classes\Quire.Markdown` finds nothing), and `.md`'s own default and other programs' choices remain; (6) install with the component unticked: no `Quire.Markdown` key; (7) the portable zip leaves the registry alone. **On Linux** (a GNOME, KDE or other desktop): the `.deb`, `install.sh` and the Flatpak: *Open With* lists Quire for an `.md` file, and opening it starts Quire on that file.

## 4. Release hygiene

- **New assets** are `*.tar.gz`, `*.deb` and `*.AppImage` for aarch64 (the existing globs), and `*.flatpak`. All of them reach the publish job as `quire-*` artifacts, get entries in `SHA256SUMS`, a build-provenance attestation in their own job (the Flatpaks inside the job's container), and the SBOM attestation (`dist/*.flatpak` was added to its subjects).
- **The publish job's download takes `pattern: quire-*` now**, because the Flatpak's crate list (`flatpak-cargo-sources`) is an artifact too and must not land in the release; before, it took every artifact and removed what didn't belong (`engine.sha256.*`, which isn't a `quire-*` name). The `rm` stays as belt and braces.
- **The release notes template** (`packaging/release-notes.sh`) lists ARM64 and the Flatpak in its table and says which assets are x86_64 only.
- **README** has the ARM64 files, a Flatpak section and a section on opening `.md` files; **RELEASING.md** the new rows, the job description and `packaging` among the checks to require.

## 5. The window's application id

`main.rs` sets the viewport's `app_id` to `io.github.bhanunexus.Quire`. On Linux, desktops match a window to its `.desktop` file by it (Wayland's app id; X11's window class, which `StartupWMClass` in the desktop entry now names): without it the window has no application id and shows a generic icon, ungrouped from the launcher entry. It matters most in a Flatpak and with Wayland. It was unset before, so on X11 the class was the program name, which the old `StartupWMClass=quire` matched. Nothing is read or stored under this id on other systems.

The archive's `install.sh` still installs `quire.desktop`, not a file named after the id, so a Wayland desktop that matches by file name (GNOME) doesn't match that install (as before), while X11 matches by `StartupWMClass`. Making it install the id-named file is left for a later change.

## 6. What the new CI jobs are, and what could fail on the first run

**`ci.yml`**: `test (ubuntu-24.04-arm)` (the existing test job on arm64), and `packaging` (validates the desktop entry, renders and validates the AppStream file for the current version and an unknown one, parses the Flatpak manifest, compiles the NSIS script with stand-in files, checks the macOS plist, `shellcheck --severity=error` on the scripts).

**`release.yml`**: the `engine` matrix has `aarch64-unknown-linux-gnu`; the `linux` matrix has `arch` and the runner; `flatpak-sources`, `flatpak-image`, `flatpak` and `flatpak-attest` are new; `macos` checks the plist; `publish` needs `flatpak` and `flatpak-attest`. Where the first run can fail:

1. **The Flatpak build's disk and time.** A cold Rust build of the full workspace plus the runtime, SDK and Rust extension on a 14 GB runner (the container shares the host's disk). If the job runs out of space, free space before the container starts (that needs the container in a later job or removing preinstalled toolchains), or build the Flatpak in a self-hosted or larger runner. The timeout is 120 minutes. Watch `flatpak (aarch64)` first.
2. **The builder image's digest isn't recorded yet, so the first tag release stops on purpose.** `ghcr.io/flathub-infra/flatpak-github-actions:freedesktop-26.08` is pinned by digest: the `flatpak-image` job resolves the tag (`docker buildx imagetools inspect`), the `flatpak` job runs `image@<that digest>`, and a tag release fails unless the digest equals the one in `packaging/flatpak/builder-image.digest`, which holds `unrecorded` until someone records it (a moved tag fails the same way). Before the first release: run the Release workflow by hand on the branch (a dry run only warns), read its `Resolved:` line, check the tag is what flathub-infra/actions-images built, and commit `echo sha256:... > packaging/flatpak/builder-image.digest`. This is trust on first use: ghcr.io and every other registry were unreachable from where this was written, so no digest could be read from a public source. The tag's existence (and its arm64 variant) was inferred from the images repository's workflow source, and the `Digest:` line parsing is untested here.
3. **The Rust extension's version** in the 26.08 runtime (1.98 when read in November): if it is older than the workspace's `rust-version`, the build fails at its start, and `rustc --version` is the first line of the log.
4. **Offline builds**: a crate whose build script wants the network, or `cargo fetch` needing something outside Cargo.lock. The generator ran on this `Cargo.lock` (916 crates) and the manifest parses; no `flatpak-builder` build ran.
5. **The smoke test of the bundle**: `flatpak run` inside a privileged container; no session bus, so it only runs `--version` and `ai engine`. If `flatpak run` fails in the container, that step needs to run with `--command` and `bwrap` options, or move to a normal runner.
6. **The arm64 link**: the system linker's flags (no ICF), an `aarch64` size over budget, a crate that fails on arm64 (the CI arm64 test job should catch it first, so run that on this branch before tagging), `libasound2-dev` on the arm runner (same package name).
7. **The AppImage tool on arm64** (`appimagetool-aarch64.AppImage`, run with `APPIMAGE_EXTRACT_AND_RUN=1`): hashed and pinned, not run on arm64 here.
8. **The aarch64 engine**: the candle CPU kernels; the engine job runs `--version` natively.
9. **The attestation job** `flatpak-attest` (a plain runner that downloads the bundles and attests them; the privileged container holds only `contents: read`, no OIDC token) runs on tag releases only, and `publish` waits for it.
10. **`--privileged`** stays: flatpak-builder needs namespaces the runner's AppArmor profile refuses, and the least set of capabilities that works (`SYS_ADMIN`, an unconfined seccomp and AppArmor profile, `/dev/fuse`) couldn't be tried here. The privilege that was removable, the signing token, is removed. Trying the narrower options on a branch run is the next step.
11. **The crate-list generator's Python packages** are installed with `--require-hashes --only-binary=:all:` from `packaging/flatpak/requirements.txt`, which `pin-requirements.py` writes (every release file's SHA-256 for each pinned version, 12 packages). It was checked by installing it here and by a hash-tampered copy failing; a Python older than 3.9 or an unlisted dependency fails the install.

## 7. What was run, here

On Linux x86_64 with the 0.12 tree: `actionlint` and `zizmor` (v1.31.1, as the `workflows` job runs it) on all workflows: clean (`actionlint` also reports no more of the four shellcheck findings it had before); `packaging/linux/package.sh` with a stand-in `cargo` and engine, for x86_64 (all four files and the sync server, the real `appimagetool`) and with `ARCH=aarch64` (tar.gz and `.deb`; the `.deb`'s `Architecture: arm64`); `desktop-file-validate`, `appstreamcli validate --no-net` (and `--pedantic`); `flatpak-builder --show-manifest`; `flatpak-cargo-generator` on `Cargo.lock`; `makensis` for both editions; the `Info.plist` parse; `packaging/test-unpack-engine.sh`; `shellcheck --severity=error` on the scripts; `pin-models.py --check --warn`. `cargo clippy -p quire-desktop -- -D warnings` for the full and the Lite edition (the only Rust change is §5; the machine was shared and a debug build of the app did not finish, so the window class was checked in winit's source, `x11/window.rs` and `wayland/window/mod.rs`, not on a screen, and the argument path is the 0.12 code and its tests, unchanged). Review round: the `packaging` job's steps were run from a clean clone (all pass; the NSIS step had failed in CI because `makensis` changes into the script's folder, so a relative script path broke the icon path), the plist checks against a plist with and without the keys, the `flatpak-image` step against a stubbed `docker` (dry run warns, tag release fails when unrecorded or different, passes when recorded), and the hashed requirements by installing them and by a tampered copy failing. Not run: any real release build, anything on macOS, Windows or arm64, `flatpak-builder` builds, Flathub's linter.

## Size budgets raised (0.13)

The first 0.13 release dry run measured the Lite `quire` at 46 MiB, over its 45 MiB budget (0.10.2 shipped at 41 MiB). Three releases of features account for it: typed links, S3/WebDAV sync, importers and the tidier (0.12), the Excalidraw editor and the sync hardening with `x25519-dalek` (0.13). The budgets move to 50 MiB Lite and 80 MiB full, which keeps the gate meaningful (about 4 MiB of headroom) without blocking the release; shrinking the binaries again is a 0.14 task (a `cargo bloat` pass over the new crates).
