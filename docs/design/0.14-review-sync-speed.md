# Review: 0.14 sync on large vaults (`0.14-sync-speed.md`)

Status: proposed (0.14, awaiting owner approval)
Area: architecture review
Code: `crates/quire-sync/src/engine.rs`, `crates/quire-app/src/vault_sync/`, `apps/quire-sync-server/src/store.rs`

Reviewer: the 0.14 architect. Read against `0.14-architecture.md` and the code at main ad3216d.

## Verdict: approve with changes

This is the design with the most to lose and it treats it that way: delete safety is left
exactly where 0.13.2 put it, every pass still does its own listing, a missing base degrades
to a conflict copy, and the stamp is set only when the engine knows the bytes. Keeping
`Tracked.disk` separate from the base print is better than the frame's wording and I adopt
it. The wire stays at protocol 3 with an advertised, optional batch route. The issues below
are gaps in the new state store's failure rules and three places where a plausible fault
stalls sync rather than loses data.

## Blocking issues

**B1. A damaged or unreadable `state.d` has no rule.** §3.3 "Open" takes "the highest-numbered
checkpoint that parses", truncates and deletes. It does not say what happens when no
checkpoint parses, or when the folder cannot be read. 0.13.2 settled this for `state.json`
(`open_state_named` in `vault_sync/state.rs`): unreadable now is an **error** (never a fresh
start); damaged is **kept aside**, sync starts afresh, and a notice says so.
*Fix:* state the same two rules for `state.d` (keep the whole folder aside, packs included).
Do the destructive part of open (truncate journal, truncate packs, delete unnamed files)
only after a checkpoint and its journal were accepted, never on the fallback path. A bad
journal line that is followed by good lines is damage, not a torn tail: stop there as
designed, but raise the notice. Add all three to the fault-injection list in §6.

**B2. An edit that stat missed can stall every pull for a day.** If a note changed while
keeping size and mtime, its manifest row is stale. An incoming revision for it then fails
the compare-and-swap on every pass (bytes on disk differ from the row). In `Engine::pull`
a failed apply leaves the cursor where it is, so nothing after that revision is applied
until the daily verify. §3.1 says a read that finds other bytes "tells the manifest", but a
failed compare-and-swap is not named as such a read.
*Fix:* make it explicit: a failed `write_bytes_if` corrects the row (or drops it) before the
pass returns, so the next pass sees a changed stamp, reads the note and merges. Test:
`an_edit_that_kept_its_time_and_size_merges_on_the_second_pass` with an incoming revision
for the same note.

**B3. Batches can be larger than what sits in front of the server.** 1,000 notes of the
bench vault are about 8 MB of text, about 11 MB as base64 JSON, and the cap is 16 MiB of
sealed bytes (about 22 MiB of JSON). Self-hosted servers behind a reverse proxy often allow
far less per request; today only large attachments hit that. A `413` (or a proxy's reset)
must not fail first sync where single pushes worked.
*Fix:* state the cap in request bytes; set the server's body limit for the route to match;
on `413` halve the batch and retry, down to single pushes, for the rest of the session.
Test with a router that refuses bodies above 1 MiB.

**B4. The own-revision cursor is argued for the server only.** "Move `cursor` while
`cursor + 1` is one of our accepted seqs" is sound where the server assigns contiguous
seqs. §3.4 claims the same fix for folder, S3 and WebDAV, where positions come from
`FolderTransport` (`next_seq`, `LanePos`, per-device logs) and are not obviously one
contiguous counter that every reader agrees on. Risk 6's property test names `MemoryServer`
only.
*Fix:* either show, per transport, why a skipped position can never hold another device's
revision, and run the three-device property test on `FolderTransport` and the S3/WebDAV
mock too; or enable the cursor advance on the server transport only in 0.14. A revision
skipped here is one that never arrives on this device, so the proof comes before the speed.

**B5. Two Quire versions on one device.** §3.7 handles "downgrade and back". It does not
say what a person sees when a 0.13 `quire-cli sync once` in cron alternates with a 0.14
app: each 0.13 run starts afresh (copies of notes changed since), each 0.14 run throws its
`state.d` away and migrates again. Nothing is deleted, but it makes copies every round.
*Fix:* detect it (a `state.json` that does not match `migrated_from` appearing a second
time) and say "an older Quire is also syncing this vault on this device; update it" as a
sync notice. Put "update every Quire on a device together" in the release notes.

## Non-blocking changes

- **Idle budgets per transport.** The frame's `sync once` rows are for the Quire Sync
  server; the "note files opened: 0" and "state bytes written" counts hold on every
  transport. The frame is corrected. The folder index cache (question 2) can wait.
- **Windows.** `Manifest::scan` must take size and time from the directory walk
  (`DirEntry::metadata` costs nothing extra there) and not call `stat` per file; otherwise
  an idle pass at 50k notes misses 600 ms on NTFS. This is a requirement on the frame's A2,
  recorded there.
- **`Manifest` shared with the UI.** `note_written` from a save must never wait for a scan
  in progress (P9). A2 queues own-write hints; the review of index-startup has the same note.
- **Pack compaction to purge a locked note** is correct. Add the sentence that a purge is
  the only compaction that may run in a pass that otherwise changed nothing (it writes).
- **Chunk size 5,000 and 16 uploads** are guesses, as marked. Keep 8 uploads unless the
  mock and one real provider show a gain; fewer moving parts in a release that already
  changes the state store.
- **Migration peak memory** equals today's pass (the whole `state.json` in memory, 697 MB
  at 50k in the scan), once. Say so in §3.7; free disk needed is about the size of
  `state.json` again until step 4.
- **Verify cadence.** Once a day when idle is fine. Skip it on battery if the platform says
  so cheaply; otherwise leave it.

## Conflicts with the frame and the other designs

1. **Frame §2 "compares the row's hash with the hash of its merge base":** replaced by
   `Tracked.disk` (the stamp of the bytes last known equal to the base). Accepted; the frame
   is updated.
2. **Frame API:** adds `Manifest::verify`. Accepted.
3. **Frame §3 "no appends":** the journal and packs append, under `SyncLock`, in
   `.quire/sync/`. That rule is for caches shared between processes; sync state is neither.
   No conflict.
4. **Index-startup** shares the `Manifest` instance in the app. Sync's rule "every pass runs
   its own scan" must not be weakened by the index's use of cached rows: the two designs
   need one sentence each saying a scan's `Delta` is delivered to every consumer, so the
   index does not rescan for what sync just found.
5. **Agent designs:** none.

## Simpler alternatives

- **Shard files instead of checkpoint plus journal.** 1,024 small files keyed by `FileId`
  prefix, each replaced whole with `quire_base::fs::write_atomic`, plus a small `head.json`
  (cursor, `left`, `skipped`, `deletes_sent`) written last. A one-note change rewrites one
  shard (about 17 KB at 50k). No replay, no line hashes, no truncation at open; crash safety
  comes from "shards first, cursor last" and the engine's existing idempotent re-pull. Its
  cost is fsyncs in bulk: a 5,000-note chunk touches every shard. The journal is better
  there and the designer's crash table is complete, so I do not ask for a change; I ask for
  one paragraph in §4 that weighs it, because the journal is about a thousand lines of new
  crash-critical code and shards are about two hundred.
- **Drop the 16-way upload and the tip-per-1,000 change (S2c for S3/WebDAV) from 0.14.**
  They are not needed for any budget in the frame and touch the transports with the least
  test coverage (the real-server job is weekly). Keep the folder batch.
- **Server-only cursor advance** (B4) if the per-transport proof is not quick.

## Questions for the owner

1. Going back to 0.13 on a device starts sync afresh there and keeps differing notes as
   copies. *Recommendation: accept; say it in the release notes with "update every Quire on
   a device together".*
2. Persist the folder/S3/WebDAV transport index so `sync once` on those transports is also
   fast? *Recommendation: not in 0.14.*
3. Measure joining a large vault (per-note fsync, all pulled revisions in memory) and fix
   it in 0.15 if it is worse than first sync? *Recommendation: yes, measure now.*
4. S3/WebDAV uploads 16 at a time? *Recommendation: stay at 8 in 0.14 unless measured
   against a real provider (differs from the designer's 16).*
5. A daily background re-read of every note (about 390 MB at 50k notes) to catch edits that
   kept their file time and size. *Recommendation: yes, when idle.*
