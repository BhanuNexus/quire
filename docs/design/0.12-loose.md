# Quire 0.12: the 0.11 follow-ups

Status: built on `feat/0.12-loose`. Owner: the 0.12 follow-ups work.

What 0.11 left open, and the startup headroom the next features need:
startup work moved off the first frame (§1), notes of unlocked locked
folders in the app's own features (§2), pictures in locked folders (§3),
sharp zoomed diagrams (§4), the floating toolbar's own buttons (§5), and
three small leftovers (§6).

## 1. Startup headroom

The perf job's startup budget is what a 10,000-note vault adds over an
empty one before the first frame: 20 ms, failing above 25 ms. 0.10.2
measured 11–12 ms in CI; 0.11 measured 19.9 ms. The next feature would
have failed CI.

### What ran before the first frame

Traced with `strace -f` on the bench build (`QUIRE_BENCH=startup`, which
exits as the second frame starts, so everything traced ran before the
first frame was on screen), on the CI bench vault (`quire-cli bench
vault`: 10,000 notes in 50 folders and `Big.md`):

* **Two walks of the whole vault on the UI thread**: 102 directory opens
  and 220 `getdents64` calls, all on the main thread. Backtraces on
  `LocalFs::list` (an instrumented debug build that printed one per call,
  from the last 0.11 startup fix) put them in
  `pdf_state::start`, which `Workspace::tick` ran in the first frame to
  queue every PDF for the text job, and in `attach::refresh_file_cache`,
  which the sidebar's Files tab ran in the first frame for the files that
  aren't notes (`Workspace::other_files`).
* Small reads: the locked-folder records (`.quire/shared/locked-folders.json`
  and this device's record), the agent policy (for the AI switch),
  `.quire/shared/vault.toml` four times (periodic notes' prefs, and the
  task timer's prefs, read again on every tick), `references.bib` (a
  stat) and `.git`. Each is one small file or a missing one.
* What 0.11 added on top of 0.10.2 that isn't a file: parsing the keymap
  and toolbar settings, and the task timer. They cost well under a
  millisecond each; the walks were the 10,000-note part.

After the changes the same trace shows no directory listing of the vault
before the first frame (20 calls on vault paths, all the small files
above, most of them missing).

### What changed

* **No listing of the vault before the first frame, and none on the UI
  thread.** The list of files that aren't notes (`attach::FileCache`: the
  Files tab's PDFs, boards and canvases, and the files embeds point to) is
  read on a thread of its own (`quire-file-list`, lowest priority), and not
  before `Workspace::start_deferred` (the second frame). Until it arrives,
  embeds don't resolve and the Files tab lists notes only; a watcher event
  marks the list stale and the old one stays until the new one arrives, so
  pictures don't flicker. `Workspace::tick` collects it (the app repaints).
* **The PDF text job lists the vault on its own thread** (`quire-pdf-list`),
  also only after the deferred start. Before, `pdf_state::start` listed the
  whole vault in the first frame's tick.
* **The task timer is read from the second frame on.** Its file is small,
  but it was read in the first frame, and the vault's prefs file
  (`.quire/shared/vault.toml`) was read on **every** tick for the pomodoro
  lengths, even with no timer running; now only while one runs.

Kept before the first frame, on purpose: settings, the session, the
records of locked folders (two small files: without them a restored note
in a locked folder whose key file is missing could be read as plain) and
the agent policy's AI switch (0.11 review S-M10: no embedder is ever set
up for a vault with AI off).

### Measured

The CI measure is wall time: the first frame with 10,000 notes minus
the first frame with an empty vault, medians of runs. This VM was shared
with two other builds the whole time (load 3–8 on two cores), which made
wall time swing by ±35 ms between runs, more than the thing measured. So
the table also gives CPU time (user and system time of the whole process
until it exits at the second frame), which the other builds don't
change, from the same alternating runs:

| `perf` profile, 10,000 notes minus empty vault | Before (main, fca9330) | After |
|---|---:|---:|
| CPU time to the first frame (median of 25 alternating runs) | +20.7 ms (136.1 vs 115.4) | −1.2 ms (116.0 vs 117.2), i.e. nothing |
| Wall time, same runs (median) | +36.9 ms | +4.0 ms |
| Wall time, `perf-check.py` (5 runs), two runs of the job | | 6.5 ms and 27.8 ms |

| Debug build, wall time (median of 9 alternating runs) | Before | After |
|---|---:|---:|
| What 10,000 notes add before the first frame | +92 ms | none measurable (−31 ms, noise) |

CI measured 19.9 ms for 0.11, the same as the CPU-time "before" here: on
an idle runner the walks were the whole cost. After, the 10,000-note
vault costs nothing measurable before the first frame, so the 20 ms
budget has its full headroom again (0.10.2 measured 11–12 ms, which
included the two walks too).

The other budgets of the job are unchanged by this work (the index
build, search, MCP and canvas code paths weren't touched; the typing

reads the file list it already had, and a sweep of locked pictures that

## 2. Locked notes in the app's features while unlocked

0.11 kept locked notes out of tasks, the agenda, Bases and views, the
graph, backlinks and reminders, even while their folder was unlocked,
because all of those read the vault index, and the vault index (and
everything built on it: agents, MCP, jobs, caches) must never hold one.

### Design: a memory-only overlay, joined at read time

* While a folder is unlocked, its notes are in a second `quire_index::Index`
  in memory (`SecureState::locked_index`, built on a thread when the folder
  unlocks, kept up to date with edits and outside changes, dropped when
  the folder locks). 0.11 used it for search only.
* **`quire_index::Joined`** reads the vault index and that overlay as one:
  `records`, `get`, `source`, `modified`, `paths`, `tasks`, `resolve` (the
  side of the linking note first), `backlinks` and `outgoing`. Each index
  resolves links only to its own notes, so the links between the two sides
  (a plain note linking to a locked one, and back) are worked out by
  `CrossLinks::build`: plain notes are visited only if they have links the
  vault index can't resolve, and every note of the overlay. It is cached
  per (vault index version, overlay version), memory only.
* **`Workspace::with_notes(|joined| …)`** is the one way in, and
  `Workspace::notes_version()` the cache key. The features that read it:
  the sidebar's Tasks tab, the agenda (list, board, calendar, time), views
  and Bases (rows, board chips, map pins), the graph (`Graph::build_joined`),
  backlinks in the Insights panel (`Workspace::overlay_backlinks`), the
  resolution of the open note's links, and reminders.
* **Nothing else reads it.** Agents, MCP (stdio and HTTP), ACP and the
  agent panel, `serve`, publish, export, background jobs (`JobCx` holds the
  vault index and the vault without keys) and every cache still read the
  vault index only. The canonical guard stays where it was:
  `AgentStore::effective` denies every path in a locked folder, and
  `Vault::without_keys` can't read one.
* **On lock** the overlay drops the folder's notes at once (not when the
  rebuilt one arrives), the cross links, view results and the cached
  agenda are cleared, and reminders of the folder leave memory (shown,
  missed and snoozed ones).

### Reminders from locked notes

* They are scheduled from the overlay, so they **fire only while their
  folder is unlocked**. One that comes due while the folder is locked (or
  Quire is closed) is listed as missed when the folder is next unlocked,
  once a session, if it is less than a week old.
* They never go into the list of shown reminders on disk
  (`<config>/reminders/<key>.json` holds a reminder's text as its key).
  `quire-cli remind` can't read locked notes, so the two never both show
  one.
* The desktop notification says "A reminder in a locked note" and the
  note's name (file names are visible on disk anyway), never the task's
  words: the system may keep its notifications on disk. The in-app notice
  and the agenda show the text (memory).

### No plaintext on disk

The task timer already wrote only the note's name for a locked task
(0.11). The scan test now covers every new path:
`secure_state::tests::unlocked_notes_join_the_features_from_memory_only`
unlocks a folder and reads it through tasks, the agenda, task notes, a
view, a Base, map pins, the graph, backlinks both ways and reminders,
starts the timer on a locked task, saves, flushes history, and then scans
every file of the vault (`.quire/` and the trash included, gzip files
decompressed) and the timer's folder for the locked notes' marker. The
same test checks what agents and jobs see while it is unlocked (the vault
index has no note of the folder, no search hit, no backlink from it; the
vault without keys can't read it; `effective` denies MCP, panel and ACP
clients), and that locking takes the notes out of every feature.

### Lint

Lint runs as a background job on the vault without keys, so it called
every link to a note in a locked folder broken (seen while checking this
by hand). It now gets the locked notes' names (names aren't secret, and
it never reads them), so such a link counts as resolved.

### Limits

* A link written with a dot in its target (`[[Day.v2]]`) from a plain note
  to a locked one isn't joined: the vault index doesn't keep such targets
  among its unresolved links. Links in locked notes are all checked.
* Related notes, unlinked mentions and link suggestions in the Insights
  panel still come from the vault index alone (they read embeddings and
  term statistics, which are never built from locked notes).
* The timeline, flashcards and lint still leave locked notes out.

## 3. Pictures in locked folders

* **Showing them.** The file list now also knows the files of locked folders
  by their plain names (`photo.png` for `photo.png.qenc`), for embeds only;
  the sidebar still lists the stored names. `Workspace::attachment_source`
  says whether an embed is a plain file or a locked one;
  `Workspace::attachment_path` never returns a locked one (its bytes on
  disk are ciphertext). `Workspace::read_locked_attachment` decrypts one
  into memory while its folder is unlocked. The desktop's
  `locked_media` hands those bytes to egui as `bytes://quire-locked/<path>`
  (the editor's inline pictures and the preview), and once a frame forgets
  the ones of folders that locked (egui's bytes and texture caches).
* **Adding them.** Pasting a picture or dropping a file into a note of an
  unlocked folder stores it with `Vault::save_locked_attachment` in the
  folder's own attachments subfolder (`Journal/attachments/`, the vault's
  attachments folder name), encrypted, with a name free of both plain and
  encrypted files. A dropped `.md` becomes a note in the locked folder. While
  the folder is locked, adding is refused with the reason.
* **Export and publish** still refuse a locked note, and a plain note that
  embeds a locked picture can't take it along (export resolves through the
  vault index, publish through the plain file list; neither finds it).
* Not done: **PDFs** in locked folders. The PDF view reads its file from
  disk by path in several places (text, pages, annotations); decrypting
  for it means a second source for all of them. A locked PDF still opens to
  the lock screen. Excalidraw drawings in locked folders aren't drawn
  either.
* Tested in `secure_state::tests::pictures_in_locked_folders` (resolution,
  decryption, paste and drop into the folder's subfolder, nothing in the
  plain attachments folder, no plain PNG and no marker anywhere on disk,
  nothing shown or added once locked) and `locked_media::tests`.

## 4. Zoomed diagrams stay sharp

A Mermaid diagram is drawn at 1.5× its size; zoomed (0.11 allows 8×) it
was that picture stretched, soft past about 2×.

* `typeset_ui::zoom_bucket(factor)`: the scale step for a picture shown at
  `factor` times its size in points: none up to 1.5×, then 2, 3, 4, 6, 8
  and 12×. Zooming within a step reuses one picture.
* **Debounced:** `diagram_ui::sharp_texture` asks for the step only once
  the zoom has rested for 250 ms; meanwhile the sharpest picture drawn so
  far (the last step, while the engine still has it, else the ordinary
  one) is stretched. It repaints itself when the wait is over.
* **Bounded cache:** zoomed pictures are kept apart from the note's other
  pictures (`Typesetter::zoomed`, keyed by the hash of (job, scale)): at
  most 6 and 160 MB, least recently used first; each is at most 4,096
  pixels a side (the existing cap). Zooming never pushes formulas and
  other diagrams out of the main cache.
* In notes, the preview and full screen (where the fit to the window
  counts as zoom too).
* Only Mermaid diagrams zoom; formulas (Typst) aren't zoomable, so they
  don't need this.

## 5. The floating toolbar's own buttons

* `[toolbar] floating_items` (TOML `[[toolbar.floating_items]]`), the same
  `ToolbarItem` as the main bar's `items`: missing, the 0.11 defaults;
  empty, no floating bar at all.
* Settings → Toolbar: "Above the editor" / "Next to selected text" picks
  which bar's buttons the list edits (add any command or macro, a
  separator, move, remove, icon, label, reset). The heading menu is
  offered for the main bar only (a menu can't stay open on a bar that
  follows the selection).
* Renaming or deleting a macro updates both bars.
* The floating bar is placed with its width as last drawn, so wider
  custom icons still stay inside the window.

## 6. Small leftovers

* **Agenda board order.** The agenda's own board has no view in the
  vault, so its settings stay on the device:
  `<config>/vaults/<key>/agenda-board.json` holds the view lines Quire
  would write in a `quire-view` block (`order.<column>`, `color.<column>`,
  `swimlanes`), so dragging, colours and lanes all work on it. Ids are
  note paths. Format: [boards.md](../formats/boards.md#the-agendas-board-012).
* **Vim's Ctrl+B, F, D and U.** `quire-text`'s Vim gains Ctrl+D and Ctrl+U
  (half a page, or `count` lines, as Vim). In Normal and Visual mode those
  four keys now go to Vim instead of Bold, Find, Add cursor and the rest
  (`[editing] vim_ctrl_scroll`, on by default, Settings → Editing). On
  macOS Quire's shortcuts are ⌘ and Vim's ⌃, so nothing changes there.
* **The AI engine's priority.** On Linux a process starts at its parent
  thread's priority, and background jobs run at nice 19 (0.11), so an
  engine a job was the first to need ran at 19 instead of the 10 that
  `nice -n 10` asks for; a lowered priority can't be raised again without
  privileges. The engine is now started from a thread of its own
  (`quire_ai::engine::prepare_spawner`), made by the UI thread at the
  deferred start; any caller hands it the command. Tested on Linux:
  started in place from a lowered thread `nice` reports 19, through the
  spawner the normal 10.
