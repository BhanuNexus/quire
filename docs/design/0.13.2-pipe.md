# Quire 0.13.2: the release pipeline and the documents

The release-pipeline-and-docs team's part of the 0.13.2 data-safety pass (branch `fix/0132-pipe`). No features, no Rust, no `Cargo.toml`. Source: the health scan's items 1, 2, 3, 4, 9 and 13 and the polish scan's items 10, 11 and 17 (read from `main` at 6cbfbcd). **Nothing here could be run as a release**: no workflow was dispatched, and nothing was built (the machine's two CPUs belonged to other teams). What was run, and what was not, is in the last section.

## 1. Guard the tag (health 1): real, fixed

**Real.** `tag-release.yml` checked only the version string, `Cargo.toml` and the changelog section. It never asked whether CI had passed, and the Flatpak builder-image check could only fail after the tag existed (a moved upstream tag burned the version). On a dry run the same mismatch was only a warning.

**Changed.**

- `tag-release.yml` has a `tag-guard` job (`contents: read`, `checks: read`, `actions: read`; no write token) that runs first, and `tag` needs it. The guard checks the version, that the tag does not exist, that CI passed on `github.sha` (`packaging/check-ci-green.sh`), that the builder image is the recorded digest (`packaging/flatpak/check-builder-image.sh`), and `pin-models.py --check` when `release.yml` sets `REQUIRE_MODEL_PINS: "true"`. `tag` checks that the commit it tags is the commit the guard checked.
- A new optional input `check_only` (default false) runs the guard and stops. The dispatch call in the brief works unchanged (`-f ref=main -f 'inputs[version]=X'`).
- The builder image's tag moved into `packaging/flatpak/builder-image.ref`, so the Release workflow and the guard read one name. `flatpak-image` now runs the same script and **fails on a mismatch, dry run or not**.
- Every action is still pinned by SHA (no new action was added; `audit.yml` reuses the pins already in `ci.yml`). `actionlint` and `zizmor` (1.31.1, `--offline`, as CI runs it) report nothing.

**What "CI passed" means** (`packaging/check-ci-green.sh`): the `CI` and `CodeQL` workflows each have a push run for the commit with conclusion `success`; and the latest check-run of every name on the commit is `success` or `skipped`. Check-runs belonging to the `Release` and `Tag release` workflows are left out (they are not CI, and a failed earlier dry run on the same commit must not block a tag). "Latest" is by `started_at` per name and app, so a re-run that passed counts. `skipped` is accepted because the `dco` job has `if: github.event_name == 'pull_request'` and is therefore `skipped` on every push to `main`: the check-runs of 6cbfbcd show `dco completed skipped`. Anything else (`failure`, `cancelled`, `neutral`, `timed_out`, still running) refuses the tag.

**The exception list and the CodeQL evidence.** The list is `packaging/ci-exceptions.txt`: one check-run name and a `# reason` per line, **empty by default**, and a line without a reason is an error. I read the check-runs of the last twelve commits of `main` (`gh api repos/BhanuNexus/quire/commits/<sha>/check-runs`):

- The failing "CodeQL" check-run is not the `CodeQL` workflow. It is the check from the GitHub Advanced Security app (`app.slug` `github-advanced-security`), titled "1 new alert including 1 critical severity security vulnerability", whose summary says "New alerts in code changed by this pull request" and links to PR 67. It sits on the commit because the PR's head commit became the `main` commit. The `CodeQL` workflow's own push run, and its `analyze (rust)` and `analyze (actions)` check-runs, were `success` on the same commits.
- The annotation is "Hard-coded cryptographic value" at `crates/quire-sync/src/crypto.rs:187`. That line is `Hkdf::<Sha256>::new(Some(domain.0.as_bytes()), ikm)`: the HKDF *salt*, a public domain-separation label (`"quire-sync v1"`, `"quire-sync key box v1"`), not a key. It is a false positive.
- That check-run was `failure` on six of the twelve commits (5a96d2e, the 0.13.1 release commit; d21b669; 0bf7aa4; 18e3db1; f92b9ea; 2fc8724) and `neutral` on b3e87f3. I read its title and annotation on the first four: identical (one critical alert, PR 67, `crypto.rs:187`); the other two I did not open. It is `success` ("No new alerts", PR 69) on 6cbfbcd. Run against these commits, the script refuses 5a96d2e (the CodeQL result only), 0bf7aa4 and b3e87f3, and passes 6cbfbcd.

So an exception **would have been needed for the 0.13.1 release commit, but none is needed for the current tip**, and the right fix for that false positive is to dismiss the alert in Security, Code scanning ("false positive", with that reason), not to list the name here. I left the list empty. If the alert reappears on a release candidate, the guard stops the tag and says which check-run; the maintainer then dismisses the alert or, last, adds `CodeQL` to the list with a reason and a date to delete it.

**Left.** The scan's other suggestion, a `main` branch ruleset requiring these checks, is a repository setting that cannot be made from a file; RELEASING.md still lists it under one-time settings, and the scan could not read the rulesets in the UI. The `v*` tag ruleset's empty `include` is unchecked too.

## 2. The dry run exercises the publish path (health 2): real, fixed

**Real.** `publish` and `flatpak-attest` had `if: startsWith(github.ref, 'refs/tags/v')`, so checksums, the file set and the SBOM step ran for the first time on the real tag.

**Changed.**

- `packaging/release-files.txt` is the one list of release files (`<v>` for the version): 27 files (twelve Linux packages, the sync server, two Flatpak bundles, two DMGs, four Windows files, the SBOM, five engine downloads). I compared it with the real 0.13.1 release's asset list (`gh api repos/BhanuNexus/quire/releases/tags/v0.13.1`): the names are the same, plus `SHA256SUMS` itself.
- `packaging/release-files.sh` (`list`, `check`, `write`, `verify`): the folder holds exactly the expected files (missing, extra and sub-folders all fail, and the message names them); `SHA256SUMS` is written outside the folder and moved in; and verification demands `<64 hex>  <plain name>` lines (two spaces, no `*`, no path), no line for `SHA256SUMS`, none with the empty-file hash, no duplicate, the same names as the expected list, and `sha256sum --strict --check`.
- A new `assemble` job (`contents: read`, no write token) runs on every run, dry or tag: it downloads the `quire-*` artifacts and runs `release-files.sh write`. `publish` (tags only, `environment: release`) needs it, downloads again, repeats `write`, and runs `verify` again just before `gh release create`. So the check runs twice on a real release, and on bytes downloaded separately each time.
- `flatpak-attest` now runs on dry runs too. It checks that `bundles/` holds exactly the two expected `.flatpak` files, each non-empty, and attests only on a tag (`if: env.IS_RELEASE == 'true'` on the attest step). It gained a checkout, for the script.
- `packaging/test-release-files.sh` runs in CI's `packaging` job on every change. It builds stand-in files and checks that a complete set passes and that each failure is refused: a missing file, an extra file, an extra folder, a changed file, a line for `SHA256SUMS` itself (the 0.13.1 bug), an empty file, a missing line, `*` markers, no `SHA256SUMS`, and a bad version. It also checks the engine rows against the `target:` entries of `release.yml`'s matrix, so the list and the matrix cannot drift apart.

**Not covered by a dry run, still:** the `release` environment, `attest-sbom`, `gh release create` and the publish, and every attestation step (they are skipped, as before). A permission or policy problem there still shows only on the real tag.

## 3. The tests leave the critical path (health 3): real, fixed

`check` was one job that did the version and notes check, the model pins and `cargo test --workspace` (22 minutes), and every build needed it. It is split: `preflight` (version, notes, pins; seconds; outputs `version`) is what the builds need; `check` (tests only, `needs: preflight`) runs beside the builds. `assemble` and `publish` need `check`, so a failed test run still stops the release. By the scan's timings the release falls from about 56 minutes to about 34 (the engine 6.4 + macOS 26.4 + publish), **not measured**. The cost is wasted runner time when the tests fail. Builds still restore no caches. `needs.check.outputs.version` became `needs.preflight.outputs.version` in the three places that read it.

## 4. AGENTS.md (health 4): real, done

`AGENTS.md` at the root (115 lines): what Quire is, the two editions, the gate with the exact commands (taken from `ci.yml`, plus the new packaging tests), the small-machine environment, P1 to P10 one line each from `docs/design/0.9.md` §1, a table of the 22 workspace members with direct workspace dependencies (from `cargo metadata --no-deps --format-version 1`, which builds nothing; `cargo tree` was also run, offline, to check the dependency claims), the files many changes collide in (from the scan's `git log` count, as of 0.13.1), commits and the DCO, the one changelog rule, how a release is made, and a never list. `ARCHITECTURE.md` named 10 of the 22 crates; it now has the same 22-row table. `RELEASING.md` has a "Release checklist for an agent". `CONTRIBUTING.md` and the PR template link to `AGENTS.md` and carry the Lite gate.

One thing in `AGENTS.md` is a judgement, not a fact I could check: `RUSTUP_TOOLCHAIN=stable` is listed only for a machine where the pinned toolchain (`rust-toolchain.toml`, 1.97.0) cannot be installed. That is how the 0.13.2 teams' machine is set up (the rules for this pass), not something the project requires.

## 5. Dependency ignores and the weekly audit (health 9): real, done

`.github/workflows/audit.yml`: Mondays 04:41 UTC and `workflow_dispatch`, one job, `permissions: {}` at the top and `contents: read` on the job, the same pinned `cargo-deny-action` as CI, `check advisories`. It opens no issue (that would need `issues: write`); a failed scheduled run is reported by GitHub like any failed workflow. `docs/dependency-ignores.md` lists each of the advisory ignores in `deny.toml` and the four Dependabot ignores, and what lifts each. The scan said 12 advisory ignores; **`deny.toml` has 13** (`grep -c 'id = "RUSTSEC'`), and the page lists 13. `deny.toml` was not touched (no comment either: its comments already say what each waits for). I did not add the dated `# review by` comment or a script that fails when a date passes (the scan's extra suggestion): the brief did not ask for it and it would need a place to fail.

## What was run, and what was not

Run: `typos` (clean); `actionlint` and `zizmor --offline` on all four workflows and the new one (clean); `bash -n` on every script under `packaging/` and the new health check; `shellcheck` on every script I added or touched, at default severity (clean), and `shellcheck --severity=error` on the set CI runs; `packaging/test-release-files.sh` and `packaging/test-check-ci-green.sh` (both pass); `check-ci-green.sh` against the live check-runs of six real commits (as described in §1; it needs a token, here only read access through `gh`); the health check against two local fake servers (a good one, one answering `no`, and nothing listening); `release-files.sh list` against the real 0.13.1 assets. `cargo metadata --no-deps` and `cargo tree --offline --locked` were run for the tables and the ignore page; they build nothing.

Not run, and the lead must check with a dry run of the Release workflow on this branch (`gh api repos/BhanuNexus/quire/actions/workflows/release.yml/dispatches -f ref=fix/0132-pipe`):

- That `release.yml` is accepted and behaves: the `preflight` / `check` split, every job's `needs`, and that `check` really runs beside `engine` and the builds. Look at the job graph first.
- That `assemble` passes on real artifacts: the 27 expected names match what the build jobs upload. The names were compared with the real 0.13.1 assets and with the packaging scripts, but a dry run builds the files for the first time under this list. A mismatch there is a bug in `packaging/release-files.txt`, not in the build.
- That `flatpak-attest` passes its new check on a dry run and still skips attestation.
- That `flatpak-image` now passes on a dry run (the recorded digest in the repository is `sha256:6ed6921b…`; it fails if the upstream tag has moved).
- The `publish` job's changes: its duplicated checksum step, the `verify` before `gh release create`, and the new `needs`. A dry run does not enter it; only a tag release does. Read that job again by eye.
- That the Tag release workflow works with `check_only`: dispatch it from `main` with `-f 'inputs[check_only]=true'` once this is on `main` (it cannot be tried on a branch, since `tag-guard` runs only on `main`). In particular that `GITHUB_TOKEN` with `checks: read` and `actions: read` can read the check-runs and workflow runs of the commit (the script was tested only with a personal token), and that `docker buildx imagetools inspect` works unauthenticated there (as `flatpak-image` already does).
- That the sync server image builds and its health check works inside it. There was no Docker daemon here. The script was tested with this machine's bash; the image's `bash` (Debian bookworm-slim) must support `/dev/tcp`, which I believe but did not run.
- The weekly `audit.yml` (first run next Monday, or dispatch it).
- Repository settings: the `main` and `v*` rulesets (RELEASING.md lists them; they cannot be set from a file), and whether the `release` environment has reviewers.

Outside the lane: `apps/quire-sync-server/Dockerfile` and the new `apps/quire-sync-server/healthcheck.sh` (brief item 6); `docs/design/0.9.md` and `docs/design/0.13-pack.md` (one-line corrections, in `docs/design`, and not another team's `0.13.2-*` note). No Rust, no `Cargo.toml`, no `deny.toml`.
