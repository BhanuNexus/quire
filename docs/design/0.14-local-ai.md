# Quire 0.14: the opt-in local AI pack (Qwen 3.5)

Status: proposed (0.14, awaiting owner approval)
Area: ai
Code: `apps/quire-ai-engine/src/` (new `qwen35.rs`, `deltanet.rs`; `models.rs`, `template.rs`), `crates/quire-ai/src/{catalog.toml,catalog.rs,toolcall.rs,engine.rs}`, `crates/quire-app/src/settings/ai_local.rs`, `crates/quire-app/src/{ai.rs,onboarding.rs,voice.rs}`, `apps/quire-desktop/src/` (Settings → AI, onboarding), `packaging/pin-models.py`, `.github/workflows/release.yml` (`REQUIRE_MODEL_PINS`), `docs/formats/model-catalog.md`

The owner chose an opt-in local AI pack for 0.14: Qwen 3.5 4B for 8 GB machines and 9B
for 16 GB, both Apache 2.0, text model only. The pack also switches on OCR of images and
scanned pages and voice transcription on this computer, which are built but held behind
the 0.9 "experimental" switch. This note says how the engine runs Qwen 3.5, which files
it downloads, what memory it needs, how we check it is right, and how people turn it on.
It keeps to the frame in [0.14-architecture.md](0.14-architecture.md) (§5 budgets, §6
layering, §7 rule 6, §9 steps L1 and L2); where it adds to the frame, §3.9 says so.

Sources named in words below: the Qwen 3.5 4B and 9B model cards and their `config.json`,
`chat_template.jinja` and `tokenizer_config.json` on Hugging Face; the transformers file
`models/qwen3_5/modeling_qwen3_5.py`; llama.cpp's `src/models/qwen35.cpp`,
`src/models/delta-net-base.cpp`, `conversion/qwen.py` and `gguf-py/gguf/constants.py`
(master, read on 2026-11-19); the Gated DeltaNet paper (Yang, Kautz and Hatamizadeh,

## 1. The problem, as measured

- **No released Quire has ever downloaded a language model.** `catalog.toml` has no
  `sha256` in any of the three commits that touched it, and `release.yml` still sets
  `REQUIRE_MODEL_PINS: "false"`. Every model row is "not available in this build", and
  all of on-device AI sits behind `[ai_local] experimental` (`AiLocalSettings::on_device`).
  So there are no Qwen3 users with downloaded files to migrate (§5.2).
- **The engine runs only Qwen3.** `apps/quire-ai-engine/src/qwen3.rs` (411 lines) reads
  `qwen3.*` GGUF keys and Qwen3 tensor names. candle 0.11.1 (the newest release,
  2026-10-31) has no Qwen 3.5 model and no Gated DeltaNet: its `models/` folder has
  `quantized_qwen3.rs`, `mamba2.rs` and `rwkv_v7.rs`, nothing hybrid.
- **What the engine does today** (docs/formats/model-catalog.md, 2 shared vCPUs, Xeon
  2.1 GHz AVX-512, load 4–6, random weights with real shapes): Qwen3 1.7B Q4_K_M uses
  1,191 MB loaded, 1,652 MB after a 1,024-token prompt; reads prompts at 12.3 tokens/s
  (256 tokens) and writes at 1.2–2.3 tokens/s. The Qwen3 4B row (`ram_mb = 3200`) is an
  estimate in the catalog's own comment, not a measurement.
- **Qwen 3.5 is a different shape.** From both `config.json` files: 32 layers, of which
  layers 3, 7, …, 31 (0-based) are full attention and the other 24 are Gated DeltaNet
  ("8 × (3 × (Gated DeltaNet → FFN) → 1 × (Gated Attention → FFN))" in the card).

| | 4B | 9B |
|---|---|---|
| hidden / FFN | 2,560 / 9,216 | 4,096 / 12,288 |
| vocabulary | 248,320 | 248,320 |
| output head tied to token table | yes | no |
| DeltaNet heads | 16 key, 32 value, 128 each | same |
| attention heads | 16 query, 4 key/value, 256 each | same |
| rotary | first 64 of 256 dims, theta 10,000,000 | same |
| conv kernel | 4 | 4 |
| MTP block | 1 (`mtp_num_hidden_layers`) | 1 |
| native context | 262,144 | 262,144 |

- **No official GGUF.** The Qwen organisation publishes Qwen 3.5 4B and 9B only as
  safetensors (plus FP8 and GPTQ for larger sizes); `ggml-org` publishes GGUFs for 0.8B
  and 35B-A3B only. Third-party Apache 2.0 GGUFs exist (§3.3).
- **Tool calls changed format.** Qwen 3.5's template asks for
  `<tool_call><function=NAME><parameter=P>value</parameter></function></tool_call>`
  (the card's serving examples use the `qwen3_coder` parser), not Qwen3's JSON body that
  `quire_ai::toolcall::read_calls` reads.
- **Size today:** the full `quire` binary has a 76 MiB budget, Lite 48 MiB, the engine
  25 MiB (`packaging/check-size.sh`). The app does not link candle: `quire-ai`'s `client`
  feature has no inference code (`crates/quire-ai/Cargo.toml`).

## 3. The design

### 3.1 The layers, as the engine computes them

All in `apps/quire-ai-engine` (frame §6: candle is allowed only there). New
`src/qwen35.rs` holds the model; new `src/deltanet.rs` holds the recurrence and the
causal conv as plain loops over `f32` slices (no `unsafe`, as the workspace requires).
Weights use `qwen3.rs`'s machinery unchanged: `MatMul::Compact` (GGUF blocks multiplied
by candle's block kernels, never repacked unless `Repack` says so) and `Embed::Compact`
(the token table stays quantized; only looked-up rows are dequantized). That last point
matters more here than for Qwen3: dequantizing the 248,320-row table to f32, as candle's
own quantized models do, would cost 2.5 GB for 4B and 4.1 GB for 9B.

Names below are the GGUF names llama.cpp writes (`gguf-py/gguf/constants.py`);
`N` is the layer.

**Block.** `h = x + mixer(rms(x, attn_norm))`, then `out = h + ffn(rms(h, post_attention_norm))`,
with `ffn(y) = ffn_down(silu(ffn_gate(y)) * ffn_up(y))`. After layer 31, `rms(·,
output_norm)` and `output` (9B) or the token table (4B, tied). Note the second norm is
`post_attention_norm`, not Qwen3's `ffn_norm`.

**RMSNorm variants.** Four, all computed in f32 with eps 1e-6
(`attention.layer_norm_rms_epsilon`):

1. Block norms, `attn_q_norm` and `attn_k_norm`: transformers computes
   `x / rms(x) * (1 + w)` (weights start at zero). llama.cpp's converter adds the 1 when
   it writes the file (`data_torch + 1` for every `norm.weight` except the DeltaNet one),
   so on a GGUF these are plain `x / rms(x) * w`, and candle's `RmsNorm` serves.
2. DeltaNet output norm `ssm_norm` (128 values, shared by all 32 value heads): no `+1`,
   and the result is multiplied by `silu(z)`: `y = rms_norm(o) * w * silu(z)`.
3. The L2 norm of DeltaNet queries and keys: `x / sqrt(sum(x²) + 1e-6)`, no weight.
   (llama.cpp writes it as an RMS norm with eps/n scaled by 1/sqrt(n); the same thing.)
4. `attn_q_norm`/`attn_k_norm` are per head (over 256 values), before the rotary step.

**Gated DeltaNet layer** (24 of 32), for a chunk of `L` tokens:

1. `qkv = attn_qkv(x)` (to 8,192 = 2,048 q + 2,048 k + 4,096 v), `z = attn_gate(x)`
   (4,096), `b = ssm_beta(x)` and `a = ssm_alpha(x)` (32 each). Newer conversions merge
   the first two into `attn_qkv_gate` and the last two into `ssm_beta_alpha`; the loader
   accepts both forms and splits a merged weight by rows (§3.3).
2. Causal depthwise conv over time on the 8,192 `qkv` channels, kernel 4, no bias
   (`ssm_conv1d`, 4 × 8,192), carrying the last 3 inputs per channel from the previous
   chunk; then SiLU.
3. Split into q, k (16 heads × 128) and v (32 heads × 128). L2-normalise q and k per
   head; scale q by 1/sqrt(128).
4. `beta = sigmoid(b)`; `g = ssm_a * softplus(a + ssm_dt.bias)`. The converter stores
   `ssm_a = -exp(A_log)`, so `g ≤ 0` and the decay `exp(g)` is in (0, 1].
5. Each value head `h` uses key head `h mod 16`. This is llama.cpp's "tiled" order: its
   converter permutes the value heads of `attn_qkv`, `attn_gate`, `ssm_alpha`, `ssm_beta`,
   `ssm_a`, `ssm_dt`, `ssm_conv1d` and `ssm_out` so that a plain repeat works.
   transformers uses `h div 2` on the unpermuted weights. Using the wrong one gives a model
   that runs and talks nonsense, so the tiny-model test (T1) is built through the
   converter's own code.
6. The recurrence, per value head, with a state `S` of 128 × 128 f32 (key × value):

   ```
   S ← exp(g_t) · S
   u ← β_t · (v_t − Sᵀ k_t)
   S ← S + k_t uᵀ
   o_t ← Sᵀ q_t
   ```

7. `o` (32 × 128) → `ssm_norm` with the `silu(z)` gate → `ssm_out` (4,096 → hidden).

**Recurrent versus chunked form.** transformers uses a chunked form (chunks of 64, a
triangular solve inside each chunk) for prompts and the step above for single tokens. The
chunked form exists to turn the recurrence into matrix products for GPUs. On a CPU the
recurrence is small: per token about 4 × 32 × 128 × 128 ≈ 2.1 M multiply-adds per layer,
50 M for the 24 layers, against about 4.2 G for the 4B weights (§3.5): about 1%. So the
engine uses **one form for prompts and decoding**: the projections, conv, norm and output
run batched over the chunk (as today, 256 tokens), and only step 6 walks the tokens.
The loop runs head-outer, token-inner, so each 64 KB state stays in cache, and the 32
heads are split across the engine's threads with `std::thread::scope`. llama.cpp likewise
runs one fused operation (`ggml_gated_delta_net`) for prompts and decoding
(`delta-net-base.cpp`). A chunked form is a later option only if Metal (open question 2)
needs it.

**Gated attention layer** (8 of 32):

1. `attn_q` gives 16 × 512: per head, the first 256 values are the query and the next 256
   the gate (transformers: `view(…, heads, 2·head_dim).chunk(2)`; llama.cpp: a view at
   offset `n_embd_head`). `attn_k`, `attn_v`: 4 × 256.
2. `attn_q_norm` / `attn_k_norm` per head.
3. Rotary on the first 64 of each head's 256 dims, "rotate half" pairing (i, i + 32),
   theta 10,000,000 (`rope.freq_base`); dims 64–255 pass through. The config asks for
   interleaved multimodal rotary (`mrope_section` [11, 11, 10]); for text all three
   position rows are the same position, so it reduces to this 1-D rotary. A test checks
   that against the sectioned formula.
4. Causal grouped attention (16 query heads over 4 KV heads, scale 1/16) through the
   engine's existing `RawInterleavedKvCache`, `flash_attn` and
   `causal_decode_f32_interleaved` (candle-nn 0.11.1 puts no limit on the head size).
5. `attn_output(attn ⊙ sigmoid(gate))`.

**Multi-token prediction.** Both models carry one MTP block (an extra attention layer
that drafts the next-next token, for speculative decoding). Skipped: llama.cpp's own
graph does not run it in the main pass, using it needs a draft-and-verify loop plus
rollback of the DeltaNet state, and on a CPU whose decoding is bound by reading the
weights the gain is uncertain. The loader never reads `blk.32.nextn.*` tensors, so they
cost disk only; §3.3 prefers files without them.

**Choosing the model.** `models.rs` reads `general.architecture` from the GGUF: `qwen3`
loads `qwen3.rs`, `qwen35` loads `qwen35.rs`, anything else fails with "unsupported
model". The chat template and tool-call parser follow the same value. The catalog format
does not change.

**Hyperparameters read from the file** (fail on a missing one): `qwen35.block_count`,
`embedding_length`, `feed_forward_length`, `attention.head_count`, `head_count_kv`,
`key_length`, `layer_norm_rms_epsilon`, `rope.freq_base`, `rope.dimension_count`,
`ssm.conv_kernel`, `ssm.state_size`, `ssm.group_count`, `ssm.time_step_rank`,
`ssm.inner_size`, and `attention.recurrent_layers` when present, else
`full_attention_interval`.

### 3.2 Context and the prompt-reuse cache

The engine keeps its 8,192-token limit (`ctx` in `load`). Qwen 3.5's attention cache is
small (§3.5), but reading prompts is the slow part on a CPU (§3.6), so a longer window
would mostly mean longer waits.

Each `generate` today clears the caches and reads the whole prompt again
(`models.rs`, `clear_kv_cache` before prefill). An agent run re-reads the system prompt,
the tools and the history at every step. Attention caches can be cut back to a prefix;
a DeltaNet state cannot, it can only be saved and restored. So the engine keeps one
**snapshot**: the token ids of the last prompt, the 24 DeltaNet states and conv tails
(50 MB, §3.5) and the attention cache length at the end of that prompt. On the next
`generate`, if the new prompt's ids start with the snapshot's ids, it restores the states,
cuts the attention cache to that length and reads only the rest. Otherwise it starts
afresh, as today. Within one agent run the rendered history only grows (the template keeps
the empty think block on assistant turns after the last user message, and `render` must
reproduce that exactly), so each step reads only the last reply and the tool results. A
tokenisation difference at the boundary just means no reuse. The snapshot lives in engine
memory only; `unload` and a crash drop it.

### 3.3 Files, quantisation and pins

**Types candle 0.11 loads** (`GgmlDType::from_u32`): F32, F16, BF16, Q4_0, Q4_1, Q5_0,
Q5_1, Q8_0, Q8_1, Q2_K–Q6_K, Q8_K. Not the IQ types (IQ4_XS, IQ4_NL, IQ3, IQ2): candle
pull request 3462 adding IQ4_XS is open. So the pick is **Q4_K_M** (Q4_K and Q6_K
blocks, F32 for norms, conv and `ssm_a`/`ssm_dt`). Every weight row length here (2,560,
4,096, 9,216, 12,288) is a multiple of 256, so no tensor falls back to an odd type.

**Which repository.** No Qwen or ggml-org GGUF exists for 4B or 9B (§1). Two maintained
Apache 2.0 sets do:

| Repository | 4B Q4_K_M | 9B Q4_K_M | Notes |
|---|---|---|---|
| `unsloth/Qwen3.5-4B-GGUF`, `-9B-GGUF` | 2.74 GB | 5.68 GB | imatrix quants |
| `bartowski/Qwen_Qwen3.5-4B-GGUF`, `-9B-GGUF` | 3.01 GB | 6.17 GB | llama.cpp b9222; the page says MTP layers were added from b9180, which likely explains the extra size *(inference)* |

Recommendation: **unsloth's Q4_K_M** for both (open question 1), the tokenizer from
Qwen's own repositories (`Qwen/Qwen3.5-4B` and `Qwen/Qwen3.5-9B`, `tokenizer.json`).
The weights come from a third party, so three checks stand in for an official file: the
pin (sha256 and size, as for every file), the header check below, and the logit
comparison with transformers on Qwen's own weights (T2).

**Header check in `pin-models.py`.** For each `.gguf` it fetches the first 16 MiB with a
`Range` request and parses the GGUF header: `general.architecture` must be `qwen35`,
`block_count` 32 (plus any `nextn_predict_layers`), and every tensor's type must be in
candle's list above. It prints the tensor names, so the reviewer of the pin diff sees
which of the split or merged forms (§3.1 step 1) the file uses. A failing file is not
pinned. The converter has changed several times this year (value-head order, merged
tensors, MTP layers, and an open fix for `linear_num_value_heads` defaults), which is why
the exact file is pinned and checked rather than "any Q4_K_M".

### 3.4 Chat template and tool calls

`template.rs` gains a Qwen 3.5 renderer next to the Qwen3 one, written from
`chat_template.jinja`:

- With tools, the system turn is `# Tools\n\nYou have access to the following
  functions:\n\n<tools>`, one JSON line per tool, `\n</tools>`, then the template's
  instruction block ("If you choose to call a function ONLY reply in the following format
  with NO suffix:", the `<function=…>`/`<parameter=…>` example and the `<IMPORTANT>`
  reminder), then the system prompt after a blank line.
- Assistant tool calls render as `<tool_call>\n<function=NAME>\n<parameter=P>\nVALUE\n</parameter>\n</function>\n</tool_call>`,
  objects and lists as JSON, other values as text. Tool results go in one user turn as
  `<tool_response>\n…\n</tool_response>` blocks (as with Qwen3).
- The reply is opened with `<|im_start|>assistant\n<think>\n\n</think>\n\n`, the
  template's own form for `enable_thinking = false`. The card says Qwen 3.5 does not
  support Qwen3's `/think` and `/no_think` switches; the engine never used them.
- Stop tokens stay `<|im_end|>` (248046) and `<|endoftext|>` (248044), looked up by text.
- The template refuses a system message that is not first; `render` already merges all
  system text into one leading turn.

**Parsing.** `quire_ai::toolcall` gains `read_xml_call(body, tools)`: it reads
`<function=NAME>` and each `<parameter=P>…</parameter>`, and converts each value by the
offered tool's JSON schema (integer, number, boolean, object and array parse as JSON;
everything else stays a string), as vLLM's `qwen3_coder` parser does. `ReplyParser`
tries the XML form first and the existing JSON repair second, inside the same
`<tool_call>` block. Every 0.10 safety rule stays (0.10-ai.md §2): only a block the model
closed with `</tool_call>` is ever repaired; a call cut off by the token limit is never
run; an unreadable block becomes `_unparsed`, which the runner refuses. Fixtures: the
template's own example rendered by transformers, and the 0.10 cases rewritten in the XML
form, streamed three characters at a time.

**Sampling.** The card's non-thinking values are temperature 0.7, top-p 0.8, top-k 20,
presence penalty 1.5, repetition penalty 1.0. The engine uses top-k 40, top-p 0.9 and a
repetition penalty of 1.1 over 64 tokens. For `qwen35` the engine uses the card's values,
with the presence penalty (subtract 1.5 from each token already in the reply) only for
plain chat, not for JSON or tool replies, where repeating a key is correct. Ask's and
the runner's temperatures stay as callers set them.

**Tokenizer.** `tokenizers` with `fancy-regex` (the engine's choice for Qwen3's
look-ahead). Qwen 3.5's `pretokenize_regex` may differ from Qwen3's, so the test
`the_pure_rust_regex_backend_splits_like_qwen3_expects` gets a Qwen 3.5 twin with the
new pattern.

### 3.5 Memory

Per token of context, f32 as the engine keeps it:

- **Attention cache:** 8 layers × 2 (K, V) × 4 heads × 256 × 4 bytes = 64 KiB. 4,096
  tokens: 256 MiB; 8,192: 512 MiB. (Qwen3 4B: 36 × 2 × 8 × 128 × 4 = 288 KiB a token,
  2.25 GiB at 8,192.) Both models have the same attention shapes, so the same numbers.
- **DeltaNet state:** fixed, whatever the length: 24 × 32 × 128 × 128 × 4 bytes =
  48 MiB, plus conv tails 24 × 3 × 8,192 × 4 = 2.3 MiB. The prompt-reuse snapshot
  (§3.2) doubles this: +50 MiB.

Engine RSS, weights as file size *(guesses until G1/G2 measure them; "other" is the
tokenizer, scratch for a 256-token chunk and the process, about 250 MB for 4B and 300 MB
for 9B)*:

| Context in use | 4B (2,740 MB file) | 9B (5,680 MB file) |
|---|---|---|
| 2,000 tokens | ≈ 3,170 MB | ≈ 6,160 MB |
| 4,096 | ≈ 3,300 MB | ≈ 6,290 MB |
| 8,192 (the limit) | ≈ 3,560 MB | ≈ 6,550 MB |

`ram_mb` (defined at about 2,000 tokens) is set to 3,300 and 6,300 with margin; both are
under the frame's 3.5 GB and 7.5 GB. The cache buffer grows by doubling from 512
positions; it is sized once from the prompt length plus `max_tokens` (capped at the
limit) so there is never a moment with two copies.

"Faster prompts, more memory" (`fast_prompts`) repacks Q4_K into wider tiles, about
twice the weight memory: about 5.9 GB for 4B. It is offered for Qwen 3.5 only when
`min_ram_gb + 8 ≤` the machine's memory, so not with 4B on 8 GB or 9B on 16 GB.

**An 8 GB machine** (the frame asks for this): 8 GB − about 3.3 GB engine leaves about
4.7 GB for the system, Quire and other programs. Quire's index uses 308 MB at 10k notes
and 1.42 GB at 50k today, 200 MB and 800 MB under the frame's budget. The frame makes the
index budget a release condition for offering 4B at 8 GB; this design agrees.

**Under pressure:**

1. At most one language model is loaded: `load` of an `llm` unloads any other `llm`
   first (today the engine's model map can hold several).
2. Below 16 GB, the language model and Whisper are not loaded together: loading one
   unloads the other. Whisper small peaks at 3.6 GB (model-catalog.md).
3. Before loading a language model the app reads free memory where that is cheap (Linux
   `MemAvailable` from `/proc/meminfo`; Windows the same PowerShell query it already uses
   for total memory, `FreePhysicalMemory`). If it is under `ram_mb + 500 MB`, it does not
   load and says "Not enough free memory for Qwen 3.5 4B (needs about 3.3 GB, 2.1 GB
   free). Close some programs and try again." macOS reports only total memory here, so
   the check there is `min_ram_gb` alone.
4. Idle unload after `idle_unload_s` (300 s) and engine exit after 10 idle minutes stay.
5. If the system kills the engine anyway, the client restarts it at most twice
   (0.9 §D.3), then the chat shows "The on-device model stopped. It may have run out of
   memory." Notes are never at risk: the engine has no vault access.

### 3.6 Speed

All guesses, scaled from the measured Qwen3 1.7B numbers (§1) by the bytes read per
written token (about the file size: 2.5× for 4B, 4.7× for 9B, whose separate token
table is only looked up) and by multiply-adds per prompt token (about 2.6× and 5.5×).
"Laptop" means four cores of a recent x86 laptop with AVX2, not shared, assumed 2–3×
the build VM.

| tokens/s *(guess)* | 2 cores (like the build VM) | 4 laptop cores |
|---|---|---|
| 4B, writing | 0.6–1.0 | 1.5–2.5 |
| 4B, reading the prompt | 4–5 | 10–15 |
| 9B, writing | 0.3–0.5 | 0.7–1.2 |
| 9B, reading the prompt | about 2 | 4–6 |

The weak point is reading: a 2,000-token Ask prompt is 2–3 minutes before the first word
with 4B on four cores *(guess)*, about 6–8 minutes with 9B. Memory bandwidth would allow
far more (a laptop's 25–40 GB/s over a 2.7 GB file is 9–15 written tokens/s); candle's
CPU kernels are the limit. What this design does about it: prompt reuse in agent runs
(§3.2); a reading-progress line in the chat ("Reading the question: 1,240 of 2,000");
and open question 3. Apple Silicon CPUs are faster per core and have more bandwidth
*(guess: 2–3× the laptop column)*.

### 3.7 Checking it is right

- **T0, kernels (CI):** the recurrence, conv, gated norm, L2 norm and partial rotary
  against a naive f64 oracle written from the equations in §3.1 (seeded random inputs,
  relative error ≤ 1e-5); the 1-D rotary equals the sectioned formula with three equal
  positions; G6's chunk-invariance as a proptest over random split points (fast in CI,
  50,000 cases in the weekly job).
- **T1, tiny model (CI):** a committed fixture (about 1 MB): a `Qwen3_5ForCausalLM` with
  random weights (seed 0; hidden 32, 4 layers = 3 DeltaNet + 1 attention, 2 key and 4
  value heads of 16, 4 query and 2 KV heads of 32, partial rotary 0.25, a 512-token
  vocabulary, one MTP layer), written to GGUF F32 with llama.cpp's conversion code
  (`conversion/qwen.py`, at a recorded commit) so the +1 norms, `-exp(A_log)`, the
  value-head order and the MTP naming come from the real converter, plus the logits
  transformers computes in f32 for three fixed id sequences of 40 tokens. The engine must
  match G5 (max abs ≤ 1e-3, same argmax everywhere). The script that makes it,
  `packaging/qwen35-fixture.py`, runs by hand (it needs torch); CI runs only Rust (P10).
  A second case quantises the fixture to Q8_0 with candle at test time and checks argmax
  agreement on at least 95% of positions *(threshold a guess)*.
- **T2, real files (before release, by hand):** on the pinned 4B and 9B files, the
  engine's `spike` example gains `--logits` (log-softmax, top 40 per position). Against
  llama.cpp at the quantizer's build on the same file and a fixed 4,096-token text from
  `docs/` (no outside text): G7. Where a machine with 24 GB is free, also against
  transformers on Qwen's bf16 weights: the engine's KL divergence to bf16 may exceed
  llama.cpp's by at most 0.005 nats *(guess)*. Results go in docs/formats/model-catalog.md
  with the RSS and speed of G1/G2 on real weights.
- **T3, behaviour (by hand, recorded):** the agent edit eval and `quire-cli eval
  sample-vault` with `--judge endpoint` against the engine, 4B and 9B, compared with the
  0.10 numbers. If the 4B misses the Qwen3 1.7B baseline, that is the frame's fallback
  case (frame risk 9): ship Qwen 3.5 only if the owner accepts the numbers.
- **Templates:** the rendered prompt equals transformers' `apply_chat_template` output,
  byte for byte, for six committed conversations (with and without tools, tool calls,
  tool results, multi-turn).

### 3.8 The opt-in flow

**The gate.** `AiLocalSettings::on_device()` today is `experimental || env`. In 0.14 it
becomes `pack || experimental || env`, with a new device-local key
`[ai_local] pack = true` written only when the person turns the pack on. Unknown to
0.13, it is kept there in `other`. `experimental` keeps working for testers. Nothing else
counts as consent: capability keys set under 0.9–0.13 (`llm = true` with `experimental`
later off) stay inert until `pack` is set, which keeps P6 for people who flipped a switch
long ago. `llm_model`'s default becomes `""` (no model chosen).

**Where it is offered.** Onboarding's AI step gets its "On this computer" card back, and
Settings → AI → On this computer shows one "Turn on on-device AI…" button. Both open one
dialog (an `OverlayView` with a `layout_samples` entry):

```
On-device AI: runs on this computer, nothing is sent anywhere.
  [x] Writing and the agent: Qwen 3.5 4B (suggested for 8 GB)     2.75 GB
  [ ] … or Qwen 3.5 9B (needs 16 GB)                              5.69 GB
  [x] Text in images and scanned PDFs (Latin script)              13 MB
  [x] Voice notes transcribed here: Whisper base                  290 MB
  [ ] Meaning search here (instead of the built-in)               133 MB
  The AI engine (Quire Lite only)                                 ≤ 25 MB
  Download: 3.05 GB. Needs about 3.3 GB of memory while writing.
  [Download and turn on]   [Cancel]
```

Sizes are the sum of the pinned `size` fields of the ticked rows, in decimal GB as the
pages show them; the values above are from the repository pages and approximate until
pinned (the Whisper size is a guess). The suggestion follows total memory rounded as
today: 4B from 8 GB, 9B from 16 GB, and below 8 GB the writing model is not offered
("needs a computer with 8 GB of memory"); OCR and transcription still are. The voice row
appears only in the full edition (Lite cannot record) and sets `[voice] transcribe =
"device"`, which today refuses while on-device AI is "experimental"
(`voice::unavailable_reason`). Meaning search stays off by default: the built-in LSA
search works without a download.

"Download and turn on" writes `pack = true` and the capability keys (atomically, as all
settings), then queues the downloads one at a time through the existing downloader
(`.part`, resume, sha256 check, fsync and rename; `installed.toml` rewritten whole).
Cancel before that writes nothing. **Crash at each step:** before the settings write,
nothing changed; after it, the pack is on and Settings shows each model as "not
downloaded" with a Download button (nothing restarts on its own); during a download,
the `.part` resumes or restarts; after the rename, the file is checked again before
use. Turning it off in Settings clears `pack`; "Delete downloaded models" removes the
files.

**The CLI.** `quire-cli ai download <id>` and `install` are explicit acts and set `pack`
themselves; their "experimental" refusal goes.

**Release.** `REQUIRE_MODEL_PINS: "true"` in `release.yml` once `pin-models.py` has run
where Hugging Face is reachable (it is not from this machine).

### 3.9 Fit with the frame

- Budgets: G1 and G2 are the frame's rows; my estimates are under them. G3 is the
  frame's "AI off" row, unchanged.
- Layering: the model code in the engine, the rows and pins in `quire-ai`, the XML
  parser in `quire-ai::toolcall` (it is used by the engine only; the app links it but
  does not call it, so nothing changes in its size). No new crate, no new dependency.
- Rule 6: unchanged; the only addition is the header check before a pin.
- Order: L1 is §8 steps 1–4 (engine layers, tests on fake and tiny models); L2 is steps
  5–8 (rows, pins, gate, memory guard). Nothing in the other designs depends on them.
- The frame calls the 3,200 MB Qwen3 4B figure "measured"; the catalog says it was

## 4. Alternatives considered

- **Use upstream candle.** Not possible in 0.14: candle 0.11.1 has no Qwen 3.5. Open pull
  requests add it (3396, "Support for Qwen 3.5 Model Series (Dense and Quantized)", tested
  on Metal, with a reported repetition bug; 3461, a chunked prefill scan; 3838; 3890,
  3897 and 3906 for GPU kernels); 3869 and 3821 were closed without merging. Even merged,
  candle's quantized models dequantize the token table (2.5 GB more for 4B) and let candle
  repack K-quants, the two things `qwen3.rs` was written to avoid (0.10-ai.md §1). We
  read them as cross-references, and switch when a release has a model that meets G1.
- **Use another pure-Rust crate.** crates.io has new ones (searched 2026-11-19):
  `lattice-model-qwen35` 0.16 (MIT/Apache, its own framework, Metal and `objc`, first
  published 2026-10-30), `alice-llm` 2.0 (AGPL or commercial, pulls `tokio`, `axum`,
  `wgpu`, `libc`), `rlx-qwen35` (GPL-3.0-only, links `llama-cpp-2`, which is C++),
  `pure-jeff` (candle, one fine-tune of 0.8B). mistral.rs has Qwen 3.5 for safetensors in
  its repository, but its GGUF loader for it (pull request 2129) is open, its last crates.io
  release is 0.8.1 (April 2026), and it brings a server stack and its own downloads, which
  `deny.toml`'s network rule does not allow. None is both small and established; writing
  about 900 lines in the style of `qwen3.rs` is less risk than any of them.
- **llama.cpp as the engine.** Fast and correct, but C++ (the owner's rule: stay in Rust).
- **The chunked (WY) form on CPU.** More code, a triangular solve, overflow care in
  log-space (pull request 3461's notes), for about 1% of the work (§3.1).
- **Host our own conversion of Qwen's weights.** Best provenance, but GitHub release assets
  stop at 2 GiB, and the 9B file is 5.7 GB; it would need a hosting account of our own.
- **Q4_0 or IQ4_XS** for smaller files: IQ4_XS does not load in candle 0.11; Q4_0 saves
  0.16 GB on 4B and loses quality against Q4_K_M.
- **Keep Qwen3 1.7B for small machines.** Not what the owner chose; kept as the fallback
  in the engine code only (§5.2).

## 5. Compatibility

### 5.1 Sync, vaults, agents, the CLI

- Sync: nothing synced changes. `settings.toml`, `installed.toml` and `models/` are
  device-local; `.quire/cache/ocr/` is a cache. 0.13.x and 0.14 devices sync as before.
- Settings shared between versions on one device: 0.13 keeps `pack` in `other` and, with
  `experimental` off, shows no on-device AI, as today. 0.13 does not know the new model
  ids and treats them as not installed. `installed.toml` stays format 1.
- Vaults: unchanged; OCR text goes to the index and its cache as built in 0.9. Agents and
  MCP: unchanged; the local model is one more `ChatModel` and its writes are proposals.
- Editions: Lite packages have no engine (`packaging/linux/package.sh` ignores
  `ENGINE_BIN` for Lite), but **Lite does download the same pinned engine when on-device
  AI is turned on** (package.sh's header; 0.13-pack.md §1). The brief's "Lite has no
  engine" is true of the package, not of the feature. Lite has no voice recording, so no
  Whisper row. P5 holds: the keys are the same in both editions.
- Size: the full `quire` binary does not link candle, so the engine work does not change
  it; the app's changes (rows, gate, dialog, parser) are kilobytes *(guess: under
  0.1 MiB)*. `qwen35.rs` adds to the engine binary *(guess: 0.1–0.3 MiB)*, inside its
  25 MiB budget; the release job's `check-size.sh engine` line gives the real number.

### 5.2 People who chose a Qwen3 model

Nobody downloaded one through Quire (§1), but settings may name one
(`llm_model = "qwen3-1.7b-q4km"` is the 0.9 default) and testers may have files from a
development build. So: an `llm_model` naming a removed id reads as "no model chosen" and
nothing downloads in its place; the pack dialog suggests by memory as above. Folders under
`<data_dir>/models/` that no catalog row names are listed in Settings → AI as "Files from
an older model, 1.1 GB · Delete" and never deleted without that click. `qwen3.rs` stays in
the engine through 0.14.x as the fallback the frame asks for (risk 9); removing it later is
one change.

### 5.3 Real-time collaboration later

The pack reads notes and proposes edits through the existing proposal path; it holds no
note state and assumes no single writer. Nothing here constrains a CRDT layer.

## 6. Risks and how each is tested

| Risk | Test |
|---|---|
| Value-head order or norm offsets wrong: fluent nonsense | T1 built through llama.cpp's converter; T2 on the real file |
| DeltaNet state carried wrong across chunks or the reuse snapshot | G6 proptest; reuse on and off give the same logits (≤ 1e-5) on the tiny model |
| A pinned file uses an unloadable type or the merged tensor form | header check at pin time; the loader's error names the tensor; unit tests for both forms on the tiny model |
| Over the memory budget | `perf` job with random weights of the real 4B shapes (2.7 GB generated, seeded), RSS after a 2,000-token prompt ≤ 3.5 GB; 9B weekly ≤ 7.5 GB |
| Too slow to be useful (§3.6) | `perf` job records prompt and writing tokens/s for 4B (report only; budgets after the first real numbers); T3 by hand |
| Tool calls misread | XML fixtures streamed 3 characters at a time, schema typing, the 0.10 cut-off cases; runner tests unchanged |
| Out-of-memory kill mid-chat | fault test: the fake engine exits mid-stream, the client restarts it, the chat shows the message, no partial call runs |
| Consent: something starts without `pack` | settings tests: a 0.13 file with `llm = true`, `experimental = false` starts no engine and downloads nothing; with `pack = true` only after a click |
| Template drift from the Jinja file | byte-equality fixtures (§3.7) |
| Third-party file replaced upstream | the pin: a changed file fails its sha256 and is never used |

## 7. What the user sees

- **On-device AI is here, if you want it.** Settings → AI → "Turn on on-device AI…" shows

## 9. Open questions for the owner

1. **Whose GGUF?** Qwen publishes none for 4B or 9B. *Recommendation:* unsloth's Q4_K_M
   (smaller, no MTP layers), pinned by hash and checked against Qwen's own weights (T2);
   switch to an official file if Qwen or ggml-org publishes one.
2. **Metal on macOS.** *Recommendation:* CPU only for Qwen 3.5 in 0.14 (the `gpu` setting
   is ignored for it, Settings says so), Metal in a later release with its own checks. One
   path to verify now; Apple CPUs are the fastest we target.
3. **Default on 16 GB machines.** 9B gives better answers but reads prompts about 2.5×
   slower than 4B (§3.6), and 4B with "faster prompts" fits in 16 GB. *Recommendation:*
   keep the owner's 9B suggestion, but decide after T2/T3 give real speeds; if 9B needs over
   5 minutes for a 2,000-token prompt on a 4-core laptop, suggest 4B with faster prompts.
4. **Lite.** Lite downloads the engine today. *Recommendation:* keep that, since OCR and
   the pack work the same in both editions; the alternative is removing on-device AI from
   Lite.
5. **"Faster voice transcription."** On-device Whisper is built, but the decoder's
   self-attention cache listed as deferred in 0.10-ai.md §7 is not (`whisper.rs` passes the
   whole token sequence at every step; candle caches only cross-attention): 30 seconds of
   audio took 46 s with Whisper tiny in the worst case on the build VM. *Recommendation:*
   ship as is in the pack (real speech is shorter than the worst case), and treat the cache
   as a separate small engine change if you want it in 0.14.
