# Quire 0.14: architecture frame

Status: current
Area: architecture
Code: `crates/quire-vault/src/` (new `changes.rs`), `crates/quire-base/src/` (new `cache.rs`), `crates/quire-index/src/actor.rs`, `crates/quire-app/src/vault_sync/`, `crates/quire-mcp/src/tools/`, `apps/quire-ai-engine/src/`, `packaging/perf-check.py`

The frame the five 0.14 designs fit into: `0.14-sync-speed.md`, `0.14-index-startup.md`,

## 1. What changes structurally

Today four parts each find out for themselves what changed, by reading everything:

- Sync: `snapshot_reads` (`vault_sync/store.rs`) reads every note, `Engine::push`
  (`quire-sync/src/engine.rs`) reads every note again through `LocalStore::digest`, and
  `save_state` (`vault_sync/state.rs`, called from `pass` in `session.rs`) rewrites every
  note's merge base on every pass.
- The index: `IndexMsg::Load` runs `parse_parallel` over the whole vault at every start
  (`quire-index/src/actor.rs`), and `run_semantic` refits `build_lsa_index` after every save.
- Agents: `common::visible` (`quire-mcp/src/tools/common.rs`) asks `AgentStore::effective_mode`
  about every record on every listing call, with filesystem calls per note.
- The reminder job and rename read every note (scan items 12 and 16; fixed outside this round,
  but they should use the same table).

0.14 replaces "read everything, then compare" with three shared pieces:

1. **One vault manifest** (§2): a table of what is on disk, kept by one scanner. Everything
   that asks "what changed?" asks it.
2. **One cache container** (§3): one file header, one versioning rule, one way to throw a
   cache away.
3. **One visibility set per agent view** (§4): computed once per policy state, used by the
   listing tools and by per-view search statistics.

Nothing else moves. Markdown files stay the truth (P1). The sync wire format does not
change shape (§7). No new process, no database, no new third-party crate is required by
this frame (a design that wants one says so and passes `deny.toml`).

## 2. The vault manifest (the change feed)

**Decision: a state table, not an append-only journal.** One row per file:

```
path        vault-relative, `/` separated (as `NotePath`)
size        bytes on disk
mtime_ns    modification time, nanoseconds (0 if the platform gives none)
hash        SHA-256 of the bytes as stored on disk (32 bytes), no BOM stripping
gen         u64: the manifest generation in which this row last changed
gone        true for a tombstone (file removed in generation `gen`)
```

plus a header: `epoch` (16 random bytes from `quire_base::rand`, new whenever the manifest
is built from nothing) and `gen` (the current generation).

Why a table and not a log: every consumer needs "the latest state of each path", none needs
the intermediate versions; a log needs compaction, a lock across processes and a recovery
story, and a table needs none of them. A row's `gen` gives the "since" query a log would.

**Owner and API.** New module `quire_vault::changes` (layer 3: it needs `Storage`,
`NotePath` and the locked-folder rule, and `quire-index` at layer 4 can use it):

- `Manifest::open(vault)`: loads the cached table if valid (§3), else starts empty.
- `Manifest::scan(&mut self, vault) -> Result<Delta>`: one listing that also returns size
  and time (from the directory walk, not a second `stat` per file: on Windows the walk has
  them for free). A row whose `(size, mtime_ns)` is unchanged is trusted. Any other file is
  read and hashed; the row changes only if the hash changed. A listing error is an error,
  never "all gone" (the 0.13.2 rule; `a_listing_that_lost_a_folder_is_retried_then_refused`).
  Each scan's `Delta` goes to every subscriber (sync, the index), so nobody rescans for
  what another consumer just found. `Manifest::verify` is `scan` with stat trust off.
- `Manifest::note_written(path, bytes) -> hash` / `note_removed(path)`: Quire's own writes
  update the row at once, so a save does not wait for a scan. They never block on a scan in
  progress (P9: they queue), and such a row counts as racy (hashed again by the next scan).
  `VaultWatcher` events (`quire-vault/src/watch.rs`) only say "scan this path"; they are
  hints, never the truth.
- `Manifest::since(gen) -> impl Iterator<Item = &Row>` and `get(path)`.

**Rules every consumer follows.**

- *Stat is a hint, hash is the fact.* A consumer that persists anything keys it by `hash`
  (and its own format version), not by `gen` and not by mtime. `gen` and `epoch` are for
  in-process "what changed since I last looked"; a persisted `(epoch, gen)` cursor is valid
  only while the epoch matches, and a mismatch means "compare everything by hash", which is
  one in-memory pass over the table and reads no notes.
- *The racy-timestamp rule.* A row whose `mtime_ns` is within 2 s of the time it was scanned
  is not trusted on the next scan (it is hashed again). This covers coarse clocks (FAT,
  some network shares) and an edit in the same tick as the scan.
- *A verify pass exists.* Tools can keep size and mtime while changing bytes. Sync must
  rehash everything now and then (the sync design picks the cadence; I suggest when idle and
  at most once a day, and on `quire-cli sync once --verify`). The budgets in §5 exclude it.
- *Locked folders.* The hash is of the stored bytes, so for a locked folder it is the hash
  of the `.qenc` file. No cache may hold plain text, terms or vectors of a locked note
  (`docs/design/0.11-secure.md`; today `run` in `actor.rs` drops them and
  `scrub_locked_text` clears them from sync state). Locking a folder purges its rows' derived
  data from every cache in the same step.
- *Other digests hang off the hash.* Sync's attachment `fingerprint` (SHA-256 of the base64
  text) and `quire_vault::ContentHash` (BOM-stripped, 128 bits) are different functions.
  They stay as they are on the wire and in formats; a consumer that needs one stores it next
  to the manifest hash. Nobody redefines either.

**Who consumes it.**

| Consumer | Uses | Persists |
|---|---|---|
| Sync (`VaultStore` as `LocalStore`) | its own `scan` every pass, then for each tracked note compares the row's hash with the stamp of the bytes last known equal to the merge base (`Tracked.disk` in `0.14-sync-speed.md`) | that stamp and a base print per `Tracked`; base text outside the state file |
| Keyword index and startup cache | rows whose hash differs from the cached record's | records keyed by hash |
| Semantic index | the same rows | passages and vectors keyed by hash and model |
| Agent views | `since(gen)` in process | nothing (§4) |
| Reminder job, rename | `since`, hash | their own small caches |

`quire-sync` does not depend on `quire-vault` and must not start to. The engine keeps its
`LocalStore` trait; `quire-app`'s `VaultStore` answers `digest` from the manifest.

## 3. Caches: where, format, invalidation, crash safety

**Where: `<vault>/.quire/cache/`, not the app's state directory.** Reasons: it is the
existing rule (`docs/formats/README.md`: "`.quire/cache/**` rebuildable"; `vectors-<model>.f16`,
`pdf-text/`, `served/` are there already); it moves and is deleted with the vault; `is_hidden`
(`quire-vault/src/storage.rs`) already keeps it away from the watcher, the index and sync;
P3 says app state lives under `.quire/`. The app's state directory (`quire_agent::approval::default_state_dir`)
stays for what must not travel with a vault or be writable through it: approvals, tokens,
models. **Sync state is not a cache**: merge bases and cursors stay in `.quire/sync/` and
are written durably; losing them costs conflict copies.

A vault on a read-only disk or a folder that a file-sync tool (Dropbox, iCloud) also carries
is the cost of this choice. So: a cache that cannot be written is a notice once and then
in-memory operation, never an error that stops the app; and every cache file is safe to
have replaced by another device's copy (it is validated against this device's files by hash).

**One container** (`quire_base::cache`, new, layer 0, no new dependencies):

```
magic     8 bytes   "QUIRECA1"
kind      u16       which cache (manifest, records, passages, ...)
format    u32       the cache's own version; bumped on any layout or meaning change
builder   u32       version of the code that derives the content (tokenizer, chunker, LSA)
flags     u32
body_len  u64
body_hash 32 bytes  SHA-256 of the body
body      private to the cache
```

- `cache::read(path, kind, format, builder) -> Option<Vec<u8>>`: `None` for a missing file,
  wrong magic, another kind, another `format` or `builder`, a short file or a bad hash.
  **Any doubt is "no cache".** A cache is never migrated: a version bump discards it.
- `cache::write(path, ...)` goes through `quire_base::fs::write_atomic` with
  `Options::STATE.lazy()`: atomic rename, no fsync. A power cut can leave an old or missing
  cache, never a torn one, and the hash catches a torn body on filesystems that reorder.
- A newer `format` than this build knows is left alone and not overwritten while the newer
  build may still be in use (P3): the older build runs without that cache. This is what
  makes a 0.13 or 0.14.0 app opening a 0.14.x vault safe.
- Edition (P5): the same bytes from full and Lite builds.

**Shape rules.**

- Whole-file replace or immutable segment files plus a small index file. **No in-place
  writes and no appends shared between processes**: the app, `quire-cli mcp`, `serve` and
  the reminder job can run on one vault at once. Two writers may replace each other's file;
  the loser's work is redone later. Nothing ever waits on a lock for a cache; a cache may
  take a non-blocking writer lock (`File::try_lock`, as `lock_sync` does) so that one
  process writes and the others only read.
- Writes are debounced: a save updates memory at once; the file is written when things have
  been quiet for 30 s, at most every 5 minutes while busy, and on clean exit. A stale cache
  is corrected by the next scan, by design.
- A cache holds text only of notes that are in the vault now: a removed note's bytes leave
  every cache at the next write, without waiting for a compaction threshold.
- Size: a cache above a few MB that changes per note must be segmented so one save does not
  rewrite it all (the manifest at 50k notes is about 5 MB *(guess: 100 bytes a row)*, fine
  to replace every 30 s; the record cache is not).
- `quire-cli cache clear` (and deleting the folder by hand) is always safe. One test per
  cache: delete it, corrupt one byte, truncate it, swap in another vault's copy; the result
  equals a cold build.
- `quire_base::fs::sweep_leftovers` runs on `.quire/cache/` at start.

## 4. Agent views

A view is the set of paths one agent connection may read. **Decision: views are keyed by a
visibility fingerprint, not by connection.** `quire-agent` builds a `Visibility` value once
per (policy state, actor zones, locked-folder list): path-prefix rules with no filesystem
calls, plus a 32-byte fingerprint of those rules. Connections with the same fingerprint
share one view. A view whose rules hide nothing is the main index itself (no copy).

- The listing tools filter with `Visibility::allows(path)`. `AgentStore::guard` stays for
  any path the agent names. This is the fix for scan item 5 and it is shared with the
  agent-index design; the two designs must not each build one.
- A view owns only statistics: its member set, document count, average length, document
  frequencies (stored or counted per query), and the meaning model fitted on its visible
  passages. It borrows records, postings and passages from the main index. It is rebuilt
  when the fingerprint changes and patched by the index actor in the same step as the note.
- Views live in memory only in 0.14. Persisting them is allowed later through §3, keyed by
  fingerprint; never in a place an agent can read (`.quire/**` is already invisible to agents, P8).
- Until a view's meaning model is fitted, that view answers by keyword with its own IDF. It
  never borrows the whole-vault model "for now": that is the leak
  (`docs/design/0.14-health-gates.md`). The reply does not say that a model is being
  prepared: that message would reveal that notes are hidden. A view may reuse the main model
  only if every passage the main model was fitted on is a member.
- At most 32 views keep keyword statistics and at most 4 keep a meaning model of their own;
  the least recently used is dropped. No idle timer.

## 6. Layering

No new crate. New modules, each in the lowest layer that can own it:

| What | Where | Why there |
|---|---|---|
| Cache container | `quire-base` `cache.rs` (layer 0) | every crate may use it; next to `fs.rs` |
| Manifest | `quire-vault` `changes.rs` (layer 3) | needs `Storage`, `NotePath`, locked folders |
| Record and passage caches, incremental semantic, view statistics | `quire-index` (layer 4) | owns `NoteRecord`, `FullText`, `SemanticIndex`; statistics are index mechanics |
| `Visibility` (rules and fingerprint) | `quire-agent` (layer 6) | owns policy, zones, `effective_mode` |
| Passing a view to the index | `quire-index` takes `Keep` today (`lib.rs`); it gains a view handle built from a predicate over a record's path and tags (tag allow lists need the tags) | `quire-index` must not depend on `quire-agent` |
| Sync state split, manifest-backed `digest` | `quire-app` `vault_sync/` (layer 7) | the only place that knows both vault and engine |
| Batch push, engine use of digests | `quire-sync` (layer 3), `apps/quire-sync-server` | protocol code; still no `quire-vault` dependency |
| MCP tool cleanup, removal of the nine 0.8 names | `quire-mcp` `tools/` (layer 8) | the registry |
| Qwen 3.5 layers | `apps/quire-ai-engine` (layer 9) | `deny.toml` allows candle only there |

`packaging/check-layering.py` needs no new edge. A design that adds a dependency edits the
table in `ARCHITECTURE.md` §3 in the same change.

## 7. Compatibility rules for every design

1. **0.13.x and 0.14 devices sync together, in both directions, on every transport.**
   `PROTOCOL` stays 3 and no design raises a space's minimum protocol. Batch push is a
   server capability advertised in `GET /v1/info`; a 0.14 client falls back to `Transport::push`
   one at a time against a 0.13 server, and a 0.14 server serves 0.13 clients unchanged.
   Revisions, `Content` and sealing do not change. Folder, S3 and WebDAV layouts do not change.
2. **Device-local sync state may change format, with a safe way back.** 0.14 reads 0.13's
   `state.json` and migrates once, durably. After migrating it must not leave a `state.json`
   that a 0.13 build would trust while it goes stale; a 0.13 build that finds none starts
   afresh and adopts the notes (the engine's identity rule), which is safe. The migration is
   crash-safe at every step: old state valid, or new state valid, never neither.
3. **Caches are disposable.** No cache is the only copy of anything. Deleting `.quire/cache/`
   changes speed, never results. A search answer with a warm cache equals the answer from a
   cold build over the same files (one equivalence test per cache, and a randomised one).
4. **Incremental equals rebuilt.** Any structure updated per note has a property test that
   compares it with a from-scratch build after random edits, as `patched_graph_equals_a_rebuild`
   does for the link graph. Where exact equality is given up on purpose (the meaning model
   between refits), the design states the bound and when a refit restores equality.
5. **The nine 0.8 MCP names are removed in 0.14** (owner decision): `search_notes`,
   `read_note`, `list_notes`, `backlinks`, `ask_notes`, `list_tags`, `create_note`,
   `append_to_note`, `replace_in_note` (`legacy::NAMES`). They are neither listed nor
   callable, in any protocol version. A call answers the ordinary unknown-tool error, whose
   text names the replacement ("No tool called `search_notes`; use `search`"), so an old
   prompt fails with a way forward. No adapters are written. `str_replace` gains `all: true`
   so `replace_in_note` has a successor; its regex form is not carried forward. Renamed
   *parameters* of the remaining tools keep their old spelling as an accepted alias (no end
   date set). The 0.8 fixtures and `answers_0_8_clients_as_0_8_did` go with the names; the
   0.9 recorded sessions are re-recorded once under `0.14-agent-tools.md`'s re-bless policy.
   The changelog says it under "Changed", first, with the table of old and new names.
6. **AI is off until turned on** (P6): no engine process, no download, no catalog fetch. Only
   files pinned by sha256 and size download (`CatalogFile::is_pinned`).
7. **Existing vaults open unchanged**; no note is rewritten by any 0.14 migration.

## 8. Keeping real-time collaboration possible

What a later CRDT or operation-log layer needs, and what 0.14 must therefore not assume:

- **No single writer.** The manifest is rebuilt from the files by scanning; it never assumes
  that Quire made a change or that changes arrive in order. `note_written` is an
  optimisation, and a scan must reach the same table without it.
- **No whole-file replacement as the unit of change in interfaces.** The manifest reports
  "this path now has this hash". It does not carry or promise a diff, and consumers must not
  infer "the note was replaced" from it. The index's per-note update takes (path, new text)
  today (`IndexMsg::Upsert`); it stays correct if the text arrives as a stream of small
  edits, as long as updates are idempotent and keyed by content hash.
- **`gen` is local.** It orders changes on this device in this epoch only. Nothing derives
  cross-device order, identity or causality from it. Those stay with `FileId`, `RevId` and
  the parent chain in `quire-sync`.
- **Merge bases are addressed by content hash**, not by path or by "the last thing this
  device wrote". An operation log would replace "base text + three-way `quire_text::merge`"
  with "base version + operations"; a base store keyed by hash serves both.
- **Caches derive from text, not from a history of edits.** Any cache can be rebuilt from
  the current files alone.
- **Where the later layer plugs in.** Above: `quire_text::Transaction` is already the unit
  of every edit (ARCHITECTURE.md §5). A CRDT layer would sit between `Document::apply` and
  the file, emit operations into a new sync lane beside the revision log, and materialise
  Markdown files. Below it, the manifest sees those files change like any other change, and
  every 0.14 consumer keeps working. The revision log stays the fallback for devices
  without the layer.

## 9. Order of work

```
Wave 0 (serial, small):  A1 cache container (quire-base)      A2 manifest (quire-vault)
                         scanner fixes I0 (quire-markdown), LSA determinism, note count in `instructions`
Wave 1 (parallel):       sync-speed S1 (stamps, prints, state store, manifest-backed store)
                         index-startup I1a (interning, stable document ids), then I1b (measure), I1c (record cache)
                         agent-tools T1 (Visibility in quire-agent, listing tools, bounds)
                         local-ai L1 (engine layers, tiny-model tests; speed measured and recorded)
Wave 2 (parallel):       sync-speed S2 (batch push, own-revision cursor)
                         agent-index keyword half (member sets, `rank_in`, tools use views): needs I1a and T1
                         index-startup I2a (per-note semantic update, background refit)
                         agent-tools T2 (one parameter convention, aliases, removal of the nine 0.8 names)
                         local-ai L2 (catalog rows, pins, the pack: writing model and OCR, memory guard)
Wave 3 (serial):         index-startup I2b (passage cache)
After 0.14.0 (0.14.x):   agent-index meaning models per view (needs I2a)
Wave 4:                  perf-job budgets switched from report to enforce; release notes
```

Dependencies: S1's store half, I1c and T1's zero-call lock list need A1 and A2. The
agent-index keyword half needs only I1a and T1 and closes the leak by itself (restricted
views answer by keyword); its meaning models need I2a. Local-ai depends on nothing here;
index-startup I2a changes the embedder interface it uses. Agent-tools T2 touches the
recorded MCP fixtures and should not overlap agent-index edits to the same tools.

On the 2-CPU machine run at most two builders at once, and never two that compile candle
or that both touch `quire-index`. Pairs that work: sync-speed with index-startup;
agent-tools with local-ai.

## 10. Risks across designs

1. **Trusting size and mtime in sync.** A missed change is a note that silently stops
   syncing. Mitigation: the racy-timestamp rule, own writes recorded by hash, the verify
   pass, and the 150-seed folder tests (`quire-sync/tests/folder_sync.rs`) run with a store
   that keeps mtimes fixed.
2. **Sync state migration.** The one place in 0.14 where a bug loses work (conflict copies
   at best). Fault-injection at every write; downgrade tested against a 0.13.3 binary.
3. **Two designs, one structure.** Index-startup and agent-index both reshape
   `SemanticIndex` and `FullText`; agent-tools and agent-index both want `Visibility`.
   §4 and §9 fix the owner and the order; the reviews check it.
4. **Per-view meaning model cost.** A fit takes 3.4 s CPU at 10k and 19.6 s at 50k *(scan)*.
   Decided: 0.14.0 gives restricted views keyword search only; their own meaning models
   come in 0.14.x, with shared views and a cap of 4.
5. **Search quality drift** between meaning-model refits, and different answers on two
   devices with the same notes. Needs a stated bound and a quality test on a fixed corpus.
6. **Memory on 8 GB machines.** 1.42 GB of index at 50k notes plus a 3.5 GB engine. The
   index memory budget is a release condition for offering the 4B model at 8 GB.
7. **Cache bugs that look like data bugs.** A stale record shows a wrong backlink or task.
   Rule 3's equivalence tests and `quire-cli cache clear` are the answer; a bug report
   template line "does it persist after clearing caches" helps.
8. **Several processes on one vault.** The no-lock rule costs duplicated work; an in-place
   or append design would cost corruption. Reviews reject the latter.
9. **Hybrid Gated DeltaNet layers in candle** are new code with no upstream reference in
   candle 0.11.1. Correctness is a release condition (the tiny-model and real-file checks of
   `0.14-local-ai.md`, and the check of the third-party files against Qwen's own weights).
   Speed is not: the owner ships the pack opt-in whatever it measures, and the number is
   recorded.
10. **Removing the nine 0.8 tool names breaks setups that still name them.** There is no
    telemetry to count them. The unknown-tool error names the replacement, the changelog
    leads with the table, and `docs/agents.md` and `skills/quire/SKILL.md` change in the same
    release.
11. **Schedule.** `quire-index` is one lane with four designs' work in it. Cut first: the
