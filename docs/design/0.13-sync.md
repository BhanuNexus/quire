# Quire 0.13: sync hardening

*Status: built for 0.13. Code: `crates/quire-sync/src/{compact,keyring,admin}.rs`, the folder, S3/WebDAV and server transports, `apps/quire-sync-server`, `crates/quire-app/src/vault_sync/harden.rs`, `quire-cli sync devices|remove-device|upgrade|compact`, Settings → Sync → Devices and sync format.*

0.12 left four things between sync and 1.0: logs that only grow, no way to shut out one device, revision headers that a sync folder or a server could rewrite, and a note that stays behind when one of its revisions is lost for good. 0.13 fixes all four. The engine, the three-way merge, the head rule and every 0.12 file format stay; the new parts are switched on per vault by an explicit upgrade (§3), because Quire 0.8–0.12 can't read them.

## 1. Compaction

### Server

The server keeps one line of revisions per note (compare-and-swap), so it can drop old ones by itself. With `QUIRE_SYNC_KEEP_DAYS=N`, once a day it deletes every revision that is **not** among its note's newest `QUIRE_SYNC_KEEP_VERSIONS` (default 20) **and** was replaced more than N days ago (by server time). A note's current revision, and a deleted note's tombstone, are never deleted. Unset, nothing is deleted (as before: a self-hosted server keeps everything unless its owner says otherwise).

Why that is safe for a device offline for months: its cursor points into the log; the next pull returns every note's newest revision past it. For a note it changed meanwhile, the engine merges three-way from the text it last synced. On a server every older revision of a note is an ancestor of the newest one (the log is linear), so that merge is exactly right; the revisions in between are only history. Its push names a parent the server no longer has as head, gets `409` with the head, and merges, as before. A deleted note keeps its tombstone, so a device that still has the note learns it was deleted. Two compactions at once are two `DELETE`s in SQLite transactions; the second deletes nothing more.

### Folder, S3 and WebDAV: snapshots

There is no single log to prune: every device appends to its own lane, and every device works out each note's current revision by walking from its first revision. A **snapshot** replaces the start of every lane at once.

* A device writes generation *g* as `snapshots/<g>-<device>/` (folder: `part-000001.jsonl`… and `manifest.json`; storage: `part-000001`… and `manifest` objects). The parts hold the **kept** revisions, unchanged (same ids, parents, sealed bytes; nothing is sealed again). The manifest holds the **cut** (per device lane: segment and line in a folder, object number in storage), for each note where its current revision is found from (its oldest kept revision on the way there), *links* (kept revision B is an ancestor of kept revision A through dropped ones), statistics, the size and SHA-256 of each part, and a MAC with the vault key (`Keys::mac`). The manifest is written last; a snapshot without a valid manifest, or whose parts don't match it (still downloading, cut short by a crash), is not used. In a folder it's built in `.<name>.tmp` and renamed into place.
* **What is kept**, per note: its current revision; every revision written or replaced in the last 90 days (`keep_days`, set with `quire-cli sync compact --keep-days`); its newest 10 versions; every revision that isn't an ancestor of the current one (a tie lost and not merged again yet) and the way back to where it forked, so its device can still merge three-way; anything this device can't decrypt (a newer key). Everything else before the cut is an ancestor of a current revision and goes.
* **Readers** take the winning snapshot plus every lane line after its cut. The head rule is unchanged, except that a note with a start in the snapshot is walked from there. Ancestry (`Transport::fork`) follows parents, links and chains (§4).
* **Two snapshots of one generation** (two devices compacting before seeing each other's): the one made by the device with the smaller id wins, on every device (`compact::winner`). Nothing is deleted for a week after a snapshot appears (`SETTLE`, measured from when this device first saw it): far longer than any sync delay, so both are seen before anything goes. A device doesn't compact while the last snapshot is settling, or while another device's snapshot of the next generation is there; S3/WebDAV check the storage again just before writing the manifest and stand back if another is there.
* **After a week**, each device deletes **its own** lane up to the cut (folder: whole segments before the cut's; storage: its own objects up to the cut, which needs `DeleteObject` on its own prefix, see [sync-backends.md](../sync-backends.md)), and older snapshots. Each device deletes only what it wrote (and lanes of removed devices), so the one-writer rule holds. A key that may not delete leaves the objects and the status says so.
* **When**: the app tries once a day after a good pass and compacts when at least 1 000 revisions and at least half the bytes would go; *Compact now* (Settings → Sync) and `quire-cli sync compact [--force]` do it on request.
* S3/WebDAV: other devices learn of a snapshot from the maker's tip (`"s": "<g>-<device>"`), so it costs no extra listing. On taking a snapshot, a device mirrors other lanes again from the cut (numbered); its own mirrored lane is cut only once the snapshot has settled.

**A device offline for months** comes back to a snapshot. For a note it didn't change, it takes the current text. For one it changed, the revision it last synced is either kept or was dropped: dropped means it was an ancestor of the current revision, so the engine merges three-way from the text it last synced, as on a server. The one case without a shared revision: it *wrote* a revision on top of one that was later dropped, and that revision never reached the device that compacted (it was offline longer than the 90 days, or the sync tool stalled). Then `Transport::fork` says `Unknown`, and the engine keeps both versions: the current text in the note, its own as a conflict copy. No text is lost; it's just not merged.

**What history means now.** "All devices" history (the sync log) keeps at least the last 90 days and 10 versions per note. Quire's own version history (`.quire/history`, Version history) is separate and never reads the sync log, so compaction doesn't touch it.

**Sizes.** After compaction a lane-based vault holds, roughly: every note's current text once (padded to at least 256 bytes, sealed: +41 bytes), every tombstone (~300 bytes per deleted note, forever), the revisions of the last 90 days, and up to 10 versions of each note. Snapshot parts store revisions hex-encoded like the folder logs (about twice their raw size), so a vault with 50 MB of attachments has a snapshot of about 100 MB. Typical text vaults: a few MB. The server keeps the same minus the snapshot encoding. Before 0.13 every saved change stayed forever.

## 2. Removing a device

### Keys

A vault starts with one key, **epoch 0** (the 0.5–0.12 vault key, `VaultKey`). Removing a device makes epoch *n+1*:

* A new random key. An `EpochRecord` holds it sealed for each remaining device (`keyring::seal_to`: an ephemeral and a static X25519 agreement, HKDF-SHA256, XChaCha20-Poly1305; the device opening it also learns who sealed it), wrapped by the sync passphrase for devices that join later (Argon2id, as before), and the previous key sealed under the new one (`prev`), so the newest key opens every older one. A MAC with the new key (`check`) covers the whole record, for devices that get the key from the passphrase or the recovery key.
* The **recovery key** becomes the new key (shown once; the old one opens only what was written before).
* New revisions are sealed under the newest epoch (`SEALED_V2`: `[2][epoch][nonce][ciphertext]`, associated data `v3` with the epoch). Older revisions stay as they are: the removed device can still read what it already had, and nothing written after its removal.
* The record names the removed device and, per lane, the last of its revisions still taken (folder: segment and line; storage: object number; server: log position). Everything it writes after that is ignored by every device.

Every 0.13 device has an X25519 key of its own (`sync-device-<space>` in the keychain) and publishes a `DeviceRecord`: its public key, its Quire version and its name (sealed), with a MAC under the vault key. Public keys are pinned on first sight (`.quire/sync/peers.json`); a record that later names another key for a device is ignored. Once the key has changed, a record authenticated only with an older key counts only for a device the newest record names, with the same key: a removed device (which has the older keys) can't slip in a device of its own.

Where records live: a folder `keys/<epoch>-<maker>.json` and `devices/<id>/device.json`; storage the same objects (a tip's `"k"` says a device took a new epoch); a server `PUT /v1/spaces/{space}/keys/{epoch}` (only the next epoch: compare-and-swap) and `PUT …/devices/{id}/record`.

**Two removals at once** (a folder or storage has no compare-and-swap): every device orders the records of one epoch the same way (a record whose maker another record removes goes last, then by maker id) and takes the first that opens for it. A maker must be a device of the previous epoch and not removed. So a removed device that comes back online and writes its own epoch record loses to the record that removed it. On a server the second record gets `409`.

**A crash in the middle.** The record is written before anything else changes. If the app stops before keeping the new key, its next pass finds the record and takes it (the maker is a member). A record file cut short doesn't parse and is ignored.

### Server tokens

A server used one shared token. In 0.13 each device swaps it, at its first pass, for a **device token** (`POST /v1/spaces/{space}/devices`, with the server's token) and keeps only that. Removing a device also calls `DELETE …/devices/{id}`: its token gets `403` from then on, and the server's token can't make it a new one. Once a space is upgraded (protocol 3), the server's token works there only to make device tokens, every push must come from the device it names, and pushes sealed under an older key epoch than the space's newest get `422` (the device takes the new key and sends again).

### What removal protects, and what it doesn't

| | Protected | Not protected |
|---|---|---|
| Reading | Anything written after every other device took the new key (seconds on a server or S3; as long as the sync tool takes in a folder) | Everything written before: the removed device keeps its notes, its mirror and the old keys. Changes another device made before it heard of the removal are sealed with the old key |
| Writing | Revisions it makes after its cut are ignored by every device; on a server they're refused | Anything it wrote before its cut and that hadn't reached the device removing it is ignored too (it's still on its own disk) |
| The storage | — | On a folder, S3 or WebDAV every device holds the same storage access. A removed device that still has it can delete or overwrite other devices' files (not forge readable content). **Pair removal with an access change** (below) |
| A device that was compromised before removal | — | Anything it planted while it was trusted (for example a fake device record before the key changed, or a modified Quire): check the device list before removing |
| The passphrase | A new passphrase locks the new key against whoever knew the old one | Keeping the same passphrase: whoever knows it can read new revisions through the new record |

**Pairing with a storage change:** S3 and WebDAV: make a new key or app password, give it to the other devices (*Update credentials…* / `sync credentials`), delete the old one; with a key per device (docs/sync-backends.md), delete only the removed device's key. A folder: stop sharing it with that device's account. A server: nothing more, unless the removed device might know the server's own token (a 0.12 setup kept it), then change `QUIRE_SYNC_TOKEN`; devices with their own tokens don't need it.

### UI and CLI

Settings → Sync → *Devices and sync format* lists the vault's devices (name as each says, its Quire version, this device, removed) with **Remove this device**, which asks for the passphrase for later devices and then shows the new recovery key and what else to do. `quire-cli sync devices <vault>` and `quire-cli sync remove-device <vault> DEVICE --recovery-key-file F`.

## 3. Authenticated headers everywhere, and the vault's minimum version

0.12 bound the whole revision header into the sealing on S3/WebDAV only. 0.13 adds a per-vault level:

| | Before | Upgraded (0.13) |
|---|---|---|
| Folder | `space.json` `min_reader` 1–2 | `format` and `min_reader` 4 |
| S3/WebDAV | `min_reader` 3 | `min_reader` 4 |
| Server | space `min_protocol` 1–2 | `min_protocol` 3 |

An upgraded vault seals revisions `v3`: file, revision, device, parents, chain (§4) and key epoch are all in the associated data, so a sync folder or server that changes any of them gets a revision that fails to open, and readers skip it as damaged (a folder now checks every other device's line with the vault's keys before using it, as S3/WebDAV did). Older revisions in the vault still open the way they were sealed.

**Older Quire gets a clear error, never a silent mix:** 0.9–0.12 refuse a folder or storage vault whose `min_reader` is above what they read ("this vault was made by a newer Quire; update Quire on this device"), 0.8 refuses a folder whose `format` is above 1, and a server answers 0.8–0.12 with `426` ("This vault now needs Quire 0.13 or later on every device"; 0.9–0.12 word it as "0.9 or later" from their own text).

**New vaults** made by 0.13 start upgraded. **Existing vaults** upgrade once, explicitly: Settings → Sync → *Upgrade sync format…* (or `quire-cli sync upgrade <vault> --yes`) first lists the devices that wrote revisions but never published a 0.13 device record ("not on 0.13 yet, as far as this vault knows": a 0.13 device that hasn't synced since updating is listed too). On a server the device needs its own token first (it gets one at its first 0.13 pass, on a 0.13 server). Removal and compaction need the upgrade; server-side compaction doesn't (it changes nothing older clients read).

**Tests with recorded fixtures:** `crates/quire-sync/tests/fixtures/folder-0.12` (a sync folder) and `remote-0.12.json` (S3/WebDAV objects) were written by the Quire 0.12.0 code (commit 5dee217, a throwaway generator in a scratch worktree). 0.13 joins both with the passphrase, reads every note, upgrades, writes, and reads its history (`harden.rs`, `harden_remote.rs`). Server: a protocol-2 client syncs alongside 0.13 devices until the upgrade, then gets the `426` text (`apps/quire-sync-server/tests/harden.rs`).

## 4. A revision lost for good

0.12: the head rule walks a note's revisions from its first one, so a revision missing for good stopped the walk on devices that never got it. 0.13 closes the gap in upgraded vaults: each `v3` revision names up to three further first-parent ancestors (`Revision::chain`, bound into the sealing). A reader that never got revision *k* still knows *k*'s parent from any later revision's chain, adds *k* as a placeholder there, and walks on: the same current revision as on a device that has *k*. Up to three consecutive lost revisions are bridged; more than that still stops the walk at the gap (as before; the status names the lost revisions on S3/WebDAV). The server never needed this (its log is linear), but stores the chain (a `chain` column, added on start).

## 5. Also

* **Faster change notice: not done.** A server already answers a long poll at once; a folder is checked every 2 seconds. S3 event notifications and WebDAV push are provider-specific and need something listening; a minute stays the price of nothing to run.
* **Moving history with `sync move`: not done.** The new place starts from the current notes, re-sealed under its own key; carrying history means re-sealing every revision and rewriting the graph under new ids. The old place keeps the history until deleted, as in 0.12.

## 6. Tests

* `quire-sync` unit tests: key boxes (wrong device, maker, context, a low-order point), removal and the passphrase/recovery joins, a removed device racing its own record, device records forged; snapshot plans (old history goes, ties and their fork points and links stay, recent and unreadable revisions stay), winners.
* `tests/harden.rs` (folder): an upgraded vault binds headers, keeps 0.9–0.12 out and still reads old revisions; the recorded 0.12 folder read, upgraded and written; a device offline through 30 rounds of edits and a compaction keeps its edit; compaction deletes old segments and bounds history; two devices compacting at once agree on one snapshot; a compaction cut short (a crash, a part still downloading) is ignored and done again; an edit built on a folded revision is kept beside the note; removing a device (it can't read new notes, what it writes is ignored, joiners need the new passphrase); a removal cut short; a lost revision doesn't hold its note back.
* `tests/folder_sync.rs`: 150 seeds each of random edits, renames and deletes through a slow sync tool in an upgraded vault, with devices compacting at random (often two at once, snapshots arriving late): every device ends with the same notes and no line is lost.
* `tests/harden_remote.rs` (S3/WebDAV over in-memory storage): compaction frees old objects and a device offline catches up; concurrent compaction leaves one winner; removal; recorded 0.12 objects read and upgraded.
* `apps/quire-sync-server/tests/harden.rs`: upgrade, device tokens only, 0.12 told to update; removal (`403`, old key refused with `422` until the new one is taken); two key changes at once (`409`); server compaction with an offline device.
* Every 0.12 sync suite still passes, including the real-server tests (moto, WsgiDAV) where run.

## 7. Deferred, and why

* **Signed revisions.** Revisions are authenticated with the vault key, which every device has; a device (or a removed one, before its cut) can still write revisions as another device. Per-device signatures (the agent-sync design's "authenticated devices") would close that; the device keys added here are a start.
* **Re-sealing old revisions after a removal.** The removed device could read them anyway; re-sealing would only cost uploads.
* **Compacting another device's lane.** Each device deletes only its own (plus removed devices'); a device that never comes back leaves its lane up to the cut, except when it's removed.
* **Device records for 0.12 devices.** Their version can't be known; they are listed as "0.12 or older, or not synced since updating".
* **Faster change notice and moving history** (§5).

## 8. Dependencies

`x25519-dalek` 2.0.1 (BSD-3-Clause; with `curve25519-dalek` 4.1, `curve25519-dalek-derive`, `fiat-crypto`, `cpufeatures`, `rustc_version`): the maintained, audited pure-Rust X25519 from the dalek project. Removing a device needs public-key encryption (the remaining devices' keys must be sealed so the removed one can't open them), and nothing in the tree offers static X25519 keys (`ring`'s are ephemeral only). No other new crates.
