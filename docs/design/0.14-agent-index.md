# Quire 0.14: search statistics per agent view

Status: proposed (0.14, awaiting owner approval)
Area: agents, security (search and Ask ranking for callers that may not see every note)
Code: `crates/quire-index/src/` (new `scope.rs`; `fulltext.rs`, `index.rs`, `sections.rs`, `hybrid.rs`, `semantic.rs`, `actor.rs`, `lib.rs`), `crates/quire-intel/src/ask.rs` (`retrieve_in`), `crates/quire-mcp/src/tools/{mod,common,legacy}.rs`, `crates/quire-mcp/src/tools/read/{ask,search}.rs`, `crates/quire-mcp/src/server.rs` (`instructions`), `crates/quire-assistant/src/runner.rs`, `crates/quire-mcp/tests/visibility.rs`, `apps/quire-cli/src/commands/bench.rs`, `packaging/perf-check.py`

The owner chose a separate index per agent view, with statistics built only from what each
connection can see. This note designs it inside the frame of `0.14-architecture.md` (§4 views,
§5 budgets, §9 wave 3). It uses `quire_agent::Visibility` from `0.14-agent-tools.md` (§3.5,
the architect's step T1) and the per-note passage store and incremental meaning model of
`0.14-index-startup.md` (step I2). That note was not written when this one was; §3.9 lists
what this design assumes from it. "View" in this note means an agent's set of visible notes.
In code the type is `Scope`, because `views.rs` already means Bases views.

## 1. The problem, as measured

From `0.14-health-gates.md` §2 and `crates/quire-mcp/tests/visibility.rs`:

- The MCP server has one `IndexService`. Its keyword statistics (`FullText`: document count
  `ids.len()`, document frequency `postings[t].len()`, average length `total_len`) and its
  meaning model (`Lsa::fit` in `semantic.rs`: vocabulary, IDF, term loadings, every passage
  vector) are built from every indexed note, deny zones included. The attachment-page index
  (`Index::attachment_text`) is the same.
- 0.13.3 made ranked tools rank only visible notes (`Keep`, the `*_where` functions), so a
  hidden note takes no place and no source number. The numbers that rank them still come from
  every note. In the test, `ask` for `secrettagzq` (a word found only in `Private/`) abstains
  in the plain vault but lists a visible "nearest passage" in the vault with hidden notes,
  because the hidden notes put that word next to "shared words" in the LSA model.
- The test tolerates this for `search`, `search_notes`, `ask` and `ask_notes` (`RANKED`):
  **58 of 1,740 calls per run** differ from the plain vault. It still requires that keyword
  hits and PDF pages are counted equally; hits found "by meaning" are not counted.
- More places where hidden notes reach an agent through numbers, found while reading for
  this note (not in the test today):
  - `search` returns each hit's `score` in its structured result (`search.rs`). BM25 scores
    use the whole-vault IDF and average length, so a hidden note that uses a query word
    lowers every visible hit's score. The test drops `score` before comparing.
  - `FullText::rank` expands a trailing prefix to at most 64 terms (`.take(64)`). Terms found
    only in hidden notes take some of the 64 slots, so fewer visible completions count.
  - `quire_intel::ask::weights` uses `ix.len()` (all notes) and `ix.idf(t)`, so whether a
    question word is "unseen" depends on hidden notes.
  - `Core::instructions` (`server.rs`) tells every agent "`({n} notes)`" with
    `n = self.index.read().len()`: the count includes deny-zone notes.
- Cost today: MCP `search` 28 ms p50 at 10k notes and 140 ms at 50k (0.14 performance scan,
  on 0.13.1). The CI budget is p95 ≤ 50 ms at 10k (`perf-check.py`, failing above
  50 × 1.25 = 62.5 ms); after 0.13.3 it measures about 18 ms (the lead's figure for this
  round). A full semantic rebuild costs 3.4 s CPU at 10k and 19.6 s at 50k; semantic adds
  137 MB at 10k (445 against 308 MB) and about 0.7 GB at 50k (2.1 against 1.42 GB).
- Locked notes are not part of the leak: `Vault::notes()` never lists a note in a locked
  folder, so the index never holds one, locked or unlocked in the process
  (`docs/design/0.11-secure.md`, "Where locked notes go"). The test's locked and unlocked
  servers show the same differences.

## 3. The design

### 3.1 What a view is

A view is the set of indexed documents (notes, and attachment pages by their file's path)
that `Visibility::allows_with_tags(path, record.tags)` accepts for one caller. Its inputs, from
`AgentStore::effective` and `candidates` (`store.rs`):

1. The actor: a human sees everything (`is_human()`); an agent has a policy key and an
   `unverified` flag (`Actor::policy_key`).
2. The active policies (`PolicyState::active()`: the approved file, or the file and the
   baseline until approved): zones by path (`Policy::modes_for`), "AI off", a revoked client.
3. The client's allow lists (`ClientPolicy::allows`: folders, and tags of the note).
4. Path rules that hold for everyone: `.quire/**` (`hard_rule`), hidden folders, links out of
   the vault, the locked-folder list (`lock::folder_of`), `.qenc` and key files.
5. The grant cap (`set_cap`): the server sets `Read` for read-only connections, which hides
   nothing, so it does not split views.

A view is built from the main index and holds only statistics (§3.3, §3.4). It borrows records,
sources, postings, passages and their text.

**Runtime changes.** A policy change, an approval, a revoke, "AI off" or a change of the
locked-folder list gives the caller a new `Visibility` with a new fingerprint, so a new view
(§3.2). A tag edit for a client with a tag allow list keeps the fingerprint and changes
membership for that one note (§3.5). Unlocking a locked folder in the process changes no view:
its notes never enter the main index, and the desktop app's separate in-memory index of
unlocked notes (0.11) is never an input to a view. Locking a plain folder, or unlocking one
for good, removes or adds notes through the index's per-note updates and changes the
locked-folder list, so every view is dropped and rebuilt (§3.6).

### 3.2 Keys and sharing

- **Key: `ScopeKey([u8; 32])` = `Visibility::fingerprint()`.** Agent-tools §3.5 defines it
  over the rules, not the notes. Equal fingerprints give equal answers for every path, so
  connections with the same fingerprint share one view. A client with a tag allow list is
  keyed by its rule; membership uses each record's tags, as agent-tools asks.
- **Request to agent-tools.** Compute the fingerprint from the read answer only
  (`Deny` or not), not from all modes. Then clients whose policy entries differ only in write
  zones (`direct`, `propose`) share a view. If the fingerprint keeps the modes, answers stay
  correct and only memory grows.
- **Typical sharing.** No deny zone and no allow list: every agent shares one view, and it
  hides nothing. One deny zone (`Private/`): every client without its own entry shares one
  view; tokens of one client share it. Each client with an allow list gets its own view.
- **Registry.** `IndexService` owns the registry (`Scopes`), so the MCP server (`Core.index`)
  and the in-app assistant (`ToolHost`, its own `IndexService`) each have one. A tool call
  gets a handle with `cx.index.scope(cx.visibility.fingerprint(), cx.visibility.clone())`.
  `quire-index` sees the predicate as `Arc<dyn Fn(&NotePath, &[String]) -> bool + Send + Sync>`
  and never depends on `quire-agent` (frame §6).
- **A human actor never gets a view.** `ScopeRead::Full` is the main index, as today.

### 3.3 Keyword statistics

`FullText` gains a dense term id per posting key (`postings: BTreeMap<Arc<str>, Posting>`, with
`Posting { term: u32, docs: HashMap<u32, f32> }`). Freed ids go back to a free list. If I1's
term interner (frame §5, "interning terms") gives ids, this design uses those ids. A document id
stays the same when its note is replaced, so view bitsets stay valid. Per view:

```rust
pub struct ScopeStats {
    notes: DocStats,   // over Index::fulltext
    pages: DocStats,   // over Index::attachment_text (pages of visible attachments)
}
struct DocStats {
    members: BitVec,   // by FullText document id
    n: u32,            // member documents
    total_len: f64,    // sum of member lengths (integer-valued: exact in f64)
    df: Vec<u32>,      // by term id: member documents using the term
}
```

`FullText::rank_in(&self, q, s: &DocStats)` is `rank` with these changes. It is one function,
and `rank` calls it with the index's own `DocStats`:

- `idf(df)` uses `s.n` and `s.df[term]`. The average length is `s.total_len / s.n`.
- `score_term` skips documents whose bit is not set. They get no score and no entry in
  `required`.
- A term with `s.df[term] == 0` counts as absent: an exact term returns no hits, as an
  unknown word does now.
- Prefix expansion takes the first 64 terms with `s.df > 0`, so hidden-only terms take no slot.
- Tag-only queries start from members only.

`Index::search_in`, `keyword_parts`, `merge_pages` and `Index::idf_in`/`len_in` take a
`ScopeRead`. Then `quire_intel::ask::weights` gets the view's count and IDF, and
`Core::instructions` gets the view's note count.

### 3.4 Meaning model

What is shared and what is not:

- **Shared:** passages (`Chunk`: path, heading, range, text) from I2's passage store. They
  describe one note and use no corpus statistics.
- **Per view:** everything `Lsa::fit` derives from the corpus: vocabulary (terms with
  `df ≥ 2` when there are 40 or more passages, at most 8,000), IDF, the term loadings
  `term_vecs`, and every passage vector. Passage vectors depend on the fitted IDF and basis,
  so they are per view as well.
- **Embeddings from a model** (an embedder from Settings → AI, `SemanticBuilder`): each
  vector comes from one passage, and `normalize` divides by that vector's own length. These are
  not statistics. Views share the main `SemanticIndex` and filter by membership. This is
  today's `search_where`, keep by bitset, with no fit. Any normalisation that uses other
  passages would make vectors per view again: mean-centring, whitening/PCA, "all-but-the-top",
  IDF-weighted pooling, or a threshold fitted on the vault. The local-AI design must not add
  one without saying so. `tau_sem`'s thresholds are constants and stay shared.

The MCP server sets no builder (`Server::with_config`), so `quire-cli mcp` and `serve` always
use LSA. The in-app assistant uses whatever the app's index uses.

```rust
pub struct ScopeMeaning {
    model: Arc<Lsa>,          // fitted on member passages only
    fit_members: u64,         // passages in the fit
    vectors: CompactVectors,  // member passages only, in passage-store order
    changed_since_fit: u32,   // for the refit rule (I2's)
}
```

**One rule for every meaning model:** a model may contain only passages that were visible to
the view when the model was fitted.

- **A view whose fit set equals the main fit set reuses the main model.** When the main model
  is fitted, the semantic worker counts each live view's members among the fitted passages.
  If every fitted passage is a member, that view reuses the main model and its vectors until
  the next main fit, with membership as the filter. This is the frame's "a view that hides
  nothing is the main index". The check is on the fit set, not the current set. If a hidden
  note is deleted after a fit, the main model still holds its statistics, so a view that now
  "hides nothing" may not reuse it until the main model is fitted again.
- **Otherwise the view fits its own model** on its member passages, in passage-store order
  (path, then offset): the same function, the same order and the same seed (`Rng(0x9E37…)`)
  as the main fit. When the view's set equals the main set, the result is the same, bit for
  bit (needed for G1; see the determinism fix below).
- **Between fits** it follows I2. A changed member passage is projected with the view's own
  basis and IDF. A removed passage loses its vector. A new member is projected. A note that
  leaves the view (a tag removed for a tag-limited client) loses its vectors at once. The
  model may keep its statistics until the next refit, because the view could read that note
  when it was fitted. Refits follow I2's rule (share of passages changed, or idle), at most one
  at a time on the semantic worker: main first, then views by most recent use.
- **Until a view has a model, it answers by keyword only.** It never uses the whole-vault
  model, as frame §4 says. If the view has at most 2,000 member passages, the first call fits
  the model on the calling thread *(guess: under 150 ms at the scale of the 2,000-note bench)*.
  This makes small vaults exact from the first call. Larger views fit in the background. The
  reply does not say that meaning is still being prepared (§9 question 2).

**Determinism fix** (step 1, needed for G1 and useful today). `Lsa::fit` sums each column's
norm in `HashMap` order. `Lsa::embed` adds weights into the output vector in `HashMap` order.
f32 addition is not associative, so two runs give vectors that differ in the last bits, and
near-ties can change rank. Both loops sort by term index first. The test `lsa_is_deterministic`
inserts the same passages in shuffled order and requires equal vectors, bit for bit.

**Compact vectors** (needed for G6). Today a passage vector is `dims + HASH_DIMS` f32
(96 + 512 = 608 floats, 2,432 bytes). The 512 hashed lexical dimensions are sparse. They are
non-zero only for the passage's vocabulary terms. `CompactVectors` stores:

- the latent part as `dims` f16 (192 bytes);
- the lexical part as sorted `(u16 bucket, f16 weight)` pairs (4 bytes each);
- one `f32` norm.

The dot product with a query is the latent dot plus a merge over the query's few non-zero
buckets. Estimate *(guess: about 4 passages per bench note, which averages 7.8 KB; about 120
vocabulary terms per passage)*: 40k passages at 10k and 200k at 50k; about 700 bytes per
passage, so **28 MB at 10k and 140 MB at 50k per view**, plus 3.5 MB of model (8,000 × 96 f32
loadings and the vocabulary). Dense f32 would be about 97 MB and 490 MB, over the frame's
rows. For bit-equality with main reuse (G1), main must use the same layout. That decision
belongs to I2 (§9 question 1).

### 3.5 Keeping views current

Views piggyback on the index actor, the single writer of `Index` (`actor.rs` `run`):

- The `Scopes` registry lives in `Index`. Keyword statistics change in the same write-locked
  step as the note's record. A reader always sees records and statistics that agree.
- In the prepare step (`Prepared::Note`, before the write lock), the actor computes each live
  view's verdict for the changed note, `allows_with_tags(path, &rec.tags)`. For a removal the
  verdict is the old bit. Under the lock, for each view: if the old document was a member,
  subtract its length and terms from `n`, `total_len` and `df`; if the new one is, add them.
  The cost is O(terms of the note) per live view *(guess: about 500 terms, 4 views, under
  50 µs)*.
- Attachment pages do the same against `pages`.
- The actor's per-note messages come from the manifest feed (frame §2: `Manifest::since`, own
  writes, watcher hints) through I1/I2. Views read nothing else. They keep no cursor of their
  own, because they are never behind the index.
- The semantic worker gets the same per-note passage changes from I2. It updates the main
  model and each view's `ScopeMeaning` (project, drop, or queue a refit).
- **A new view** (an unknown key): the tool call sends `IndexMsg::AddScope(key, predicate)`
  and waits for the reply. The actor takes a read lock and computes members (one `allows` per
  record and per attachment, no filesystem call with `Visibility`). It sums `df` over member
  documents' terms and installs the result under a short write lock. Because the actor is the
  only writer, nothing changes between build and install. Readers are never blocked during the
  build. Saves queue behind it *(guess: 20–40 ms at 10k, 100–250 ms at 50k; measured in
  step 3)*.

### 3.6 Caps and eviction

- Keyword statistics are small (G6), so up to **32** views keep them. Past 32, the least
  recently used view is dropped. Its next call rebuilds it (§3.5) and waits for that.
- Meaning models are large, so at most **4** views have their own (frame §4: "at most 4
  views"). The views that reuse the main model do not count. Past 4, the least recently used
  view's own model is dropped. That view answers by keyword only until it is again among the
  4 most recently used and is refitted. With the compact layout, 4 own models cost at most
  4 × 140 MB at 50k.
- This differs from the frame's single cap of 4 views: the frame's cap is about memory, and
  keyword statistics are about 1% of it. Dropping keyword statistics would send a call back to
  the leaking path or block it.
- A view unused for 10 minutes is dropped. A change of the locked-folder list drops every view
  at once and makes the main model refit before any view reuses it, because those models hold
  statistics of notes that are now locked (frame §2: "Locking a folder purges its rows'
  derived data from every cache in the same step").

### 3.9 What this design assumes from the other designs

- **Agent-tools (T1):** `Visibility` with `allows_with_tags` and `fingerprint()`, in `ToolCx`.
  The fingerprint is computed from read answers only (§3.2). `ToolHost` builds `ToolCx` with
  the actor's `Visibility`.
- **Index-startup (I1, I2):** stable document ids per path in `FullText`, or permission to
  make them stable; term ids from the interner, if it has them; a passage store in a fixed
  order (path, offset) that a fit can borrow by index; a per-passage change stream on the
  semantic worker; an incremental projection that takes a model handle, so it serves main and
  views; and the compact vector layout for LSA (§3.4), or a stated reason why not.
- **Frame:** nothing persisted (§4); the manifest feed through the index actor (§2);
  budgets (§5). The frame says a view "is patched from `Manifest::since`". Here it is patched
  one step later, by the index actor's per-note updates that the manifest drives. The result is
  the same and the view is never behind the index.

### 3.10 Disk, crash safety, migration, concurrency

- **Disk.** Views write nothing (G9). The LSA fit writes nothing today (`build_lsa_index`), and
  views add no `VectorCache`. Shared model embeddings are cached only by the main index, as
  today. No locked-folder statistics can be written in plain text, because no view is ever built
  from a locked note (§3.1). If views are persisted in a later release, it must go through the
  frame's §3 container under `.quire/cache/` (invisible to agents), keyed by fingerprint and
  `builder`. Before that, a test must show that a vault with a locked folder, unlocked in the
  process, writes no view file whose inputs touch that folder.
- **Crash safety.** Everything is in memory and rebuilt on first use after a restart. A crash
  at any step loses nothing.
- **Migration from 0.13.** None: no file, no format, no setting.
- **Concurrency.** Keyword statistics change only on the index actor under the write lock;
  readers see a consistent snapshot. Meaning models are `Arc` snapshots replaced by the
  semantic worker; a reader holds one model for its whole call. `Scopes` LRU bookkeeping is an
  atomic "last used" per view; eviction happens on the actor. Several processes on one vault
  (app, `quire-cli mcp`, `serve`) each have their own views; nothing is shared between them.

## 4. Alternatives considered

- **A full `Index` per view** (records, text, postings, graph). That is what "a separate
  index" says literally, and it is simple to reason about. It costs 1.42 GB per view at 50k
  (the scan's keyword peak) plus parsing per view. Records and postings are per-note facts,
  not statistics, so sharing them leaks nothing. Rejected.
- **Statistics from the intersection of all live views.** One model for everyone, built from
  notes every connection may see. But one connection's answers would change when another
  connects with a narrower rule, which tells the first that a narrower view exists and which
  notes it lacks. Rejected.
- **Keep shared statistics and blunt the output** (drop "by meaning" hits for agents, round or
  hide scores). Order still depends on hidden IDF and co-occurrence. Rejected.
- **Document frequency counted per query** (`|postings(t) ∩ members|`, nothing stored but the
  bitset, `n` and `total_len`). Exact and smaller. But `ask` asks the IDF of up to 10 words plus
  10 keyword searches, and a prefix may test many terms, each walking a posting list. Kept as
  the fallback for step 3 if term ids are not available yet.
- **Keyword-only search for every restricted view** (the frame's fallback, risk 4). Simplest,
  and it closes the larger part of the leak. But any vault with a deny zone loses meaning search
  for agents. Kept as what ships if I2 slips (§8).
- **One view per connection.** No sharing; every connection pays a fit (3.4 s at 10k).
  Rejected.
- **Use a model embedder for agents** (no corpus statistics, so views share vectors). That is
  correct when the person has turned one on, and §3.4 uses it then. AI is opt-in (P6), so it
  cannot be the default.

## 5. Compatibility

- **Sync, 0.13.x devices.** Nothing persisted, nothing on the wire. 0.13.x and 0.14 sync as
  before.
- **Existing vaults and agent setups.** No setting changes. An agent that can see every indexed
  note gets the same answers as before. An agent with a deny zone or an allow list gets
  rankings and `search` scores computed from its own notes. That is the fix, and the changelog
  says so. `instructions` may show a smaller note count.
- **CLI.** `quire-cli search` and `ask` are the person's: unchanged. `quire-cli mcp` and `serve`
  get views.
- **Real-time collaboration later.** Views derive from records and passages through per-note
  updates keyed by path and content. They assume one writer per process for the index (the
  actor, as today), not one writer of the vault. A CRDT layer that writes Markdown files feeds
  the same manifest and the same per-note updates. Views are per-process memory with nothing to
  merge between devices.

## 6. Risks, and how each will be tested

| Risk | Test |
|---|---|
| A view's statistics include a note it may not see (the leak again). | `a_scope_ranks_like_an_index_of_its_notes` (proptest in `quire-index`, 256 cases in CI, 50,000 weekly): random notes from a 40-word vocabulary with tags, a random member set, random queries (words, prefixes, phrases, tags, exclusions). For `search_in`, `search_sections_in` (all three `kind`s), `hybrid_search_in` and `retrieve_in`, results over the view equal results over a fresh `IndexService` loaded with the member notes only: paths, order, scores bit-equal, `by_meaning`. Plus the exact `visibility.rs` (§3.8). |
| Incremental statistics drift from a rebuild. | `scope_stats_patched_equal_a_rebuild`: 400 random edits, renames, deletes, tag flips and attachment changes; after each, every view's `DocStats` equals one built from scratch. The same model as `patched_graph_equals_a_rebuild`. |
| Main-model reuse after a hidden note was deleted (§3.4). | `reuse_needs_a_fit_without_hidden_notes`: fit with a hidden note, delete it, check the view does not reuse main until the next main fit; the reply equals a view-only index's. |
| Non-deterministic LSA breaks bit-equality. | `lsa_is_deterministic` (shuffled insertion order, equal bits); the visibility test run three times in CI, as now. |
| A prefix query counts hidden completions. | `prefix_completions_count_only_members`: 70 hidden terms share the prefix; the visible completion still ranks. |
| A locked folder's statistics survive in memory after locking. | `locking_a_folder_drops_every_view`: lock a folder that had notes, then check that no view and no reused main model was fitted with them (fit generation and member count). |
| Memory over budget. | `Scope::heap_bytes()` on the 10k bench vault, exact count in `perf-check.py` (G6); 50k reported. |
| Search slower for agents. | `bench.rs` `mcp_suite` runs a second pass with a policy that denies `Folder 0/`–`Folder 4/` (10%), approved as `visibility.rs` does; `search_restricted_p95_ms` budget 60 (G5). The default pass keeps its budget (G4). |
| A new view blocks saves at 50k. | `quire-index` timing test of `AddScope` at 10k (report) and the G7 count; a fault-injection test where the actor stops after building and before installing (the view is simply absent, and the call builds it again). |
| Eviction thrash with many clients. | unit test: 40 keys round-robin; caps hold (G10), every answer equals a fresh view's, and meaning falls back to keyword only, never to main. |
| Views written to disk. | G9 test: a counting `Storage` and a listing of `.quire/` and the state directory before and after 100 calls from 3 views. |

## 7. What the user sees

- **Security:** An agent's search and Ask now rank notes using only word statistics from the
  notes that agent may see. A word that appears only in a private zone can no longer bring up
  one of its visible notes, and `search` scores no longer shift with hidden notes.
- **Fixed:** When an agent connects, the note count Quire tells it counts only the notes it may
  see.

## 9. Open questions for the owner

1. **The compact LSA vector layout for the main index too?** Views need it to stay within
   150 MB at 50k, and bit-equality with a reused main model needs main to use the same layout.
   It would also shrink the main semantic index *(guess: about 70% less)*. Cost: f16 rounding
   changes the owner's "by meaning" order slightly. **Recommendation: yes**, decided together
   with index-startup (I2). If no, views never reuse the main model (each restricted agent pays
   its own model), or meaning stays keyword-only for views above 10k notes.
2. **Should a reply say "meaning search is still being prepared" while a view's model is
   fitted?** Agent-tools §3.9 suggests saying so in `indexing`. That message only appears
   when the view differs from the whole vault, so it tells the agent that hidden notes exist.
   **Recommendation: say nothing**; the "by meaning" hits simply appear a few seconds later.
3. **Caps: 32 keyword views and 4 meaning models** instead of the frame's single 4. Past 4,
   the least recently used agent loses meaning search until it is used again.
   **Recommendation: as proposed**, not a setting in 0.14.

## Conflicts with other designs

- **Agent-tools §3.9** keeps "the closure form as the fallback while the views are not built"
  and reports a building view in `indexing`. The closure form ranks with whole-vault
  statistics, which is the leak (frame §4). Here a view's keyword statistics are built before
  the first call answers (§3.5), so that fallback is never needed. Only meaning search waits,
  and silently (question 2).
- **Agent-tools §3.5 fingerprint** covers all modes. This design asks for a read-only
  fingerprint (§3.2). Not a correctness issue.
- **Frame §4** caps views at 4 and says "a view whose rules hide nothing is the main index
  itself". This design caps meaning models at 4 and keyword statistics at 32. It reuses the
  main meaning model by fit set, not by rules, and keeps its own small keyword statistics
  always (§3.4, §3.6).
- **Index-startup (I1, I2)** owns `FullText` and `SemanticIndex` layout. This design needs
  stable document ids, term ids, a passage store in a fixed order, projection that takes a
  model handle, and the compact layout (§3.9). It also asks that locking a folder forces a main
  refit.
