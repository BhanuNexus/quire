# Quire 0.14: search statistics per agent view

Status: current
Area: agents, security (search and Ask ranking for callers that may not see every note)
Code: `crates/quire-index/src/` (new `scope.rs`; `fulltext.rs`, `index.rs`, `sections.rs`, `hybrid.rs`, `semantic.rs`, `actor.rs`, `lib.rs`), `crates/quire-intel/src/ask.rs` (`retrieve_in`), `crates/quire-mcp/src/tools/{mod,common}.rs`, `crates/quire-mcp/src/tools/read/{ask,search}.rs`, `crates/quire-mcp/src/server.rs` (`instructions`), `crates/quire-assistant/src/runner.rs`, `crates/quire-mcp/tests/visibility.rs`, `apps/quire-cli/src/commands/bench.rs`, `packaging/perf-check.py`

The owner chose a separate index per agent view, with statistics built only from what each
connection can see. This note designs it inside `0.14-architecture.md` (§4 views, §5
budgets, §7 rule 4, §9 waves 2 and 3). It uses `quire_agent::Visibility` from
`0.14-agent-tools.md` (§3.5, step T1) and the hooks of `0.14-index-startup.md` §3.8 (steps
I1a and I2a). It folds in the architect's review, `0.14-review-agent-index.md`. "View" means
an agent's set of visible notes. In code the type is `Scope`, because `views.rs` already
means Bases views.

## Decided (owner, 2026-11-19)

- **Two releases.** 0.14.0 ships the keyword half: restricted agents get exact keyword search
  with their own statistics and no meaning search. That alone closes the leak. Per-view
  meaning models come in a 0.14.x (§8).
- **No message while a model is fitted.** A restricted agent is told nothing while its
  meaning model is fitted.
- **Compact f16 vectors everywhere**, including the main index. Index-startup §3.3 adopts
  the layout of §3.4.
- **Caps: 32 views with keyword statistics, 4 with a meaning model of their own.** This is not
  a setting. Eviction happens by the caps only: no idle timer (§3.6).
- From the review: a new view is built on the calling thread, with the registry beside the
  index (§3.5). Exactness is split into keyword and meaning (G1, G2). Document frequency is
  counted per query unless the step-3 measurement says otherwise (§3.3).

## 1. The problem, as measured

From `0.14-health-gates.md` §2 and `crates/quire-mcp/tests/visibility.rs`:

- The MCP server has one `IndexService`. Its keyword statistics (`FullText`: document count
  `ids.len()`, document frequency `postings[t].len()`, average length `total_len`) and its
  meaning model (`Lsa::fit` in `semantic.rs`: vocabulary, IDF, term loadings, every passage
  vector) are built from every indexed note, deny zones included. The attachment-page index
  (`Index::attachment_text`) works the same way.
- 0.13.3 made ranked tools rank only visible notes (`Keep`, the `*_where` functions), so a
  hidden note takes no place and no source number. The numbers that rank them still come from
  every note. In the test, `ask` for `secrettagzq` (a word found only in `Private/`) abstains
  in the plain vault but lists a visible "nearest passage" in the vault with hidden notes,
  because the hidden notes put that word next to "shared words" in the LSA model.
- The test tolerates this for `search`, `search_notes`, `ask` and `ask_notes` (`RANKED`):
  **58 of 1,740 calls per run** differ from the plain vault.
- Reading for this note found four more places where hidden notes reach an agent through
  numbers. None is in the test today:
  - `search` returns each hit's `score` (`search.rs`). BM25 uses the whole-vault IDF and
    average length. The test drops `score` before it compares.
  - `FullText::rank` expands a trailing prefix to at most 64 terms (`.take(64)`). Terms found
    only in hidden notes take some of the slots.
  - `quire_intel::ask::weights` uses `ix.len()` and `ix.idf(t)` over all notes.
  - `Core::instructions` (`server.rs`) tells every agent "`({n} notes)`" with
    `n = self.index.read().len()`, which counts deny-zone notes.
- Cost today:
  - MCP `search` takes 28 ms p50 at 10k notes and 140 ms at 50k (0.14 performance scan, on
    0.13.1). The CI budget is p95 ≤ 50 ms at 10k and fails above 50 × 1.25 = 62.5 ms. After
    0.13.3 it is about 18 ms (the lead's figure).
  - A full semantic rebuild costs 3.4 s CPU at 10k and 19.6 s at 50k. An LSA fit on 10,000
    passages takes 0.8 s (`ARCHITECTURE.md` §11.6).
- Locked notes are not part of the leak. `Vault::notes()` never lists a note in a locked
  folder, so the index never holds one, locked or unlocked in the process
  (`docs/design/0.11-secure.md`).

## 3. The design

### 3.1 What a view is

A view is the set of indexed documents that `Visibility::allows_with_tags(path, record.tags)`
accepts for one caller: notes, and attachment pages by their file's path. The inputs, from
`AgentStore::effective` and `candidates` (`store.rs`):

1. **The actor.** A human sees everything. An agent has a policy key and an `unverified` flag.
2. **The active policies** (`PolicyState::active()`): zones (`Policy::modes_for`), "AI off", a
   revoked client.
3. **The client's allow lists** (`ClientPolicy::allows`): folders, and the note's tags.
4. **Rules for everyone:** `.quire/**`, hidden folders, links out of the vault, the
   locked-folder list, `.qenc` and key files.
5. **The grant cap.** `Read` for read-only connections hides nothing, so it does not split
   views.

A view holds only statistics (§3.3, §3.4). It borrows records, sources, postings and
passages.

**Runtime changes:**
- **New fingerprint, new view.** A policy change, an approval, a revoke, "AI off" or a change
  of the locked-folder list gives the caller a new `Visibility` with a new fingerprint, and so
  a new view.
- **Tag edits.** For a tag-limited client, a tag edit keeps the fingerprint and changes one
  note's membership.
- **Unlocking a folder in the process changes no view.** Its notes never enter the main
  index, and the desktop's separate in-memory index of unlocked notes is never an input.
- **Locking a folder, or unlocking it for good,** changes the locked-folder list. Index-startup
  §3.3 marks the main model tainted, and views never reuse a tainted model.

### 3.2 Keys and sharing

- **Key.** `ScopeKey([u8; 32])` = `Visibility::fingerprint()`. Agent-tools computes it over
  read answers only, so clients that differ only in write zones share a view. A tag-limited
  client is keyed by its rule; membership uses each record's tags.
- **Typical cases.**
  - No deny zone and no allow list: all agents share one view, and it hides nothing.
  - One deny zone: every client without its own entry shares one view.
  - A client with an allow list gets its own view.
- **Registry.** `IndexService` owns a `Scopes` registry, so the MCP server and the in-app
  assistant (`ToolHost`, its own `IndexService`) each have one.
- **Getting a view.** A tool call gets a handle with
  `cx.index.scope(cx.visibility.fingerprint(), cx.visibility.clone())`. `quire-index` sees the
  predicate as `Arc<dyn Fn(&NotePath, &[String]) -> bool + Send + Sync>` and does not depend on
  `quire-agent`.
- **Humans.** A human actor uses `ScopeRead::Full`, the main index as today.

### 3.3 Keyword statistics

**Per view, always:**

```rust
pub struct ScopeStats {
    notes: DocStats,   // over Index::fulltext, by DocId
    pages: DocStats,   // over Index::attachment_text
}
struct DocStats {
    members: BitVec,   // by stable DocId (index-startup §3.3)
    n: u32,
    total_len: f64,    // integer-valued sums: exact in f64
    all: bool,         // members == every document: hides nothing
}
```

**Document frequency: counted per query (plan A), stored only if the measurement says so
(plan B).**

- **Plan A.** `FullText::rank_in(&Query, &DocStats)` walks each query term's posting list
  twice: first it counts members (the term's `df`), then it scores members only. A term with
  member `df == 0` counts as absent. Prefix expansion keeps the first 64 terms that have *any*
  member (the count stops at the first hit). `idf_in(term)` for `ask::weights` walks at most
  10 lists. A view with `all` skips counting and uses `postings.len()`. Per-note patching is
  one bit plus `n` and `total_len`.
- **Plan B.** `df: Vec<u32>` by `TermId` (index-startup §3.2 interner), patched per note under
  the write lock: O(terms of the note) per live view. Lookup is O(1).

**Measured in step 3** before choosing, on the 10k bench vault with 10% denied, and reported
at 50k:
- (a) MCP `search` p95, restricted against default, on the bench's 600 two-word queries;
- (b) MCP `ask` p95, restricted, with 10-word questions;
- (c) a worst-case prefix query (a one-letter prefix over the vault's most common letter);
- (d) the extra cost of saving one note with 32 live views (plan B only).

**Decision rule.** Keep plan A if restricted `search` and `ask` p95 are within G5 and within
1.3× the default view's p95. Otherwise use plan B. If B is chosen, (d) must keep "save to
keyword-searchable" within the frame's 50 ms p95.

**Changes in both plans:**
- `rank` calls `rank_in` with the index's own statistics, so there is one ranking function.
- `score_term` skips non-members.
- Tag-only queries start from members.
- `Index::search_in`, `keyword_parts`, `merge_pages`, `idf_in` and `len_in` take a
  `ScopeRead`, so `ask::weights` and `Core::instructions` use the view's numbers.

### 3.4 Meaning model (0.14.x)

**Shared and per view:**
- **Shared:** passages (path, heading, range, text) from index-startup's passage store.
- **Per view:** everything an LSA fit derives from the corpus (vocabulary, IDF, term
  loadings) and every passage vector, because vectors depend on the fitted IDF and basis.
- **Model embedders.** Vectors from a model embedder (Settings → AI) are per passage, and
  `normalize` uses the vector's own length. These are not statistics. Views share them and
  filter by membership, with no fit.
- **What would make vectors per view again:** any normalisation over other passages
  (mean-centring, whitening/PCA, "all-but-the-top", IDF-weighted pooling, thresholds fitted on
  the vault). `tau_sem` thresholds are constants.
- **MCP uses LSA.** The MCP server sets no builder, so it always uses LSA.

```rust
pub struct ScopeMeaning {
    model: Arc<Lsa>,          // fitted on member passages only
    vectors: CompactVectors,  // member passages, passage-store order
    used_since_fit: bool,
    changed_since_fit: u32,
}
```

**The rule: a model may contain only passages that were visible to the view when it was
fitted.**

- **Reuse of the main model.** A view reuses the main model if every passage of the main
  fit was a member at fit time and the model is not tainted. The semantic worker counts
  members at each main fit. A view that hides nothing therefore costs no fit. After a hidden
  note is deleted, the main model still holds its statistics, so no reuse until the next
  main fit.
- **Own fit.** Otherwise the view fits its own model. It uses member passages, which
  `Lsa::fit` sorts by text first (equal texts are interchangeable), the same function and the
  same seed as the main fit. With the
  determinism fix (step 1) and the shared compact layout, equal passage sets give equal
  bits.
- **Between fits.** The view follows index-startup §3.3: `Lsa::project(&model, text)` with
  its own model for changed and new members, and dropped vectors for removed ones.
- **Refits.** Same rule as main (10% of passages changed, or idle), at most one at a time:
  main first, then views by most recent use. **A view is refitted only if it was used since
  its last fit.**
- **Until a view has a model it answers by keyword only.** It never falls back to the
  whole-vault model, and the reply says nothing about it.
- **Fitting on the first call.** With at most 1,000 member passages, the first call fits
  on its own thread: about 80 ms, scaled from 0.8 s per 10,000 passages
  (`ARCHITECTURE.md` §11.6), and measured in step 6. Larger views fit in the background.
  `ToolHost::call` runs on the agent panel's run thread (`agent_panel_ui.rs` spawns it), never
  on the UI thread (P9).

**Determinism fix** (step 1, wave 0). Two loops add floats in `HashMap` order: `Lsa::fit`
sums column norms that way, and `Lsa::embed` adds weights that way. Both sort by term index
first, and `Lsa::fit` also sorts the passages by text first, so the order they arrive in
does not matter. Test: `lsa_is_deterministic`.

**Compact vectors** (decided; main and views). Each passage vector holds:
- the latent part as `dims` f16;
- the lexical part as sorted `(u16 bucket, f16 weight)` pairs;
- one f32 norm.

That is about 700 bytes a passage, against 2,432 bytes dense. Per own model that is about
28 MB at 10k and 140 MB at 50k *(guess: 4 passages a note)*, plus about 3.5 MB of model.

### 3.5 Building and patching views

**The registry sits beside the index, not inside it.** `IndexService` holds
`Arc<RwLock<Index>>` and `Arc<Mutex<Scopes>>`. Lock order: index, then registry, never the
reverse. A load (`*ix = Index::new()` in `run`) therefore keeps the registry and its
predicates.

**A new view is built on the calling thread.**
1. The caller takes the index read lock.
2. It looks up the key in the registry. If the key is present, it uses the view.
3. Otherwise it computes members and totals: one `allows_with_tags` per record and per
   attachment. These are pure calls with no filesystem access.
4. It inserts the view into the registry, then releases the read lock.

The actor is the only writer and cannot write while the read lock is held, so the view is
consistent with the records. The actor's next write updates it with the rest. Readers are
never blocked. The actor waits at most one build, as it does for the graph build today
*(guess: 5–20 ms at 10k with plan A, measured in step 4)*. If two callers build the same key,
the second insert finds the first and drops its own.

**During a vault load** a view holds the records indexed so far and is patched as the rest
arrive. A search during load answers from the partial index at once, as it does today.

**Per-note patching, by the actor under its write lock.** For each changed record and each
live view, the actor computes the verdict (a pure call) and updates the bit, `n` and
`total_len` (and `df` under plan B). Removals use the old bit. The actor resets every view's
statistics in the same write that replaces the index on `Load`. Changes arrive from the
manifest feed through the index's per-note messages (frame §2, §4), so views are never
behind the index.

**Meaning (0.14.x).** The semantic worker receives index-startup's passage change stream and
updates the main model and each `ScopeMeaning`.

### 3.6 Caps and eviction

- **Keyword statistics: at most 32 views.** Past 32, the least recently used view is dropped.
  Its next call rebuilds it (§3.5).
- **Own meaning models: at most 4.** Views that reuse the main model do not count. Past 4,
  the least recently used view loses its own model and answers by keyword only until it is
  again among the 4 most recently used and is refitted. Memory: at most 4 × 140 MB at 50k.
- **No idle timer.** A quiet agent keeps its view and model (review B3).
- **Policy and locked-folder changes** also evict. Views whose key no callers produce any more
  are dropped, and a locked-folder list change drops them all at once.

### 3.9 What this design takes from the others

- **Agent-tools (T1):** `Visibility` with `allows_with_tags` and a read-only `fingerprint()`, in
  `ToolCx`; `ToolHost` builds the same.
- **Index-startup:**
  - from I1a (wave 1): stable `DocId`s and `TermId`s, `FullText::doc_terms(DocId)` and `FullText::doc_len(DocId)`;
  - from I2a (wave 2): the passage store in (path, offset) order, the passage change stream,
    `Lsa::project` with a model handle, the compact layout, and a tainted model when a
    folder is locked (§3.8 of that note).
- **Frame:** nothing persisted. Views are patched by the index actor in the same step as the
  note. The caps are those of §4.

### 3.10 Disk, crash safety, migration, concurrency

- **Disk.** Views write nothing (G8). No view is built from a locked note (§3.1), and
  index-startup never writes a tainted model. If views are persisted later, it goes through
  the frame's §3 container under `.quire/cache/`, keyed by fingerprint. A test must then show
  that no view file is derived from a locked folder's text.
- **Crash safety.** Everything is in memory and rebuilt on first use. A crash loses nothing.
- **Migration from 0.13.** None.
- **Concurrency.** Keyword statistics change only under the index write lock. Readers see
  records and statistics that agree. Meaning models are `Arc` snapshots. Each process (app,
  `quire-cli mcp`, `serve`) has its own views.

### 3.11 As built in 0.14.0, and what is left

From the build and Fable's review of it:
- **Plan A kept** (§3.3). At 10k notes with 10% denied, restricted `search` and `ask` p95 came
  out at 1.0 to 1.3 times the default view's with keywords only.
- **Meaning only after a refit.** The main meaning model is fitted on every note. A view gets
  it only if the view hides nothing now, and the fit started after the view last hid a
  document. Each fit takes a number before it reads a note. A view records how many fits had
  started when it last hid one. So deleting a hidden note does not bring meaning back until
  the next refit. A view built after a document left the index (first built, built again
  after eviction, or after a reload) can't tell whether it would have hidden that document.
  It starts marked as of the last removal, which the service keeps. `Scoped::semantic` is the only way a tool gets the model, and it is used
  for retrieval, the extractive answer and abstaining.
- **No storage call under the write lock.** A view's predicate says whether it may read the
  vault. The index worker asks it without that permission. A folder the caller's
  `Visibility` has not checked then gives no answer, and the note stays hidden and
  undecided. On every registry hit, the view takes the caller's own predicate and decides the
  undecided notes on the caller's thread: three storage calls per new folder at most, once.
  A note decided hidden from a folder cache that was stale stays hidden until it is changed
  again: this fails closed, and is left as it is.
- **Timing (not closed).** A word that only hidden notes use often still costs a scan of its
  posting list, all of whose entries are hidden, before the view counts it as absent. An
  agent that times its searches could tell such a word from one no note uses. Closing this
  needs per-view document frequencies (plan B, or a df table per view) and is left for 0.14.x.
  Nothing hidden is returned, and the ranking does not change.

## 4. Alternatives considered

- **A full `Index` per view.** That costs 1.42 GB per view at 50k. Records and postings are
  per-note facts, and sharing them leaks nothing. Rejected.
- **Statistics from the intersection of all live views.** One connection's answers would
  change when another connects, which tells it that a narrower view exists. Rejected.
- **Blunt the output** (drop "by meaning" hits, round scores). The order still depends on
  hidden IDF. Rejected.
- **Stored `df` as the plan.** It costs term ids, a vector per view and per-note patching for
  up to 32 views, and its only gain is O(1) lookup. It is plan B, chosen only by the step-3
  measurement (§3.3).
- **Build views on the index actor** (the first draft). The first call would wait behind a
  vault load (9.4 s cold at 50k, against a 500 ms "first search answer" budget). Rejected
  (review B1).
- **Drop idle views after 10 minutes** (the first draft). A quiet agent would pay a fit every
  time. Rejected (review B3).
- **One view per connection.** Every connection would pay a fit. Rejected.
- **Use a model embedder for agents.** That is correct when one is on, and §3.4 uses it then.
  AI is opt-in (P6), so it cannot be the default.

## 5. Compatibility

- **Sync, 0.13.x devices.** Nothing is persisted or sent. They sync as before.
- **Existing vaults and agent setups.**
  - No setting changes.
  - An agent that can see every indexed note gets the same answers.
  - An agent with hidden notes gets its own rankings and scores. In 0.14.0 it gets no
    "by meaning" hits.
  - `instructions` may show a smaller note count.
- **CLI.** `quire-cli search` and `ask` are unchanged. `mcp` and `serve` get views.
- **Real-time collaboration later.** Views derive from per-note updates keyed by path and
  content. They assume one index writer per process (as today), not one writer of the vault.
  A CRDT layer that writes files feeds the same updates. Nothing needs merging between
  devices.

## 6. Risks, and how each will be tested

| Risk | Test |
|---|---|
| Keyword statistics include a non-member (the leak). | `keyword_scope_ranks_like_an_index_of_its_notes` (proptest, 256 cases in CI, 50,000 weekly): random notes from a 40-word vocabulary with tags, random members, random queries (words, prefixes, phrases, tags, exclusions). `search_in`, `search_sections_in` (all `kind`s), `hybrid_search_in` and `retrieve_in` with meaning off must equal a members-only `IndexService`: paths, order, bit-equal scores. Plus `visibility.rs`. |
| A meaning model depends on a non-member. | `meaning_scope_depends_only_on_members`: one random edit history replayed in the full index (with a view) and in a members-only index. After each `flush_semantic`, bit-equal results. Between refits, equal results too, because both fold in the same member passages with models fitted on the same members. |
| Patched statistics drift. | `scope_stats_patched_equal_a_rebuild`: 400 random edits, renames, deletes, tag flips, attachment changes and a `Load` in the middle. |
| A view is built while the actor writes. | `a_view_built_during_writes_is_consistent`: 8 threads create views while the actor applies 1,000 edits. After a flush, every view equals a rebuild. A build during `Load` returns at once (G7). |
| Main-model reuse after a hidden note was deleted, or after a lock. | `reuse_needs_a_fit_without_hidden_notes`, `a_tainted_model_is_never_reused`. |
| Non-deterministic LSA. | `lsa_is_deterministic`; `visibility.rs` run three times in CI. |
| Hidden prefix completions. | `prefix_completions_count_only_members`: 70 hidden terms share a prefix. |
| Plan A is too slow. | the step-3 measurements and the decision rule (§3.3); G5 in `perf-check.py`. |
| Memory over budget. | `Scope::heap_bytes()` exact count at 10k (G6). |
| Eviction thrash. | 40 keys round-robin: caps hold (G9), answers equal fresh views, and meaning falls back to keyword only, never to main. |
| Views on disk. | G8 test. |

## 7. What the user sees

- **Security:** An agent's search and Ask now rank notes using only word statistics from the
  notes that agent may see. A word found only in a private zone can no longer bring up one of
  its visible notes, and search scores no longer shift with hidden notes.
- **Changed:** An agent that cannot see every note searches by keyword only for now. Search
  by meaning for these agents returns in a later 0.14 update. (0.14.0 only; the 0.14.x
  release replaces it with "Agents that cannot see every note can search by meaning again,
  using only notes they may see.")
- **Fixed:** When an agent connects, the note count Quire tells it counts only the notes it may
  see.
