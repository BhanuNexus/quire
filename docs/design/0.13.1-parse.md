# Quire 0.13.1: parsers and hostile input

Status: record
Area: parsers and hostile input

A record of a pass; not a description of today's code.

The hardening pass adds no features. This note covers what the review of `chore/hardening` found about parsers (S-L1, S-L3, S-L4, D-L3) and the two dependency claims the security review could not check.

## 1. Text kept as written is never edited through (D-L3, S-L3)

The front-matter reader keeps some values as text instead of reading them into fields: maps nested more than 64 levels deep (block maps, and flow maps `{a: {a: …}}`), and lists of maps. A writer that went *through* such a value (a dotted path such as `k0.….k63.newkey`) used to rewrite the whole entry from what was read: the deep part was dropped (a 10,616-byte note became 4,498 bytes and lost its leaf) or, for a flow map, re-quoted as one string.

Now `set_field_path`, `remove_field_path` and `rename_field_path` return `Err(Refused)` when the path runs through such a value, and write nothing. `Refused` says which path and that the note is unchanged. The error reaches every caller:

- **Properties panel** (`set_property_path`, `remove_property_path`): a warning notice with that text; the note's bytes are unchanged.
- **Templates** (`new note from template` with preset values): the same notice; the template text is left as it is.
- **Refactors** (rename/merge/delete a property across notes): the note's whole operation is dropped, so a merge never removes the source key and then fails to write the target. The plan lists the notes it left out (`plan_with_refusals`, `Preview::refused`), and a warning notice says how many.
- MCP, the CLI and agents set top-level properties only (`set_field`); that replaces one entry on purpose and never goes through another.

Replacing or removing a whole entry (`set_field(src, "k", …)`, `remove_field(src, "k")`) still works: it is the person's explicit choice of that entry. Editing any other key keeps the kept-as-text entry byte for byte; the tests run every writer that touches front matter (`set_field`, `set_field_path`, `remove_field`, `rename_field_path`, `append_list_item`, `edit_list_items`, and the linter's tidy with every front-matter rule on, including date modified and sorting) over a deep flow map and a deep block map and compare the entry's lines. Importers write new front matter and do not rewrite an existing note's, so they have nothing to round-trip.

## 2. Deep YAML, JSON and TOML (S-L1)

`yaml-rust2` limits flow nesting (`[[[…`, 255) but not block nesting: `- - - …` or deeper indentation recurses through the loader, `Clone`, `PartialEq` and `Drop` until the stack is gone, and a stack overflow aborts the app. It was reached by the linter on save and on Tidy (`real_tags`, `real_map`), by `frontmatter::yaml_valid` (link rewrites, field edits) and by Bases (`.base` files: `base::parse`, `set_view_key`).

All of them now call `frontmatter::load_yaml`, which first runs `yaml_depth_ok`: one pass over the lines, no recursion, that counts indentation levels in force plus the `-`, `?`, `:` indicators opening a collection on the same line, and refuses more than 64. A refused text is "not readable": the linter leaves the note as it is, a `.base` shows "this base can't be read: it is nested too deeply to read", and the file is never changed. Block scalars count like other lines, so a pathological one is refused too (the safe side). Flow nesting is left to the parser's own 255 limit; the mixed cases are in the tests.

Every other place user text reaches a recursive parser:

| Entry point | Parser | Depth limit |
|---|---|---|
| Linter, `yaml_valid`, `.base` files | `yaml-rust2` | `yaml_depth_ok` (64) plus its flow limit |
| Front-matter reader and writers | Quire's own | 64 (`MAX_NESTING`), deeper kept as text |
| `.canvas`, Excalidraw (`.excalidraw`, `.excalidraw.md`), MCP and sync JSON, importers (Keep, Roam, Day One, Bear) | `serde_json` | its default 128; `unbounded_depth` is not enabled anywhere (`cargo tree -e features`) |
| Canvas ordered JSON (`ojson`) | Quire's own | 200 (`MAX_DEPTH`) |
| `vault.toml`, policy and contract files, themes, settings, state files | `toml` 1.2 and `toml_edit` 0.25 (`toml_parser`) | its own recursion limit |
| BibTeX libraries (`.bib`: citations, reference lists) | `biblatex` | none of its own: it overflowed the stack on 100,000 nested `{`, so `parse_bibtex` and `other_fields` now refuse more than 128 levels (`too_deeply_braced`) |

Tests, each with 100,000-deep input (lists, maps, flow and a mix; block maps as deep as the indentation allows), run on a thread with an ordinary stack (2 MiB, or smaller), so a stack overflow aborts the run and fails the test: `quire-markdown` `frontmatter::tests::deep_yaml_reaches_no_recursive_parser` (linter, `yaml_valid`, `parse`), `quire-import` `base::tests::a_base_nested_100000_deep…`, `quire-canvas/tests/deep_json.rs` (three JSON readers), `quire-vault` `prefs` (`vault.toml`), `quire-agent` `policy`, `quire-app` `themes` and `citations`.

Found and not fixed: the linter's *other* rules take about 48 s (debug build) on a note with a single line of 100,000 `[`, whether the line is in front matter or the body. That is the Markdown inline scanner, not a parser overflow; it is the same slowness any such text causes, and it is left to the performance work.

## 3. PDF pages with a huge size (S-L4)

`apps/quire-ai-engine` rendered a page at `dpi/72` with no limit: `MediaBox [0 0 20000 20000]` at 300 dpi asked hayro for 65,535 × 65,535 pixels (17 GB). `quire-pdf` capped a side at 8,000 px (a 256 MB image) and `scale.clamp(0.05, MAX_SIDE / side)` panicked for a side over 160,000.

Both now use `page_scale(want, width, height)`: the wanted scale, at least 0.05, lowered so that no side is over 8,000 px and the image is at most 40 megapixels (160 MB of RGBA), raised to one pixel for a tiny page; `None` (an error, not a render) for a size that is zero, negative or not finite, or too thin to give a pixel. `quire_pdf::render_page` covers the desktop viewer (zoom, and the canvas card thumbnail), so those need no change. Tests: huge, tiny, zero, negative, infinite and NaN sizes on the arithmetic, and PDFs with a huge, zero, tiny and negative `/MediaBox` rendered through `render_page` in both crates.

## 4. The two claims the security review could not check

- **Can note text become raw Typst in the PDF export (RUSTSEC-2026-0194/0195)?** No. Text is escaped for Typst markup (`escape_markup`: every ASCII punctuation character) or written as a string literal (`typst_string`); no raw-Typst passthrough exists. The one place Typst code is evaluated from note text is math, where the converted formula goes through `eval(…, mode: "math")` and a `#` would start code. mitex writes every `#` from the note as `\#` (`#read(…)` in `\text{}`, `\mathrm{}`, `\operatorname{}`, `\color{}`, matrices and `$…$` inside `\text{}` all come out escaped), `\iftypst` is refused, and the test `formula_text_never_becomes_typst_code` checks that the only unescaped `#` in the output of a corpus of hostile formulas are calls mitex itself writes. The Typst world serves no file the note did not put there, so `bibliography(style: "x.csl")` could not find a user CSL file either. The claim holds.
- **Is mitex-spec's rkyv archive reader called (RUSTSEC-2026-0235)?** Yes, which the earlier wording of `deny.toml` and `0.13.1-deps.md` got wrong. `mitex_spec_gen::DEFAULT_SPEC` calls `CommandSpec::from_bytes` once, on first use, on the `default.rkyv` that mitex's build embeds; `mitex::convert_math(input, None)` uses it. Quire always passes `None`, so the archive read is that fixed build-time file and no user byte reaches rkyv. The advisory stays ignored on that ground, and both texts now say so.

## 5. Dependencies rolled back

hayro 0.8 and resvg 0.49 (and skrifa 0.49) were rolled back to 0.7, 0.47 and 0.44 because Typst 0.15 pins hayro 0.7 and resvg 0.47, and two copies of the PDF and SVG stacks took the full edition to 77 MiB against its 74 MiB budget. See `0.13.1-deps.md`.
