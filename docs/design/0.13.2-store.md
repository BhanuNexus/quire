# 0.13.2 storage and locks

What the storage-and-locks team of the 0.13.2 data-safety pass found and
did. Items are numbered as in the brief; "scan item N" is the entry of
`reliability.md` (the 0.13.2 read-only scan). Every fix has a test that
fails without it, except where this note says otherwise.

Files: `crates/quire-vault/**`, `crates/quire-app/src/atomic.rs`,
`crates/quire-app/src/secure_state.rs` (and its tests),
`crates/quire-app/src/history_ops.rs`. Outside the lane, each as small as
it could be: see the last section.

## 1. The trash replaced same-named files (scan item 2) — real, fixed

Confirmed by the test below failing on the old code: two `notes.md` from
`A/` and `B/` trashed with the same stamp left one file.

`LocalFs::move_to_trash` keeps the name it had (`.trash/<YYYYmmdd-HHMMSS>
<file name>`) and, when that is taken, uses `<stamp> <stem> (2).<ext>`,
`(3)`, …. The name is claimed with `create_new` (an empty file) and the
note renamed over that claim, so neither this process nor another one (the
CLI, a second window, `serve`) can make two trashings land on one name. A
rename that fails removes its claim. Nothing reads `.trash` by name (it was
checked: the agent, MCP and sync code only skip it), so the old names and
contents read as before; only the ` (n)` suffix is new.

Tests: `the_trash_never_replaces_a_file_trashed_in_the_same_second` (two
folders, same stamp; 40 more in a loop through the real clock),
`the_trash_is_safe_from_several_writers_at_once` (two storages on one
folder, 40 trashings with one stamp from two threads).

## 2. Windows replace fails while a file is open (scan item 4) — real, fixed; proof on Windows rests on CI

The reading of the code in the scan holds (tempfile 3.27's `persist` is a
bare `MoveFileExW`). Not reproducible here (Linux).

- New `quire_vault::replace_file(tmp, dest)`, used by `LocalFs` and by
  `quire_app::atomic::write`: it closes the temporary file, makes it an
  ordinary file (`TempPath::keep`, which clears Windows' temporary
  attribute), and renames it with `std::fs::rename`, which on Windows 10
  1607+ uses `FileRenameInfoEx` with POSIX semantics and so replaces a
  file others have open for reading. A rename refused with access denied
  (5), sharing violation (32) or lock violation (33) is retried, waits
  doubling from 5 ms to 50 ms, for 400 ms in all. Any failure removes the
  temporary file. The same retry covers `LocalFs::rename` and the trash
  move. Other systems never retry (an open file doesn't block a rename).
- Tests: platform-neutral `a_replace_blocked_for_a_moment_is_retried_and_one_blocked_for_good_gives_up`
  (the retry logic with an injected "busy" error) and
  `a_failed_replace_leaves_no_temporary_file`; `#[cfg(windows)]`
  `replacing_a_file_that_is_open_for_reading` (held open with `File::open`;
  held without delete sharing for 100 ms, then released; held for good:
  fails in bounded time, no temp file left) and, in `atomic.rs`,
  `replaces_a_file_that_is_open_for_reading`. **These two run only on the
  Windows CI runner.**
- The app no longer works against itself: while this process converts a
  folder (lock, unlock for good, key change), `secure_state::vault_event`
  ignores events for files in that folder (no `rebuild_locked_index`, no
  `history.keep`, no read of the key file or `.qenc` files being
  rewritten). When the job ends, success or failure, the locked index is
  rebuilt once and open locked notes are checked against the disk
  (`recheck_locked_docs`). Test: `own_conversions_are_not_read_back_while_they_run`.
- Also: a conversion thread that panicked left "Locking X/…" up forever and
  refused every later conversion (`try_recv().ok()`); a disconnected job
  now ends with a "stopped unexpectedly" message (same test).
- Whether this was *the* cause of the flaky
  `changing_a_folders_key_from_the_app` can only be shown by CI runs on
  Windows. With item 3 the test's failure, if any remains, now says why.

## 3. A failed key change hid the new recovery key (scan item 5) — real, fixed

Confirmed by reading and by the new test (on the old code a stopped key
change gives `Done::Failed { recovery: None }` and the lock-specific
message).

- `lock::change_key` is now `begin_change_key` (writes the key file with
  the new key, checks it reads back, returns the new recovery key before
  any file changes) followed by `finish_change_key` (re-encrypts, clears
  `rotating`). `change_key` remains as the two together. The app and the
  CLI call the two parts, so the recovery key is shown (app) or written to
  the file asked for (CLI) even when the rest stops.
- Resuming (`rotating` set): the passphrase given is kept if it opens the
  key file; another one (8+ characters) re-wraps the same new key with it;
  an empty one keeps the current (the CLI's resume). Before, the second
  passphrase was ignored without a word. The key file is written with a
  compare-and-swap against the one read, so another device's change in
  between isn't overwritten.
- Each conversion has its own failure message. A key change that stopped
  after the key file changed says: every note still opens, only with the
  new passphrase and the new recovery key (shown now), and how to finish
  ("Change a locked folder's passphrase…" with "Also change the folder's
  key", the new passphrase as the current one). One that stopped before
  says nothing changed. Unlocking with the old passphrase or old recovery
  key while `rotating` adds why it fails. Locking and unlocking for good
  have their own texts.
- The old passphrase and recovery key cannot keep working during a key
  change without a format change (the key file would need the old key
  wrapped by the old passphrase); not done. Instead the new ways in are
  shown before anything else changes.
- Tests: `a_key_change_that_stops_anywhere_always_leaves_a_way_in`
  (quire-vault: a failure injected at every storage step; before the key
  file changed the old passphrase and recovery key open everything; after,
  the new passphrase and the returned recovery key do, and a retry with a
  third passphrase keeps that one), and
  `a_key_change_that_stops_shows_the_new_key_and_how_to_finish` (app, real
  disk, a damaged file stops the change after the key file). The existing
  `changing_the_key_interrupted_at_any_step_finishes` resumed with a
  6-character "unused" passphrase that was ignored; it now passes the new
  passphrase.

## 4. Lock and unlock for good against autosave (scan item 8) — real, fixed

- `lock_folder` phase 1: a plain file gone between listing and reading
  (an autosave wrote the `.qenc` and removed it) is skipped; the `.qenc`
  is written only over the copy read just before (compare-and-swap), so a
  save that lands in between is kept. Test: `a_save_during_locking_is_kept`.
- `unlock_folder_permanently`: the plain file is written only where none
  is (compare-and-swap with "absent"); a file saved meanwhile is kept and
  the decrypted copy goes beside it, as for any differing plain file. A
  `.qenc` gone meanwhile is skipped. Test: `a_save_during_unlocking_for_good_is_kept`.
- Key change: a `.qenc` moved or trashed meanwhile is skipped, and
  `finish_change_key` clears `rotating` only when every `.qenc` opens with
  the new key (up to three passes, then an error asking to run it again).
  Before, a file the pass missed (moved, or saved with the old key) stayed
  under the old key with `rotating` cleared, and a second key change would
  have dropped that key. Test: `a_note_moved_during_a_key_change_is_skipped`
  (fails without the extra pass).
- Interrupted unlock for good after a restart: real (saves fail as
  "locked"). The refusal is kept on purpose: a key file renamed to the
  `unlocking` name by someone else must not make the folder plain (0.11
  security review). What changed is that it is now visible: on open the
  notice says unlocking for good didn't finish, that notes there can't be
  saved until it does, to run "Stop locking a folder…" again, and to rename
  the key file back if the person didn't start it. Running it again
  resumes (it already did; the test proves it after a restart). Test:
  `an_unfinished_unlock_for_good_is_reported_and_can_be_finished`.
- The "Keep both" suggestion after an interrupted lock: real. Plain files
  next to an identical encrypted copy were "kept both" as duplicates.
  `keep_both` now removes such a plain file instead of copying it, and the
  notice says to run "Lock a folder…" again first (which finishes the
  lock). Test: `keep_both_makes_no_copy_of_a_file_identical_to_its_encrypted_one`.
- Not done: unlocking for good trashes each `.qenc` without comparing it
  with what it decrypted (another device writing it in that moment would
  put its newer ciphertext in the trash, not lose it). Left: it needs a
  hash per file kept through the run; the window is a sync race only.

## 5. The watcher lost changes (scan item 9) — real by reading, fixed

- `Remove` is classed by whether the file exists now, like create and
  modify. Test: in `notes_and_attachments_are_told_apart`.
- On a watcher error or an event with notify's `need_rescan()` flag, a
  rescan is asked for. Asks are coalesced (one pending at a time, started
  after 300 ms) and run on their own thread, one at a time. The watcher
  keeps what it last knew of each visible file (modified time, size: from
  a background scan at start, then from each event) and reports the
  differences as ordinary `Changed`/`Removed`/`Attachment*` events, so no
  consumer (and no other team's code) had to change. Test:
  `a_rescan_reports_what_the_lost_events_would_have` (also: events already
  seen are not reported again; twenty asks make one rescan).
- Cost: one extra listing with metadata at each watcher start (app, MCP
  server, assistant runner, CLI sync and serve), off the calling thread,
  and one map entry per file.
- Not run on macOS: the FSEvents merging rests on the notify source the
  scan cited.

## 6. Version history stopping without notice (scan item 10) — real, fixed

- The history thread runs each job under `catch_unwind` (a panic no
  longer ends history for the session) and records failures. The first
  failure is shown once as a notice ("Quire couldn't keep a version of …");
  later ones stay quiet until a version is written again. Test:
  `a_history_failure_is_told_once`.
- Agents: an agent edit and an accepted proposal no longer write when the
  "before" snapshot fails (`?` instead of `let _ =`). Test:
  `no_edit_is_written_without_the_version_from_before` (quire-agent). The
  "after" snapshots are still best effort (the note is written; the ledger
  then has no `snap_after`).
- Future-dated newest snapshot: `same_burst` now needs `0 <= age < 2 min`.
  Test: in `history.rs`, `a_snapshot_from_the_future_is_never_replaced`.

## 7. Small items

- **11, write lock across fsync — real, fixed.** `LocalFs` writes and
  flushes the temporary file first and takes the process-wide lock only
  for the check and the rename. A compare-and-swap that then fails drops
  its temporary file (tested in `a_failed_replace_leaves_no_temporary_file`).
  Not measured on a slow disk.
- **12, case-only renames — real, fixed in storage; proof rests on CI
  (macOS, Windows).** `LocalFs::rename` lets `meeting.md` → `Meeting.md`
  through when the target "exists" only by case folding (same folder,
  names equal ignoring case, and no entry with the exact new name). Tests:
  `a_case_only_rename_works_where_case_is_ignored` (`cfg(windows/macos)`),
  `case_only_renames_are_told_from_name_clashes` (all). Left: rolling
  back link rewrites when a rename fails halfway, and `auto_name` retrying
  every tick (workspace code, not this lane; with the rename working the
  retry no longer loops in this case).
- **13, append lock vs. readers on Windows — real by reading, fixed.**
  `LocalFs::read_bytes` retries briefly on Windows lock and sharing
  errors, and `history_paths_under` returns an error for an unreadable
  log (empty only when there is no log), so phase 3 of a lock and a key
  change stop instead of skipping history. No Windows test of the lock
  itself (timing-dependent).
- **14, storage part (settings written whole by each window) — real,
  documented only.** Each window saves `settings.toml` from memory; a
  change made in one window is undone by another's save. Fixing it means
  merging with the file on disk field by field in the settings module,
  which isn't small and isn't this lane. Settings writes do now get the
  Windows replace fix (via `atomic::write`). The other parts of item 14
  are sync's.

## 8. For the sync team: `LocalFs::walk` — fixed

A subfolder that disappears between being listed and being read (or whose
entry type can't be read because it's gone) is left out; the vault root
that can't be read is still an error. Test:
`listing_skips_a_folder_that_vanishes_but_not_a_missing_root`.
