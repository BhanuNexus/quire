# Quire 0.13.1: security hardening

The security team's part of the hardening pass. No features: fixes, tests, and
notes for the owner on what was left and why. The full list with every
location is kept outside the repository with the pass's other scan results
(`hard-scan/sec-findings.md`, `hard-scan/codeql-findings.md`).

## 1. CodeQL

The CodeQL run on `chore/hardening` (43694645902) finished, but its result
artifacts couldn't be downloaded from the session that did this work (the
artifact storage host was refused by its network proxy, and the
code-scanning API answers 403). The two known open alerts were handled; the
rest of the list needs a look once the artifacts are read in a browser.

### `rust/hard-coded-cryptographic-value` at `quire-sync` `crypto.rs:93` and `keyring.rs:155`

**Not a bug.** The "keys" are HKDF domain labels (`"quire-sync v1"`,
`"quire-sync key box v1"`): the salt of HKDF-Extract, which RFC 5869 §3.1
allows to be public and fixed. The secret is the input key material.

**Restructured** to the library call: the labels are a type (`Domain`) and
`derive32` is `hkdf::Hkdf::<Sha256>::new(Some(label), ikm).expand(info, …)`,
as `quire-vault`'s lock format already does. `hkdf` 0.13 was already in the
tree through `quire-vault`. Output bytes are unchanged: five known answers
(computed with Python's `hmac` module) are pinned, and the recorded 0.12
fixtures pass.

A first attempt wrote HMAC out over `sha2` so the label never reached
`KeyInit::new_from_slice`. CodeQL followed the label through the hashing and
reported four alerts instead of two, so it was dropped: hand-written HMAC is
not worth having to satisfy a scanner.

If CodeQL still reports the library form, dismiss it as a false positive
with the reason above.

## 2. Findings and fixes

### H1. A repository's own git settings ran programs when a vault opened (fixed)

Quire detects git and runs `git status` as soon as a vault opens, and again
every minute. A repository's `.git/config` travels with a copied, unpacked or
folder-synced vault, and some settings make a plain `git status` run a
program: `core.fsmonitor` (a hook command) and clean filters
(`filter.<name>.clean`, with `.gitattributes`). Opening such a folder ran the
program, with no other action. Repository hooks ran on Quire's own
auto-commit, which the vault's shared settings (`.quire/shared/vault.toml`,
which travel too) can turn on.

Fix (`quire_app::git`): before running git, Quire reads the repository's own
settings (`git config --list --show-scope --includes`, local and worktree
scopes only; the user's and system settings are the person's own) and looks
for settings that run a program: `core.fsmonitor` other than a boolean,
`core.sshCommand`, `core.askPass`, `core.alternateRefsCommand`,
`core.gitProxy`, filter commands (Git LFS's standard ones are fine), diff
commands and textconv, merge drivers, credential helpers that aren't a bare
helper name, `gpg.*program` and `gpg.ssh.defaultKeyCommand`,
`remote.*.uploadpack/receivepack/vcs`, `protocol.*.allow = always`, trailer
commands. Where one is set, Quire runs no git there (status bar: "git: off
here", with the reason; Commit, Pull and Push say the same). Where the
repository has hooks (or sets `core.hooksPath`), Quire doesn't commit, pull or
push by itself; when asked it does, and the hooks run as git would run them.
`git show` for a note's history runs with `--no-ext-diff --no-textconv`. The
check runs again before each status, commit, pull and push, so a setting
added later is caught too.

Behaviour change: someone who set up an fsmonitor hook or a custom filter in
a notes repository gets "git: off here"; someone with hooks and auto-commit
gets commits only when they ask. Both are told why. A per-device "trust this
repository" switch would remove that friction; it is left for later (it needs
a setting and UI).

Tests: `a_repository_whose_settings_run_a_program_gets_no_git`,
`repository_hooks_stop_auto_commit`, `settings_that_run_programs_are_recognised`.

### M1. `quire-cli serve` read request bodies before checking sign-in (fixed)

The web app read every POST body (up to 8 MB) before looking at the
session, and the MCP endpoint read up to 4 MB before checking the bearer
token, as did the OAuth token and revoke forms (open by design). With no
limit on concurrent connections, anyone who could reach the server could
make it hold gigabytes with a few hundred slow uploads.

Fix: the web app reads a POST only with a good session (otherwise it answers
"signed out" without reading), and the sign-in form is limited to 16 KB (a
larger `Content-Length` is refused before any of it is read); MCP
checks the token first and reads the body after; the OAuth forms are limited
to 64 KB. Test: `bodies_are_not_read_before_sign_in` (a post that promises
8 MB and sends a few bytes is answered at once).

### M2. Deeply nested front matter exhausted the stack (fixed)

Quire's own front-matter reader recursed once per nesting level, both for
flow maps on one line (`k: {a: {a: {a: …}}}`) and for indented block maps. A
note of a few hundred kilobytes, arriving by sync, a shared folder or an
import, crashed whatever read its properties (indexing, the editor, the web
app, MCP), each time it was read. Flow maps also took quadratic time.

Fix: maps nested more than 64 levels deep are kept as text (block maps keep
their lines, flow maps their source). Ordinary properties read as before.
Test: `deeply_nested_properties_are_read_without_exhausting_the_stack` (on a
256 KB stack).

### L1. Secrets in `Debug` output (fixed)

`AnthropicModel` and `OpenAiCompatible` (API keys), `HttpTransport` (the
sync token), `quire_sync::admin::Removal` (a passphrase) and the sync
server's `Enrolled` (a device token) derived `Debug`. Nothing printed them
today, but any `{:?}` in a log or panic message would have. Each now has a
`Debug` that leaves the secret out.

### Workflows

zizmor 1.31.1 (`--persona=auditor`, offline: the online audits need a token
this session doesn't have) and actionlint 1.7.12, on `.github/workflows`.

Fixed:
* CodeQL: permissions moved from the workflow to the job, each explained
  (excessive-permissions); superseded pull-request runs are cancelled
  (concurrency-limits).
* Release: the engine's `--features` reach `cargo` through an environment
  variable, not a template expanded into the script (template-injection; the
  matrix is static, so this is hardening). Every write permission says why.

Left, for the owner:
* `secrets-outside-env` (8): the macOS and Windows signing secrets are
  repository secrets used outside an environment. Moving them into a
  `signing` environment restricted to `v*` tags (and adding
  `environment: signing` to those two jobs) means a workflow run on another
  ref can't read them. It needs repository settings, and branch dry runs
  would then build unsigned, so it isn't done here.
* The engine, Linux, macOS and Windows jobs build (running dependency build
  scripts) in the same job that holds `id-token: write` for attestations.
  A malicious build script could request an OIDC token and attest other
  files. The Flatpak jobs already split building and attesting; doing the
  same for the others (upload, then attest in a job without the build) is the
  stronger shape. Not done: the release workflow can't be run from here.
* `anonymous-definition` (21, informational): giving jobs a `name:` changes
  the check names that branch protection may require.

Token permissions: every workflow sets `permissions: {}` or `contents: read`
at the top; jobs add only what they use (CodeQL: `security-events: write`;
attesting jobs: `id-token` and `attestations: write`; publish: `contents:
write`; tag: `contents: write` and `actions: write`). No job persists
checkout credentials. No `pull_request_target` or `workflow_run` triggers.

## 3. Checked and fine

* Web sign-in: Argon2id, sessions hashed in memory, strict cookies,
  `__Host-` with https, CSRF token plus Origin on every POST, the limiter
  counts a try before checking it, `safe_next` refuses `//`, `\` and
  control characters; CSP, frame, nosniff and referrer headers on every
  response; vault files sandboxed. The global limiter forgets wrong tries 30
  minutes after the last one, so a guesser gets about 10 tries per 45
  minutes (with the 10-character minimum, acceptable).
* MCP over HTTP: Host and Origin guard, PKCE S256 only, codes bound to
  client, redirect URI and resource, the browser-binding fix, tokens stored
  hashed. Consent request ids are checked before they become file names.
* Sync server: the token check runs before any body is read (route-layer
  middleware), server token compared as SHA-256 in constant time, device
  tokens looked up by hash, every SQL statement parameterised, ids
  validated, page and wait limits, 32 MB body limit.
* Paths: `canonical_path` refuses absolute, `..`, `\`, `:` and hidden
  segments; `resolve_at` canonicalises (which also maps Windows trailing
  dots and spaces, 8.3 names and device names, the last ending outside the
  vault) and re-checks the real path; zones and web-hidden folders compare
  case-insensitively and in NFC.
* Secrets on disk: `atomic::write(.., private: true)` creates the temporary
  file 0600 from the start; recovery keys use `write_new_private`; login,
  tokens, consent and the keyring fallback file are private.
* Subprocesses: git with prompts off and a time limit, arguments passed as a
  list; ACP agents and the AI engine are started from settings, never from
  the vault; on Windows `Command` doesn't search the working directory.
* Parsers: PDF text runs under `catch_unwind`; YAML validation
  (`yaml-rust2`) caps flow nesting at 255; JSON uses serde_json's recursion
  limit; importers have their own hostile-input limits (0.12).
