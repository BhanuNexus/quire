# Quire 0.13.1: security hardening

The security team's part of the hardening pass. No features: fixes, tests, and
notes for the owner on what was left and why. The full list with every
location is kept outside the repository with the pass's other scan results
(`hard-scan/sec-findings.md`, `hard-scan/codeql-findings.md`).

## 1. CodeQL

The CodeQL run on `chore/hardening` (43694645902) finished, but its result
artifacts couldn't be downloaded from the session that did this work (the
artifact storage host was refused by its network proxy, and the
code-scanning API answers 403). The two known open alerts were handled; the
rest of the list needs a look once the artifacts are read in a browser.

### `rust/hard-coded-cryptographic-value` at `quire-sync` `crypto.rs:93` and `keyring.rs:155`

**Not a bug.** The "keys" are HKDF domain labels (`"quire-sync v1"`,
`"quire-sync key box v1"`): the salt of HKDF-Extract, which RFC 5869 §3.1
allows to be public and fixed. The secret is the input key material.

**Restructured** to the library call: the labels are a type (`Domain`) and
`derive32` is `hkdf::Hkdf::<Sha256>::new(Some(label), ikm).expand(info, …)`,
as `quire-vault`'s lock format already does. `hkdf` 0.13 was already in the
tree through `quire-vault`. Output bytes are unchanged: five known answers
(computed with Python's `hmac` module) are pinned, and the recorded 0.12
fixtures pass.

A first attempt wrote HMAC out over `sha2` so the label never reached
`KeyInit::new_from_slice`. CodeQL followed the label through the hashing and
reported four alerts instead of two, so it was dropped: hand-written HMAC is
not worth having to satisfy a scanner.

If CodeQL still reports the library form, dismiss it as a false positive
with the reason above.

## 2. Findings and fixes

### H1. A repository's own git settings ran programs when a vault opened (fixed)

Quire detects git and runs `git status` as soon as a vault opens, and again
every minute. A repository's `.git/config` and hooks travel with a copied,
unpacked or folder-synced vault, and many of them make git run a program:
`core.fsmonitor` and clean filters on a plain `git status`, hooks on status
(`post-index-change`) and on commit, an `ext::` remote on pull. The vault's
shared settings (`.quire/shared/vault.toml`, which travel too) can turn on
auto-commit, pull on start and push after commit. Opening such a folder ran
the program, with no other action.

#### First fix, replaced: a deny-list

The first fix (d36e2cc) read the repository's own settings and refused git
where a listed setting ran a program, and stopped auto-commit, pull on start
and push after commit where the repository had hooks. The independent review
showed it was both bypassable and too strict:

* Bypassed (reproduced): `post-index-change` runs on Quire's own `git
  status` (S-H1); a submodule's own `core.fsmonitor` runs on the
  superproject's status (S-H2); `protocol.ext.allow = user` (or
  `protocol.allow = user`) with an `ext::` remote runs a command on pull,
  including pull on start (S-H3); Git LFS `lfs.extension.*` commands run on
  status through the exempt LFS filter (S-M1); a linked worktree's hooks are
  in the common git folder, which the guard didn't look in (S-M2). Log and
  Show didn't check the guard at all (S-L2).
* Too strict (D-M2): a local `core.sshCommand` (multi-account ssh),
  git-crypt, nbstripout, `gpg.program`, a merge driver or a credential helper
  with arguments switched git off entirely; any hook (Git LFS, husky,
  pre-commit, lefthook) silently stopped auto-commit; and the state lasted
  until Quire restarted.

git has far more ways to run a program than any list can name (and new
versions add more), so the list was dropped.

#### The fix: per-repository trust

Quire runs **no git at all** in a repository until you have trusted that
repository on this computer (`quire_app::git_trust`).

* **Finding the repository runs no git.** `find_repo` walks up from the
  vault with git's own rules: a `.git` folder, or a `.git` file read as
  git's `read_gitfile` does (the whole file is `gitdir: <path>`, only
  trailing CR and LF removed), and that git folder's `commondir` (read as
  bytes; trailing CR and LF removed). A git folder needs a `HEAD` that git's
  `validate_headref` accepts (a symlink into `refs/`, even to a branch not
  born yet; `ref: refs/…`; or an object id), and `objects` and `refs` in its
  common folder. Running `git rev-parse` instead was rejected: any git
  started inside the repository reads its config, and the review found
  config that runs a program on far less than a status.
* **It fails closed.** A `.git` of any kind (`symlink_metadata`, so a
  dangling symlink counts) that isn't a git folder `find_repo` fully
  accepts ends the search with nothing found, where git would skip a broken
  `.git` folder and look further up. A folder on the way with a `HEAD` entry
  of any kind next to `objects` or `refs` (a bare repository to git, which
  files placed in a vault can make) ends it too. A `commondir` that can't be
  read cleanly (other than missing) does too. The trust re-review showed why:
  a `.git` whose `HEAD` is a dangling symlink was skipped by the first
  version but used by git, so git ran a placed repository's config under a
  trusted one (finding 1); a `.git` file with extra spaces or a `.git`
  folder without `refs` made the two disagree in the other direction
  (findings 4, 5); a non-UTF-8 `commondir` was read as missing (7).
* **git does no search of its own.** Every git gets
  `--git-dir=<the checked git folder> --work-tree=<the checked top folder>`,
  so it can only use what was found and trusted (a linked worktree's git
  folder names its common folder in `commondir`, which was checked too). It
  still runs in the vault's folder, so `-- .` pathspecs and
  `status.relativePaths=false` work as before; checked for an ordinary
  repository, a vault in a subfolder, a linked worktree and a submodule
  checkout. `-c safe.bareRepository=explicit` stays: an explicit git folder
  is allowed by it, so it costs nothing. git's environment loses `GIT_DIR`,
  `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_INDEX_FILE`,
  `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`,
  `GIT_CEILING_DIRECTORIES`, `GIT_DISCOVERY_ACROSS_FILESYSTEM` and
  `GIT_NAMESPACE` (they come from the user's environment, not the vault;
  `GIT_CONFIG_PARAMETERS` and `GIT_CONFIG_COUNT` are the user's own settings
  and stay).
* **Repositories inside the vault are left alone** (finding 2). git adds an
  untracked folder holding a repository as a submodule, and from then on
  its status ran that repository's config. Status runs with
  `--ignore-submodules=all`; commit leaves out untracked folders that are
  repositories (with `--untracked-files=all` git lists only those as
  folders) and every gitlink already in the index (`git add -A` looks into a
  changed submodule even with `diff.ignoreSubmodules=all`, by experiment), and
  says once per folder that it isn't committed and why; pull and push get
  `--no-recurse-submodules`. Checked by experiment with an fsmonitor marker
  in a nested repository and in a committed submodule: status, add, commit,
  log, show, pull and push as Quire runs them start nothing there. A
  submodule's new commits are then never staged by Quire; your own git
  still can.
* **One function runs git.** `git::run_git(trust, repo, dir, args)` is the
  only caller of the process spawn. At the moment of running it checks again
  that `dir` is still in `repo` and that `repo` is trusted in the store
  *now* (so trust taken back stops anything already queued). Otherwise it
  returns "Git is off for this repository…" without starting a process.
  Status, commit, pull, push, log, show and the version check all go through
  it.
* **What remains of the check-then-run window** (finding 8). With an
  explicit git folder and working tree, a folder swapped on the way up
  between the check and the spawn can no longer make git pick another
  repository. What remains: something that can write the checked git folder
  or the folders above it can still change what is at those paths in that
  moment (replace the trusted `.git` itself, or a parent with a symlink).
  Whoever can do that can already write the trusted repository's config,
  which trust accepts.
* **Trust is kept on this computer, never in the vault**:
  `git-trust.toml` in Quire's settings folder (the same folder as
  `settings.toml`), a list of `{root, git_dir, common_dir, id}`, the paths
  canonical. Trusting writes a new random 128-bit id to `quire-trust` in the
  repository's git folder (the worktree's own, for a linked worktree) and
  keeps it in the list; `is_trusted` needs the paths to match and that file
  to hold the same id. So a different repository that later appears at a
  trusted path (another USB stick with the same name, an archive unpacked
  where a trusted one was deleted) is untrusted (finding 3): it has no id,
  or another one, and the id isn't in the vault for anyone to copy (a copy
  of the whole `.git` brings it, but at another path the paths don't
  match). Portable and needs no file ids or unsafe code; the cost is one
  small file in the git folder, which git ignores, and trusting needs write
  access to the git folder. A repository that was copied, unpacked or
  synced to another path or computer is untrusted there; another worktree
  of a trusted repository is untrusted until trusted itself; a vault reached
  through a symlink or opened from a folder inside the repository is the
  same repository. An unreadable file trusts nothing and isn't overwritten.
  Stop trusting removes the entry and the `quire-trust` file.
* **Untrusted:** the status bar says `git: off (not trusted)`; clicking it
  (or *Trust this git repository…* in the palette, or the button in the Git
  tab) opens a confirmation: a repository's settings and hooks can run
  programs on this computer whenever git runs, they travel with the folder,
  trust only repositories whose origin you know. When the git folder or the
  common folder is outside the vault's top folder (a `.git` file pointing
  elsewhere), it shows them and says plainly that this folder uses the git
  repository there (finding 6: a one-line `.git` file could otherwise point
  Quire's commits at another repository of yours). When the vault's own
  settings turn on auto-commit, pull on start or push after commit, the
  confirmation says so, and that Quire will then do them without asking.
  Trusting takes effect at once, without reopening the vault; pull on start
  waits until the vault is next opened, so trusting doesn't itself start a
  network operation.
* **Revoking:** *Stop trusting this repository* in the Git tab. git stops at
  once (including anything queued), no restart.
* **Trusted:** git runs as your own git would: hooks, filters, LFS,
  git-crypt, `core.sshCommand`, signing, credential helpers. Auto-commit,
  pull on start and push after commit work with hooks again (D-M2). `git
  show` for a note's history keeps `--no-ext-diff --no-textconv` (the diff is
  shown as stored), and arguments are passed as a list with paths after
  `--`.
* **The CLI and everything outside the desktop app run no git.** The only
  process spawn of `git` in the workspace is `spawn_git` in
  `crates/quire-app/src/git.rs`; `rg 'Command::new\("git"|Proc::new\("git"'
  crates apps` finds only it and the tests. It is reached only through
  `Workspace` (`nav::tick`/`start`), and outside tests only
  `apps/quire-desktop/src/app.rs` makes a `Workspace`; `quire-cli` (serve,
  MCP, publish, agent, sync) uses `secure_state::open_vault` and never ticks
  a workspace. So there is no CLI trust command; if the CLI ever runs git, it
  must go through `run_git` and get one.

Found in passing and fixed: for a vault in a folder inside the repository,
`git status` gave untracked files relative to that folder, so new notes
weren't seen as changes; status now runs with `status.relativePaths=false`
(tested by `trust_is_per_repository_path_and_can_be_taken_back`).

Upgrading from 0.13.0: git is off once in each repository until you trust
it; auto-commit, pull on start and push after commit don't run until then.

What trust doesn't cover: once you trust a repository, later changes to its
settings, hooks or the vault's `[git]` settings (for example arriving by a
folder sync) are trusted with it, exactly as with your own git in a
terminal.

Tests (`quire-app`): `an_untrusted_repository_runs_no_git` builds the
review's five reproductions (S-H1 `post-index-change`, S-H2 a submodule's
`core.fsmonitor`, S-H3 an `ext::` remote with `protocol.ext.allow = user`, S-M1
an `lfs.extension` clean command (skipped, with a message, when git-lfs isn't
installed), S-M2 a linked worktree of a trusted repository with a

auto-commit delay and asks to commit, pull, push and show history: no marker
file appears, and no git process was started under the test folder (every

`trust_is_per_repository_path_and_can_be_taken_back` (a symlinked path is

### M1. `quire-cli serve` read request bodies before checking sign-in (fixed)

The web app read every POST body (up to 8 MB) before looking at the
session, and the MCP endpoint read up to 4 MB before checking the bearer
token, as did the OAuth token and revoke forms (open by design). With no
limit on concurrent connections, anyone who could reach the server could
make it hold gigabytes with a few hundred slow uploads.

Fix: the web app reads a POST only with a good session (otherwise it answers
"signed out" without reading), and the sign-in form is limited to 16 KB (a
larger `Content-Length` is refused before any of it is read); MCP
checks the token first and reads the body after; the OAuth forms are limited
to 64 KB. Test: `bodies_are_not_read_before_sign_in` (a post that promises
8 MB and sends a few bytes is answered at once).

### M2. Deeply nested front matter exhausted the stack (fixed)

Quire's own front-matter reader recursed once per nesting level, both for
flow maps on one line (`k: {a: {a: {a: …}}}`) and for indented block maps. A
note of a few hundred kilobytes, arriving by sync, a shared folder or an
import, crashed whatever read its properties (indexing, the editor, the web
app, MCP), each time it was read. Flow maps also took quadratic time.

Fix: maps nested more than 64 levels deep are kept as text (block maps keep
their lines, flow maps their source). Ordinary properties read as before.
Test: `deeply_nested_properties_are_read_without_exhausting_the_stack` (on a
256 KB stack).

### L1. Secrets in `Debug` output (fixed)

`AnthropicModel` and `OpenAiCompatible` (API keys), `HttpTransport` (the
sync token), `quire_sync::admin::Removal` (a passphrase) and the sync
server's `Enrolled` (a device token) derived `Debug`. Nothing printed them
today, but any `{:?}` in a log or panic message would have. Each now has a
`Debug` that leaves the secret out.

### Workflows

zizmor 1.31.1 (`--persona=auditor`, offline: the online audits need a token
this session doesn't have) and actionlint 1.7.12, on `.github/workflows`.

Fixed:
* CodeQL: permissions moved from the workflow to the job, each explained
  (excessive-permissions); superseded pull-request runs are cancelled
  (concurrency-limits).
* Release: the engine's `--features` reach `cargo` through an environment
  variable, not a template expanded into the script (template-injection; the
  matrix is static, so this is hardening). Every write permission says why.

Left, for the owner:
* `secrets-outside-env` (8): the macOS and Windows signing secrets are
  repository secrets used outside an environment. Moving them into a
  `signing` environment restricted to `v*` tags (and adding
  `environment: signing` to those two jobs) means a workflow run on another
  ref can't read them. It needs repository settings, and branch dry runs
  would then build unsigned, so it isn't done here.
* The engine, Linux, macOS and Windows jobs build (running dependency build
  scripts) in the same job that holds `id-token: write` for attestations.
  A malicious build script could request an OIDC token and attest other
  files. The Flatpak jobs already split building and attesting; doing the
  same for the others (upload, then attest in a job without the build) is the
  stronger shape. Not done: the release workflow can't be run from here.
* `anonymous-definition` (21, informational): giving jobs a `name:` changes
  the check names that branch protection may require.

Token permissions: every workflow sets `permissions: {}` or `contents: read`
at the top; jobs add only what they use (CodeQL: `security-events: write`;
attesting jobs: `id-token` and `attestations: write`; publish: `contents:
write`; tag: `contents: write` and `actions: write`). No job persists
checkout credentials. No `pull_request_target` or `workflow_run` triggers.

## 3. Checked and fine

* Web sign-in: Argon2id, sessions hashed in memory, strict cookies,
  `__Host-` with https, CSRF token plus Origin on every POST, the limiter
  counts a try before checking it, `safe_next` refuses `//`, `\` and
  control characters; CSP, frame, nosniff and referrer headers on every
  response; vault files sandboxed. The global limiter forgets wrong tries 30
  minutes after the last one, so a guesser gets about 10 tries per 45
  minutes (with the 10-character minimum, acceptable).
* MCP over HTTP: Host and Origin guard, PKCE S256 only, codes bound to
  client, redirect URI and resource, the browser-binding fix, tokens stored
  hashed. Consent request ids are checked before they become file names.
* Sync server: the token check runs before any body is read (route-layer
  middleware), server token compared as SHA-256 in constant time, device
  tokens looked up by hash, every SQL statement parameterised, ids
  validated, page and wait limits, 32 MB body limit.
* Paths: `canonical_path` refuses absolute, `..`, `\`, `:` and hidden
  segments; `resolve_at` canonicalises (which also maps Windows trailing
  dots and spaces, 8.3 names and device names, the last ending outside the
  vault) and re-checks the real path; zones and web-hidden folders compare
  case-insensitively and in NFC.
* Secrets on disk: `atomic::write(.., private: true)` creates the temporary
  file 0600 from the start; recovery keys use `write_new_private`; login,
  tokens, consent and the keyring fallback file are private.
* Subprocesses: git only in a trusted repository (H1), with prompts off and
  a time limit, arguments passed as a list; ACP agents and the AI engine are started from settings, never from
  the vault; on Windows `Command` doesn't search the working directory.
* Parsers: PDF text runs under `catch_unwind`; YAML validation
  (`yaml-rust2`) caps flow nesting at 255; JSON uses serde_json's recursion
  limit; importers have their own hostile-input limits (0.12).
