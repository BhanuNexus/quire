# Quire 0.14: sync on large vaults

Status: current
Area: sync
Code: `crates/quire-sync/src/{engine,transport,http,folder,protocol}.rs`, `crates/quire-sync/src/remote/mod.rs`, `crates/quire-app/src/vault_sync/{store,state,session,setup,workspace}.rs` (new `vault_sync/journal.rs`), `apps/quire-sync-server/src/{lib,store}.rs`, `apps/quire-cli/src/commands/sync.rs`, `packaging/perf-check.py`

Two items of the 0.14 performance scan (main 6cbfbcd, v0.13.1; the scan is not kept in
the repository): every pass reads the whole vault twice and rewrites all note text, and a
first sync sends one request per note. This note fixes both on every transport (folder,
Quire Sync server, S3, WebDAV) inside the architect's frame
([0.14-architecture.md](0.14-architecture.md)). The wire formats, the sealing, the head
rule and the three-way merge do not change. Approved by the owner on 2026-11-19, with the
architect's review ([0.14-review-sync-speed.md](0.14-review-sync-speed.md)) folded in:
its blocking issues B1–B5 are answered in §3.3, §3.1, §3.4, §3.4 and §3.7.

## 1. The problem, as measured

From the scan (items 2 and 8), `--profile perf` Lite builds on the 2-core VM, vaults from
`quire-cli bench vault` (10,000 notes, 78 MB; 50,000 notes, 391 MB), warm page cache:

| Measure | 10k notes | 50k notes |
|---|---:|---:|
| `quire-cli sync once` with nothing to sync: read | 127 MB | 634 MB |
| same: written | 44 MB | 220 MB |
| same: wall time | 0.5 s | 3.5 s |
| same: peak memory | 179 MB | 697 MB |
| `state.json` size | 44 MB | 220 MB |
| First sync to a local `quire-sync-server` | 20 s (client 4.4 s CPU, server ~9 s CPU) | 99 s |
| The pass right after that first sync (receives nothing) | not measured | 18.6 s |

Causes, confirmed by reading today's code (the scan's line numbers predate the split of
`vault_sync.rs` into `vault_sync/`):

* `snapshot_reads` (`vault_sync/store.rs`) reads every note into `VaultStore::seen`, as
  the expected value for the compare-and-swap write.
* `Engine::push` (`engine.rs`) calls `LocalStore::digest` for every tracked note. For a
  note, `digest` is `fingerprint`, which is the full text; only attachments have a
  (size, mtime) cache (`VaultStore::digests`). It also clones every `Tracked`, whose
  `base` is the full text.
* `Session::pass` (`session.rs`) calls `save_state` after every pass, and
  `save_state_named` (`state.rs`) serialises every `Tracked::base` into one JSON file,
  changed or not. `sync once` also loads that file first (the 44 MB in the "read" column).
* `Engine::push_one` sends one revision per `Transport::push`. On the server each push is
  its own `IMMEDIATE` transaction under `synchronous = FULL` (`Store::push`,
  `apps/quire-sync-server/src/store.rs`). In a sync folder each revision costs a
  `note_own` (atomic write with fsync of `folder-own.json`), an append with `sync_data`,
  and a `folder-seq` rewrite (`FolderTransport::append`, `next_seq`). S3 and WebDAV go
  through the same folder code for their mirror, then upload 8 objects at a time
  (`PARALLEL` in `remote/mod.rs`).
* The 18.6 s pass: `Engine::pull` is the only place that moves `SyncState::cursor`. A
  device's own accepted pushes are past the cursor, so the next pull downloads all 50k of
  them again and skips each (`t.head == r.rev`). The scan did not investigate this; the
  cause is from reading `engine.rs`.

When it runs: after every save (800 ms debounce in `worker.rs`) and at least every
2 minutes (`APP_POLL`), in the app, `sync watch` and `serve --sync`.

## 2. Goals and non-goals

Goals, with the architect's budgets (§5 of the frame), which this note adopts:

| Measure | Budget 10k | Budget 50k | How CI checks it |
|---|---:|---:|---|
| Idle `sync once` against a local server: wall | 150 ms | 600 ms | perf job, median |
| same: bytes read | 8 MB | 40 MB | `/proc/self/io` in the perf job |
| same: bytes written | ≤ 4 KB | ≤ 4 KB | same |
| same: peak memory | 60 MB | 200 MB | same |
| Idle pass in a running worker, any transport: note files opened | 0 | 0 | count, exact (test store) |
| Pass after one note changed: note files opened | ≤ 2 for that note, 0 for the others | same | count, exact, the manifest's opens included |
| Pass that receives one note: note files opened | ≤ 3 for that note, 0 for the others; 1 more in the next pass | same | count, exact, the manifest's opens included |
| same: sync state bytes written (journal + base pack) | ≤ 64 KB + the note | same | count |
| First sync to a local server | 6 s | 30 s | perf job |
| Pass right after first sync | 150 ms | 600 ms | perf job |

Why 2 and 3 (corrected after the review of the build; the frame first said 1): a changed
note is hashed by the manifest's scan and then read by sync for its text. A received note
is read by the engine's check for changes here, by its check for an unsynced file in the
way, and by the write's compare-and-swap; the next pass hashes the written file once more,
because the manifest's own-write rows are racy. The counts include the manifest's opens.

Added by this note (counts are exact and runner-independent):

| Measure | Budget | Check |
|---|---|---|
| Server requests for a first sync of N notes | ≤ ⌈N / 1000⌉ + ⌈request bytes / 4 MiB⌉ + 10 | test server counter |
| Folder first sync: `sync_data` calls | ≤ 2 per log segment written + 10 | counting hook in `folder.rs` tests |
| S3/WebDAV first sync of N notes: `PUT`s | ≤ N + 10 (unchanged layout: one object per revision) | mock server counter |
| Base packs on disk, steady state | ≤ 2 × live base bytes + 16 MB | unit test |
| Migration of a 0.13 `state.json` at 50k | once; ≤ 10 s *(guess)* | perf job, report only |
| Joining a 50k-note vault from a local server: wall, peak memory, fsyncs | measured, no budget yet | perf job, report only (owner: measure now, fix in 0.15) |

Non-goals:

* **Making a join of a large vault fast.** A device joining 50k notes writes each note with
  its own fsync (`LocalFs`, the storage team's lane) and `HttpTransport::pull` holds every
  pulled revision in memory. 0.14 measures it (the report-only row above); the fix is 0.15
  (§9).
* **Fast `sync once` on folder, S3 and WebDAV.** A new process reads the whole sync folder
  or mirror once to build the transport's index (`FolderTransport::scan`); a running worker
  then reads only new bytes. The frame's idle `sync once` rows are for the Quire Sync server
  (frame §5 says so). The "note files opened" and "state bytes written" counts hold on every
  transport. Persisting the transport index is not in 0.14 (§9).
* No change to revisions, `Content`, sealing, folder/S3/WebDAV layouts, or `PROTOCOL` (3).

## 3. The design

### 3.1 An idle pass reads nothing: the manifest plus a per-note stamp

The architect's vault manifest (`quire_vault::changes::Manifest`, frame §2) is the change
feed. It holds, per file, `size`, `mtime_ns` and `hash` (SHA-256 of the bytes on disk).
`Manifest::scan` does one listing and one `stat` per file, and hashes only files whose
size or mtime changed (and racy rows, within 2 s of the scan).

Sync does not persist anything the manifest owns. It adds one field per tracked note:

```
Tracked.disk: Option<Stamp>   // Stamp = the manifest hash of the bytes last known equal to `base`
```

The manifest hash is of raw bytes; the engine's `base` is of decoded text (BOM stripped,
lossy UTF-8; attachments as a fingerprint of base64). They are different functions, so
the stamp is stored next to the base, as frame §2 asks ("a consumer that needs one stores
it next to the manifest hash").

`LocalStore` gains three methods with defaults that keep today's behaviour (so
`MemoryStore` and every existing test run unchanged):

```rust
fn stamp(&self, path: &str) -> Option<Stamp> { None }               // this pass's row
fn read_stamped(&self, path: &str) -> Option<(String, Option<Stamp>)> // text + hash of exactly those bytes
fn print(&self, path: &str) -> Option<Print>                       // replaces `digest`
```

In `Engine::push`, for each tracked note held here:

1. `t.disk.is_some() && local.stamp(&t.path) == t.disk && t.path == t.synced_path`:
   unchanged, nothing read.
2. Otherwise read it (`read_stamped`), compute its print and compare with `t.base`. Equal:
   set `t.disk` to the stamp of the bytes read (learned clean; a small state change).
   Different: push it, as today.

The engine sets `t.disk` only when it knows the file's text equals the new base: after
writing exactly the incoming text (the stamp of the bytes written), or after a push of
text read with a stamp. After a merge or a conflict copy it leaves `disk` empty, and the
next pass reads the note once. A wrong guess costs one read, never a missed change.

**`VaultStore` per pass.** `snapshot_reads` becomes `begin_pass`: run `Manifest::scan`,
and keep `listed: HashMap<path, Option<Stamp>>` and `folded` (case-blind names) from its
rows. No note is read. The compare-and-swap write (`as_read`, `unchanged_since_read`)
compares the hash of the bytes on disk now with the hash of the bytes the engine **first
read** at that path in this pass, or with the scan's row if it never read it. That keeps
0.13's rule (a save between the engine's look and its write is never overwritten) without
holding text. If a read finds bytes whose hash differs from the row, `VaultStore` tells the
manifest (`observed` with those bytes), so a stale row is corrected at once.
`VaultStore::write` and `remove` also call `note_written` / `note_removed`.

**A failed compare-and-swap corrects the row (review B2).** When `write_bytes_if` or
`trash_if` refuses because the bytes on disk differ from what was expected, `VaultStore`
reads those bytes and passes them to `observed` (which also tells the manifest's
subscribers) before returning the error (or drops the row with `note_removed` if the file
is not found). Without this, a note edited without
changing its size and mtime would fail the same write on every pass, and since a failed
apply leaves the cursor where it is, nothing after that revision would arrive until the
daily verify. With it, the next pass sees a new stamp, reads the note and merges. Test:
`an_edit_that_kept_its_time_and_size_merges_on_the_second_pass`, with an incoming revision
for that note.

In the app, `VaultStore` uses the workspace's shared `Manifest` (one scanner per vault, as
the frame wants); the CLI opens its own. Either way **every pass runs its own `scan`**:
that listing is the anchor of the 0.13.2 rules (§3.6). A cached manifest never stands in
for a listing. The scan's `Delta` goes to every subscriber (frame §2), so the index does
not rescan for what a sync pass just found; the index's use of cached rows never weakens
sync's own scan. Our writes reach the manifest through `note_written`, which never waits
for a scan in progress (it queues, P9), so a save in the editor is never held up by sync.

**The verify pass (owner: yes).** Size and mtime can stay the same while bytes change (a
tool that restores times, a coarse clock). Once per 24 hours, in a pass whose scan found
nothing to do, `VaultStore` asks the manifest to rehash every file (`Manifest::verify_where`,
frame §2: `scan` with stat trust off). That reads the vault once a day (about 390 MB at
50k notes). It is skipped on battery where the platform says so cheaply, and tried at the
next idle pass. `quire-cli sync once --verify` does it on request. `verified_at` is kept in
the sync state. The frame's budgets exclude it. As built in the app, the session the workspace starts scans
with the workspace's manifest (one per vault, shared with the index); its verify then leaves
the Markdown notes to the workspace's own daily verify (`quire-app` `manifest_verify`) and
rehashes only the other files it tracks. `sync once` and `serve` keep their own manifest
and verify every tracked file, with the 48-hour rule.

**Settings lane.** `.quire/shared/` is hidden, so the manifest does not cover it.
`VaultStore` keeps an in-process (size, mtime) → hash cache for those files, like
today's attachment `digests`. They are few and small; a fresh `sync once` reads them once.

### 3.2 Bases out of the state file

`Tracked.base`, `KeptCopy.base` and `LeftCopy.base` become a `Print` (32 bytes:
SHA-256 of `fingerprint(path, text)`). Everywhere except a merge the engine only compares
bases, so a print is enough: `same_as_base`, rename detection in `push` (today
`local.digest(p) == t.base`), `is_version_of`, `LocalStore::moved_out` (now takes a
`&Print`).

The text is needed for `merge3` in `apply`, `merge_left`, and a kept copy rejoining. The
engine gets it from a new trait:

```rust
pub trait Bases {
    fn get(&self, p: &Print) -> Option<String>;
    fn put(&mut self, p: Print, text: &str) -> Result<(), String>;
}
```

`quire-sync` ships `MemoryBases` for tests. Only notes are put (attachments, settings
files and `.qenc` files are never merged; their print is all the engine keeps, as today's
`sha256:` fingerprint). If `get` returns nothing (a damaged pack), the engine treats the
fork as `Fork::Unknown`: both versions are kept, the other device's beside this one as a
conflict copy. No text is lost; it is just not merged.

**Where the bases live.** Content-addressed records in append-only pack files beside the
state (`quire-app`'s `PackBases`, new `vault_sync/journal.rs`):

```
.quire/sync/state.d/               (state-partial.d, state-shared.d: one per 0.13 state file)
  checkpoint-000007.json           whole state, without base text
  journal-000007.jsonl             deltas since that checkpoint
  bases-000003.pack                records, ≤ 16 MiB per pack
  bases-000004.pack                the pack being appended to
```

A pack record is `u32 length | 32-byte print | u8 codec | bytes`, codec 0 (raw) or 1
(deflate level 1, `flate2`, already a `quire-app` dependency). Where each print lives
(`pack, offset, length`) is part of the state, so no pack is read until a merge needs it.
Text compresses well; the ratio is a guess until measured on the bench vault.

**Why not one file per base:** at 50k notes that is 50k files and, to be durable before
the state names them, 50k fsyncs on a first sync. **Why not fetch the base from the
transport** (the revision `t.head` is in the folder log or the S3/WebDAV mirror):
compaction (0.13 §1) can drop exactly that revision, and the 0.13 design relies on the
device's own copy of the last synced text then. A server would also cost a request per
merge.

**Pruning.** At each commit the live set is every print referenced by `files`, `kept` and
`left`. A pack whose live bytes fall under half, and that isn't the one being appended to,
is compacted: its live records are copied to the active pack, the commit names their new
places, then the old pack is deleted. Disk stays under 2 × live + 16 MiB.

**Locked folders (0.11 promise).** `scrub_locked_text` clears prints, but the purge is
**not** decided by what it returns: in the ordinary flow the pass sends the plain note's
delete first, which already replaces its base by the empty print, so the scrub finds
nothing to clear. **The purge is derived from the committed record.** At each commit,
every print that the record last committed names at a path in a locked folder (in
`files`, `kept` or `left`) and that the new state no longer names is **purged in that
commit**: every pack with any bytes the record doesn't name, the active one included, is
compacted at once, whatever its ratio, so no version of that text stays in a pack. This
holds whichever came first, the delete or the scrub, and after a crash between them (the
committed record still names the print at the next commit). The commit that purges is
written as a checkpoint, not a journal line, so the older journal lines that held the
note's print and stamp go with it; a pack the record no longer names that couldn't be
deleted is tried again at the next commit, not only at the next open. A print shared with
a plain note elsewhere stays (that text is still in the vault in plain). A purge is the
only compaction that may run in a pass that otherwise changed nothing, and so the only
reason such a pass writes. Test: `locking_most_of_a_vault_syncs_and_leaves_no_plain_text`
locks the folder, runs a real pass (delete first) and then finds the plain text in no
pack's raw bytes.

### 3.3 The state: checkpoint plus journal, written only when it changed

The state without bases is about 350 bytes a note in JSON *(guess: path, ids, three
hex hashes, chain)*: 3.5 MB at 10k, 17.5 MB at 50k. Rewriting that on every change would
break the 64 KB budget, so the state is a checkpoint plus a journal.

* **Commit** (end of `Session::pass`, after the engine, the S3/WebDAV `flush` and the
  scrub): diff the engine's state against the last committed copy. Empty diff: **write
  nothing** (the idle budget). Otherwise:
  1. flush and `sync_data` the active pack (if anything was appended);
  2. append one journal line `{"h": <SHA-256 of d>, "d": <delta>}` and `sync_data`. The
     delta holds changed `files` entries (or `null` for removed), and `cursor`, `left`,
     `skipped`, `deletes_sent`, `verified_at` and the pack table whole when they changed.
* **Checkpoint**: when the journal passes max(256 KiB, a quarter of the checkpoint), write
  `checkpoint-<g+1>.json` with `quire_base::fs::write_atomic` (`Options::STATE`: fsync,
  rename), then delete the old checkpoint and journal.
* **Open**: the highest-numbered checkpoint that parses; then its journal lines in order
  while each line's hash matches. We hold `SyncLock`, so nothing else writes here. The
  tidy-up (truncate a torn journal tail, truncate packs to the lengths the state names,
  delete checkpoints, journals and packs it doesn't name) runs **only after** a checkpoint
  and its journal were accepted, never on any of the fallback paths below.
* The diff needs the committed copy in memory (about 2 × 15 MB at 50k *(guess)*). That
  is chosen over dirty flags in the engine: a missed flag would lose state silently, a
  diff can't.
* Read-only loaders (`load_state`, used by `sync status`, history and setup) read the
  checkpoint and journal without truncating or deleting anything.
* A checkpoint whose `format` is newer than this build knows is an error ("This vault's
  sync record was written by a newer Quire; update Quire on this device"), never a fresh
  start.

**A damaged or unreadable `state.d` (review B1), by the 0.13.2 rules of `open_state_named`:**

* **Can't be read now** (no permission, a disk error, while listing the folder or reading
  a checkpoint or journal): an **error**. The pass doesn't run and nothing is written:
  "Couldn't read what sync did last (…)". Starting afresh over it would forget what was
  synced.
* **Damaged** (no checkpoint parses, or its body fails its check): the whole folder, packs
  included, is **renamed aside** to `state.d.unreadable` (`-2`, `-3` if taken; a rename,
  so no copy of the packs is needed), sync starts afresh, and the 0.13.2 notice says so
  once (nothing deleted; differing notes kept beside the synced version as copies).
* **The highest checkpoint is damaged but a lower one parses**: the lower one and its
  journal are complete (a checkpoint is written before the older pair is deleted), so they
  are used; the damaged file is kept aside and the notice is raised.
* **A torn tail** (only the last journal line fails its hash, or has no newline): the
  normal end of a crash; truncated silently.
* **A bad journal line followed by good lines** is damage, not a crash: replay stops at
  the bad line, the journal is copied to `journal-<g>.jsonl.unreadable`, the state up to
  there is used and saved as a new checkpoint, and the notice is raised. That state is
  older than the last commit, which is the crash case of §3.5: the passes since are redone
  and merge to the same text.
* **A pack record that is missing, short or fails its print**: that base is missing
  (§3.2: kept as a conflict copy if a merge needs it); a notice once. A pack that can't be
  *read* now fails the pass that needs it with an error, as above.

All of these are in the fault-injection list of §6.

Other per-pass writes are made conditional too: `harden::save_pins` only when a pin
changed. `last.json` stays (under 1 KB). In a sync folder `snapshots-seen.json` is still
written each pass while a snapshot is settling (0.13 §1); it is small.

### 3.4 First sync, batched per transport

**Engine.** `Transport` gains:

```rust
fn push_batch(&self, revs: &[Revision]) -> BatchReply   // default: `push` one at a time
pub struct BatchReply { pub outcomes: Vec<BatchOutcome>, pub error: Option<TransportError> }
pub enum BatchOutcome { Accepted { seq: u64 }, Conflict, LostParent }
```

`outcomes` covers the prefix that was handled, so an error after k revisions still tracks
those k. `Engine::push` keeps its two stages: the plan is worked out whole first (so the
delete checks of §3.6 see every delete before anything is sent), then it is sent in
batches of at most 1,000 revisions and at most 4 MiB of request body (the JSON as sent,
sealed bytes hex-encoded). A revision whose request alone is over 4 MiB (a large
attachment) goes through the single `push`, as today. Texts are read when a batch is built, not in the plan, so
memory holds one batch. A `Conflict` marks the pass for another round (as today, up to
`MAX_ROUNDS`) but the rest of the batch stands; `LostParent` is sealed again as a first
revision and goes in the next batch, as `push_one` does today.

**Chunked passes.** A pass sends all of its deletes and at most 5,000 other revisions
*(guess, to be tuned on the perf job)*. The rest go in the next pass, which the worker
starts at once (as it does for `RemoteTransport::more_to_fetch`). Each pass commits (§3.3),
so a crash during a 50k-note first sync redoes at most one chunk, and the status can say
"Sending 15,000 of 50,000 notes…".

**The own-revision cursor: server only in 0.14 (review B4).** On a Quire Sync server the
server alone assigns `seq`, one counter per space, in commit order. The engine remembers
the seqs of its accepted pushes and, after each batch, moves `cursor` forward while
`cursor + 1` is one of them. A position it skips was given to one of its own accepted
revisions, which it already holds as head; a gap (another device's revision between) stops
it there, and the next pull returns from the gap. This fixes the 18.6 s pass.
A transport says whether its seqs allow this (`Transport::own_seqs_skippable`, default
`false`; `true` for `HttpTransport` and `MemoryServer`). On folder, S3 and WebDAV the
positions are handed out by `FolderTransport` per process (`next_seq`, restarted lower
after a restart), and the proof that a skipped position can never hold another device's
head isn't written yet; a revision skipped by mistake would never arrive on this device.
So there the engine keeps today's behaviour: its own heads come back once and are skipped
by `t.head == r.rev` (a local read of each line, no network). Tests: the three-device
property test with interleaved pushes runs on `MemoryServer` and the real server
(`apps/quire-sync-server/tests/end_to_end.rs`); a test checks that folder and the S3 mock
never advance the cursor past a pull.

**Server: a new endpoint, advertised, never required.**

```
POST /v1/spaces/{space}/revisions/batch   {"revisions": [Revision, ...]}   ≤ 1,000 items, ≤ 8 MiB body
200 {"outcomes": [{"accepted": {"seq": n}} | {"conflict": {}} | {"lost_parent": {}}], "latest": n}
```

* One `IMMEDIATE` transaction for the batch (`Store::push_many`): the newest key epoch and
  `MAX(seq)` are read once; each item is checked against its file's head in order, as
  `Store::push` does; one commit, so one fsync under `synchronous = FULL`. The long-poll
  bell rings once with the last seq.
* Refused whole, with nothing stored: any id that isn't valid or more than 2 parents
  (`400`); a device token pushing as another device (`403`); any item sealed under an
  epoch older than the space's newest (`422`, the 0.13 rule). The route sits behind the
  same `require_token` and `require_protocol` layers as every 0.13 route, so a removed
  device gets `403` and an old client `426`.
* A conflict outcome carries no head (the engine never reads it; today's single push
  returns it for compatibility and keeps doing so).
* `GET /v1/info` gains `"features": ["batch-push"]` (`ServerInfo`, `#[serde(default)]`;
  0.13 clients ignore unknown fields). `HttpTransport` reads it once per session; without
  it, or on a `404`/`405` from the route, it falls back to single pushes for the session.
  `PROTOCOL` stays 3 and no space minimum is raised.
* **Body limits (review B3).** The route's own limit is 8 MiB, twice the client's cap (the
  single-push route keeps `MAX_BODY`). Self-hosted servers often sit behind a proxy with a
  smaller limit. On a `413`, `HttpTransport` halves the batch's byte cap and sends the same
  revisions again, down to one revision per request; at one it uses the single `push`
  route for the rest of the session. A connection reset while sending a batch over 1 MiB is
  treated once as a `413`; if the halved batch also fails that way it is an ordinary
  offline error. The smaller cap holds for the session, so a first sync that worked with
  single pushes in 0.13 works now. Test: a router that refuses bodies over 1 MiB, then one
  that resets the connection instead.

**Folder.** `FolderTransport::push_batch` checks every head under one lock, then writes
the lines of the batch per log segment with one `note_own` (noting the length after all
of them, before writing: "noted before written" holds, a crash leaves the file shorter
than noted, never longer) and one `sync_data`; it starts a new segment past
`SEGMENT_LIMIT` as now. `folder-seq` is written once per batch, not per revision (it
already may lag; `next_seq`'s comment). The lines are the same lines; 0.8–0.13 readers see
no difference.

**S3 and WebDAV.** The mirror append uses the folder batch (local code, the same lines).
The object layout is fixed by the compatibility rule (one object per revision, 0.12 §1),
so uploads stay one `PUT` per revision, 8 at a time (`PARALLEL`, unchanged: owner's
decision), and the tip and outbox rules stay as they are. A first sync of 50k notes to
real storage is bound by round trips: about 50,000 / 8 × 50 ms ≈ 310 s at 50 ms per
request *(estimate, not measured)*; that is why only request counts are budgeted for these
transports.

### 3.5 Crash safety, step by step

| The app stops… | State on disk | Next pass |
|---|---|---|
| during `Manifest::scan` | manifest cache old or new (atomic replace) | scans again |
| while pulling and writing notes | notes written, state not committed | as today: the same revisions are pulled again and merge to the same text (reliability scan, "Sync pass") |
| after a batch was accepted, before commit | revisions on the server or in the log; not tracked | each tracked note is pushed again on its old parent, gets a conflict, pulls its own revision, merges to the same text; a new note is adopted by the identity rule (`arriving`). No duplicate, no loss (as today) |
| while appending base records | pack longer than the state says | truncated at open, after the state was accepted |
| mid journal line | torn last line | its hash fails; ignored and truncated; the pass is redone as above |
| while writing a checkpoint | temp file, or two checkpoints | the highest that parses wins; leftovers deleted |
| (not a crash) a damaged checkpoint, journal or pack | see §3.3 "damaged or unreadable" | kept aside, notice; never a silent fresh start |
| during pack compaction | new pack not named, or old pack no longer named | whichever isn't named is deleted at open |
| during migration (§3.7) | `state.json` alone, or both | see §3.7 |

Commit order is always: data first (pack), then the record that names it (journal or
checkpoint), each flushed before the next.

### 3.6 Delete safety (0.13.2) keeps holding

Nothing in §3.1–§3.4 decides a delete. The rules stay where they are, in the same order:

* **A vault that can't be listed stops the pass.** `begin_pass` fails when
  `Manifest::scan` fails to list (the frame makes that an error, never "all gone"), and
  the pass returns `SyncError::List` before the engine runs, as `snapshot_reads` does now.
  The manifest's cached rows and its `gone` tombstones are never used for a delete.
  `Engine::sync` and `push` still call `LocalStore::list` and stop on its error.
  `VaultStore::list` answers from this pass's scan; `shared_files` and `unselected` keep
  their own error rules.
* **A delete is checked once more before it is sent.** `LocalStore::missing` stays a
  direct storage call (only "not found" counts; the iCloud stub check), never the
  manifest.
* **The deletion stop.** `MANY_DELETES`, `DELETE_WINDOW_MS`, `deletes_sent` and
  `MANY_SETTINGS_DELETES` are unchanged, and the check still runs on the whole plan before
  the first batch is sent. Chunking never splits deletes: all of a pass's deletes go in that
  pass, so an approved set is sent in one pass and `held-deletes.json` goes only after it.
  `deletes_sent` marks count accepted outcomes, as they count accepted pushes now.
* **Approvals.** `HeldDeletes`, its digest (`HeldDeletes::id`), the 15-minute expiry and
  `Engine::allowed_deletes` are untouched.

Tests that must pass unchanged: `a_vault_that_cant_be_listed_sends_no_deletes`,
`many_deletes_wait_until_the_person_allows_them`, `deleting_the_shared_settings_asks_first`,
`a_note_evicted_to_an_icloud_stub_is_not_sent_as_deleted` (vault_sync tests);
`a_vault_that_disappears_in_halves_still_stops`, `the_many_deletes_hour_slides_across_its_end`,
`an_empty_or_unreachable_server_deletes_nothing_here` (convergence);
`a_sync_folder_that_vanished_or_emptied_deletes_nothing_here` (folder_sync). New:
`a_listing_error_with_a_warm_manifest_still_stops`, `deletes_are_never_split_across_chunked_passes`,
`an_approved_set_larger_than_a_chunk_is_sent_in_one_pass`.

### 3.7 Migration from 0.13, and the way back

At the first 0.14 session over a vault with `state.json` (and likewise `state-partial.json`,
`state-shared.json`):

1. Read it with today's loader (`open_state_named`: a damaged file is kept aside and sync
   starts afresh, with the notice, as in 0.13.2).
2. Put each note base into a pack and turn every base into a print. Leave `disk` empty
   (the first pass reads each note once, which 0.13 did on every pass).
3. Flush the pack; write `checkpoint-000001.json` with `migrated_from`, the SHA-256 of the
   old file's bytes.
4. Delete `state.json` and flush the folder.

At open: a `state.json` beside a `.d` folder whose `migrated_from` matches it is a leftover
of a crash after step 3: it is deleted. One that doesn't match was written later by an
older Quire (a downgrade and back): **the old file wins**, the `.d` folder is discarded and
step 1 runs again. Either way exactly one valid state is used (frame §7.2).

Migration holds the whole `state.json` in memory once, as every 0.13 pass did (697 MB peak
at 50k notes in the scan), and needs free disk of about the size of `state.json` again
(the packs) until step 4 deletes it. If the disk is full, step 3 fails, `state.json` stays,
and the pass reports the error; nothing is lost.

**Two Quire versions on one device (review B5).** A 0.13 `quire-cli sync once` in cron and
a 0.14 app on the same vault would alternate: each 0.13 run starts afresh (copies of notes
changed since), each 0.14 run migrates again. Nothing is deleted, but copies pile up. The
checkpoint carries `older_runs`, a count kept across re-migrations (the new checkpoint
copies it from the discarded `.d` folder, plus one). From the second time a non-matching
`state.json` appears, every such migration raises a sync notice: "An older Quire (0.13 or
earlier) also syncs this vault on this device, so each of them starts sync afresh and keeps
changed notes as copies. Update every Quire on this device (the app and `quire-cli`)
together." The first time is the ordinary downgrade-and-back and says only that sync
re-read the older record. Test: `an_older_quire_syncing_the_same_vault_is_named`, with
three alternations.

Downgrade: a 0.13 build finds no `state.json`, starts afresh and adopts the notes by the
identity rule; notes changed on this device since its last pass are kept beside the synced
version as copies (`Plan (2).md`). Nothing is deleted. A 0.13 build ignores the `.d`
folders. `sync_set_selection_at` renames `state.d` ↔ `state-partial.d` instead of the JSON
files; `stop_sync` and `remove_sync_files` remove the `.d` folders.

### 3.8 Key epochs, levels and the 0.13.3 retry

Sealing is unchanged and still decided per revision by `Content::seal_as` with the
transport's `sealing()`; a batch asks `sealing()` once and seals every item under the
engine's current `KeySet`. Keys change only in `Session::refresh_keys`, which runs before
the engine in every pass, so one batch never mixes epochs.

* A key change during a chunked first sync: on a server, the next batch sealed under the
  old epoch gets `422` whole, the pass fails, the next pass's `refresh_keys` takes the new
  key and the rest is sealed under it. Folder, S3 and WebDAV refuse the old sealing ways
  in `seal_as` and keep the level they read (`RemoteTransport::read_level`, 0.13.3).
* The 0.13.3 retry holds: `key_news` stays set until a refresh succeeds, and chunked
  passes each call `refresh_keys` first. New tests: `a_key_change_during_a_chunked_first_sync_seals_the_rest_anew`
  (server and S3 mock), next to `a_key_refresh_that_fails_is_tried_again_next_pass` and
  `after_a_key_change_a_remote_device_seals_at_the_vaults_new_level`.
* `hardening.json` (the level floor), `peers.json`, `LaneRules` and removed-device cuts
  are untouched. The base packs hold plain text only of notes that are plain on this disk,
  never anything sealed.

### 3.9 Per transport, in one place

| | Idle pass (worker) | Idle `sync once` (new process) | First sync |
|---|---|---|---|
| Server | 1 `changes` request + key records; stat only | meets the budget (state ~3.5 / 17.5 MB, manifest cache) | batch endpoint, 1 transaction per batch (≤ 1,000, ≤ 4 MiB, halved on `413`); own-revision cursor |

### 3.10 Fit with the architect's frame

* Uses `Manifest` (scan, `observed` for bytes it reads, `note_written` for bytes it wrote,
  `note_removed`, `verify_where`) as the change feed; persists only
  hashes; keeps sync state out of `.quire/cache/` (frame §3: "Sync state is not a cache").
* The journal is an append to a file only the `SyncLock` holder writes, so frame §3's "no
  appends shared between processes" holds.
* Merge bases are addressed by content hash (frame §8).
* `quire-sync` still does not depend on `quire-vault`; `Stamp` is an opaque 32 bytes.
* The revised frame took in this note's three additions: the idle `sync once` rows are
  for the server transport (frame §5); `Manifest::verify` (frame §2); sync compares the row
  with `Tracked.disk`, not with the base's hash (frame §2's consumer table).
* Frame §2: the scan takes size and time from the directory walk (no second `stat` per file;
  this matters on NTFS at 50k notes); `note_written` queues and never waits for a scan; each
  scan's `Delta` goes to every subscriber. Sync still runs its own scan every pass (§3.1).
* Frame §7 rule 2 (the way back) is met by §3.7; rule 1 by §3.4 and §5.

## 4. Alternatives considered

* **Keep `state.json`, write it only when changed.** Fixes the idle write but not the
  read (44–220 MB per `sync once`) or the memory; a one-note change still rewrites it all.
* **SQLite for the client state.** Adds `rusqlite` (bundled C) to both editions and the
  CLI; the frame asks for no new dependency.
* **Bases in `.quire/history`.** History has its own retention and can be cleared.
* **Trust the watcher instead of stat.** Events get lost; frame §2 makes them hints.
* **New pack objects on S3/WebDAV for a first sync**, or writing the first sync as a 0.13
  snapshot. Either changes what 0.13 devices must read, or bends compaction's rules
  (settling, the one-snapshot-per-generation race). Not for 0.14.
* **Advance the cursor to the server's `latest` after pushing.** Skips other devices'
  revisions that landed in between. Only contiguous own seqs are safe.
* **Shard files instead of checkpoint plus journal** (the review's suggestion): 1,024 small
  files keyed by `FileId` prefix, each replaced whole with `write_atomic`, plus a small
  `head.json` (cursor, `left`, `skipped`, `deletes_sent`) written last. A one-note change
  rewrites one shard (about 17 KB at 50k); there is no replay, no line hashes and no
  truncation at open, and crash safety comes from "shards first, cursor last" plus the
  engine's idempotent re-pull. It is roughly 200 lines of crash-critical code against
  roughly 1,000 for the journal. Its cost is fsyncs in bulk: a 5,000-note chunk of a first
  sync, or a migration, touches every shard, which is 1,024 fsyncs per chunk against the
  journal's two. Kept the journal for that, and because its crash table (§3.5) and damage
  rules (§3.3) are written out; the shards remain the fallback if S1b's fault-injection
  tests show the journal is too costly to get right.
* **16 S3/WebDAV uploads at a time and a tip every 1,000 objects.** Not needed for any
  budget, and they touch the transports with the least test coverage (the real-server job
  is weekly). Dropped for 0.14 (owner's decision on the 8).

## 5. Compatibility

**Older devices.** 0.13.x and 0.14 sync together on every transport, both ways. Server:
a 0.14 client uses single pushes against a 0.13 server; a 0.14 server serves every 0.13
route unchanged and 0.13 clients never call the new one. Folder, S3, WebDAV: same lines,
same objects; tips may move more often during an upload, which 0.12+ readers already
handle. 0.8–0.12 are unaffected beyond what 0.13 already decided (0.13 §3).

**Existing vaults, agents, CLI.** Migration is automatic and once per state file (§3.7).
No note is rewritten. `quire-cli sync once` gains `--verify`; `sync status` and history
read the new state. Agents and `serve --sync` sync through the same session code.

**Real-time collaboration later.** Nothing here assumes one writer: the server's batch is
per-item compare-and-swap, the manifest is rebuilt from files, the journal is device-local
bookkeeping. Bases are keyed by content hash, so an operation-log layer can use the same
store for "base version + operations" (frame §8). A CRDT lane would be another engine
state (`<lane>.d/`), as the settings lane is today.

## 6. Risks and how each is tested

1. **A change missed because stat was trusted.** Racy rule in the manifest, own writes
   recorded by hash, daily verify. Test: `folder_sync`'s 150 seeds run twice, once with a
   store whose stamps are honest (results must equal today's, seed by seed), once with a
   store that keeps size and mtime fixed across edits; after one verify pass every device
   converges.
2. **State lost or wrongly replayed.** Property test: random sequences of engine state
   changes committed and reopened equal the in-memory state; every live print returns its
   text. Fault injection: each write and fsync in commit, checkpoint, compaction and
   migration fails or stops in turn; reopen gives the old or the new state and the next
   pass converges (no lost text, no duplicate note).
3. **A merge without its base.** A pack record corrupted on purpose: the note is kept
   with a conflict copy, never overwritten (`a_missing_base_keeps_both_versions`).
4. **Plain text of a locked note left in a pack.** The scrub test of §3.2.
5. **Batch semantics on the server.** Unit tests per outcome; a batch mixing accepted,
   conflicting and lost-parent items; `403` for another device, `422` for an old epoch,
   `426` for an old client, all storing nothing; two devices batching the same notes at
   once (`concurrent_pushes_keep_one_linear_history_per_note` in `end_to_end.rs`, run
   with batches too); a 0.13 client against a 0.14 server
   (existing `protocol.rs` and `harden.rs` suites) and a 0.14 client against a router
   without the route.
6. **Cursor skipping someone else's revision.** Property test with interleaved pushes from
   three devices on `MemoryServer` and on the real server: every revision is applied on
   every device. Folder and the S3 mock: the cursor never moves except in `pull`.
7. **A stale manifest row stalling a pull.** `an_edit_that_kept_its_time_and_size_merges_on_the_second_pass` (§3.1).
8. **A proxy with a small body limit.** Routers refusing bodies over 1 MiB, and resetting
   the connection instead (§3.4).
9. **Damaged state.** Fault injection on `state.d` (§3.3): unreadable folder or checkpoint
   (error, nothing written); no checkpoint parses (folder kept aside, fresh start, notice);
   damaged highest checkpoint with a good lower one; torn tail (silent); a bad journal line
   followed by good ones (stop, copy aside, notice); a short or corrupt pack record. Each
   case checks that nothing destructive ran before a state was accepted.
10. **Two Quire versions on one device.** `an_older_quire_syncing_the_same_vault_is_named`
   (§3.7).
11. **Migration and downgrade.** Recorded `state.json` fixtures (0.13.3, with kept copies,
   `left`, `skipped`, `deletes_sent`) migrate to an equal state; the
   downgrade-and-back case rebuilds from the newer `state.json`.
12. **Budgets.** §2's rows in `perf-check.py`, report-only until wave 4 of the frame, then
   enforced; counts enforced from the start.

## 7. What the user sees

* Sync no longer reads and rewrites your whole vault on every pass. With nothing to sync,
  a pass on a 50,000-note vault takes well under a second and writes nothing.
* Setting up sync on a large vault is several times faster with a Quire Sync server
  updated to 0.14, and the status shows how many notes are left to send. It also works
  behind a proxy that limits request sizes.
* After updating, the first sync pass reads every note once to move sync's record to a
  new format. If you go back to Quire 0.13 afterwards, it starts sync afresh and keeps any
  differing notes as copies.
* Update every Quire on a device together: the app and `quire-cli`. If an older one also
  syncs the same vault there, sync says so.
* `quire-cli sync once --verify` re-reads every note to catch changes that kept their file
  time and size; Quire also does this by itself once a day.

## 10. As built: S1a–S1c

Where the code departs from §3, all small (commits on `feat/0.14-sync-s1`):

1. **An attachment's print** is the SHA-256 of its base64 text, which is the hash
   inside 0.13's `sha256:` fingerprint, not the SHA-256 of the fingerprint string
   (§3.2). A note's print is the same either way. This makes the 0.13 state convert
   to prints and back without loss (`quire_sync::bases::State13`).
2. **`LocalStore` has a fourth method**, `print_stamped`: an attachment's print
   comes from a cache keyed by its stamp, so after a migration (no `disk` yet) an
   unchanged attachment is not read and encoded again.
3. **`Bases::get` returns `Result<Option<String>, String>`**: a pack that can't be
   read now fails the pass (§3.3), one that lost the record answers `None` (§3.2).
4. **A purge compacts every pack that has any unnamed bytes**, the active one
   included, not only the packs holding the cleared print: older synced versions
   of a note that is locked now leave the packs in the same commit too.
5. **`VaultStore` opens its own `Manifest`** in the app as in the CLI: the
   workspace has no shared one yet. `VaultStore::with_manifest` takes one when it
   does.
6. **The daily verify** runs in the pass after an idle one (or a session's first
   pass) once `verified_at` is 24 hours old. There is no battery check: no cheap
   cross-platform way without a new dependency.
7. **`LocalStore::missing` also checks that the vault's own folder can be listed.**
   `VaultStore::list` answers from the pass's scan (§3.6), so a vault unplugged
   after its scan would otherwise read as every unchanged note gone.
8. **A file that is listed but can't be read** is per-note, after the 0.13.2 rule that only a listing error stops the pass. The manifest's scan reports it in `Delta.unread` and keeps its row; `begin_pass` leaves it out of the listing and `LocalStore::unstorable` answers for it, so the engine skips it as it skips a name this computer can't store: never sent, never sent as deleted, never written over, an incoming revision kept in `skipped` until the file can be read. The same holds for a file whose row was trusted and that only fails when the engine reads it: `apply_or_skip` records the revision as skipped when the store says the file is unreadable, and a write never replaces a path the store couldn't read. The sync status names it on every pass ("Needs attention"; `sync once` exits with that error), and the rest syncs.
9. **Note files opened** (§2): an idle pass opens none. A pass that sends one
   changed note opens it twice: the manifest's scan hashes it (its size or time
   changed) and sync reads its text; the budget of 1 counts sync's read only. A
   pass that receives one opens it three times (the engine's check for changes
   here, its check for an unsynced file in the way, and the write's
   compare-and-swap), and the next pass hashes the written file once more (the
   manifest's own-write rows are racy).
10. **Folder transport, `sync once`:** the cursor is a per-process position there,
    so each new process moves it and an idle `sync once` commits one journal line
    (about 100 bytes). `FolderTransport` also rewrites `folder-seq` once per
    revision while it indexes the folder (10,001 writes, 160 KB at 10k notes): the
    folder batch of S2c.

Measured at 10,000 notes (`quire-cli bench vault`), sync folder, Lite debug build
on the shared 2-CPU VM, idle `sync once` (S1c against the merge base 7156952):
notes opened 20,002 → 0; bytes written 44.3 MB → 160 KB (sync state: 105-byte
journal line and `last.json`); bytes read 461 MB → 339 MB (now nearly all the
folder transport's index, §2 non-goal); record on disk 44 MB → 15.5 MB (11.3 MB of
packs, a 4.3 MB checkpoint); one note changed: 20,003 → 2 opens. Wall times
(27–48 s before, 15–21 s after) are of debug builds on a loaded machine and say
little. The server rows were not measured.

S2a–S3, where the code departs from §3.4 and §2 (commits on `feat/0.14-sync-s2`):

11. **Texts of changed tracked notes are read in the plan**, as before: the plan
    needs them to tell a change from none. Only new files (all of a first sync)
    are read when their batch is built. A pass of edits to many tracked notes
    holds their texts, at most a chunk of them.
12. **The 5,000 a pass counts across the pass's rounds**: a conflict round sends
    only what is left of it. Deletes never count and are never split.
13. **Progress:** `quire-cli sync once` runs passes until nothing is left and
    prints "Sending X of Y notes…" to stderr after each; the worker starts the
    next pass after 100 ms. The desktop status says "Syncing…" while passes are
    left (no new `SyncStatus` variant, so the desktop's matches are untouched).
14. **The request size is an estimate** (`transport::request_len`: the hex of
    the sealed bytes, ids, links and a fixed overhead), a little over the JSON
    as sent.
15. **A cut connection** is an I/O error of kind reset, broken pipe, aborted or
    unexpected end. On a request of more than one revision it halves the cap,
    whatever the size, and again on each cut after, down to one revision; a
    cut on one revision is an ordinary offline error and never turns batches
    off. A cap lowered by cuts goes back to the one `413`s left at the next
    pass without a cut (`Transport::begin_pass`). A batch whose reply was cut
    after the server took it is sent again in halves within the pass and
    taken at its positions.
16. **A resend is idempotent on the batch route and `MemoryServer`**: a revision
    already stored for its file, the same bytes from the same device, is
    `accepted` at its position (the same ids with anything else are a
    conflict). The single route
    is unchanged (a resent revision there gets `409`, as in 0.13). A first
    parent never stored is a `lost_parent` outcome in a batch (the single route
    answers `422`).
17. **`folder-seq`** is written once per batch and once per pull, which also
    ends the 10,001 writes of item 10.
18. **`quire_sync_server::app_0_13`** (hidden) serves the routes as 0.13 did,
    for the pairing tests.
19. **Sync's own writes reach the index through the shared manifest**
    (`Manifest::observed` in `VaultStore::wrote`), not only through the file
    watcher. Removals do not: the manifest has no published form of a removal;
    they reach the index through the watcher or the next scan.
20. **Perf job (S3):** `packaging/perf-check.py --server` measures the §2 rows
    with processes: bytes read and written are `rchar` and `wchar` of
    `/proc/<pid>/io` (system calls, sockets included), peak memory is
    `ru_maxrss`, push requests are counted by a proxy in the script, fsyncs of
    the join and of a folder first sync only where `strace` is installed. Only
    the request bound fails the job; the rest reports. The migration row uses
    `quire-cli bench sync-013` (`vault_sync::bench_write_013_state`, built
    only with the `bench-hooks` feature, which the perf job turns on) to
    write a 0.13 `state.json` from the current state. S3 and WebDAV `PUT`s
    and folder `sync_data` calls are counted in tests, not in the job.
