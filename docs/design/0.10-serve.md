# Quire 0.10: headless sync and the web app (`quire-cli sync`, `quire-cli serve`)

Status: in 0.10, as Beta for self-hosters (see the end). Setup guide: [../serve.md](../serve.md).

## Why

The owner wants (1) to read and lightly edit the personal vault from a
work laptop's browser, with nothing installed or downloaded there, and
(2) agents in a VM to use the vault over MCP without the vault being copied
into the VM. Quire Sync is end-to-end encrypted, so its server can't do
either. A headless Quire on a machine the owner controls can: it holds a
plain copy (all of the vault, or chosen folders), syncs it like any device,
and serves people and agents over one port.

Compared with a plain "web reader for a vault plus MCP" (Tephra and
similar), the differences are Quire's agent model (zones, suggestions with
review, provenance, undo), editing with conflict checks, and encryption in
transit through Quire Sync.

## 1. Headless sync

`quire-cli sync join | once | watch | status | scope` runs the same engine,
transports (sync folder, Quire Sync server), conflict handling and history
as the app.

* **One pass, two callers.** `quire-app::vault_sync` had the pass inline in
  the app's worker thread. It is now `Session::pass`, run by the app's
  `SyncWorker` and by `sync_once_at` / `SyncWorker::start_headless`. Setup
  is `sync_create_at` / `sync_join_at` on a folder path (the app's
  `Workspace::sync_create/join` call them). The device's state, config and
  secrets are where the app keeps them, so a headless device is an ordinary
  device to the others (tested: an app workspace and a headless worker
  through a folder, edits both ways and a same-note race).
* **Secrets.** Passphrase from a no-echo prompt (`stty -echo` on Unix),
  `QUIRE_SYNC_PASSPHRASE`, or `--passphrase-file`; server token likewise
  (`QUIRE_SYNC_TOKEN`, `--token-file`). Never argv, never printed. `--create`
  writes the recovery key to a new 0600 file named with
  `--recovery-key-file` and refuses without it. Storage is the existing
  keychain-or-0600-file store (`QUIRE_SECRETS_FILE`).
* **Stopping.** SIGINT/SIGTERM (a tokio signal listener on its own thread)
  sets the worker's stop flag and joins it, so the pass under way finishes;
  vault writes are atomic (temp file + rename), so nothing is half-written.
  Tested by killing `watch` mid-pass with SIGTERM.
* **Status.** Each pass writes `.quire/sync/last.json` (`format: 1`): when,
  outcome, counts, conflict copies. `sync status` reads it with the config
  and engine state (another process may be the one syncing); no secret is
  read for it beyond checking the key exists.

### Selective sync

`--only F…` / `--exclude F…` (stored in `.quire/sync/config.json` as `only`
/ `exclude`; unknown to 0.9, which ignores them). The rule: **a note
outside the selection is never written, read or pushed by this device, so
its absence is never sent as a delete.**

* `LocalStore::in_scope(path)` (default true) and
  `LocalStore::moved_out(base)` (default none) are new engine hooks.
  The vault store answers from the selection; `.quire/shared/` follows its
  own switch, not the selection.
* The engine tracks out-of-scope notes (`Tracked::outside`, serde-defaulted)
  without writing them, skips them when pushing, and marks every tracked
  note outside the selection after each pass, whatever the result.
* Moves: a note moved out of the selection elsewhere leaves this device
  (to `.trash/`); one moved in arrives; a note moved here into an
  unselected folder is found by content (`moved_out`) and sent as a rename.
  If this device edited a note another device moved out, its text stays
  where it was and is sent as a note of its own (never lost).
* Widening: notes marked outside that the selection now includes are
  forgotten and the log is read from the start, so they arrive as new; a
  stale local file at the same path is kept beside them
  (`protect_unsynced`). Narrowing deletes nothing anywhere.
* A device with a selection keeps its engine state in
  `state-partial.json` instead of `state.json`. Quire 0.9 never reads it: if
  0.9 opened such a folder it would start from empty state, which can't
  delete anything, rather than read unselected notes as deleted.
  `sync scope` moves the file when a selection is set or cleared.
* Folder names are compared exactly (case included): a wrong case selects
  nothing, which is safe.
* Tests: engine-level (`quire-sync/tests/selective.rs`: edits outside,
  moves out and in, local move out, local edit vs remote move, widen and
  narrow, a real delete inside still travels), vault-level (an app
  workspace and a selective headless device through a folder), CLI-level
  (a third device with `--only Work`).

## 2. `quire-cli serve`

One axum server: quire-mcp's HTTP server (`/mcp`, OAuth AS,
`/.well-known/…`) with the web app's routes merged in through a new hook,
`HttpServer::start_with(server, cfg, |urls| Mount { router, consent_page })`.
MCP keeps its own guard (Origin/Host) on its routes; the web app checks
Host the same way and Origin on every form. The MCP test suite runs with a
mounted fallback router on the same port. `--sync` runs a headless
`SyncWorker` in the same process, nudged by the vault watcher.

The web app is a new crate, `quire-web` (both editions; `typeset` feature
adds math/diagram SVG), server-rendered with ~250 lines of plain JS and one
CSS file, embedded with `include_str!`. One `fallback` handler parses the
request and runs the page in `spawn_blocking` (pages read the index and
the disk synchronously).

* **Content:** the vault index of the MCP server (no second index): BM25
  full-text search with folded accents and case, quick open (`/api/quick`),
  tags, backlinks. Notes render through
  `quire_app::publish::render_note`, factored out of the site publisher
  (callouts, wikilinks, embeds, tags, citations, views, heading anchors),
  with links pointed into the app and links to notes the reader can't see
  left as plain text, as publishing does for private notes. Relative
  Markdown links and images are resolved against the note's folder. Code is
  coloured by a small tokenizer in `app.js` (no Syntect: size). Full
  edition: `$…$`, `$$…$$` and Mermaid become SVG images
  (`quire-typeset`, cached, inverted for dark mode); Lite shows source.
* **Files:** `/f/<path>`, inline for images, PDFs, audio, video and plain
  text; everything else is a download. Every vault file except a PDF gets
  `Content-Security-Policy: sandbox`, so an SVG or HTML file from the vault
  never runs as this site.
* **Editing:** textarea + preview (`/api/preview`, or a no-JS round trip),
  new note. Save sends the start text and its hash; the server compares
  with the note under a process lock, then writes atomically. On mismatch:
  clean `merge3(start, now, mine)` → shown for review, nothing written;
  otherwise a diff with "Save mine as a copy" or "Edit mine against the
  saved version". Before writing, the current text is snapshotted (synced
  or outside edits aren't always in history), then the new text with
  provenance `{kind: human, via: web, device, device_name}`. `Via::Web` is
  new; 0.9 can't parse it and shows a plain save. CR LF notes keep CR LF.
* **Read-only (`--read-only`):** no edit/new routes, no buttons, and the
  MCP server's `allow_write = false` now also caps HTTP tokens to read (it
  used to matter only for stdio; every HTTP caller passed `true`).

### Auth and browser security

* A passphrase per user config (`<config>/serve/login.toml`, 0600, Argon2id
  PHC via the `argon2` crate already in the tree for sync; `changed`
  timestamp ends older sessions). `serve` refuses to start without one.
* Sessions: 256-bit random token in a cookie (`HttpOnly; SameSite=Strict;
  Path=/`, plus `Secure` and the `__Host-` name when the public URL is
  https), server keeps the SHA-256 in memory, idle 8 h, absolute 7 d, at
  most 32 sessions. Restart signs out.
* CSRF: a per-session token in every form, compared in constant time, and
  a required same-origin `Origin` on every POST. Sign-in uses a
  double-submit cookie. `SameSite=Strict` is a third layer.
* Wrong passphrases: 5 free, then a global wait doubling from 1 s to
  15 min; a success clears it. Global because behind a proxy every client
  has the proxy's address; the cost is that someone hammering the login
  can delay the owner by at most 15 minutes per try. 0.10.1 (security
  review #5): a try is checked and counted in one step under the lock
  (`Limiter::begin` counts it as wrong until `end` says it was right), so
  parallel guesses can't all pass the check before the first is counted,
  and at most `MAX_VERIFYING` (2) Argon2 checks (19 MiB each) run at once;
  others get 429 with a one-second wait. `safe_next` refuses control
  characters and spaces (`/%09/evil.example`).
* Host must be one this server answers on (bind address, loopback names,
  public URL host); allowed Origins are those addresses and the public
  origin. Binding anything but loopback warns; `0.0.0.0` requires
  `--public-url`.
* Responses: `Cache-Control: no-store` (except fingerprinted assets),
  `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: same-origin`, and a
  CSP allowing only same-origin scripts/styles/images (plus `data:` images),
  no inline script or style, `frame-ancestors 'none'`, `form-action 'self'`,
  `base-uri 'none'`; external images in notes don't load (privacy, and
  nothing leaks a visit). CSP can't stop a page from navigating itself
  (`navigate-to` was dropped from CSP 3 and never shipped), and a note's
  `<meta http-equiv="refresh">` took the signed-in browser to a look-alike
  sign-in page (security review #4). So since 0.10.1 note HTML is cleaned
  to an allow-list in `publish::render_note`, for the web app and published
  sites alike (`quire_app::sanitize`, built on `ammonia`): formatting,
  tables, callouts (`data-callout`), `details`, footnotes, disabled task
  boxes, images and audio stay; `meta`, `base`, `link`, forms and their
  controls, frames, `object`, `embed`, inline SVG and MathML, scripts,
  `on…` attributes and other `data-…` attributes go; URLs may be `http(s)`,
  `mailto`, `tel`, relative, or `data:` for a picture or sound only; `style`
  keeps a short list of text properties.
* Excalidraw drawings embed their pictures through the same checks
  (`drawings::embedded_file`: `quire_agent::vault_file`, picture types only,
  and the caller's own rule, which for the web is the hidden folders).

### Visibility

* Every path from a URL or form goes through `paths::Guard::check`:
  `quire_agent::canonical_path` (NFC, relative, no `..`, no hidden
  segment), then a rejection of `.quire` and other dot segments, then the
  web-hidden folders, then `AgentStore::resolve` (symlinks must stay in the
  vault and out of hidden places) and the web-hidden check again on the
  real path. Hidden-folder matching is case-insensitive, because a
  case-insensitive file system would otherwise open `journal/x.md` from a
  hidden `Journal/`. Lists use the cheap check (no disk access); search hits
  get the full check before display. `LocalFs::list` already skips
  symlinks, so they never reach the index or the tree.
* Web-hidden folders: `[web] hide = […]` in `.quire/shared/vault.toml`
  (re-read when the file changes) plus `--hide`. Agent zones are separate:
  `private` (deny) zones are invisible to MCP, visible on the web unless
  hidden there.

### MCP and OAuth through the web login

Identical endpoint and AS to `serve-http`. The OAuth waiting page now links
to `{consent_page}?request=<id>` when a web app is mounted. The consent page
(signed in) shows host, name, scopes and the verification code, and Approve
/ Deny post to the shared `ConsentStore` (so `quire-cli mcp approve` keeps
working), then redirect to `/oauth/authorize/wait`. The code is still
released only to the browser holding the request's `HttpOnly` secret (the
0.9 browser-binding fix): approving from another browser or device decides
the request but gets that browser a 403, and the original window continues
by itself. Tested end to end with a CIMD client.

## Deferred

* An end-to-end encrypted in-browser client (WASM). The web app's routes
  are page-shaped today; a JSON API for a WASM client would sit beside
  them (`/api/…`, same session and CSRF rules) and use the sync protocol
  directly, so the server would not need the plain text.
* Reviewing agents' suggestions in the web app (they're reviewed in the
  app once synced).
* Rename, move and delete in the web app; attachments upload.
* Per-address login limits behind a trusted proxy header.
* Persisted sessions (restart signs out).

## Status: Beta, for self-hosters

`serve` ships in 0.10 as **Beta**: "your agents and your browser, on a
server you own". `quire-cli serve --help`, the web app (a "Beta" label in
the top bar, on the sign-in page and in the footer), docs/serve.md, the
README and the changelog all say so, and all say that the server holds a
decrypted copy of the folders it serves and syncs, unlike Quire Sync. It is
not presented as "Quire on the web".

## Later: Quire Web, end-to-end encrypted in the browser

"Quire on the web" will be a separate app: the sync client compiled to
WASM and run in the browser, decrypting notes there with the vault key, so
the server it talks to (a Quire Sync server) never holds plain text. It
would reuse the sync protocol and the rendering crates, not `serve`'s
server-rendered pages; `serve` stays the self-hosted option for agents
(MCP needs plain text on the server) and for browsers on machines you own.
Open questions: key entry and storage in a browser, offline storage
(IndexedDB/OPFS), search without a server index, and the size of the WASM
bundle.
