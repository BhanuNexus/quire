# Quire 0.12: typed links and hierarchy

Status: built on `feat/0.12-links`. Formats: [docs/formats/links.md](../formats/links.md).

## Why

"Link types and link metadata" is Obsidian's 6th most-voted feature request
(822 likes), and the Breadcrumbs plugin gained 61k downloads in 30 days.
People already write typed links with Dataview inline fields and
Breadcrumbs properties; Quire reads them as written, so a vault moves in
and out unchanged. Typed relations also give agents structure to follow
(`parent`, `supports`, `contradicts`) instead of bare links.

## Decisions

**A typed link is a link with a field name.** `quire_markdown::Link` gained
`field: Option<String>`; `extract` sets it for links inside inline fields
and adds links found in front-matter values (until 0.11 the front matter
held no links). One reason: everything that follows links (backlinks,
rename, lint, the graph, unlinked mentions, "follow link") sees typed links
without new code paths. Front-matter links now count as backlinks, as they
do in Obsidian since 1.4.

**Parse like Dataview, not like YAML.** Inline keys follow Dataview's
character rules and normalization (`**Parent Note**` → `parent-note`), and
fields are found line by line outside code. Front-matter links are found in
the raw text of the block (each `[[…]]` after a key, typed by the nearest
key), so their byte ranges are exact; that is what makes renames byte-exact.
Both scans are skipped when a note has no `::` or no `[[` in its front
matter.

**What a type means lives in the index, per vault.** `[links]` in
`.quire/shared/vault.toml` maps field names to `up`, `down`, `same`, `next`
and `prev` (defaults: Breadcrumbs' five plus `parent`, `child`, `sibling`)
and turns implied reverse edges on or off. The index worker reads the
section when it loads the vault, so the UI thread does nothing new before
the first frame. Later edits of vault.toml reach the index through the
existing vault.toml poll (`nav::read_prefs`, one added line); the first
read after opening is skipped because the worker already has it.

**Edges are built with the backlinks.** `LinkGraph::build` already resolves
every link once per index batch; it now also collects `(from, field, to)`
for typed ones and builds `Relations` (outgoing typed edges with implied
reverses, incoming typed links, field counts). Same incremental path, no
extra walk of the vault: one `Vec` push per typed link and one pass over
them.

**Every walk is bounded.** Ancestor/descendant walks keep a visited set and
stop after 5000 steps; trails keep the notes on the current path (a note
on a cycle ends that trail) and keep at most four paths of at most 32
notes; the tree view never expands a note already above it in its branch
(shown with "(again)"). A property test runs every walk on random cyclic graphs
under a timeout.

**Writing keeps the note's style and its bytes.** `fields::add_link` writes
an inline field when the note mostly uses them, else a property; it only
touches the field's own line(s): a flow list gets `, "[[X]]"` before its
`]` (comments after it stay), a block list a new item, an inline field `,
[[X]]`. Renames and moves go through `rewrite_links` as before; since
front-matter links are now links, they are rewritten too, changing only
the target inside `[[…]]` (with `''` for `'` in single-quoted YAML).

**The UI is cached per index version.** `Workspace::note_relations` (groups
for Insights, trails for the banner) is computed once per index version
and note and shared as an `Rc`; the trail banner's `available` check is
that cached value. The Hierarchy tab caches its rows per index version and
expanded set, walks only expanded branches, and paints only the rows in
view. Graph edge types are computed when the graph is built (already per
index version); per frame it costs one colour lookup per edge, plus a
point-to-segment distance per typed edge while the pointer is over the
graph and no note is hovered.

**Agents get typed relations through the same guard.** `links` (a note's
links and backlinks with types, filterable), `hierarchy` (ancestors,
descendants, siblings, previous/next and trails, depth 1–10) and typed
`neighbors` edges pass every note through `visible` (the canonical policy
guard: zones, allowed tags and folders, locked folders). Walks don't pass
through hidden notes, trails with a hidden note are dropped, and the list of
types in use comes only from notes the client may see, so a hidden note
doesn't leak through a field name either. `add_link` is an `EditOp` in the
shared `edit` path, so it applies in agent zones and is a reviewed
suggestion elsewhere, with versions and rebasing like `str_replace`; a
target the client can't see reads as "not found". The allow-list property
test (`quire-mcp/tests/connections.rs`) now writes typed links (inline,
bracketed, front matter, and a field named after each note's secret
marker) and calls `links`, `hierarchy`, typed `neighbors` and `add_link`
for every note.

**Commands get no default shortcuts.** "Add typed link…", "Go to parent",
"Go to next sibling", "Go to previous sibling" and "Show hierarchy" are in
the palette; Settings → Commands binds keys.

**No new crates.** `quire-index` now depends on `serde` (already in the
workspace) for `LinkConfig`.

## Deferred, and why

* **Breadcrumbs' other edge builders** (list notes, tag notes, Dendron,
  Johnny.Decimal, date, regex and folder notes) and **transitive rules**
  beyond reversal (`[parent, parent] -> grandparent`). They derive edges
  from naming schemes rather than from links people wrote; each is a
  feature of its own. The reversal rule covers the default setup.
* **Link metadata beyond the type** (`[supports:: [[X]] (strong)]`, edge
  properties). No format the two plugins share; the value text is kept as
  written and could be read later.
* **Editing `[links]` in Settings.** The section is small and hand-edited
  like the rest of vault.toml; a Settings page can come with the other
  vault.toml sections.
* **Typed links in the web app of `quire-cli serve` and in published
  sites.** They render as the links they are; grouping them there is a
  separate UI.
* **Bases `link()` values and `file.hasLink` by type.** Bases compares a
  typed field as its targets; Obsidian's link objects aren't modelled.
