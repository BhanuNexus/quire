## 1. Locked folders (encryption at rest, opt-in)

Encryption at rest is the most requested missing feature (79.7k views on
Obsidian's forum thread). It conflicts with invariant P1 ("Markdown files
are the truth"), so it is opt-in and per folder: a **locked folder**
(`Journal/`) keeps its notes and attachments encrypted on disk. The rest of
the vault stays plain Markdown and works as before.

### Threat model

Protected, for files in a locked folder, while the folder is locked:

* **A stolen laptop or disk.** Note text, attachments and their history are
  ciphertext. The thief needs the passphrase or the recovery key, and
  Argon2id makes guessing a passphrase slow.
* **A cloud folder provider** (Dropbox, iCloud Drive, OneDrive, Google
  Drive, a Syncthing peer) holding the vault or a sync folder. It sees
  ciphertext.
* **Backup copies** (Time Machine, a git remote, a copied folder). They
  hold the ciphertext and the wrapped key, nothing more.

Not protected:

* **The running, unlocked app.** Malware or another person using your
  session can read what you can. Locking (on demand, on idle, on quit) is
  what ends the exposure.
* **Memory.** Unlocked text lives in the app's memory. Quire doesn't write
  it to disk, but the operating system may page memory to swap or a
  hibernation file. Use full-disk encryption (FileVault, BitLocker, LUKS)
  for that; locked folders don't replace it.
* **Names and shapes.** File and folder names, the number of files, their
  approximate sizes and times stay visible (`Journal/2026-11-06.md.qenc`).
* **What existed before locking.** Locking rewrites the files, but the old
  plain bytes may survive on the disk, in file-system snapshots, backups,
  git history, a cloud provider's version history, and on other devices
  that synced the folder earlier. Quire removes what it controls (its own
  history and caches on this device) and says the rest.
* **Things you take out.** Copying (Copy as HTML, the clipboard) and
  moving a note out of the folder put plain text where you chose.

### What happens on disk

```
Journal/
  quire-lock.json          the folder's key, wrapped by the passphrase (format 1)
  2026-11-06.md.qenc       a note
  photo.jpg.qenc           an attachment
  Trips/Lisbon.md.qenc     subfolders are part of the locked folder
.quire/history/<fnv>/<ms>.md.gz.qenc   history of a locked note, encrypted the same way
```

`quire-lock.json` is an ordinary (not hidden) file so every copy of the
folder carries it: Quire Sync, sync folders, git and backups. With the
passphrase, or the recovery key alone, the folder can be read anywhere; the
format is documented in [../formats/locked-folders.md](../formats/locked-folders.md)
so another tool can decrypt it.

### File format (summary)

A `.qenc` file is a 46-byte header (`QENC`, version 1, kind, the folder's
16-byte id, a random 24-byte nonce) followed by the XChaCha20-Poly1305
ciphertext of the file's bytes. The header up to the nonce is the
associated data, so a file can't be moved to another locked folder, and a
history snapshot can't pass for a note, without failing to decrypt. File
names are not bound: a rename (by Quire, git or a file manager) needs no
re-encryption. The cost is that someone with write access could swap two
files of one folder; they still can't read or change either.

### Keys

* **Folder key:** 256 random bits, made when the folder is locked. The file
  key and a check value are derived from it with HKDF-SHA256.
* **Passphrase:** at least 8 characters. Argon2id (64 MiB, 3 passes, the
  same as Quire Sync, settings stored in the key file) derives a key that
  wraps the folder key with XChaCha20-Poly1305. Changing the passphrase
  rewrites only `quire-lock.json`; the files stay as they are.
* **Recovery key:** the folder key itself, written in Quire Sync's recovery
  key alphabet (52 Crockford base32 characters plus a 4-character check, in
  groups). Shown once when the folder is locked. It opens the folder even if
  `quire-lock.json` is lost, and can set a new passphrase.
* **Unlock automatically on this computer** (off by default): the folder key
  goes into the OS keychain under the vault's key and the folder id. It is
  offered only when a system keychain is in use, never with the private-file
  fallback, which would leave the key next to the vault. It means that anyone
  who can sign in to this computer account can open the folder.
* The crypto is the RustCrypto crates Quire Sync already uses
  (`chacha20poly1305`, `argon2`, `hkdf`, `hmac`, `sha2`, `zeroize`).

### Unlocking and locking

* **Unlock** derives the key (about half a second), checks it against the
  folder's check value and keeps it in memory (`quire_vault::KeyRing`,
  zeroed on drop). Notes are decrypted into memory when opened and
  encrypted when saved. Nothing in plain text is written to the vault, to
  `.quire/` or to a temporary file.
* **Lock** saves open notes in the folder, closes them, forgets their text
  and search entries, and drops the key. It happens on demand (command,
  status bar, the folder's menu, `quire-cli lock`), after an idle time
  (Settings, default 15 minutes, "Never" possible) and when the app quits.
* A locked note shows as `🔒 name` in the sidebar. Opening it shows a
  "Locked" page with an Unlock button; search shows nothing from it.

### Where locked notes go and don't go

The rule that makes this hold everywhere: **`Vault::notes()` never lists a
note in a locked folder**, locked or not, so the vault index and everything
built on it (tasks, agenda, Bases views, graph, backlinks, reminders,
flashcards, lint, embeddings, claims, contradictions, staleness, timeline,
Ask, the agent panel, MCP, publish) never sees one. Locked notes are read
only by name, through the key ring, by the desktop app's editor and its
own in-memory search. And the storage layer refuses to write a plain file
into a locked folder (`VaultError::Locked`), whoever asks.

| Area | Behaviour |
|---|---|
| History | Snapshots of a locked note are encrypted (`.md.gz.qenc`) with the folder key. Locking a folder encrypts the folder's existing snapshots on this device; unlocking it decrypts them. History is read only while unlocked |
| Caches in `.quire/cache/` | Built from the vault index or from plain files only, so nothing from a locked folder gets there (embeddings, claims, contradictions, pdf-text, OCR, staleness, served). Locking a folder removes this device's cache entries that can point to its notes: the whole `served/` cache and `stale.json`; the rest are keyed by content and were built from the plain text before it was locked, so they are cleared too (`claims/`, `contradict/`, `pdf-text/`, `ocr/`, `embeddings.bin`, `vectors-*.f16`) and rebuilt from what is still plain |
| Search | Covers unlocked locked notes from a separate in-memory index (search, quick open). It is never written anywhere and is dropped on lock. Locked notes are not in tasks, backlinks, graph, views or AI |
| Sync | **The ciphertext syncs**, as an attachment: the engine never sees plain text, so its base copies (`.quire/sync/base/`) and the server hold only `.qenc` bytes, and sync keeps working while the folder is locked. Another device unlocks with the same passphrase (the key file travels with the folder). Encrypted files can't be merged: two devices editing one locked note offline keep both versions (a conflict copy, or a numbered name). A device running Quire 0.10 doesn't know locked folders: a plain note it puts into one is refused on 0.11 devices (sync reports that file) until it is moved out of the folder there |
| Agents and MCP | Locked folders are **invisible to agents, always**, locked or not: a hard rule in `AgentStore::effective` (like `.quire/**`) denies every path in a locked folder and every `.qenc` file, for MCP (stdio and HTTP), ACP and the in-app agent panel. `list`, `search`, resources, backlinks and `ask` never show them. Agent processes also get no keys |
| `quire-cli serve` (web app) | Locked folders are hidden from the web app: `serve` never holds a key in 0.11 (unlocking in a browser would need the key on the server; the planned end-to-end encrypted Quire Web is the right place) |
| Export, Copy as HTML | Export to HTML or PDF is refused for a locked note (Quire writes exports to `Exports/` in the vault, unencrypted). Copy as HTML works for an open note: the clipboard is your choice |
| Publish | Never publishes a note from a locked folder |
| Git | Commits the ciphertext and `quire-lock.json`. Diffs of locked notes show as binary |
| Quick capture | Into a locked folder only while it is unlocked (encrypted as written); otherwise refused with "Journal/ is locked". The CLI's `capture` can't unlock and is refused the same way |
| Templates | Creating a note from a template into a locked folder works while unlocked. The templates folder itself can't be locked |
| Daily notes | A locked daily-notes folder works while unlocked; while locked, "Today" opens the lock screen (or, when today's note doesn't exist yet, says the folder is locked) |
| Pictures in locked notes | Stored encrypted. Pasting a picture into a locked note is refused in 0.11 (it would go to the plain attachments folder); embedded pictures inside a locked folder aren't displayed yet |
| Links | Links between locked and plain notes keep working while unlocked (a link to a locked note opens its lock screen while locked, and never creates a new note). Renaming a locked note updates links in plain notes; renaming a plain note doesn't update links inside locked notes |

### Converting a folder

"Lock a folder…" and "Stop locking a folder…" (and `quire-cli lock` /
`quire-cli unlock --convert`) are crash-safe and resumable:

* **Lock:** write `quire-lock.json`; from then on agents can't see the
  folder and nothing plain can be written into it. For each plain file,
  write `name.qenc`, read it back, decrypt it with a key unwrapped again
  from `quire-lock.json` and compare byte for byte. Only after every file
  passed is any original removed. Then the history of those notes is
  encrypted and the caches cleared. An interruption at any point leaves
  either the plain file or a verified `.qenc` (or both); running the
  conversion again ("Lock a folder…" or `quire-cli lock`) finishes the job,
  and the app reports such a folder when it opens the vault. The plain originals are
  deleted, not moved to the trash (a plain copy is what locking removes);
  the verification is the safeguard.
* **Unlock permanently:** rename `quire-lock.json` to
  `quire-lock.unlocking.json` (the folder is plain again for writes), write
  each plain file and verify it against its `.qenc`, then move the `.qenc`
  files and the key file to `.trash/` (the backup; it is ciphertext) and
  decrypt the history. If interrupted, the folder still has its key file
  under the `unlocking` name and the next run finishes.
* Refused for the vault root, `.quire`, hidden folders, the templates
  folder, a folder inside or containing a locked folder, and a folder
  holding a copy of a key file (`quire-lock…` under another name).
* Also on locking: this device's agent suggestions about the folder's notes
  (they hold their text) are deleted, and the caches above are cleared.

### CLI

```
quire-cli lock   <vault> <folder> [--recovery-key-file F] [--passphrase-file F]   lock (or finish locking) a folder
quire-cli lock   <vault> <folder> --change-passphrase [--recovery-key] [--new-passphrase-file F]
quire-cli unlock <vault> <folder> --check | --cat NOTE | --convert                 test, print one note, decrypt for good
quire-cli status <vault>                                                         locked folders and unfinished conversions
```

Passphrases come from a no-echo prompt, `QUIRE_LOCK_PASSPHRASE` (new ones:
`QUIRE_LOCK_NEW_PASSPHRASE`) or a file, never argv, as for sync. Locking a
new folder writes the recovery key to a new 0600 file
(`--recovery-key-file`, required) and never prints it, as `sync join
--create` does. The CLI keeps no unlocked state: `unlock --check` tests a
passphrase, `--cat` prints one note to standard output, `--convert` decrypts
the folder for good.

### Tests

* No plain text on disk: a vault with a locked folder goes through edits,
  saves, history, the index, search, agents and sync between two devices;
  then every file under the vault and `.quire/` is scanned for marker
  strings of the locked notes.
* Wrong passphrase, wrong recovery key, a flipped bit, a truncated file, a
  file moved between two locked folders, a history snapshot passed off as a
  note: all fail to decrypt and are reported, never shown as empty.
* Conversion interrupted after every single step (a storage that fails the
  Nth write): the folder always ends complete and identical after resuming.
* Two devices through a sync folder: lock on A, unlock on B with the same
  passphrase, edit on both, see both versions kept.
* Fixed test vectors for the format, so later versions still read 0.11
  files.

## 2. Agent connections

Notion (per-connection audit and revoke), Bear (MCP limited to chosen tags)
and Joplin (AI off by default) set the bar. Quire already had zones,
per-client policy entries, scopes and the ledger; 0.11 adds the view and
the controls.

### Settings → Agents → Connections

One row per agent that has used this vault, gathered from:

* the ledger (all devices' copies with shared review history): every
  actor that read (when read logging is on), wrote, suggested or was
  decided on; keys `mcp:<client>`, `mcp:<name>?` (unverified), `oauth:…`,
  `token:<name>`, `acp:<name>`, `panel:<provider>`;
* the token store (`<config>/mcp/tokens.json`): personal tokens and OAuth
  clients, even unused ones;
* `[clients]` entries in the agent policy, including revoked ones.

Each row shows the kind, last used, reads and writes (last 90 days of the
ledger), pending suggestions, and permissions: the mode per zone that
`AgentStore::effective` gives this client (so it is what's enforced, not a
re-statement). **Activity** opens the connection's log from the ledger,
filterable by kind (reads, writes, suggestions, decisions) and text.

### Revoke

* **HTTP tokens and OAuth:** every token of that client is deleted from
  the token store (its next request gets `401`), and its key is marked
  revoked in the policy as below, so a token issued meanwhile on another
  device is no use either.
* **stdio and ACP:** `[clients."<key>"] revoked = true` and `log_reads =
  true` are written to the agent policy. A revoked key is denied every path
  (effective mode `deny`), and `quire-cli mcp --client <key>` refuses to start
  with "Access for <key> was revoked in Quire (Settings → Agents →
  Connections)". Unverified clients (`mcp:name?`) are matched by name, so
  dropping `--client` doesn't get around it. Revoking narrows the policy, so
  it takes effect on every device without approval; **Restore** widens it
  and needs approval on other devices, as any widening does.
* The agent panel (`panel:<provider>`) can be revoked the same way, or
  turned off for the vault with **AI off**.

### Limited to tags or folders (per connection)

```toml
[clients."mcp:claude-code"]
allow_folders = ["Projects/", "wiki/"]
allow_tags = ["work"]
```

When either list is present, the client sees a note only if it is under
one of the folders or carries one of the tags (front matter `tags` or an
inline `#tag`; `#work/q4` counts as `work`). Everything else is `deny` for
that client. It is enforced in `AgentStore::effective`, the one check every
MCP tool, resource, list, search hit, backlink, neighbour and Ask source
already goes through, and the tags are read from the file itself (cached by
modification time), not from an index the client could influence. A
property test generates vaults and allow-lists and checks that no path,
title or text of an excluded note comes back from `search` (snippets
included), `list`, `neighbors`, `backlinks`, `view`, `outline`, resources or
`ask`. Adding a list narrows; removing one widens (approval on other
devices).

### AI off (per vault)

`ai = "off"` at the top of the agent policy (Settings → Agents, Settings →
AI). It denies every agent every path (MCP, ACP, the agent panel), and the
app sends nothing from this vault to an AI provider or to on-device AI:
writing help, Ask, embeddings, claims and contradictions, and voice-note
transcripts. Independently of AI off, a locked note is never sent to a
provider: writing help through a provider refuses it, and the agent panel
doesn't offer it as context. Turning it on travels with the vault; turning it back off is a
widening and needs approval on the other devices.

### Imported skills

`quire-cli skill install <dir>` still installs Quire's own skill.
`quire-cli skill install <dir> --from <file>` installs someone else's: it
prints the source (path, size, SHA-256) and the first lines, and installs
only with `--yes`. It writes `SKILL.source.json` beside it. A `SKILL.md`
inside a vault with that file beside it, or one an importer brought in, is
untrusted: agents receive it inside the untrusted-data fence, and any
change to it is a suggestion (as for every `SKILL.md`).

## 3. Deferred

* Unlocking in the web app (`serve` would hold the key; better done by the
  end-to-end encrypted Quire Web).
* Pictures inside locked notes (display, and pasting into the locked folder
  instead of the attachments folder).
* Locked notes in tasks, backlinks, the graph and Bases views while
  unlocked (needs a second, memory-only index path through those
  features).
* Hiding file names (would need an encrypted manifest, and breaks links
  and every outside tool).
* Wiping old plain copies from free disk space (not reliable on SSDs or
  copy-on-write file systems; full-disk encryption is the answer).
