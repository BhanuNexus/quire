# Review: 0.14 per-note index updates and a startup cache (`0.14-index-startup.md`)

Status: proposed (0.14, awaiting owner approval)
Area: architecture review
Code: `crates/quire-index/src/`, `crates/quire-app/src/secure_state.rs`, `crates/quire-markdown/src/scan.rs`

Reviewer: the 0.14 architect. Read against `0.14-architecture.md` and the code at main ad3216d.

## Verdict: approve with changes

The design is correct where it matters: the cache is validated by the manifest's hash and
never by itself; `DERIVE_VERSION` with a golden test is the right answer to "the parser
changed"; fold-in with a background refit and a stated drift bound is what the frame's
rule 4 asks for; the three-phase load keeps the app usable; and the locked-folder section
goes further than any other design (purge on lock, check before and after each write, check
on load, a tainted model that is never written). It also gives agent-index everything it
asked for.

My concern is size. This is two large and four medium steps in the crate that every other
index change waits behind. The changes below close one privacy hole and cut work.

## Blocking issues

**B1. Text of a removed note stays in a segment until compaction.** A removed note's row is
dropped from `records.idx`, but its record (`plain`) and source stay in the `r-*.seg` file
until dead bytes pass 50% of all segments (§3.6 "Steady state"). Two cases reach that
without passing `forget_derived`:
- another device moves a note into a locked folder; sync here removes the plain file and
  writes the `.qenc` one. The index gets `IndexMsg::Remove`; the plain text stays in the
  cache. That breaks `docs/design/0.11-secure.md` ("no plain text of a locked folder's
  notes stays"), and the load-time check does not see it because the old path is not in a
  locked folder;
- a person deletes a note and then copies or zips the vault folder: the "deleted" text
  travels inside `.quire/cache/index/`.
*Fix:* removal is a purge. A segment that holds a removed (or replaced) note is rewritten
without it at the next flush, and that flush is not allowed to wait for the 50% rule. A
segment is at most 512 notes, so this is a few MB per removal. Extend the marker test:
remove a note through sync into a locked folder on "another device"; after the next flush
no byte under `.quire/cache/` holds the marker. State the rule in §3.6 and in
`docs/formats/index-cache.md`: "the cache holds text only of notes that are in the vault
now, within one flush".

**B2. The write budget row contradicts the design.** §2 promises "≤ 64 KB + 2× the note,
every ≥ 30 s" per save. §3.6 rewrites `records.idx` whole on each flush, "about 5 MB at 50k
*(guess)*", plus `passages.idx`. While someone types, that is about 10 MB every 30 s.
*Fix:* pick one. Either flush less often (my recommendation: when the index has been quiet
for 30 s, at most every 5 minutes while busy, and on clean exit; a stale cache only costs
parses after a crash), or split the index file. State the real number in §2. The frame's
"at most every 30 s" is changed to the same rule.

**B3. Stable `DocId`s belong in step I1a, not I2.** §3.3 introduces them with the semantic
store and I2c lists them as needing I2a. Agent-index's keyword half (its steps 3–5, the part
that closes the leak) needs only stable ids and the interner. As planned it waits behind
the large cache step and the large semantic step.
*Fix:* move "a note keeps its `DocId` across updates; ids are reused after the removing
batch" into I1a. Then agent-index steps 3–5 can start when I1a merges.

## Non-blocking changes

- **Do not keep the BM25 list on the record.** §3.2 keeps `Vec<(TermId, f32)>` per record
  "because the agent views need it", 8 bytes a term. At 50k notes that is on the order of
  100–200 MB *(my guess: 300–500 distinct terms a note)*, and it is not in the memory table
  of §3.5, whose keyword total is already 780 of 800 MB. `FullText::doc_terms` already has
  each document's `TermId`s and the weight is in the posting. If agent-index takes my
  suggestion of counting document frequency per query, views do not need the list at all.
- **One cache writer per vault.** With the app and `quire-cli mcp` on one vault (the normal
  agent setup), both write segments for the same changed notes and replace each other's
  index file; the 10-minute orphan rule and the two-process test exist only for that. Take
  a non-blocking lock file in `.quire/cache/index/` (`File::try_lock`, as `lock_sync` does
  in `vault_sync/state.rs`): the holder writes and may delete unreferenced segments at once;
  every other process reads the cache and never writes it. Nothing ever waits. The frame's
  "nothing takes a lock for a cache" is changed to "nothing waits on a lock".
- **Measure the hand codec against a derived one in I1b.** `quire_markdown::{Link, Task,
  Stats}` do not derive serde today, so both routes need work; a hand codec is several
  hundred lines that every new field must touch. I1b should time three candidates on the
  bench vault: the hand codec, `serde_json` plus deflate, and a small binary serde format
  (a new crate, which the frame allows with a `deny.toml` review). Take the derived one if
  it meets the 0.5 s / 2.0 s row; a stale-cache bug costs more than 20% of load time.
- **I2b (passage cache and model file) is the step to cut if time runs short.** Without it
  a start refits the model once in the background (3.4 s CPU at 10k, 19.6 s at 50k in the
  scan) while keyword search is already complete. No budget row in the frame needs it. Its
  cost is real for `quire-cli mcp`, which starts often, so keep it in the plan, last.
- **One-shot CLI commands** should write the cache only when it is missing or more than a
  few percent stale, and never when another process holds the writer lock; otherwise every
  `quire-cli search` rewrites index files on exit.
- **Disk row.** Section B (sources) is justified: record and source come from the same
  segment, so ranges always match the text. If deflate does not reach a third, raising the
  frame's row to 1.2× the vault is accepted; reading notes at start is not the fix.
- **Phase 2 gap.** Between "install" and "fill", `Index::source` is `None` for cached notes.
  List what a caller shows then (a hit without a snippet), and test one.
- **Scanner fixes (I0a, I0b)** are not index work but are small, independent and visible.
  Fine here; they can merge before anything else.

## Conflicts with the frame and the other designs

1. **Frame §3 flush cadence and "no lock":** changed as in B2 and the writer lock above.
2. **Frame §5 "Caches on disk ≤ 400 MB at 50k":** may become 1.2× the vault after I1b.
3. **Sync-speed** runs `Manifest::scan` every pass; this design scans at load "only when no
   scan ran in this process yet". Both must get the same `Delta`: the manifest delivers
   each scan's changes to every subscriber, so the index does not rescan and does not miss
   what sync found. One owner for that fan-out: the `Manifest` in `quire-vault` (A2).
4. **Agent-index** needs the main index to use the compact vector layout; this design
   adopts it. It also needs a main refit forced by a lock; adopted as "tainted". Consistent.
   The only open point is B3 (ordering).
5. **Agent-tools** uses `Index::modified`; this design fills it from the manifest. Settled.
6. **Local-AI:** f16 dense vectors for a neural embedder (question 3) need that design's
   agreement; see its review.
7. **`NoteRecord::terms` as `TermId`s** changes a public field that `quire-intel` reads;
   nothing else in the round touches it.

## Simpler alternatives

- The writer lock, the derived codec and dropping the record's BM25 list (above).
- **Ship I1 without I2b**, and I2a without persisted vectors, as a first cut.
- **Do not persist LSA vectors at all, only the model** (3 MB): at load, project passages in
  the background with the cached model. It removes `p-*.seg` and its rewrite after every
  refit (70–140 MB at 50k). It costs re-tokenising passage text at start. Worth one
  measurement in I1b before I2b is built.

## Questions for the owner

1. The startup cache holds a compressed copy of the text of plain (never locked) notes
   under `.quire/cache/`. With B1 it holds only notes that still exist. *Recommendation:
   yes.*
2. Rebuild the cache only when indexing code changes, not on every update? *Recommendation:
   yes (`DERIVE_VERSION` and its golden test).*
3. 16-bit vectors for meaning search, in memory and for the built-in model's layout: a
   small change in the "by meaning" order, about half the memory. *Recommendation: yes.*
4. Refit rule: after 10% of passages changed, or when idle 10 minutes and the fit is older
   than 6 hours. *Recommendation: as proposed; revisit with the quality numbers.*
5. May the cache on disk be up to 1.2× the size of the notes if compression is weaker than
   guessed? *Recommendation: yes.*
