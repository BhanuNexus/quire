# Quire 0.10: speed budgets in CI, smaller binaries, MCP start-up

Status: done for 0.10. Owner: the 0.10 performance work (`feat/0.10-perf`).

This note records what 0.10 measures, what it changed to stay inside the
budgets of [0.9 §9](0.9.md#9-performance-budgets) and the size budget of
[0.9 §2.3](0.9.md#23-editions), and the numbers.

## 1. Speed budgets, checked on an optimised build

Until 0.10 the §9 budgets were checked in debug builds, or not at all. The
CI job `perf` (`.github/workflows/ci.yml`) now builds `quire-cli` and the
desktop app with `--profile perf` and runs `packaging/perf-check.py`.

* **`[profile.perf]`** inherits `release` (with its per-crate opt-levels,
  §2) but without LTO, with 16 codegen units and without stripping, so it
  builds in about 17 minutes from cold on the 2-core VM (less on a 4-core
  runner with the cache). Release builds are a little faster still, so a
  budget met here is met there.
* **`quire-cli bench --suite NAME[,NAME] [--runs N]`** prints JSON lines
  `{"suite", "metric", "value"}` (ms). Each value is the median of `N` runs
  in one process. Suites: `index` (parse and index 2,000 notes of ~4 KB from
  disk), `search` (BM25, 2,000 notes), `sections` (section search with the
  meaning scan), `semantic` (the meaning scan alone), `mcp` (`view` and
  `search` over 10,000 notes, as `crates/quire-mcp/tests/bench.rs`), `pdf`
  (text extraction per page: a 40-page synthetic PDF and the quire-pdf
  fixtures via `QUIRE_BENCH_PDFS`), `mcp-pdfs` (MCP server start with 200
  new PDFs, §3). `quire-cli bench vault DIR N` writes the desktop runs'
  vault: `N` notes and a 100 KB `Big.md`.
* **The desktop app with `--features bench`** (never in releases) has
  three runs, chosen with `QUIRE_BENCH`:
  `startup` (from `main` to the start of the second frame, i.e. the first
  frame is on screen), `typing` (opens `Big.md`, waits until the vault is
  indexed, then types a character a frame and times each keystroke from its
  input to the end of that frame's UI work; painting is left out because
  Xvfb's software OpenGL says nothing about a real GPU) and `canvas` (the
  1,000-card canvas drawn without a window, pan and zoom frames).
* **`packaging/perf-check.py`** runs the CLI suites once (`--runs 5`) and
  each desktop run as separate processes (`--app-runs 5`: five startups of
  each vault, three typing and canvas runs), takes medians, and **fails when
  a median is above its budget × 1.25**. The 25 % is headroom for shared CI
  runners: run-to-run noise on the 2-core VM is ±10–15 % for the CLI suites
  and up to ±25 % for the typing percentiles. It writes the table to the
  job summary and `perf.json` as an artifact.
* The checks take about 1.5 minutes after the build; the build is the rest
  (17 minutes from cold on the 2-core VM; GitHub's 4-core runners with the
  cache take less). Budget: 30 minutes (`timeout-minutes`), aiming for
  under 25.

The startup budget is "0.8 + 20 ms": 0.8 has no instrumented build, so the
job checks the part the budget is about, what a 10,000-note vault adds over
an empty one before the first frame, and caps the whole at 1.5 s.

WS-C reported the meaning scan at 212 ms over 24,000 passages in the debug
gate. Optimised it is 1.5 ms over 10,000 passages (the dot product
vectorises), well inside section search's 15 ms.

### What was over budget, and the fixes

* **Index build: 690 ms → 340–390 ms.** Every note was parsed by pulldown-cmark
  three times (`extract`, `outline`, `verbatim_ranges`) and its words were
  segmented, folded and stemmed twice (content terms and search terms), with
  two allocations a word and SipHash on every map access. Now `extract`
  collects the outline and the verbatim ranges from its own parse
  (`outline::Outliner`, `scan::Verbatim`), `fulltext::note_terms` makes both
  term maps in one pass reusing one buffer, the term maps use FxHash
  (`tokenize::FastHash`; the keys are the person's own words), and
  `is_stopword` is a `match` instead of a binary search that called
  `memcmp` seven times a word.
* **Keystroke → frame in a 10,000-note vault: p50 22 ms, p95 34 ms → p50 6 ms, p95 9–14 ms.** The
  Files tab rebuilt, sorted and laid out all 10,000 rows every frame. It now
  keeps the sorted tree until the index, the sort settings or the list of
  other files change (`SidebarState::files`), and rows out of view only take
  their space. The list of non-note files was read from disk every 5 s on
  the UI thread; with a watcher it is now cleared by the watcher's events and
  read again at most once a minute.
* **Startup with 10,000 notes: +31 ms over an empty vault → +11–14 ms.** The index load (two
  parser threads on two cores) and the folder watcher started before the
  first frame. The app now opens its startup vault with
  `Workspace::open_vault_deferred` and starts both on the second frame
  (design §9: nothing but settings is read before the first frame). Sync
  starts there too, after the watcher, so a note it changes is always
  merged into the open tabs (0.10 review, finding 6).

## 2. Smaller binaries

0.9.1 shipped at 48/84 MiB (Lite/full) against 28/68 MB in 0.8. The growth
came from 0.9's agent, MCP/HTTP (tokio, hyper, axum, rustls), PDF (hayro)
and readability/import code (dom_smoothie, html5ever, cssparser), on top of
Typst and egui.

What 0.10 changed (no feature dropped, `panic` stays `unwind`):

1. **Dependencies are optimised for size** (`[profile.release.package."*"]
   opt-level = "z"`), except those on a hot path, which stay at 3: egui,
   epaint, eframe, glow, the font and glyph crates (skrifa, read-fonts,
   vello_cpu, fearless_simd, kurbo), ropey, pulldown-cmark, nucleo, unicode
   segmentation and normalisation, memchr, aho-corasick, regex, hashbrown,
   crossbeam-channel, serde_json, similar, spellbook, strsim, hayro's
   parser and interpreter, the image decoders (image, png, zune-jpeg,
   image-webp, fdeflate, miniz_oxide, crc32fast and the deflate crate), resvg, tiny-skia,
   sha2, the sync cryptography (chacha20poly1305, argon2, blake2), and the
   AI engine's inference crates (candle, gemm, rten, ocrs, tokenizers,
   rayon). Typst, Mermaid, D-Bus (zbus), windowing, HTTP and TLS, the
   readability and import code are cold: they run once per action, not per
   frame.
2. **Our cold crates are at `opt-level = "s"`**: quire-mcp, quire-agent,
   quire-import, quire-web, quire-sync, quire-assistant, quire-ai,
   quire-plan, quire-typeset, quire-cli, and quire-app and quire-desktop.
   What a frame runs is mostly egui and the editor crates (quire-text,
   quire-markdown, quire-index, quire-intel, quire-canvas, quire-pdf, all
   still at 3); the perf job checks the typing and canvas budgets with
   these settings.
3. **The fonts were in the full edition twice** (2.3 MB). quire-typeset
   and the desktop both embedded Inter, JetBrains Mono and STIX Two Math as
   `const` byte strings, which Rust copies into every crate that uses them.
   They are `static` now, and the full edition's desktop takes them from
   quire-typeset.
4. **Identical code folding** (`-C link-arg=-Wl,--icf=all`, set in
   `packaging/linux/package.sh`): the linker keeps one copy of functions
   that compiled to the same machine code. About 1 MiB per binary. (Windows'
   linker does this by default; macOS's doesn't offer it.)
5. **axum without the defaults nothing uses** (`tracing`, `tower-log`,
   `matched-path`, `original-uri`).

Tried and not kept: fat LTO (the two final links ran out of memory with
7 GB, and it would have added several minutes per release job); DT_RELR
packed relocations (would shave 3–5 MB but needs glibc 2.36, and the Linux
builds support 2.35); a non-PIE executable (no ASLR).

The cost: Typst is size-optimised, so math, diagrams and PDF export are
slower: exporting a note with 80 formulas and 5 Mermaid diagrams to PDF
took 135 ms and takes 185 ms (same output). They run off the UI thread
and once per change, not per frame. Release builds take about the same
time (thin LTO and one codegen unit as before; "z" code compiles a little
faster): 18 minutes for the full edition's desktop and CLI on the 2-core
VM.

## 3. MCP server start-up with many PDFs

`quire-cli mcp` and `serve` read every PDF's text when the server started
(cached afterwards), so a vault with hundreds of new PDFs kept agents
waiting. Now `Server::with_config` starts a background pass
(`quire_app::pdf_state::index_pdfs_in_background`, thread `pdf-text`) and
answers at once; PDF pages become searchable as they are read. While the
pass runs, `search` with `filters.kind` `attachments` or `all` adds
`indexing: {done, total}` to its structured result and a sentence to its
text ("Quire is still reading the vault's PDFs (12 of 200 read): PDF pages
may be missing."); notes-only searches are complete and say nothing.
`Server::pdf_indexing()` and `Server::wait_for_pdfs(timeout)` expose the
same to the CLI and tests.

With 200 new two-page PDFs: the first answer comes 1.5 ms after the
server starts (before, it came only after all of them were read, about
2 s); all 200 are searchable after 2.1 s. `crates/quire-mcp/tests/pdf_search.rs` checks the behaviour with 200
small PDFs.

## 4. Known limits

* The typing run measures the UI work of a frame, not painting: Xvfb's
  software OpenGL doesn't stand for a GPU.
* On two cores, typing while a 10,000-note vault is first indexed is slower
  (p50 6–10 ms): the index threads take turns with the UI. They don't run
  at a lower priority yet (that needs a platform call the code base doesn't
  make without `unsafe`).
* The Insights panel lays out every heading and outgoing link of the open
  note each frame; for the 100 KB test note (about 1,000 rows) that is
  about half of a keystroke's UI time. Laying out only the rows in view
  would take typing p50 from 6 ms to about 3 ms; it is left for the
  parallel 0.10 work that is changing that panel.
* The size table is Linux only; macOS and Windows get the same opt-levels
  and font fix (Windows also folds identical code), but CI checks size on
  Linux.
