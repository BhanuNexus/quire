# 0.14 codebase health: front matter and lints

Part of the 0.14 codebase-health pass (plan items 1, 3, 8, 9 and 20; defects
D1, D4, D5 and D7). No new features: behaviour changes only where a defect
is fixed, and each one is listed below.

## 1. One rule for where front matter ends

### The rule

`quire_markdown::frontmatter::fences(src) -> Option<Fences>` is the only
code that decides where front matter is. The rule is the reader's
(`frontmatter::parse`) as it was at 3f33a14, unchanged:

- **Opens** only when the file's first line is exactly `---` followed by
  `\n` or `\r\n`. A byte-order mark, a space or a blank line before it, or
  `---  ` (trailing spaces), means the note has no front matter.
- **Closes** at the first later line that is `---` or `...` once its line
  break and trailing white space (Rust's `str::trim_end`, so a tab or an
  NBSP too) are taken off. `  ---` (indented), `----` and `--- x` do not
  close it. The closing line may be the last line, without a line break.
- **Unclosed:** no closing line means no front matter; the whole file is
  body.
- `Fences { open, close, nl }` gives the opening and closing lines (with
  their line breaks) and the opener's line break, which writers use.
  `is_opening_line` and `is_closing_line` are the same tests for code that
  reads one line at a time (the spell checker).

Why the reader's rule and not a wider one (BOM, `---  `): every writer
(`set_field`, `remove_field`, …), the index and the properties panel
already work from the reader, so widening it would change what Quire reads
from real notes, a feature change. Narrowing the outliers to it changes
only what was already inconsistent.

### The differential test

`crates/quire-markdown/tests/fences.rs` runs 28 notes
(`tests/fences/cases.rs`: the research's 13, and BOM with CRLF, a tab or
NBSP after the closer, indented and `--- x` lines, a `...` closer at EOF,
lone CR line breaks, a blank first line, a `...` opener, an empty file, the
D1 skill, …) through the seven finders as they were at 3f33a14, and records
each one's answer. The reader and the editor's block scan run live; the
other five were private to their crates, so the test keeps a copy of each
as it was. On 3f33a14 they disagreed on 17 of the 28 cases. A second test
checks that `fences` gives exactly the 3f33a14 reader's answer on every
case and that the live finders in quire-markdown agree with it. The spell
checker's own test runs the same cases through its line-by-line scan.

pulldown-cmark's metadata block (the editor's colours, `extract`) is a
separate parser and is shown in the table for comparison only. It differs
from the rule on six of the cases: it opens on `---  ` and after a blank
first line, and it finds no front matter when the closer has a tab or an
NBSP after it, or when the block is empty (closed by `---` or `...`). Changing what the editor colours was out of
scope; the linter already guards the `---  ` case (below).

### Finders: 7 → 1

| Was | Now | Changed for a real note |
|---|---|---|
| `frontmatter::parse_doc` | `fences` | no |
| `blocks::verbatim_blocks` | `fences` | no |
| `linter::front::locate` | `fences` | a `---  ` opener is no longer located (see below) |
| `quire-index` `derived::body_start` | `fences` | no |
| `quire-spell` `LineContext::advance` | `is_opening_line`, `is_closing_line`, `LineContext::for_document` | BOM and `---  ` openers, unclosed blocks (see below) |

What changes, per caller:

- **Linter.** It used to locate a `---  ` opener and then report the block
  unreadable. It now does not locate it, and to keep the bytes as they were
  it still refuses to add a "date modified" block above such a note. The
  note it shows changes from "can't be read; left alone" to "isn't valid
  YAML; left alone". The trailing-spaces rule still leaves a `---  ` first
  line alone, because trimming it would turn the lines below into front
  matter. Text is unchanged in every case.
- **Spell checker.** `Speller::check_document` and a `LineContext` made with
  the new `LineContext::for_document(text)` now check the lines of a note
  that opens with a BOM and `---` or with `---  ` (no front matter for the
  reader), and no longer skip the rest of a note whose `---` block never
  closes. The desktop app, the only app caller, checks one line at a time
  and skips the lines the editor colours as front matter, so nothing a
  person sees changes. quire-spell now depends on quire-markdown directly.
- **Agent contracts.** `max_bytes` and `must_link_to_source` now measure the
  body after the closing line for notes closed with `...`, with `----` or
  `--- x` inside, closed with `---` and trailing white space, or empty.
  Before, the body started after a later `---` rule, inside the front
  matter, part-way through the closing line, or was the whole note.

Left alone, deliberately: `linter/mod.rs` and `linter/rules.rs` test
whether the first line *looks like* a fence (`trim_end() == "---"`) to
protect `---  ` lines; that is a guard, not a finder. `fields.rs` works
inside a block it is given. `quire-import/src/bear.rs` checks
`starts_with("---\n")` on importer output.

## 2. D1: an imported skill could read as trusted

Two halves, both fixed:

- **Writer** (`quire-cli skill install --from`, `mark_untrusted`). It
  stripped `trust:` lines only up to the next `---` line, so with a `...`
  closer it kept the skill's own `trust: trusted`. It now removes every
  `trust` field the reader sees, in any case and however written (quoted
  key, block value), with `frontmatter::remove_field`, then puts
  `trust: untrusted` first in the block `fences` finds. A note without
  front matter (or with an unclosed block) gets a new block on top.
- **Reader** (`AgentStore::trust_of`). `frontmatter::parse` keeps the last
  of two fields with the same key. Front matter can only lower trust, so
  the store now reads every top-level field (`frontmatter::fields_in_order`)
  and marks the note untrusted if any `trust` field, in any case, says
  `untrusted` as text or as a list item.

Tests: duplicate keys, `Trust:`, `trust: [untrusted]`, a `...` closer with
a `---` rule in the body, CRLF, a quoted key with a block value, an
unclosed block, and a `...`-closed skill installed and then copied without
its `SKILL.source.json` (CLI test, through the real store).

## 3. D5: a value's leading space was lost

`yaml_scalar` trimmed the value, so `set_field(src, "a", Str(" A"))` wrote
`a: A`. It no longer trims: a value that starts or ends with white space is
double-quoted (`a: " A"`), so it reads back as given. Values without edge
white space are written exactly as before. Every writer that goes through
`yaml_scalar` (importers, MCP capture, tasks, the properties panel) now
keeps such white space instead of dropping it.

`crates/quire-markdown/tests/props.rs` holds the property tests from
`tests.md`, adapted: values now include leading and trailing spaces (the
D5 case), and the tidy property asserts idempotence only. Whether a tidy
rule needed the safety net is not asserted, because `trailing-spaces` gives
up on a code span that crosses a line (`tests.md` finding 1; the note is
still safe, the net works). Fixing that rule is not part of this pass.
The committed `props.proptest-regressions` holds the D5 seed found before
the fix, so it replays on every run.

**`proptest` as a dev-dependency.** Hand-written seeded generators exist in
19 files, but they do not shrink a failure or save it, and the D5 case was
missed by them and found by proptest at 30,000 cases. proptest is a
dev-dependency of quire-markdown only, so nothing ships with it. With
default features off (`features = ["std"]`, no `fork` or `timeout`) it adds
three crates to the lock (proptest, rand_xorshift, unarray); the rest it
uses is already in the tree. `cargo deny check` passes. 256 cases a
property take about 0.15 s; all four pass at 30,000.

## 4. D4: template answers in hash order

`templates::with_defaults` merged prompt answers case-insensitively while
iterating a `HashMap`, so with answers for both `Name` and `name` the one
used depended on hash order. It now builds a `BTreeMap`: an answer written
exactly as the prompt's key wins; otherwise the first matching key in byte
order (`NAME`, then `Name`, then `name`); an answer matching no prompt is
kept under its own key. quire-app's lookup for prompts left in a note
took the first case-insensitive match in hash order too; both now use
`templates::answer_for`. Only answers that differ just in case are
affected: the prompt dialog gives one per prompt, but a template action
written in a note can hold both. The test runs the same answers through
64 fresh maps (each with its own hash seed).

A clean `clippy -D warnings` (full and Lite) means no site is left without
a fix or an `expect`.

**Suppressions by kind** (attribute lines in `.rs` files): `allow` 58 → 47,
`expect` 37 → 114. The 47 `allow`s left are the one header of each
integration-test file; there is no `#[allow]` or `cfg_attr(…, allow)` left.

**Test-file headers.** 26 files said `#![allow(clippy::unwrap_used, reason
= "test code")]` in three wordings, two said `#![expect(…)]`, 19 said
nothing. All 47 now start with the same header, allowing `unwrap_used`,
`panic` and `tests_outside_test_module`: an integration test's `#[test]`s
are never inside a `#[cfg(test)]` module, and clippy.toml's
`allow-*-in-tests` options cover `#[test]` functions but not helpers.
`allow`, not `expect`, so a file that doesn't unwrap does not fail.

**`panic`.** With a scratch clippy.toml that adds `allow-panic-in-tests =
true` and `allow-dbg-in-tests = true` (passed with `CLIPPY_CONF_DIR`; the
repository's file is unchanged), `clippy -W clippy::panic -D warnings`
passes on this branch: no `panic!` outside tests, and the 8 in test helpers
are covered by the header. Turning it on is one line in `[workspace.lints]`
once clippy.toml has those two options.

**Symlinks (`filetype_is_file`).** A `DirEntry`'s type does not follow a
link, so today the vault listing (`Storage::walk`), `list_under`, the
watcher's scan and sync's shared-files listing all skip a symlinked note
or folder, the same way. That stays: following a link could read (and
sync) a file outside the vault, and a link inside it would make one file
two notes. The lint's suggestion, `!is_dir()`, would also take FIFOs and
sockets, and reading a FIFO blocks. The temp-file sweep removes only plain
files.

**D7: `eprintln!` in the desktop app.** Two now reach the person: an
unreadable settings file is a warning notice at start
(`Settings::load_reporting`; the CLI still prints it), and an embedding
cache that can't be saved is shown in Settings → AI
(`SemanticIndex::cache_problem`). Three stay on stderr as log lines, with
the reason in their `expect`: the two `QUIRE_TRACE` timing lines, and the
drawing editor's last-resort write in `Drop`, which runs only when no
workspace is left to show a notice.

**`print_stderr` "in the engine's protocol module".** The engine's
protocol code writes through its own handles and has no `print!`, so it
needs no `expect`; only `--version` (`handle_args`) prints.

## 6. Always-on feature flags (item 20)

Deleted: `quire-app`'s `remote-llm`, `keychain` and `update-check`, the
desktop app's no-op `remote-llm`, and `quire-mcp`'s `http`, with their
never-built `cfg(not(…))` branches (the "this build has no network
providers" and "made without the update check" stubs, and the voice
transcription stub). Their dependencies (`keyring`, `ureq`, axum, tokio,
futures-core) are now plain dependencies of the same crates; `Cargo.lock`
is unchanged. Both editions build the same code as before, because both
apps always turned all of them on.

Kept: `quire-intel`'s `remote-llm`. No shipped binary builds quire-intel
without it (quire-app and quire-assistant turn it on), but quire-agent
depends on quire-intel without network code, and keeping the feature keeps
that true. Its comments now say so instead of "no network code ships unless
asked for". `quire-sync`'s `http` and `remote` are kept (the sync server
builds sync without `remote`).

The desktop's "Build with --features remote-llm and set ANTHROPIC_API_KEY"
hint, shown when generative help fails, was wrong in every build; it now
says "Pick a provider in Settings → AI for generative help."

The release workflow and packaging scripts name none of the deleted
features. `ARCHITECTURE.md` §quire-intel still says "Default build ships no
network code"; that file belongs to the docs team.
