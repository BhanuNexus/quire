# Review: 0.14 agent tools (`0.14-agent-tools.md`)

Status: proposed (0.14, awaiting owner approval)
Area: architecture review
Code: `crates/quire-mcp/src/tools/`, `crates/quire-agent/src/store.rs`

Reviewer: the 0.14 architect. Read against `0.14-architecture.md` and the code at main ad3216d.

## Verdict: approve with changes

The note is careful, its inventory matches the registry, and the split "listed" versus
"callable" is the right way to think about deprecation. `Visibility` as specified is the
type the frame asks for. Three things must change before it is built: two are visibility
holes the fast path opens, one is a claim about the adapters that the code contradicts.

## Blocking issues

**B1. A folder locked while the server runs stays visible until something rebuilds
`Visibility`.** Today `candidates` (`quire-agent/src/store.rs`) calls `lock::folder_of` on
every answer, so a folder locked by the desktop app is hidden from a running `quire-cli mcp`
or `serve` on the next call. The design caches the locked-folder list under a key that
contains the list itself (§3.5 "cached with the key (policy stamp, approvals generation,
locked-folder list)") and takes the list from the manifest. Nothing says when another
process's lock is noticed. Until the index drops the records, `list`, `tags`, `tasks` and
`properties` return titles, tags and task text of notes the person has just locked. That is
a regression against `docs/design/0.11-secure.md`.
*Fix:* per call, re-check the locked set without touching notes: one `exists` for
`lock::KEY_FILE` and `lock::UNLOCKING_FILE` per distinct folder that holds indexed notes
(40 folders: 80 calls, microseconds each when cached by the OS), or a directory-mtime check
per folder. Change G4 from "at most 8 calls in total" to "0 per note, at most 2 per distinct
folder". Add the test: lock a folder through a second `Vault` handle, call `list` at once,
nothing from the folder comes back. Do not rely on the watcher for this.

**B2. "A path from the index is a regular file" is assumed, not enforced.** §3.5 point 5
drops `resolve_in` for index paths because `LocalFs::walk` and the watcher skip symlinks.
But `IndexMsg::Upsert` takes any path from any caller (a save of a note the person opened
through a symlinked folder, a job). Today `effective` resolves it and applies the rules of
the real target (outside the vault or in a hidden folder: denied). With `allows` it passes
by prefix.
*Fix:* make it true in one place. Either `run` in `quire-index/src/actor.rs` refuses an
upsert whose path is not in the manifest's listing (the manifest only has regular files
under regular folders), or the listing tools test `visibility.allows(p) && manifest.has(p)`
(a hash lookup, no filesystem call). Add the property-test case: a note reachable only
through a symlinked folder is upserted; no listing tool returns it.

**B3. `search_notes` is not `search` with another renderer.** Table §3.4.1 says "none" for
differences. In the code `search_notes` ranks notes with `hybrid_search_where`
(`tools/legacy.rs`) and `search` ranks sections with `search_sections_where`
(`tools/read/search.rs`). An adapter changes which notes come back and in what order, so G7
("same results as 0.8 for the same arguments") cannot hold for it, and `backlinks` through
`neighbors` gains a 200-row cap it does not have today.
*Fix:* say so, and choose per tool. My recommendation: adapters for the seven that really are
the same operation (`read_note`, `list_notes`, `list_tags`, `ask_notes`, `create_note`,
`append_to_note`, `backlinks` with the cap stated); for `search_notes` either accept the new
ranking and reword G7 to "same shape, same visibility, ranking may differ", or keep its own
handler. Check the 0.8 read fixture before deciding: if it pins search hits, the adapter
fails `answers_0_8_clients_as_0_8_did`. I prefer the adapter with the reworded goal, because
it leaves agent-index one keyword-and-meaning path fewer to make view-aware.

**B4. The view predicate needs tags.** §3.5 keeps tag allow lists out of the fingerprint
and filters by the record's tags (`allows_with_tags`). That is sound, but then the handle
`quire-index` receives cannot be a path predicate (the frame's wording, and `Keep` today).
*Fix:* define it here as `Fn(&NotePath, &[String]) -> bool` (path and the record's tags)
and have `quire-index` call it with the record. The frame is corrected to match. A
tag-limited client's view is then rebuilt like any other when a note's tags change.
*Update:* the note's later revision adds `Visibility::predicate` with this type and a
fingerprint over read answers only. Resolved.

**B5. A building view must not report `indexing`.** §3.9 still says "a caller whose view is
still building sees `indexing` in the result". `0.14-agent-index.md` (question 2) shows that
this message appears only for restricted views, so it tells the agent that notes are hidden.
*Fix:* drop the sentence; a restricted view answers by keyword, silently, until its model
is ready. Also drop "the closure form stays until a view is fitted" if any trace remains:
the closure form ranks with whole-vault statistics.

## Non-blocking changes

- **`NoteRecord.mtime_ns` (step 5) is not needed.** `Index::modified(p)` and `set_modified`
  already keep "the file's time at load, the time of an update after" (`quire-index/src/index.rs`);
  `list.rs` ignores it and calls `Storage::modified`. Use it. This removes the dependency on
  index-startup and step 5 shrinks to a one-line change inside step 2.
- **Times.** Ten-digit integers are Unix seconds, the commonest thing an agent sends. Keep
  refusing them (guessing is worse), but make the message name it: "looks like Unix seconds;
  send milliseconds, a date, or 7d".
- **`tags` keyset on (count desc, tag).** Counts change between pages, so rows can repeat.
  Sort the cursor order by tag name and return counts as data, or say that `tags` pages may
  repeat. `total` on every list costs a full filter pass per page: fine at the G5 budgets,
  but measure `tasks` at 50k (200k tasks) before promising it.
- **Clamping.** `limit` above the maximum is clamped, not refused, and the result says
  `truncated`. Say this once in `docs/agents.md`.
- **G2.** 41,315 − 3,045 = 38,270 bytes before roughly 30 new schema properties. 40,000 is
  tight; set the budget after step 3 from the measured size plus 5%.
- **"Callable but not listed" is removal for many clients.** Most MCP hosts only let the
  model call listed tools. Say in the changelog that prompts naming the old tools must
  switch on modern clients; scripts that call the server directly keep working.

## Conflicts with the frame and the other designs

1. **Listing in 0.14 (frame §7 rule 5).** The design unlists the nine for modern-era clients
   in 0.14. I accept this as better than my rule, subject to the owner (question 1 below).
   Old eras keep the frame's behaviour.
2. **"Unchanged on the wire".** Bounding `read_note`, `list_notes`, `list_tags` is right;
   an unbounded adapter would be worse. The frame's rule becomes "unchanged except bounds
   and the notice".
3. **Aliases last as long as the names**, not a fixed window: accepted.
4. **Agent-index** takes `Visibility`, its fingerprint and the predicate of B4 from here.
   It must not start before step 2 lands. Step 8 (`RANKED` removed) belongs to agent-index's
   last step, not to this plan.
5. **Index-startup**: no dependency once `Index::modified` is used.
6. **jiff migration**: the note already flags `parse_time`; land step 4 first.

## Simpler alternatives the design missed

- `Index::modified` instead of a new record field (above).
- `ToolSpec.deprecated` plus bounds on the existing legacy handlers would deliver everything
  users see without rewriting nine handlers. The adapters are worth it only for the reason
  in B3 (one search path). If step 6 runs late, ship the flag and the bounds and move the
  adapters to 0.15: nothing user-visible is lost.
- `str_replace` with `all: true` is a new capability in a release that has none. It is small
  and it is the only way to retire `replace_in_note`; fine, but it is the owner's call.

## Questions for the owner

1. Stop listing the nine old tool names to modern clients in 0.14 (design) or keep listing
   them with "Deprecated" (frame)? *Recommendation: the design's version.* Removal: not
   before 1.0.
2. Add `all: true` to `str_replace` so `replace_in_note` can go, dropping its regex form?
   *Recommendation: yes.*
3. Tag allow lists read tags from the index (a fraction of a second stale after an outside
   edit)? *Recommendation: accept; `view` still checks the file.*
4. Lower the `tasks` and `query_view` maximum from 1,000 to 500 rows, with a cursor?
   *Recommendation: yes.*
