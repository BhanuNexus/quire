# Quire 0.13.2: sync safety

The sync team's part of the 0.13.2 data-safety release. No features. Items
are from the reliability scan (`opt-scan/reliability.md`, outside the
repository): #1, #3, and the sync parts of #14. Each was confirmed before
it was changed; how is said under each.

Code: `crates/quire-sync/src/{engine,names,fsx,folder}.rs`,
`crates/quire-app/src/vault_sync.rs`, and two small additions to
`quire-cli sync` (below). Tests: `crates/quire-sync/tests/{convergence,folder_sync}.rs`,
`crates/quire-sync/src/{names,fsx}.rs`, and the `vault_sync` tests.

## 1. A failed listing could send a delete for every note (#1, large)

**Real.** Confirmed with a test before changing anything
(`vault_sync::tests::a_vault_that_cant_be_listed_sends_no_deletes`, first
written against 0.13.1): a vault folder renamed away under a running
`VaultStore` gave an empty listing (`storage().list().unwrap_or_default()`),
the pass succeeded, and the other device moved all three notes to its
trash. A missing or unreadable subfolder fails `LocalFs::walk` the same way.

What changed:

* **A listing error stops the pass.** `LocalStore::list` returns
  `Result`. `Engine::sync` lists once before anything else, so a folder that
  can't be read is neither read as empty nor written into (a pull into a
  vanished USB drive's mount point would have recreated folders on the
  system disk); `push` lists again and fails the same way. The new
  `SyncError::List` says, in words, that nothing was sent and that sync goes
  on once the folder can be read; the app shows it as the sync status
  ("Needs attention"), and `VaultStore` reports the vault's folder and its
  settings folder (`.quire/shared/`, which also skipped unreadable folders
  silently) the same way. A settings subfolder that is *gone* is still
  just empty.
* **A delete is checked once more before it is sent.** A tracked note that
  isn't listed and wasn't renamed is sent as deleted only if
  `LocalStore::missing` says it isn't there. `VaultStore` answers that from
  the storage: only "not found" counts, so a file that exists but can't be
  read for a moment (a lock, a permission, a cloud placeholder) keeps its
  note, and its delete isn't sent. Nor is a note iCloud evicted to a
  hidden `.Name.md.icloud` stub beside it (macOS 13 and older, "Optimise
  Mac Storage"), nor one tracked under a name this computer can't store
  (a vault copied here from another system: "not found" means nothing for
  it; it is kept as skipped and reported once, see §2).
* **Deleting most of a vault at once waits for the person.** The deletes of
  a pass are worked out first and added to those this device sent in the
  hour before now (`DELETE_WINDOW_MS`, sliding: the sync state keeps one
  `{at, held, sent}` per pass that sent deletes in that hour as
  `deletes_sent`, at most 64, the oldest folded together so the count never
  shrinks). A time after now (the clock was set back) counts as now, so
  setting a clock back never starts the hour again; setting it far forward
  does end it early. When the total is more than
  `MANY_DELETES` (10) **and** more than half of the most notes this device
  held in that hour, the pass sends nothing (no edits either) and fails
  with `SyncError::ManyDeletes`, which lists the notes. Why this rule: an
  empty or vanished folder (a drive's mount point with the drive gone, a
  cloud folder signed out, the case a listing error can't catch because the
  folder is there and empty) looks exactly like "every note deleted", and a
  person rarely deletes most of a vault in one go; the floor of 10 keeps
  small vaults and ordinary cleanups from ever asking. Why an hour: a
  folder that empties gradually (a cloud client removing files, a sync
  client or a failing drive) does so within minutes, over passes a minute
  or two apart, and a 400-note vault disappearing in halves now stops at
  the second pass; a person tidying up for longer is asked at most once an
  hour.
  * Not counted (sent like any delete, after the same checks): app data
    under `.quire/` (vault settings and review history, which the agent
    prunes by itself after 30 days), and a note whose plain file was
    replaced by its encrypted one, or the other way round: locking a
    folder, unlocking it for good (`.qenc` sibling, or a plain file in a
    folder locked here; `LocalStore::counts_as_delete`).
  * **Vault settings** have a small rule of their own: more than one file
    under `.quire/shared/` outside the agent's review history
    (`.quire/shared/agent/`) deleted in one pass asks the same way
    (`MANY_SETTINGS_DELETES`, `SyncError::SettingsDeletes`). Evidence: the
    app itself deletes at most one such file at a time (the
    locked-folders record when the last locked folder goes; it never
    deletes `vault.toml`, `agent-policy.toml` or the review logs), while a
    `.quire/shared/` deleted to "reset" settings would delete every vault
    setting on every device. The review history stays uncounted, so the
    agent's pruning never stops the lane (D-M2).
  * **What it still doesn't catch:** a part of the vault that is less than
    half of it (a 400-note folder of a 1000-note vault unmounted or made
    online-only sends 400 deletes), a vault that empties more slowly than
    half per hour, and deletes sent by a 0.13.1 device. They go to the
    other devices' trash.
  * **The way on.** The app shows it in Settings → Sync (the status bar's
    sync label opens it): how many notes would be deleted on the other
    devices and that nothing was sent, *Show which notes*, and *Send these
    deletes* (`Workspace::sync_allow_deletes`). `quire-cli sync
    allow-deletes <vault>` does the same, mentioned only as an
    alternative: it prints how many and the first 10 paths (`--list`: all)
    and asks on a terminal (`--yes` otherwise). Either way the approval
    names the set that was shown (its count and a digest of the note ids,
    `HeldDeletes::id`); if the held set changed meanwhile (more went
    missing), it is refused, nothing is sent, and the new list shows. The
    15 minutes are this computer's clock: setting it back lengthens them,
    but they still cover only the notes shown. The held deletes are kept in `.quire/sync/held-deletes.json`
    (file ids and paths); allowing them sets an expiry 15 minutes out. A
    pass then sends them only if every delete it counts is among those, and
    only before the expiry; a different set (more notes went missing) is
    asked again from scratch, and the file goes once a pass succeeds. If
    the deletes weren't meant, putting the folder back is enough. Nothing
    here is touched meanwhile: the pull only takes other devices' changes
    in.
* **Receiving side.** Checked, and safe by construction: the engine deletes
  a note here only for a delete revision another device sent (or a file
  that is exactly an old version of a note that moved, which is in the
  history). An empty, vanished or unreachable server, sync folder, S3 or
  WebDAV store yields no revisions or an error, never a delete. Tests:
  `an_empty_or_unreachable_server_deletes_nothing_here` (convergence) and
  `a_sync_folder_that_vanished_or_emptied_deletes_nothing_here`
  (folder_sync). Not added: a guard on *applying* many deletes from
  another device. A 0.13.1 device that hits #1 can still send them; they
  go to the trash here, and that device sends the notes back on its next
  good pass (as before). Worth considering for 0.14.
* **The `unwrap_or_default()` / `.ok()` on listings and reads in the sync
  paths**, checked one by one: `VaultStore::list` and `shared_files` (fixed
  above); `VaultStore::unselected` (used to tell a move out of the selection from a
  delete: when it fails, no delete is sent that pass); attachment sizes and shared-file
  reads that drop a file from the listing (now covered by `missing`); the
  folder transport's scan (`read_dir` of `devices/`, and of each device:
  an error reads as "no lines yet", which delivers nothing and deletes
  nothing); `own_len`, `load_seen` and the remote mirror's `progress`
  (device-local bookkeeping; a damaged one only makes a check lenient or
  re-reads); S3/WebDAV `list().unwrap_or_default()` in compaction's
  clean-up (deletes less, never more). None of the others can turn into a
  delete.

Left to the storage team (their lane, `quire-vault`): `LocalFs::walk`
skipping a subfolder that vanished mid-walk. With that, a folder deleted
by another program during the walk lists as gone rather than failing the
pass, and its notes are then deleted normally, subject to the checks
above. The vault root itself vanishing must stay an error there.

## 2. A name this computer can't store stopped all sync on it (#3, large)

**Real.** Confirmed with a test against the 0.13.1 engine (a store that
refuses `:` as Windows does): every pass failed at the revision of
`10:30 meeting.md`, the cursor never moved, and the Windows device's own
edit of another note never left it. Read and traced, not run on Windows:
on a disk that ignores capitals, `local.read("plan.md")` returns
`Plan.md`'s text, `protect_unsynced` copies it aside, and the
compare-and-swap write then fails ("it changed while syncing"), once more
every pass.

What changed: **one such note never blocks the rest.**

* `LocalStore::unstorable(path, own)` says why a note can't be stored here.
  The engine asks it before applying any revision that writes a note
  (`Engine::apply_or_skip`): when it can't, the revision is **skipped on
  this device**. What the device has of the note stays exactly as it was,
  the cursor moves on, the other notes are applied and this device's own
  changes are pushed.
* Skipped revisions are kept in the engine state (`SyncState::skipped`,
  `docs/formats/sync-protocol.md`). A skipped note is never pushed from
  this device: not as deleted (it isn't here) and not under its old name
  (a note renamed elsewhere to a name this computer refuses stays here
  under its old name, untouched; sending it would rename it back for
  everyone). Its local edits wait meanwhile.
* **Retried**: each pass, a skipped note whose name can be stored now (the
  file in the way was renamed or deleted) is fetched from its history and
  applied; a newer revision (renamed on another device to a name this
  computer takes) is applied as usual, with a three-way merge from what
  this device last had.
* **Told once**: `Report::skipped` lists a note the first time it is
  skipped (again only if its name or the reason changes). The app shows a
  notice ("“10:30 meeting.md” from another device can't be stored on this
  computer: Windows doesn't allow “:” in a name. It stays on your other
  devices and the rest keeps syncing; rename it there to get it here.");
  `quire-cli sync once`, `watch` and `serve --sync` print it.
* No renaming scheme: other devices see nothing change. Renaming to a safe
  local name (as the scan suggested) would need the push side to tell a
  local alias from a rename; a correct skip was enough for 0.13.2.

The rules are pure functions in `quire_sync::names`, tested on every
system: `windows_problem` (`< > : " \ | ? *`, control characters, a
trailing dot or space in any part of the path, `CON PRN AUX NUL COM1–9
LPT1–9` (and `COM¹²³`) with or without an extension, more than 255 UTF-16
units in one part), `unix_problem` (a NUL, more than 255 bytes in one part,
which a long CJK name from Windows can hit on Linux), `problem_here`, and
`fold_case` / `same_ignoring_case` for names that differ only in capitals.
`VaultStore` uses `problem_here`, and on a disk that ignores capitals (found
out once: `.quire` is found as `.QUIRE` too) looks the folded name up among
the files listed at the start of the pass and written since. A note's own
old file never counts (a rename that changes only capitals still works).
Platform tests: `names::tests::this_windows_refuses_what_the_rules_say`
(`#[cfg(windows)]`) and `vault_sync::tests::this_disk_refuses_what_sync_skips`
(`#[cfg(any(windows, target_os = "macos"))]`, the real `VaultStore` on the
runner's disk). Neither ran here (Linux only).

Also: conflict copies are named after the other device; a device name with
`* ? " < > |` now gives a name every system can store (only `/ \ :` were
replaced before).

Other equivalences a disk applies (Unicode forms on APFS, `é` written two
ways; Greek final sigma): `VaultStore::unstorable` also skips a note whose
name opens a file here that its folder doesn't list under exactly that
name, so such a pair is skipped and reported like a case clash instead of
falling into the copy-every-pass loop (review D-L3). Not run on macOS here.

Not done: names that a Linux device can't store on an NTFS, exFAT or SMB
mount (the vault on such a disk) still fail the write and stop the pass, as
before, since nothing tells a Linux process what the mount refuses. A
folder renamed elsewhere only in capitals (`notes/` → `Notes/`) reaching a
disk that ignores capitals is written into the existing folder, and the
next listing sends the old capitals back, undoing the rename everywhere;
no text is lost (review D-L3, documented, not fixed).

## 3. Sync state files (#14, small; the sync parts)

All four were real (read, then tested where a test could show it):

* **State saved without fsync, its result ignored.** `save_state_named` now
  uses `quire_app::atomic::write` (random temporary name, `create_new`,
  fsync, rename). A failed save makes the pass's status an error ("Couldn't
  save what sync did in … Your notes are fine; sync tries again.") instead
  of nothing.
* **An unreadable state file silently reset.** `open_state_named`: a damaged
  file is copied to `state.json.unreadable` (the app's convention,
  `atomic::keep_unreadable`), sync starts afresh, and the person gets a
  notice once (what that means: nothing deleted, differing notes kept as
  copies). A file that can't be *read* (permission, disk error) is an error
  instead: starting afresh over it would forget what was synced. Read-only
  looks at the state (`sync status`, history) still use the lenient loader.
* **Folder sync writes with no fsync and a fixed `.tmp` name in the shared
  folder.** `quire-sync` gets a small private helper, `fsx::write_atomically`
  (random hidden temporary name, `create_new`, fsync of the file, rename,
  fsync of the folder on Unix), used for every small file the folder
  transport writes: `space.json`, key and device records, snapshot parts
  and manifests, and `folder-own.json`. Two counters in this device's
  `.quire/sync/` that are written for every revision (`folder-seq`) or
  pass (`snapshots-seen.json`) get the random name but no flush
  (`fsx::write_quickly`), as before: flushing them too made the folder
  sync test suite about twice as slow, and both were already allowed to
  lag. Two devices writing `space.json`
  at once no longer write into one `space.tmp`. **A shared helper should
  replace both this and `quire_app::atomic::write`** once one crate both can
  depend on holds it. The S3/WebDAV mirror's own `write_atomically` already
  fsyncs and writes only in this device's private mirror; left as is.
* **`note_own` dropped its write error.** It now returns it, and `append`
  stops before writing the line: a line written but not noted would make
  the next scan say "Another computer is syncing as this one". Test:
  `a_line_whose_length_cant_be_noted_is_not_written` (folder_sync).

Settings written whole by each window (#14's last point) is not sync's and
was left to its owner.

## 4. Checked, not changed: a restored device, a wrong clock

**A device restored from a backup** (notes and `.quire/sync/` from the
same moment): its state is older than the server, so the next pass pulls
everything since; notes unchanged since the backup take the newer
versions, notes deleted meanwhile go to its trash, new ones arrive. In a
sync folder its own log is longer than its restored `folder-own.json`
says, so it stops with "Another computer is syncing as this one" and the
documented way out. Nothing is lost on other devices.

**Risky case, reported not fixed:** notes restored *without* the state
(only the Markdown files, over a current `.quire/sync/`). Each note
restored to an older text differs from the last synced text, so it is
pushed as an edit and every device takes the older text. The newer text
is not lost (it's in the sync history and in each device's version
history), but nothing tells the person. Notes created after the backup are
missing and are sent as deleted; the new many-deletes check stops that
when they are many. A fix would need to notice "local text equals an
older synced version of this note" before pushing; worth a look for 0.14.

**A wrong clock** doesn't decide which version wins anywhere: a server
orders by its log, a folder by the smallest revision id (`folder.rs`
head rule), and snapshots settle only after a week *and* 72 passes ten
minutes apart. What the clock does affect: compaction keeps every
revision written in the last 90 days by the *writer's* clock, judged by the
*compacting* device's clock, so a device whose clock is far ahead (or
revisions from one far behind) loses older versions from "All devices"
history earlier than 90 days. The current text, the newest 10 versions of
each note and any unmerged tie are always kept, so no current text is
lost. Version timestamps and conflict copy dates follow the writing
device's clock. S3 refuses requests from a clock that is far off (already
reported as a clock-skew error).

## 5. Second round: the 0.13.2 data review

Each finding was confirmed with a test that failed on the merged branch
(merge commit `9d72b…`, `chore/0.13.2`) before it was changed, unless said otherwise.

* **D-M1, locking a big folder stopped sync.** Real (test
  `locking_most_of_a_vault_syncs_and_leaves_no_plain_text`). Fixed:
  conversions don't count toward the rule (§1), so the plain deletes and the
  `.qenc` files go in the same pass. The plain text left in `state.json`
  was real too: `scrub_locked_text` cleared `base` only for notes already
  marked deleted. It now also clears it for a tracked note in a locked
  folder whose plain file is gone, so the 0.11 promise holds even while a
  pass fails for another reason. Other devices drop their plain copies when
  the deletes arrive, which is now the same pass.
* **D-M2, the settings lane could block for good.** Real (test
  `pruning_review_history_never_stops_the_settings_lane`). Fixed: deletes
  under `.quire/` don't count; the listing-error and "really missing"
  checks still apply there.
* **D-M3, the rule could be passed in pieces.** Real (test
  `a_vault_that_disappears_in_halves_still_stops`; and
  `a_note_evicted_to_an_icloud_stub_is_not_sent_as_deleted`). Fixed with
  the one-hour window and the iCloud stub check (§1); its limits are
  listed there.
* **D-M5 and D-L7, no way out on the desktop; a blanket allowance.** Real
  (read: `Workspace::sync_allow_deletes` had no caller, and the old
  `allow-deletes` file allowed any deletes at any later pass). Fixed: the
  Settings → Sync block and the narrow, expiring allowance (§1).
* **D-L2, a tracked note whose name can't be stored here was sent as
  deleted.** Real (test
  `a_tracked_note_whose_name_cant_be_stored_here_is_not_deleted`). Fixed:
  kept as skipped instead, reported once.
* **D-L3, other name equivalences fell into the copy loop.** Real by
  reading; can't be shown on Linux. Fixed for notes (§2); a case-only
  folder rename is documented, not fixed.
* **D-L4, a long name couldn't go to the trash.** Real (test
  `a_note_with_a_very_long_name_can_be_deleted_by_another_device`). Fixed
  in `quire-vault`'s `trash_name` (the storage team's file, by agreement):
  the note's name is shortened on a character boundary to fit 255 bytes
  with the date, keeping the extension; ` (n)` keeps two apart.
* **D-I2, downgrade and re-upgrade.** Documented: a 0.13.1 build drops
  `skipped`; after upgrading again, a local edit to the old-named copy of a
  note renamed elsewhere to a name this computer can't store is sent under
  the old name, which renames it back for everyone (no text is lost).
* **D-I3, leftovers after a crash.** `fsx` temporary files
  (`.<name>.<16 hex>.tmp`) older than a day are now removed from the
  shared folder's space folder, `keys/` and each `devices/<id>/` when the
  folder transport tidies up (after its daily compaction check). An empty
  file left in `.trash` by a crash between claiming a trash name and moving
  the note there is not removed: it can't be told from a trashed empty
  note.

## 6. Third round: the final review

* **F-L2, the hour was fixed, not sliding, and a clock set back reset it.**
  Real: tests `the_many_deletes_hour_slides_across_its_end` (one delete at
  9:00, the folder emptying around 10:00: 300 of 400 were sent) and
  `a_clock_set_back_doesnt_reset_the_many_deletes_hour` failed on
  `chore/0.13.2`. Fixed: the sliding record of §1; both now stop at 200 of
  400. `the_many_deletes_record_stays_small` checks the bound.
* **F-L3, approval could cover more than was shown.** Real by reading
  (`sync_allow_deletes_at` stamped whatever the file held). Fixed: the
  approval carries the shown set's count and digest and is refused if it
  changed; the CLI lists and asks first (§1). Test: the 12 shown, then 20
  held, then approving the 12 is refused and nothing is sent
  (`many_deletes_wait_until_the_person_allows_them`).
* **F-I2, a leftover iCloud stub blocks a real delete silently.**
  Documented, not changed. A stub beside a missing note means "evicted",
  and an evicted note can stay a stub for months, so no age tells a stub
  iCloud forgot to remove from a note still in iCloud; an age limit would
  bring back the deletes D-M3 stopped. Reporting it once would need a
  per-path record of when each stub was first seen, kept in the state;
  not small enough for 0.13.2. What happens: such a note's delete is not
  sent from this device, nothing is reported, no text is lost; deleting it
  on another device, or deleting the stub (`.Name.md.icloud`) here, sends
  it.
* **F-I3, deletes under `.quire/` were uncounted.** Fixed with the small
  settings rule of §1 (test `deleting_the_shared_settings_asks_first`: one
  file is sent, the whole folder asks, the agent's history never counts).
