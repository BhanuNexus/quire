# Review: 0.14 search statistics per agent view (`0.14-agent-index.md`)

Status: proposed (0.14, awaiting owner approval)
Area: architecture review
Code: `crates/quire-index/src/{fulltext,semantic,actor,index}.rs`, `crates/quire-mcp/tests/visibility.rs`

Reviewer: the 0.14 architect. Read against `0.14-architecture.md` and the code at main ad3216d.

## Verdict: approve with changes

The security reasoning is the best in the round: the rule "a model may contain only
passages that were visible to the view when it was fitted", reuse of the main model decided
by fit set and not by rules, and the extra leaks it found (`score`, the 64 prefix slots,
`ask::weights`, the note count in `Core::instructions`) are all correct against the code.
The staging is right: keyword statistics first (steps 1–5), meaning models last (step 6).
The changes below are about one stall, one promise that cannot hold as written, and doing
less.

## Blocking issues

**B1. The first call of a new view waits behind the index actor's queue.** §3.5 sends
`IndexMsg::AddScope` and waits. `run` (`quire-index/src/actor.rs`) drains its queue in
batches and a batch can hold `IndexMsg::Load`: the first agent call after start then waits
for the whole load (9.4 s cold at 50k in the scan; the perf job has "MCP start to first
search answer" at 500 ms). Today `search` answers from a partial index at once. Also, `run`
replaces the index on load (`*ix = Index::new()`), which would drop a `Scopes` registry kept
inside `Index`.
*Fix:* build a new view on the calling thread, not on the actor. Keep the registry beside the
index under its own lock (lock order: index, then registry). The caller takes the index read
lock, computes members and totals, and inserts into the registry before releasing the read
lock; the actor cannot have written in between, and it updates live views under its write
lock as designed. Readers are not blocked; the writer waits at most one build, as it does
for the graph build today. Say what a view is during a load (built from the records there
so far, patched as the rest arrive) and that a load keeps the registered predicates.

**B2. G2 is stated more strongly than incremental updates allow.** "Searching a view gives
exactly what an index of only that view's notes gives ... bit for bit" holds for keyword
search always, and for meaning search only right after a fit: between fits the view holds
passages projected on an older basis (I2), while a fresh index would have fitted on them.
Frame §7 rule 4 asks for the bound to be stated.
*Fix:* split G2. Keyword: exact, always. Meaning: exact after `flush_semantic` (which
refits), and between refits "a function of member notes only" (tested by building the same
edit history in a members-only index and comparing). The security property, that nothing
depends on a non-member, is what must be exact, and it is.

**B3. The idle drop makes a quiet agent pay a fit every time.** §3.6 drops a view unused
for 10 minutes. A restricted agent that calls every 15 minutes then answers by keyword
only, then triggers a fit that costs 3.4 s CPU at 10k and 19.6 s at 50k (scan), every time.
*Fix:* no timer. Evict by the caps only (least recently used), and when the policy or
locked-folder list changes. Memory is already bounded by G6 × 4.

## Non-blocking changes

- **Sync fit on the calling thread (≤ 2,000 passages).** ARCHITECTURE.md §11.6 measured
  0.8 s for 10,000 passages, so 2,000 is about 160 ms, not "under 150 ms", and it lands on
  the first call. Fine for MCP. For `ToolHost::call` (`quire-assistant/src/runner.rs`)
  confirm in the note that it never runs on the UI thread (P9); lower the threshold to
  1,000 or measure it in step 6.
- **A restricted view can be told apart in its first seconds** (keyword-only until its model
  is fitted, while an unrestricted agent has meaning hits at once). The note calls timing a
  non-goal; say this case out loud in §2 so the owner accepts it knowingly. It reveals that
  a restriction exists, never what is hidden.
- **Caps 32 keyword / 4 meaning:** accepted; the frame's "at most 4 views" now reads "at
  most 4 fitted meaning models".
- **Refit load.** Main plus four view models is up to five fits a round, 19.6 s each at
  50k. Keep "one fit at a time" and add "a view is refitted only if it was used since its
  last fit".
- **Step 2** (note count in `instructions`) is a fix on its own: merge it now.

## Conflicts with the frame and the other designs

1. **Agent-tools §3.9 says a building view reports `indexing`.** This design says nothing is
   reported, because the message itself reveals that notes are hidden. This design is
   right; agent-tools must drop that sentence. No closure fallback with whole-vault
   statistics may remain in `search` and `ask` once step 5 lands.
2. **Fingerprint over read answers only, predicate over (path, tags):** agent-tools has
   already taken both in its current text. Settled.
3. **Index-startup must provide:** stable document ids in `FullText` (today `insert` removes
   and assigns `next_id`, so every edit changes the id), a passage store in (path, offset)
   order, projection that takes a model handle, a main refit forced when a folder is locked,
   and the compact vector layout if main-model reuse is to stay bit-equal. If index-startup
   does not adopt the compact layout for the main index, this design has two honest choices:
   agent views never reuse the main model (every MCP server pays a second fit, also with no
   deny zone: not acceptable), or the visibility test compares "by meaning" scores to a
   tolerance. So the compact layout is in practice a requirement on I2; see that review.
4. **Frame §4 "patched from `Manifest::since`":** patched by the index actor's per-note
   updates instead. Better; the frame's sentence is loose and this is what it meant.
5. **Build order:** steps 3–4 reshape `FullText` and must come after index-startup I1 has
   landed its interner, not beside it.

## Simpler alternatives the design missed or underrates

- **Document frequency per query, as the primary design.** §4 keeps it as a fallback. I
  would make it the plan and the stored `df` vector the fallback. A view then holds only the
  member bitset, `n` and `total_len`. `rank_in` counts members while it walks each posting
  list it has to walk anyway (count first, then score: two passes over the same few lists);
  `ask::weights` walks at most ten lists; prefix expansion needs "any member?", which stops
  at the first hit. What disappears: term ids and their free list in `FullText`, a `df`
  vector per view, per-note `df` patching for up to 32 views, and most of G3. Budget check:
  search is 18–28 ms p50 at 10k today against a 60 ms budget for restricted views; doubling
  the posting walk fits. A view that hides nothing short-circuits to `postings.len()`.
  Measure in step 3; store `df` only if G5 fails.
- **Ship keyword-only views in 0.14.0 and meaning models in 0.14.x.** Steps 1–5 close the
  leak completely (restricted views lose "by meaning" hits; unrestricted agents are
  unchanged because they reuse the main model). Step 6 is the largest and most coupled piece
  in the release (it needs I2, the compact layout and the refit queue). I recommend the
  owner treat step 6 as "if I2 lands by the cut", not as a 0.14.0 condition.

## Questions for the owner

1. If time runs short, may 0.14.0 ship with keyword-only search for agents that have hidden
   notes, and meaning search for them in a later 0.14.x? *Recommendation: yes; the leak is
   closed either way.*
2. Should a reply say "meaning search is still being prepared" for a restricted agent?
   *Recommendation: no (the design's answer); the message reveals that something is hidden.*
3. Compact (f16 plus sparse) meaning vectors for the main index too, which slightly changes
   the owner's own "by meaning" order and cuts semantic memory by about 70% *(the design's
   guess)*? *Recommendation: yes, decided with index-startup.*
4. Caps: 32 views with keyword statistics, 4 with a meaning model, not a setting.
   *Recommendation: yes.*
