# Quire 0.12: sync through S3-compatible storage and WebDAV

*Status: built for 0.12. Code: `crates/quire-sync/src/remote/`, `crates/quire-app/src/vault_sync.rs`, `quire-cli sync`, Settings → Sync. Setup per provider: [docs/sync-backends.md](../sync-backends.md).*

Quire Sync went through its own server or through a folder another tool syncs. 0.12 adds two more places: **S3-compatible object storage** (AWS S3, Cloudflare R2, Backblaze B2, Wasabi, MinIO and others) and **WebDAV** (Nextcloud, ownCloud, Fastmail Files, Synology, Apache `mod_dav`, `rclone serve webdav`). Remotely Save and Self-hosted LiveSync show how many people want exactly this: their own bucket or their own Nextcloud, nothing else to run.

Everything else stays as it is: the encryption ([sync.md](sync.md)), the engine and its three-way merge, selective sync and the sync lock ([0.10-agentsync.md](0.10-agentsync.md)), locked folders travelling as ciphertext ([0.11-secure.md](0.11-secure.md)), shared review history and conflict copies.

## 1. The design: folder sync, with storage in place of the folder

The server keeps revisions in order with a compare-and-swap per note. Object storage has no such thing that works everywhere: AWS S3, R2 and MinIO accept `If-None-Match: *` on a write (create only if absent), Backblaze B2 refuses that header with an error (see the Proxmox patch that skips it for B2), and for Wasabi we found no statement either way. WebDAV servers differ too. So the design doesn't depend on it.

Folder sync already solves the same problem without any atomic operation, by never letting two devices write the same file (design [sync.md](sync.md#sync-through-a-folder-free)). The remote transport keeps that rule:

* **Each device writes only its own objects, and each object once.** Revision *n* of device *d* is `devices/<d>/<n>.rev`, and is never changed. Two devices syncing at the same moment never write the same name, so neither can overwrite the other, on any storage.
* **The same order on every device, from the revision graph.** Each device reads every device's revisions and works out each note's current revision with the folder rule: start from the note's first revision, follow the child with the smallest id. The answer doesn't depend on timing or on what arrived first.
* **The losing device merges again** (`Transport::fork_base`), as in folder sync. Nothing is overwritten and no text is dropped.

### Layout

```
<bucket>/<prefix>/quire-sync/<space>/          (or <WebDAV folder>/quire-sync/<space>/)
  space.json                        the wrapped vault key; format 3, min_reader 3 (written once)
  tips/<device>                     {"n":42,"w":"<writer>"}: that device has uploaded 42 revisions
  devices/<device>/000000000042.rev its 42nd revision (never changed)
```

* A **revision object** is `quire-rev/1\n`, the revision's ids as JSON (`file`, `rev`, `parents`, `device`; `sealed` empty), `\n`, then the sealed bytes raw. That's half the size of the hex the folder logs use. A reader rejects an object whose ids aren't 32 lower-case hex digits, which has more than two parents, or whose `device` isn't the folder it was found in.
* A device's **tip** is the only object ever overwritten, and only by its own device. It says how many revisions that device has uploaded; `w` is a random id of the process that wrote it. Listing `tips/` is **one request**, whatever the number of notes, so checking for other devices' changes costs one listing.
* `space.json` is written with `If-None-Match: *` where the storage has it (or after a check where it doesn't), so a vault id is never reused. `min_reader: 3` keeps future formats honest; no earlier Quire reads this layout anyway.

### The mirror and the outbox

The device keeps the revisions it has fetched, and its own, in the folder transport's layout under `.quire/sync/remote/mirror/<space>/devices/<device>/000001.jsonl`. A plain `FolderTransport` over that mirror does the rest: the head rule, `fork_base`, history, "another computer is writing as this one". No graph code is duplicated.

* **Pull:** list `tips/`; for each other device whose tip moved, fetch its new objects (8 at a time) and append them to its mirrored log, in order, up to the first one that isn't readable yet ("waiting"). Then the folder transport reads the mirror.
* **Push:** append to this device's mirrored log (durable on this device), and queue the revision in the **outbox**. `RemoteTransport::flush` (end of every pass; also the start of the next) uploads the outbox, 8 at a time, then writes the tip.
* **Interrupted uploads resume.** The outbox is just "own log lines past the tip", worked out again at start. A revision uploaded before a crash and before its tip is found by `If-None-Match` (412) or a check, compared byte for byte, and counted. Nothing is uploaded twice, nothing is skipped, and the tip only ever moves past revisions that are there.
* **A lost mirror is restored:** if this device's tip is ahead of its mirrored log, its own revisions are fetched back before the folder transport first reads its log.
* The mirror is the same size as the remote log (it plays the part of the synced folder). History in the app reads the mirror, not the storage.

Why not a log segment per device, overwritten like a folder log? Overwriting a growing object re-uploads it whole on every change, and a reader can see the old or the new one but must re-download it all. One object per revision costs one `PUT` per change and nothing else.

### What two devices at once can and can't do

| Situation | Outcome |
|---|---|
| Two devices push at the same moment | Different object names; both kept. Each sees the other's at its next pull; the tie rule picks the same current revision everywhere, the loser merges again (tested: two threads, 12 rounds, real HTTP, every line kept) |
| A device is cut off mid-upload | Its revisions are in its mirror; the next pass uploads the rest; others don't see them until the tip moves, which is only after they're there |
| A storage without `If-None-Match` (B2, some WebDAV) | Same outcomes: nothing in the design needs it (tested with it off) |
| A copied vault (`.quire` included) makes two computers write as one device | Noticed: an object number already taken by other bytes, or our tip written by another process. Sync stops with "Another computer is syncing as this one". With conditional writes this is caught before anything is overwritten; without them a write that races the check by milliseconds can overwrite one object of that misconfigured pair, which stays in the other computer's mirror |
| A tip lists revisions that aren't readable yet (eventual consistency, a slow WebDAV server) | Fetched up to the gap; the rest next pass; the status says "Waiting for …" |

**WebDAV `ETag`s.** Many servers derive the `ETag` from the file's time in whole seconds and its size (WsgiDAV does; the real-server test found it). Two tip writes within one second can then keep the same `ETag`, so on WebDAV the tips are always read (one small `GET` per device per pass). On S3 the `ETag` is the object's MD5 (Quire never uploads in parts), so an unchanged `ETag` is trusted.

**No `LOCK`.** WebDAV locks would serialise devices but leave stale locks after crashes and aren't implemented by every server; with one writer per object there is nothing to lock.

## 2. What the storage can see

Everything the folder transport reveals, and:

| Visible to the storage | How |
|---|---|
| How many vaults, devices, and revisions per device | `quire-sync/<space>/`, `tips/<device>`, the tip's `n` |
| Which revisions belong to the same note, and the revision graph | The plaintext ids in each object's header (`file`, `rev`, `parents`, `device`), as on a Quire Sync server |
| Roughly how big each revision is | Object sizes; content is padded (256 B, powers of two to 64 KiB, then 64 KiB steps) before sealing, so short notes all look alike; a large size suggests an attachment |
| When each device syncs, and from where | Object times, request logs and IP addresses: about one listing a minute per open app |
| When the vault was made | `created` in `space.json` |
| The wrapped vault key | `space.json` (Argon2id, 64 MiB, 3 passes; the passphrase is the only thing between it and an offline guess, as for a sync folder) |

**Not visible:** note text, note and folder names, tags, links, which notes are in a locked folder, or which files are attachments (beyond size). Object names are ids and numbers only.

## 3. Client, signing, TLS

* **HTTP:** `ureq` 3, already used by the server transport: blocking, pure Rust, rustls with the platform verifier (the system's certificates). No new HTTP stack. Redirects are never followed (a redirect could send signed requests or a WebDAV password to another host); the error names the host to use instead. `http://` is refused except to this computer, unless the person ticks "Allow http://" (a NAS on their network).
* **SigV4:** about 100 lines over `hmac` and `sha2` (already used for sync's own crypto) in `remote/sigv4.rs`, rather than `aws-sigv4` and its dependency tree. Tested against AWS's published vectors (`get-vanilla`, `post-vanilla`, `get-vanilla-query-order-key-case`) and the four worked examples of the S3 API reference, all also confirmed with botocore 1.43; plus a botocore vector for a conditional `PUT` with a session token, a port and a key with a space, `ü` and `+`. The mock S3 server checks every request's signature over the headers as received, and moto (when run) checks them independently. Payloads are signed (`x-amz-content-sha256`).
* **Retries:** network errors, `429` and `5xx` (not `501`) are tried up to 4 times in all, with exponential backoff and jitter (400 ms doubling, at most 8 s), honouring `Retry-After` up to that cap. AWS's `409` on racing conditional writes is retried as such.
* **Pagination:** `ListObjectsV2` continuation tokens, at most 150 pages and 100 000 entries per listing; a server that repeats a token or never ends is refused.
* **No multipart.** The largest object is a 10 MB attachment's revision, about 14 MB sealed: far under every provider's single-`PUT` limit (5 GB on AWS, R2, B2, Wasabi). Multipart would add requests, state and a cleanup job for nothing at these sizes. Replies are limited to 64 MiB for objects and 8–16 MiB for listings and errors.
* **XML:** `roxmltree` 0.21 (already in the tree through `usvg`): DTDs refused, so no entity expansion and no external entities; at most 400 000 nodes. Names are matched by local name (and the `DAV:` namespace for WebDAV).
* **Clock skew:** S3 refuses requests more than 15 minutes off. A `RequestTimeTooSkewed` error, or any `403` whose `Date` header is more than 5 minutes from this computer's clock, becomes "This computer's clock is N minutes behind/ahead…".

**Never trust remote names.** Only names that are ids (32 lower-case hex digits) are used from any listing; `..`, `/etc/passwd`, absolute URLs to other hosts, names with `/`, and broken `%` escapes are dropped. Keys sent are built from ids and numbers only. Tests feed hostile servers: endless and 9 MB listings, broken XML, an entity bomb, redirects to another host, names with `..`, and a 70 MB body.

## 4. Credentials

* Kept as JSON in the OS keychain (or the private secrets file), under the same entry a server's token uses (`sync-token-<space>`). `config.json` holds only the profile: kind, endpoint, region, bucket, prefix or URL. Tests check no secret reaches it.
* In memory, secrets are `Zeroizing` and their `Debug` output names the access key or user only. They never appear in errors, status lines or `last.json`.
* With a profile, `config.json` keeps the device id under `remote_device`, so Quire 0.11 and older can't read it and show sync as off rather than try a server with no address.
* Expired or rotated credentials: "Update credentials…" in Settings → Sync, or `quire-cli sync credentials <vault>`; the new ones are tested before they're kept.

## 5. Setup

* **Settings → Sync** offers "S3-compatible storage" and "WebDAV" beside the folder and the server: provider presets (AWS, Cloudflare R2, Backblaze B2, Wasabi, MinIO) fill the endpoint and region; then bucket, folder in the bucket, access key and secret, or the WebDAV URL, user and app password. **Test connection** (in the background) lists, writes, reads back and deletes a probe object and reports whether conditional writes work. Errors say what to fix: wrong key or secret, expired credentials, the clock, the region, a missing bucket or folder, a redirect, an untrusted certificate. No CORS setup is needed: Quire isn't a browser.
* **CLI:** `quire-cli sync join <vault> --s3 <endpoint> --bucket B --region R [--prefix P]` or `--webdav <url> --user U`, with secrets from `QUIRE_S3_SECRET_ACCESS_KEY` / `AWS_SECRET_ACCESS_KEY`, `QUIRE_WEBDAV_PASSWORD`, a file or a prompt (never the command line). `sync test`, `sync credentials`, and `sync status` naming the storage.
* **Moving a vault between transports:** `quire-cli sync move <vault> --s3 …` (or `--webdav`, `--folder`, `--server`): a last pass where it syncs now, then a new sync vault in the new place from this device's notes. Other devices `sync join` the new vault; their notes are adopted, not copied (the engine's identity rule), as tested. Revision history stays in the old place.

## 6. Tests

* `quire-sync` unit tests: SigV4 vectors, encoding, XML (S3 listings, errors, WebDAV multistatus, DTD/entity refusal), backoff, scheme rules, the object format, prefixes and ids, spaces, the probe, and the transport over an in-memory store: ties, a cut upload resumed by a new process, a deleted mirror restored, a second computer as the same device (with and without conditional writes), hostile objects and names.
* `quire-sync/tests/remote.rs`, over real HTTP to the **in-process mock servers** (`remote::mock`, feature `mock-server`; plain `std::net`, no network): two devices syncing **at the same moment** for 12 rounds on S3 (listings paged 3 keys at a time) and WebDAV, with no lost line and identical files; the same without conditional writes (B2-style `501`, WebDAV ignoring the header); overlapping edits making the usual conflict copy; an upload cut after 7 of 20 objects, a pass while still down, then resumed with each object uploaded once; `503`/`500` retried; a wrong passphrase; a wrong key, wrong secret, wrong region, expired credentials (also mid-sync) and a 40-minute clock skew; hostile servers; storage seeing only ciphertext.
* **Real servers**, behind `QUIRE_SYNC_REAL_SERVERS=<python>`: **moto** 5.2 (`moto.server`, with IAM auth on, so it checks every SigV4 signature and the IAM policy of docs/sync-backends.md, and conditional writes) and **WsgiDAV** 4.4 (Basic auth). Both run the two-devices-at-once check; moto also proves the key can't reach the rest of the bucket. **MinIO could not be fetched here**: `dl.min.io` and GitHub releases are blocked by the network allowlist and the Go module proxy refused `github.com/minio/minio`; moto and WsgiDAV came from PyPI. Run the real-server test against MinIO or a provider when you can (`docs/sync-backends.md` has the steps).
* `quire-app`: an end-to-end test through `sync_create_at`, `sync_join_at` and `sync_once_at` for S3 and WebDAV (wrong passphrase refused, selective sync, settings switch, no secret in `config.json`, expired then renewed credentials), and `sync move` from a folder to WebDAV with the other device's notes adopted.
* CI needs no network: the mock tests always run; the real-server test is skipped unless the variable is set.

## 7. Deferred, and why

* **Compaction.** Like folder logs, revision objects accumulate (about the size of your edits over time). Dropping old ones safely needs the epoch design from [sync.md](sync.md) (a snapshot every device moves to); not built for folders either.
* **Temporary credentials that refresh themselves** (AWS SSO, instance roles, `credential_process`): a session token can be given, but Quire doesn't renew it; a long-lived key limited to one bucket prefix is the documented setup.
* **Digest auth for WebDAV.** Basic over HTTPS covers Nextcloud, ownCloud, Fastmail, Synology and rclone; Digest adds code for little.
* **S3 as storage for `quire-sync-server`** (from [sync.md](sync.md)'s component table): a different feature, for people who run the server.
* **Faster change notice** than one listing a minute (S3 event notifications, WebDAV push): provider-specific; the minute keeps cost and code low.
* **Moving history** with `sync move`: the new vault starts from current notes; the old place keeps the history until deleted.

## 8. Dependencies

No new crates in `Cargo.lock`. `quire-sync` gains optional `roxmltree` (0.21, MIT/Apache-2.0, already built for `usvg`), `chrono` and `base64` (workspace versions), behind its new `remote` feature, which `quire-app` turns on in both editions. Lite gets S3 and WebDAV too: the code is small and reuses what Lite already links.
