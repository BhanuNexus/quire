# Quire 0.10: agent review across devices

Status: in 0.10. Format: [../formats/shared-review.md](../formats/shared-review.md).
User guide: [../serve.md](../serve.md#agents-on-the-server-review-on-your-desktop), [../agents.md](../agents.md#suggestions-from-another-device).

## Why

0.10 makes "agents on a server you own" a headline: an agent connects to
`quire-cli serve` on a home server and writes there. In 0.9 proposals and
the ledger are device-local (`.quire/agent/`, design 0.9 §8.3), so:

* the person can't review the server agent's suggestions in the desktop app;
* "Revert run" works only on the device where the agent ran.

## Shape

Review history travels with the existing opt-in, **"Also sync vault
settings and review history"** (`shared_state`), which already carries
`.quire/shared/**` in its own lane (design 0.9 §B.5, CHANGELOG 0.9.1):
through a server once every device is on protocol 2 (the space minimum
makes 0.8 clients get `426`); through a sync folder in
`<space>/shared/devices/`, which 0.8 never scans.

The local stores stay where they are. Each 0.10 device **publishes**
copies under `.quire/shared/agent/` before each sync pass and **takes in**
the other devices' after it:

```text
.quire/shared/agent/devices/<device>.json             id and name
.quire/shared/agent/proposals/<device>/<id>.json      proposals its agents made
.quire/shared/agent/decisions/<device>/<id>.json      what was decided on it, per proposal
.quire/shared/agent/ledger/<device>/<yyyy-mm>.jsonl   its ledger, without reads
.quire/shared/agent/texts/<device>/<yyyy-mm>.jsonl    texts its changes need to be undone
```

**One writer per file**: the device in the path. Two devices never write
the same file, so sync never merges one, and a conflict copy of a JSON
file can't happen.

`quire_agent::shared` does both halves (`AgentStore::export_shared`,
`AgentStore::import_shared`); `quire_app::vault_sync::Session::pass` calls
them around every pass when shared state is on, so the desktop app,
`quire-cli sync once|watch` and `quire-cli serve --sync` all share review
history the same way. Importing writes only `.quire/agent/` files, which
the desktop's agent watcher already follows, so the Inbox updates by
itself; the same watcher nudges the app's sync when a decision is made
here, so a rejection (which changes no note) reaches the other devices at
once instead of at the next poll.

### Proposals: mirrors

A proposal from another device is copied into the local store as a
**mirror**: the same file format, with `origin: {id, name}` (the device)
and `origin_body` (the hash of the fields taken from the origin). The
desktop's Inbox, review in the editor, Accept all and the CLI work on a
mirror exactly as on a local proposal.

* Only the origin device publishes a proposal (a file under another
  device's folder that names a different origin is ignored).
* The agent on the origin keeps amending it there. A mirror is never
  amended here (`own_pending` skips mirrors), so a desktop agent with the
  same client key gets a proposal of its own instead.
* When the origin's copy changes (amended, or resolved there), the mirror
  takes the new text and keeps everything decided here (decisions,
  decided content, change states). A mirror resolved here and amended at
  the origin afterwards comes back as waiting, with the decided hunks still
  hidden.
* A proposal resolved at the origin before this device saw it is not
  copied.

### Decisions: events, merged the same way everywhere

Each device publishes what was decided **on it**, per proposal: hunk
decisions (id, action, time, edited text), the content of decided hunks
(below) and whole-change states (create, rename, delete accepted or
rejected; an edit with every hunk decided). The file only grows: an
export adds to what an earlier export wrote.

Every device merges the same events the same way:

* **per hunk**: one that wrote text (accepted or edited) wins over a
  rejection, since the note carries that text; between equals, the
  earliest (time, device);
* **per change**: the state of highest rank (applied, partially applied,
  rejected, superseded), ties by earliest (time, device); an edit's state is
  also what its merged hunk decisions give, when that ranks higher;
* the proposal's status follows from the changes (`settled_status`).

So two devices deciding the same proposal at once end with the same
outcome whatever order the files arrive in (tested both ways round). A
decided hunk stays decided: it is hidden by id and by content
(`review::visible`).

### Text is applied once

Only the device where the person decides writes the note. Importing a
decision never writes a note: it records it, hides the hunk and settles
the change. The note then syncs like any edit; on the other device the
agent's lines are already in it (the rebase shows no hunk), or, until the
note arrives, the hunk is hidden as decided. Two devices accepting the same
hunk at the same time make the same edit, which sync's three-way merge
takes once (tested).

An edit with nothing left to show for the note as it is here (every hunk
decided somewhere, or its text already synced in) is settled by the
import (`settle_quiet`), so the Inbox doesn't keep an empty suggestion.

### Ledger and revert across devices

The ledger of each device is published without `read` events (they stay
on their device, 30 days as before), for the current and two previous
months, each month at most 4 MB (newest lines kept). `AgentStore::log`
reads this device's ledger plus the other devices' copies, so Activity,
"who last changed this note" and revert see every device. Local-only
reads are `log_here`.

Revert builds its plan from all devices' ledgers. A ledger entry points
at history snapshots by time (`snap_before`/`snap_after`), which mean
nothing on another device, so a text is found:

1. by snapshot time, checked against the entry's hash (this device);
2. by hash among the note's last 200 versions here (sync keeps the
   versions it receives with their provenance);
3. in the **texts the origin device carried** for its recent changes
   (`texts/<device>/<month>.jsonl`, gzip + base64, each ≤ 256 KiB, each
   month's file ≤ 4 MB, for changes of the last 35 days).

The third is what makes a run with two writes between syncs undoable on
the desktop, which never saw the middle version. The undo is still
three-way against the current text, so the person's edits made since (on
any device) are kept; overlapping ones make a revert proposal for review,
as before.

### Rejected suggestions stay rejected

0.9 re-dropped rejected hunks on amend by **id**, and ids are content
hashes: an agent that rewrote the lines around a rejected line, or the
same line with other spacing, brought it back. Now each decided hunk keeps
its **content** in the change (`decided: [{action, old, new, before,
after, at, device}]`): the replaced lines and the agent's lines,
normalised (NFC, whitespace collapsed, trimmed, lower case, blank lines
dropped), and the nearest non-empty line before and after it.

A hunk is hidden (on review, after a rebase, and dropped on amend) when it
**only brings back** a rejected change at the same place:

* every line it adds is a line the rejected change added, and every line it
  removes is a line the rejected change would have replaced, **apart from
  trivial differences only**: letter case and spacing (normalising takes
  them out) and punctuation at the end of the line (`review::same_line`).
  Any other difference, a digit, a date, a number or a word, makes it a
  different suggestion that is asked about (before the review fix: at 85 % similarity,
  "March 14" rejected hid the corrected "March 21", data review #7);
* and one of its replaced lines or its context matches one of the rejected
  change's replaced lines or context (the same place). Only here may a line
  differ a little: at **similarity ≥ 0.85** (normalised Levenshtein;
  `DECIDED_LINE_SIMILARITY`) for lines of 20 characters or more, since the
  agent may have rewritten the lines around the change.

A hunk that also adds or removes anything else is asked about again, so
nothing new is lost. When the agent amends its proposal, a rejected line
inside such a bigger hunk (the agent rewrote the line next to it, so both
are one hunk) is taken out of the agent's text: it goes back to the line it
replaced, or goes, for an insertion, and only the rest is asked about
(`DecidedContent::strip`; only the proposal's text changes, never the
note).

The same holds across runs: a **new** proposal by the same agent for the
same note takes the rejected content of that agent's proposals resolved in
the last 30 days (on this device, or merged in from another), so the agent
suggesting the same thing in its next run isn't asked about again. A change
left with nothing is settled as rejected at once. Acceptances made on another device are matched the
same way (until the note with that text arrives); this device's own
acceptances are already in the proposal's base. Hunks or records longer
than 200 lines are compared by exact normalised lines only.

Property tests (`review.rs`): a rejected hunk brought back reworded (case,
spacing, a full stop) is never shown again; a line brought back with a
digit, date, number or word changed is always shown
(`property_a_changed_digit_date_number_or_word_is_never_hidden`), and a
trivial rewording never is (`property_trivial_rewordings_stay_hidden`); a
hunk adding a line no rejection has is never hidden; hiding never changes
the person's text (applying what is shown equals applying everything with
the hidden hunks rejected); every hidden hunk is covered by a rejection.

## Other devices' files are untrusted (0.10.2)

Every device holds the vault key, so "one writer per file" is a
convention, not a guarantee: a compromised device in the sync space can
write any file under `.quire/shared/agent/`. The security review (#2, #11)
showed a forged ledger line making **Revert run** write an attacker's file
to `.obsidian/plugins/…`, and a decisions file settling another device's
suggestion unseen. Until files are signed (below), each device checks what
it can:

* **Paths.** Every path in another device's proposal (`path`, `from`, `to`)
  and ledger line (`path`, `to`) goes through `quire_agent::vault_file`:
  `canonical_path` (NFC, relative, no `..`, no drive, root or control
  characters), no hidden segment at all (`.quire`, `.obsidian`, `.git`,
  `.trash`), and through symlinks the file must stay inside the vault and
  outside hidden folders. A proposal with one bad path is not taken in; a
  ledger line is dropped. Revert (plan and apply) and accept (`resolve_change`,
  `accept_in_file`, `decide_*` with an acceptance) check again where they
  write, and `LocalFs` refuses drive and rooted paths outright.
* **Policy.** Accepting never writes where the proposing agent is denied.
  Undoing another device's ledger entries is direct only where each was an
  agent's change the agent could have made directly here (an agent zone);
  for a person's note, or a job's or importer's change, the undo becomes a
  revert proposal (`ProposeCreate`, `Propose`, `ProposeDelete`), and a
  rename made elsewhere is left for the person.
* **Who.** A device is the folder its files are in: `devices/<id>.json`
  must name `<id>` (so no device can take another's id, this device's
  included); a mirrored proposal's `origin` and actor must be that device
  and the actor can't be a person; a ledger line's actor must be that
  device; a decision is recorded with the device whose folder it came from.
  Device ids are random (`DeviceInfo::generate`); names are what each
  device says about itself and are shown as such ("“home server”
  (self-reported name, device d_7K2M…)").
* **Trust** of a mirrored proposal can be lowered here (a source that is
  untrusted on this device), never raised.
* **This device's own files** are built from its local state. Its
  decisions file adds to a local record (`.quire/agent/sent-decisions/`),
  not to the shared copy, so an event another device slipped into it isn't
  sent on as this device's.
* **Decisions from elsewhere are visible and reversible.** A waiting
  proposal settled here by another device's decisions keeps `settled_by`;
  the Inbox lists it under Resolved as "decided on “…” (self-reported name,
  device …)" with **Reopen**, `quire-cli agent proposals --all` says the
  same, and Activity has an entry. Reopening (`reopen_proposal`) drops
  other devices' states and hunk decisions from this copy and ignores their
  decisions made before then. The note is never written by an import.

Tests: `shared_tests.rs` (`forged_ledger_lines_never_write_…`,
`another_devices_agent_change_to_a_persons_note_is_undone_only_by_review`,
`mirrored_proposals_with_bad_paths_or_actors_are_not_taken_in`,
`a_suggestion_settled_by_another_device_says_so_and_can_be_reopened`,
`this_devices_decisions_file_is_rebuilt_from_its_own_record`).

**Future work: authenticated devices.** The checks above limit what a
forged file can do; they don't prove who wrote it. The fix is a per-device
signing key (Ed25519) made when a device joins, its public key enrolled in
the sync space by a device already in it (the person confirms a short code
on both), and every file under `.quire/shared/agent/<kind>/<device>/`
signed by that device. Readers then drop unsigned or wrongly signed files,
and a removed device's key is revoked. That needs a join flow on every
surface and a format bump, so it is planned for a later release.

## Compatibility

* **Off (the default):** nothing is published or taken in; every device
  works as in 0.9. The Inbox and Activity say: "Suggestions from other
  devices appear here when 'Also sync vault settings and review history' is
  on" (only when the vault syncs).
* **Quire 0.9 devices** in the same space carry `.quire/shared/agent/**`
  like any other settings file: they list it (0.9's settings lane takes
  every file under `.quire/shared/` up to 10 MB), write what arrives and
  never delete it. They read nothing there (0.9 reads only `vault.toml`,
  `agent-policy.toml` and `srs/`), so they neither misread nor act on it.
  Tested with a 0.9-shaped device (both lanes, no publishing) between two
  0.10 devices: every file arrives intact and its own Inbox stays empty.
  A 0.9 device's own agents' suggestions stay on it, as before.
* **Quire 0.8** never sees `.quire/shared/` (the lanes, unchanged).
* Local proposal files keep format 1; the new fields (`origin`,
  `origin_body`, `decided`, decisions' `device`, changes' `state_device` /
  `state_at`) are unknown fields to 0.9, kept when it rewrites a file.
* A shared file with a higher `format`, a device id that isn't one
  (`[A-Za-z0-9_-]{1,64}`), or a proposal published under another device's
  folder is ignored.
* `.quire/shared/agent/.gitignore` (`*`) keeps review history out of the
  vault's git repository, which otherwise commits `.quire/shared/`.
* A shared review file deleted by another device (it stopped sharing it)
  is removed, not moved to `.trash/`.

## Sizes and retention

Sync skips files over 10 MB, and a file that grew past that would look
deleted to every device, so nothing here gets near it:

| File | Limit | Kept |
|---|---|---|
| proposal | gzipped (`packed`) above 256 KiB; not shared above 4 MB (reviewed on its device) | while waiting, and 30 days after it is resolved |
| decisions | ≤ 4 MB | with its proposal; 30 days after the last decision once the proposal is gone |
| ledger month | ≤ 4 MB, newest lines kept; no reads | this month and the two before |
| texts month | ≤ 4 MB; each text ≤ 256 KiB | this month and the one before (changes of the last 35 days) |
| device | a few bytes | always |

A typical vault shares a few hundred KB.

## UI

* **Inbox:** a group from another device reads "Claude · on home server ·
  14:02"; review in the editor says "Claude (on home server) suggests 2
  changes"; Resolved lists the device. Review, Accept all and Reject all
  work the same.
* **Activity:** lanes per actor, grouped under a caption per device ("This
  device", "home server") when runs came from more than one; run cards say
  "Claude · on home server". "Revert run" on a server run works on the
  desktop.
* `quire-cli sync share <vault> on|off` turns the opt-in on from a server
  (as Settings → Sync does in the app).

Two smaller fixes from the integration report ride along:

* A line that only embeds a recording (`![[Voice note ….wav]]`) shows a
  small player under it in the editor: **▶ Play / ■ Stop** with the
  position (full edition, through the `cpal` already used for recording:
  the WAV is decoded with `quire_ai::wav` and resampled to the speaker),
  the length, and **Open in system player** (both editions; also for MP3,
  M4A, Ogg, FLAC).
* With a `.base` (or canvas, PDF) open, Insights shows that file: what it
  is, its folder, and for a base its views (kind, columns, what isn't shown)
  and formulas, instead of the note that was open before; the status bar
  no longer shows that note's word count either.

## Tests

* `quire-agent` (`shared_tests.rs`): a suggestion made on a server and
  reviewed on the desktop (accept one hunk, reject one; the server never
  writes the note); both devices deciding at once (opposite decisions, and
  the same acceptance) converge and the text is applied once; a rejection
  on the desktop holds when the server's agent rewrites around it; a server
  run with two writes between syncs undone on the desktop with the
  person's edit kept, and an overlapping edit becoming a revert proposal;
  newer formats and bad names ignored; packing, the 4 MB cap and retention;
  a proposal amended after the desktop resolved it; a rejection holding in
  the agent's next run.
* `quire-agent` (`review.rs`): the content match and its property tests.
* `quire-app` (`vault_sync`): two 0.10 devices and a 0.9-shaped device in
  one sync folder, through the real engine and lanes; off by default.
* `quire-cli` (`serve_cli`): `serve --sync` on a headless device with an
  agent writing over MCP, and the laptop reviewing (and undoing the
  server's run) through a real Quire Sync server, in both editions.
* By hand (Xvfb): a suggestion made through `serve --sync` reviewed in the
  desktop, light and dark: Inbox, review in the editor, the server seeing
  it resolved, the agent's next run without the rejected line, Activity
  lanes per device, Revert run of the server's run, the off-state text,
  the voice-note player and Insights for a base.

## Deferred

* Reviewing suggestions in the web app of `quire-cli serve` (still: review
  in the app once synced).
* An acceptance undone in the editor (Ctrl+Z after Accept) stays decided on
  the other devices: decision events only grow.
* A 0.9 desktop decides mirrors it already has but doesn't publish the
  decision, so the server's copy waits until it expires.
* A decision made with `quire-cli agent accept|reject` on a headless device
  that changes no note (a rejection) goes out with the next pass of `sync
  watch` / `serve --sync` (their poll), not at once; the app nudges its sync
  as soon as it decides.
