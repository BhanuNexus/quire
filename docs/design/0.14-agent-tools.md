# Quire 0.14: agent tools, one set with one convention

Status: proposed (0.14, awaiting owner approval)
Area: agents/MCP: the tool registry (`ToolRegistry`) shared by MCP, the agent panel and ACP agents
Code: `crates/quire-mcp/src/tools/{mod,common,legacy}.rs`, `crates/quire-mcp/src/tools/read/*.rs`, `crates/quire-mcp/src/tools/write/{append,edit_section,str_replace}.rs`, `crates/quire-mcp/src/{bounds,server}.rs`, `crates/quire-agent/src/` (new `Visibility`, owned by this design as the architect's step T1), `crates/quire-assistant/src/runner.rs` (`ToolHost::defs`), `apps/quire-cli/src/commands/agent.rs` (`agent tools`), `packaging/perf-check.py` (budgets), `docs/agents.md`, `skills/quire/SKILL.md`; tests in `crates/quire-mcp/{src/tools/mod.rs,src/server/tests.rs,tests/visibility.rs}`

This note covers the agent-tool half of 0.14. It adds no tool and removes no capability. It does four things: it stops listing the nine 0.8 duplicates and turns them into thin adapters, it gives every tool the same parameter names (old names keep working), it bounds every listing, and it removes the per-note disk reads from listings. This note keeps to the frame in `0.14-architecture.md` (its section 4 for views, section 5 for budgets, rule 5 of section 7 for the deprecation window); where it differs, section 3.4.3 says so. `ask` and `search` take their view of the index from the per-agent index design (`0.14-agent-index.md`); section 3.9 says what the tools need from it.

## 1. The problem, as measured

Sources: the 0.14 performance scan (item 5), the 0.14 polish scan (items 3, 5 and 6), and the fixtures in `crates/quire-mcp/tests/fixtures/`.

**Nine duplicate tools.** `ToolRegistry::standard()` registers the 0.8 tools first (`legacy::tools()`), and `tools_list` offers them to every era. A client with a write grant sees 42 tools; nine are the 0.8 names in `legacy::NAMES`: `search_notes`, `read_note`, `list_notes`, `backlinks`, `ask_notes`, `list_tags`, `create_note`, `append_to_note`, `replace_in_note`. In `mcp-0.9-modern.jsonl` the `tools/list` result is 41,315 bytes (about 13,800 tokens by the estimate in `bounds.rs`, `ceil(bytes / 3)`). The nine take 3,045 bytes of that (about 1,000 tokens). The skill and `docs/agents.md` already tell agents to ignore them, yet agents spend context on them and sometimes pick them. The agent panel offers them too: `ToolHost::defs` lists every `Read` and `Write` tool, and only the "core" mode filters by `CORE_TOOLS`. A small on-device model in the full panel mode pays for them.

The nine are a second implementation of the same reads. The 0.13.3 leak (hidden notes taking source numbers in `ask` and `search`) was in `ask_notes` and `search_notes` as well. Each duplicate is another place where the visibility rule can be forgotten. Their gaps, from the polish scan: no `outputSchema`, one-line descriptions, no `expected_version`, `create_note` takes `title` + `folder` where `create` takes `path`, `append_to_note` has no `run`, `list_notes` takes any `limit` (default 200), `read_note` is unbounded, `ask_notes` and `search_notes` have no cursor.

**Names disagree.** The same idea has several names:

- A section is `view.section`, `edit_section.heading` and `append.under_heading`.
- A line range is `view.lines: [10, 40]` but the resource template is `?lines=10-40`.
- A result count is `limit` (most tools), `k` (`ask`) or `max_rows` (`query_view`).
- Folder and tag filters are `search.filters.{folder, tags[]}`, `list.{folder, tag}`, `tasks.{path, tag}`.
- A time is `search.modified_after`, `recent_activity.since`, `read_version.as_of`, `revert.since`, and each description spells the formats differently.
- `diff.from/to` are versions; `rename.from/to` are paths.
- `proposals.mine` (bool) against `recent_activity.actor` (string).
- `parse_time` (`common.rs:90`) reads any bare integer as Unix milliseconds, so `since: "7"` means 1970 and returns everything.

**Unbounded results.** Only `search`, `view`, `ask`, `read_version` and `canvas_read` take `max_tokens`. `tasks` (up to 1,000 rows), `query_view` (1,000), `recent_activity` (500), `tags`, `properties`, `proposals`, `history`, `neighbors`, `links`, `hierarchy` and `diff` return a whole list with no token bound and no `truncated`. `tasks` stops at `limit` without saying so, so an agent cannot tell "200 tasks" from "200 of 900" (`tasks.rs`: `if rows.len() >= limit { break; }`). `docs/agents.md` says the default bound is 4,000 tokens; `search` uses 2,000 (`search.rs`: `bounds::max_tokens(a, 2_000)`).

**Listings touch the disk once per note.** `list`, `tags`, `properties`, `tasks`, `links`, `vault_info`, `query_view` and the `where` filter call `common::visible` for every record. That calls `AgentStore::effective`, which for each note runs `resolve_in` (two `canonicalize` calls), `lock::folder_of` (two `exists()` per folder level) and `policy_state()` (reads and hashes the policy file). Timings from the scan (`quire-cli mcp`, p50 of 5 calls):

| Tool | 10k notes | 50k notes |
|---|---:|---:|
| `list` | 165 ms | 918 ms |
| `tags` | 165 ms | 742 ms |
| `properties` | 166 ms | 816 ms |
| `vault_info` | 162 ms | 812 ms |
| `links` | 154 ms | 886 ms |
| `tasks` | 188 ms | 807 ms |
| `query_view` (notes) | 156 ms | 796 ms |
| `search` (for comparison) | 28 ms | 140 ms |
| `backlinks` (for comparison) | 2.5 ms | 17 ms |

The perf job (`packaging/perf-check.py`) checks only `view` and `search`. `list` with `sort: modified` also calls `Storage::modified` for every note (`list.rs`), and the path and title sorts lower-case in every comparison.

**What 0.13.3 already fixed.** Output order no longer depends on hash order (`tasks`, `links`, `neighbors`, `properties` and `list` sort before they cut). A `where` condition is one line (`views::parse_where`) and runs only over visible notes (`views::run_over` with `visible`). This note keeps both and does not touch them.

## 2. Goals and non-goals

Goals, each with a number a test can check:

| # | Goal | Check |
|---|---|---|
| G1 | A modern client with a write grant is offered 33 tools (today 42); a read-only one 19 (today 25). | A test counts `tools/list` per era and grant. |
| G2 | `tools/list` for that client is at most 40,000 bytes (today 41,315, with the nine). | A byte-budget test on the modern fixture's session. It fails when a tool grows the list. |
| G3 | Every tool that returns a list takes `limit` (default and maximum in the schema), `max_tokens` and returns `truncated`; every one that can have more rows than a page also returns `next_cursor`. | A schema test over `ToolRegistry::standard()` (section 6). |
| G4 | No filesystem call per note in any listing: zero per note, and at most 8 per call in total (policy file, ledger). The architect's budget ("filesystem calls per note: 0") is a count, so it is exact. | A counting `Storage` wrapper in a test (section 6), and the same count in `perf-check.py`. |
| G5 | `list`, `tags`, `properties`, `tasks`, `links`, `vault_info`, `query_view` p50: at most 30 ms at 10k notes and 150 ms at 50k (today 154-188 ms and 742-918 ms). These are the architect's budgets (section 5 of the frame); the job fails above budget x 1.25. | `perf-check.py` `BUDGETS`, next to `view` and `search`. |
| G6 | One parameter name per idea across the 33 tools; every old spelling still works. | A table-driven test sends each old name and expects the same result as the new one (section 3.2). |
| G7 | The nine 0.8 names keep working (same results as 0.8 for the same arguments) until 1.0. | The `answers_0_8_clients_as_0_8_did` test and the 0.8 fixtures stay. |

Memory, disk, network: no new persistent data, no new file, no network. `Visibility` (3.5) holds the rules and a locked-folder list, not one entry per note: kilobytes. The architect's frame budgets the views' statistics separately (40 MB per restricted view at 10k notes); that is the agent-index design's, not this one's.

Non-goals:

- No new tool, no tool renamed, no tool merged. The 0.9 names and order are the contract (`every_0_9_tool_is_there_in_the_designs_order`).
- No new filter or capability beyond making the existing ones consistent. (`tasks` gets `folder`; it does not get `where`.)
- No change to who can see what. The visibility rule is the one in `crates/quire-mcp/AGENTS.md`.
- No dependence on the next MCP spec (section 3.7).
- The index itself (persisted index, per-agent views) is another design. This note needs two things from it (3.5 and 3.8).

### 3.2 The target convention

One table. "Accepted too" are old spellings. They are read by the handlers, kept out of the advertised schema (so the 41 KB list does not grow for them), and kept as long as the nine legacy names are (3.4.3): an alias costs one `or` in an argument reader. `docs/agents.md` lists them in one sentence.

| Idea | Canonical | Accepted too | Tools |
|---|---|---|---|
| A note | `path` (title also resolves, as `existing()` does today) | `note` (legacy tools only) | every per-note tool |
| Two notes | `from`, `to` (paths) | | `rename` |
| Two versions | `from_version`, `to_version` | `from`, `to` | `diff` |
| A section | `section` | `heading` (`edit_section`), `under_heading` (`append`) | `view`, `edit_section`, `append` |
| A line range | `lines`: `[10, 40]` or `"10-40"` | | `view`; the resource template's `?lines=` takes the same two forms |
| Row cap | `limit` | `k` (`ask`), `max_rows` (`query_view`) | every list |
| Size cap | `max_tokens` | | every list and every read |
| Paging | `cursor` in, `next_cursor` out | | every paged tool |
| Folder | `folder` (prefix) | `filters.folder` | `search`, `list`, `tasks`, `query_view` filters |
| Tags | `tags` (array; every tag must be on the note) | `tag` (one string), `filters.tags` | `search`, `list`, `tasks` |
| Property filter | `where` (one line) | `filters.where` | `search`, `list` |
| A time range | `since`, `until` | `modified_after`, `modified_before` (`search`), `filters.*` | `search`, `list`, `recent_activity`, `revert` |
| A point in time | `as_of` | | `read_version` |
| Whose changes | `actor` (an id; `"me"` means the caller) | `mine: true` (`proposals`) | `proposals`, `recent_activity`, `revert` |
| Optimistic lock | `expected_version` | | every edit of one note |
| Group of changes | `run` | | every write |
| Link types | `type` (array) | | `neighbors`, `links` |

Decisions that are not obvious:

- **Flat beats nested.** `search` keeps reading `filters{}` (it is on the 0.9 wire), but the advertised schema is flat, like `list`.
- **`list` gains `since` and `until`** (the same filter `search` has) so that "notes changed this week" is not a `search` with an empty query. This is the only new filter, and it exists because the old spelling is `modified_after`. It needs a modification time per note (3.5).
- **`tasks.path` stays** (one note, what it means today) and `tasks` gains `folder`. `tag` and `tags` both work.
- **Times.** One parser, one description string (`TIME_FORMATS`: "RFC 3339, YYYY-MM-DD, or a time back from now: 30m, 24h, 7d, 2w") used in every schema. `parse_time` rejects a bare integer shorter than 13 digits with `invalid_args` ("`since: 7` has no unit; write 7d, or a date"). Thirteen digits or more stays Unix milliseconds, as today, so nothing that works breaks. A time that cannot be parsed is `invalid_args` and names the argument.
- **`lines`** is accepted as an array or as `"10-40"` in the tool and in the resource template, because agents copy whichever form they last saw.
- **Results.** Every list keeps its array name (`notes`, `tasks`, `events`, ...). Each adds `total` (the count after filtering, when known), `truncated` and `next_cursor`. These are new fields on existing objects, so no client breaks.
- **`version` is opaque.** `docs/agents.md` says `sha256:` plus 32 hex digits. It will say: "compare versions for equality, never parse them". Today they are content hashes; a later layer may issue other values (section 5).

### 3.3 Bounds for every list

Two bounds, whichever is hit first: `limit` (rows) and `max_tokens` (size, estimated as `ceil(bytes / 3)`, hard maximum `HARD_MAX_TOKENS` = 20,000, `bounds::max_tokens` clamps to 100-20,000). A cut result has `truncated: true` and, if more can be fetched, `next_cursor`. `fit()` always keeps at least one row, so a single huge row cannot make an empty page that never advances.

| Tool | `limit` default / max | `max_tokens` default | Cursor | `total` | Changes from today |
|---|---|---:|---|:-:|---|
| `search` | 10 / 50 | 2,000 | offset | no | none. The docs are fixed to say 2,000 |
| `ask` | 6 / 20 (`limit`, `k` accepted) | 4,000 | none (one answer) | no | `truncated` added |
| `list` | 100 / 500 | 4,000 | keyset | yes | `max_tokens`, `total`, `truncated` |
| `tasks` | 200 / 500 (was 1,000) | 4,000 | keyset | yes | maximum lowered, `max_tokens`, cursor, `total`, `truncated` |
| `query_view` | 100 / 500 (was 1,000; `max_rows` accepted) | 4,000 | keyset when ungrouped | yes | same; a grouped view is cut by `max_tokens` and says `truncated` |
| `recent_activity` | 100 / 500 | 4,000 | keyset | yes | `max_tokens`, cursor, `total`, `truncated` |
| `history` | 20 / 200 | 4,000 | keyset | yes | same |
| `proposals` | 50 / 200 | 4,000 | keyset | yes | adds `limit`, the rest as above |
| `tags` | 200 / 1,000 | 4,000 | keyset | yes | adds `limit`, sorted by count then name |
| `properties` | 100 / 500 keys | 4,000 | keyset | yes | adds `limit` |
| `outline` | 500 / 2,000 headings | 4,000 | keyset (line) | yes | adds `limit`, `max_tokens`, `truncated` |
| `neighbors` | 50 / 200 | 4,000 | none | yes | `max_tokens`, `total`, `truncated` |
| `links` | 100 / 500 | 4,000 | keyset | yes | `max_tokens`, cursor, `total` (it has `truncated`) |
| `hierarchy` | 200 / 500 | 4,000 | none | yes | `max_tokens`, `total` (it has `truncated`) |
| `diff` | n/a | 4,000 | offset (line) | no | `max_tokens`, `truncated`, `next_cursor` |
| `view`, `read_version` | n/a | 4,000 | offset (line) | n/a | none |
| `canvas_read` | n/a | 4,000 (200-20,000) | none | n/a | none (it cuts and says `truncated`) |
| `vault_info` | `zones` capped at 50 | n/a | none | n/a | `truncated` on `zones` |

Why two kinds of cursor:

- **Offset** (as `bounds::Cursor` is today: `{"o": offset, "v": version}`) stays for results that are one ranked list or one note's lines. A ranked list changes with the index, so `cursor_stale` is the honest answer when the question changed.
- **Keyset** for lists with a total order: the cursor carries the last sort key and path (`{"o": n, "v": fingerprint, "k": "<last key>"}`; `k` is a new optional field). The next page starts after that key. A note created or deleted between two pages then cannot make a page repeat or skip a row, which an offset allows. `Cursor::decode` still reads old cursors (no `k`), so a cursor in flight across the upgrade still works. The fingerprint is the arguments with `cursor` removed, as `list` does today. `since: "7d"` is resolved to a timestamp on the first call and the cursor carries that timestamp, so "7 days ago" does not move between pages.
- Keys: `list` (sort key, path), `tasks` (path, line), `recent_activity` (time, ledger position), `history` (time), `proposals` (created, id), `tags` (count desc, tag), `properties` (key), `links` (direction, path), `outline` (line).

A cursor for a changed fingerprint answers `cursor_stale`, as now. The page size when `max_tokens` is the limit varies by row size; the text of a cut result says how to continue, as `list` does today.

### 3.4 What is deprecated, and how long it lasts

The 0.8 names are not an era problem. A client on 2025-11-25 is a current client, so "list the nine only to legacy eras" (the scan's suggestion) would hide them from most users and from nobody who needs them. Two separate questions have separate answers: is a tool *listed* (so a model discovers it), and is it *callable* (so a prompt or script that names it keeps working).

| Release | Listed in `tools/list` | Callable | Notes |
|---|---|---|---|
| 0.14 | Modern era (2026-07-28): no. The four older versions: yes, in the same place (first), with the description starting "Deprecated: use `search`." | yes | the nine become adapters (3.4.1) |
| 0.15 | no, any era | yes | `agent tools` lists them under "Deprecated names" |
| 1.0 | no | the owner decides (open question 1; recommended: removed at 1.0 with a changelog line in 0.15 and 0.16 announcing it) | |

Why not remove them at once: the cost of keeping them callable is small once they are adapters (about 150 lines instead of 317; a guess), the fixtures that guard them exist, and the break would land on agent setups we cannot see. Quire has no telemetry and the activity ledger records the actor and the operation, not the tool name, so there is no count of who still uses them. Why not keep them listed: they cost about 1,000 tokens in every session of every client, and a listed duplicate is a choice an agent can get wrong.

#### 3.4.1 The nine become adapters

Each legacy handler turns its arguments into the new tool's arguments, calls the new tool through the same registry path (so the same visibility rule and bounds apply once), and renders 0.8's text shape from the structured result. The 0.8 text and `isError` shape are what the fixtures pin.

| Legacy | Calls | Differences a legacy client may see |
|---|---|---|
| `search_notes` | `search` | none in results; 0.8 text format rendered from `hits[]` |
| `read_note` | `view` | now cut at 20,000 tokens (about 60 KB of text) and says "continue with `view` {path, cursor}"; before it was unbounded |
| `list_notes` | `list` | `limit` above 500 is 500 and the text says "N more; use `list` with a cursor"; before there was no maximum |
| `backlinks` | `neighbors` (`direction: in`, `depth: 1`) | none; the edge's `context` is the linking line |
| `ask_notes` | `ask` (`mode: extractive`) | none |
| `list_tags` | `tags` | capped at 1,000 tags with a line saying so |
| `create_note` | `create` | the adapter picks the unique name (`folder/title.md`, never overwrites), then submits like `create` |
| `append_to_note` | `append` | none |
| `replace_in_note` | no equivalent | see below |

`replace_in_note` is the one tool with no 0.9 successor: it replaces every occurrence and can take a regex, and `str_replace` replaces exactly one. Recommendation (open question 2): `str_replace` gains an optional `all: true` (replace every occurrence; `no_match` if there is none; `not_unique` is not raised). The regex form is not carried forward. The legacy name keeps its regex through the existing matcher (`quire_app::find`) until it is removed. Its deprecation text says "use `str_replace` (add `all: true` for every occurrence)".

`legacy::NAMES` stays frozen: no name is added, none is renamed, and the constant is the single list the registry, the order test and `agent tools` read. A new field on `ToolSpec`, `deprecated: Option<&'static str>` (the replacement's name), is how the server knows; it is `Some` exactly for these nine, and a test checks that equivalence.

### 3.5 No disk read per note

The cause is that `AgentStore::effective` answers one path at a time, and every answer re-derives things that depend only on the folder or on the whole call.

What a visibility answer depends on (`store.rs`: `effective`, `candidates`):

1. The policy state: one `Arc<PolicyState>`, valid until the policy file, the device state or the approvals change. Reading and hashing the file belongs to the call, not to the note.
2. The folder: zones, hidden folders (a segment starting with `.`), and locked folders (a key file in some folder above) are all decided by the folder prefix, not by the file. `lock::folder_of_with` already takes an existence test.
3. The file name: encrypted names and key files (`is_encrypted_name`, `is_key_file`), checked on the string.
4. For a client with an allow list (`c.limited()`): the note's tags (`tags_of`, which today stats the file for its cache stamp).
5. Symlinks. `resolve_in` follows them. But the vault listing skips every symlinked note and folder (`storage.rs:193` and `:536`: "a symlinked note or folder is skipped"), so a path that comes from the index is a regular file below regular folders, and `real == path`. The canonicalize calls are for paths an agent names, which keep `guard()`.

The design follows the frame's section 4: **`quire_agent::Visibility`**, a value built from path-prefix rules with no filesystem call, plus a 32-byte fingerprint of those rules. This design owns it (the architect's step T1); the agent-index design uses it and must not build a second one.

- **What it holds.** The actor, the policy snapshot (1), the folder rules of (2) as prefixes (zones with their modes, hidden segments, the locked-folder list), the file-name rules of (3), and the allow-list rule of (4) when the client has one. API: `allows(&self, path: &NotePath) -> bool`, `allows_with_tags(&self, path, tags: &[String]) -> bool` (for a client with a tag allow list; other clients ignore the tags), `fingerprint(&self) -> [u8; 32]`, and `predicate(self: &Arc<Self>) -> Arc<dyn Fn(&NotePath, &[String]) -> bool + Send + Sync>`, which is what `quire-index` takes (it cannot depend on `quire-agent`; the agent-index design names this type).
- **The locked-folder list needs no disk read when a manifest exists.** The manifest (`quire_vault::changes::Manifest`, architect step A2) lists every file, key files included, from one scan; `lock::folders_in(listing)` already turns a listing into the list of locked folders. Without a manifest (in-memory vaults in tests; whatever a host that has none does) `Visibility` falls back to `folder_of_with` with an existence test, once per distinct folder, never per note. Correctness does not depend on the manifest; only the count of calls does.
- **One rule, written once.** `AgentStore::effective` and `Visibility::allows` call the same `fn decide(rules, actor, folder, name, tags)`. `Visibility` never has its own list of rules. A property test (section 6) checks `allows` against `effective_mode(.., Read)`.
- **When it is rebuilt.** It is cached with the key (policy stamp, approvals generation, locked-folder list). `AgentStore::visibility(actor)` returns a clone of the current `Arc<Visibility>` and rebuilds when the key changed, so a call checks a few integers and one hash, not the policy file per note. A call uses one `Visibility` from start to end, so a policy change during a call applies to the next call. Subscriptions keep their own URI check, asked again for every notification (`subs::Visibility`, a different type in `quire-mcp`; it will be renamed `UriVisibility` so the two names do not meet).
- **Fingerprint.** It covers everything that can change an answer of `allows`, and nothing else: which zones deny reading for the actor (not their other modes, so clients that differ only in `direct` or `propose` zones share a view, as the agent-index design asks), "AI off", "revoked", the client's allow list (the rule, not the tags), the hidden-segment rule, and the sorted locked-folder list. Two actors with equal fingerprints get equal answers for every path. A test builds random policies and paths and checks this one way (equal fingerprint, equal answers). The converse is not needed: unequal fingerprints may still agree, which only costs a view.
- **Use.** `ToolCx` gets `visibility: Arc<Visibility>` (taken once when the call starts, so a tool that never lists pays one clone). `common::visible(cx, path)` keeps its signature and calls `cx.visibility.allows(path)`; listing tools call `allows` directly. A human actor short-circuits as today (`actor.is_human()`).
- **Paths an agent names** (`existing()`, `guard()`) still go through `resolve_in` and the full check, with the canonicalize calls. `Visibility` is only for paths that came out of the index.

The tag allow-list case (4) uses the index record's tags, not the file's. The index lags a file by the watcher's debounce, so for a client with a tag allow list a note whose tag was just removed outside Quire may be listed for that short time. `view` of it still runs the full guard, which re-reads the file. This is the one place `Visibility` is looser than `effective`; open question 3 lets the owner say no. Clients with an allow list are rare (a policy option) and no other client is affected. The fingerprint of such a client does not include tags; the agent-index design (its 3.2) keys that client's view by the rule and uses each record's tags for membership, so a tag edit moves one note in or out of the view at the next index update, with the same lag.

What stays on the disk, and is bounded by the page, not the vault:

- The `last_actor` column of the rows a call returns (a ledger lookup; at most `limit` rows, and `limit` is capped at 500).
- `modified` for every row and for `sort: modified`, `since` and `until`: today `list` stats every note. The manifest row has `mtime_ns` and the index already reads the manifest to decide what to parse, so this note asks the index design for `NoteRecord.mtime_ns` (0 if the platform gives none), set from the manifest row and kept in step on every update. With it `sort: modified` costs a sort and `modified` costs nothing. Until it exists the fallback is today's behaviour (stat the notes that pass the other filters). This is the interface I need from the index-startup design.
- `vault_info`'s attachment count: from the manifest's file list (zero filesystem calls); without a manifest, the walk it does today (`storage().list()`), now with `Visibility` instead of a per-file guard.

Other costs found while reading, fixed in the same step because they dominate once the disk reads go:

- `list` sorts by path and title with `to_lowercase()` in every comparison; it will sort with `sort_by_cached_key`.
- `tasks`, `properties` and `tags` collect and sort every visible record by path on each call (the 0.13.3 fix for stable output). With keyset cursors they still sort once, then skip to the cursor, take `limit` and count the rest for `total`; the sort is cheap next to the disk reads it follows.
- `tasks` counts newlines from the start of the note for every task to get its line number (`matches('\n')` over `src[..offset]`). It will count only for tasks it returns.
- `query_view` (`views.rs:785`, `sort_rows`) allocates in every comparison; that is the performance scan's item 11, designed by the performance team. This note only passes `limit` and the cursor to it.

Expected result: the filesystem work in a listing goes from one `resolve` plus several `exists` per note to none per note. The time target is G5.

### 3.7 MCP spec compatibility

The server implements 2026-07-28 and four older versions (`protocol.rs`: `MODERN`, `LEGACY`). The next version is expected around March 2027. Nothing here depends on it, and nothing here blocks it.

- Everything in this note uses features of 2026-07-28 that are already in use: `inputSchema`, `outputSchema`, `structuredContent`, annotations, `resource_link`, `_meta`. The new fields are plain JSON in existing objects.
- The deprecation signal does not use a spec feature. Description and title text and an extra text item work in every version. `_meta["quire/deprecated"]` is a vendor key; a client that ignores it loses nothing.
- Pagination of `tools/list` itself is not needed (33 tools, at most 40,000 bytes).
- Tool names use only lower-case letters, digits and underscores. A test asserts `^[a-z][a-z0-9_]{0,63}$` for every name, so a naming rule a later spec may adopt for tools is already met.
- Era handling stays in `protocol.rs` and `tool_result`; the tools produce `ToolOutput` and know nothing about eras. When a new spec arrives it is a new `Era` value and a new fixture, as 2026-07-28 was. The 0.9 note (section 4.7) asks for one recorded session per era; that stays.
- A guess, to be checked when the spec is published: a later spec may change how tools declare output or errors. The adapters and aliases live in the handlers and the registry, not in the wire layer, so the change would be in `tool_result` and `tools_list` only.

### 3.8 The panel, ACP and the in-app assistant

All three use this registry; none has its own tool list.

- **In-app assistant (`quire-assistant`, `ToolHost`).** It holds its own `ToolRegistry::standard()` and `IndexService`. `defs(cap, core)` builds the model's tool definitions from `offered_for(grant)`. Change: `defs` skips every spec with `deprecated: Some(_)`, in every mode (the full mode lists them today, which costs a small model about 1,000 tokens of context; by the same estimate). The calls the panel makes are by 0.9 names, so `describe_call` and `describe_result` (which match `"search"`, `"view"`, `"list"`) do not change. `CORE_TOOLS` stays. Panel models see the canonical (new) argument names because `defs` copies the advertised schema; aliases only matter for models that remember the old names. `ToolHost::call` builds a `ToolCx` per call, so it takes the actor's `Visibility` from its `AgentStore` like the server does. The panel is an actor (`panel:<provider>`), so it gets the same per-agent view as any other agent (3.9).
- **ACP.** `acp.rs` starts the external agent's MCP server as `quire-cli mcp <cwd> --allow-write --client acp:<key>`. An ACP agent is an ordinary stdio MCP client: it gets whatever `tools/list` gives its era, the deprecation text if it is on an older version, and the same bounds. Nothing in `quire-assistant` changes for ACP except what `ToolHost` changes above. The `--allow-write` stderr line (polish item on `mcp.rs:91`) is not part of this note.
- **CLI.** `quire-cli agent tools` and `agent log --since` use the registry and `parse_time`. `--since 7` (a bare integer) now fails with the message from 3.2 instead of meaning 1970; the CLI prints it as its usage error.

### 3.9 What `ask` and `search` take from the per-agent index

The leak fixed in 0.13.3 for tool results (hidden notes cannot take a place) leaves one in the statistics: IDF and the meaning model are built from every note (`0.14-health-gates.md`). The owner decided to fix it with a separate index per agent view. This note only fixes the seam. The names below are the frame's and `0.14-agent-index.md`'s:

- `ToolCx` today carries `index: &IndexService` (records, sources, links, search). `search` and `ask` call `search_sections_where(..., &|p| visible(cx, p))` and `retrieve_where`. The agent-index design (3.2, 3.7) replaces these with a handle: `cx.index.scope(cx.visibility.fingerprint(), cx.visibility.predicate())`, then `search_sections_in` and `retrieve_in` on it, without a `visible` closure, with the view's own statistics. Connections with the same fingerprint share one view (at most 4 are kept); a human actor never gets a view. Until a view's meaning model is fitted it answers by keyword with its own IDF, never with the whole-vault model (frame section 4). A caller whose view is still building sees `indexing` in the result, as it does today for PDFs. `ToolHost` builds its `ToolCx` with the actor's `Visibility`, as the server does.
- Every other tool keeps reading records from the shared index and filtering with `Visibility`. A record list leaks nothing statistical: `tags` counts and `list` rows come only from notes the caller can see.
- `search` and `ask` keep their second guard, `hits.retain(|h| visible(cx, &h.path))`. The visibility test (section 6) keeps running every read tool, so a mistake in a view still fails it.
- The 0.13.3 tolerance in `tests/visibility.rs` (`RANKED` and `COUNTED`: they accept different `ask` and `search` rankings, as long as nothing hidden is named) is removed when the views land (the agent-index design's section 3.8 has the diff): with a view per agent the replies of the plain and the hidden-notes vault must be identical, scores included. Nothing in this note touches that test except that the new arguments (`cursor`, `max_tokens`, `since`, aliases) are driven by the same schema loop.

## 4. Alternatives considered

- **Remove the nine now.** Simplest, saves the most code. It breaks hard-coded prompts and scripts we cannot see, with no way to measure them. The listing and the callability are separate costs, so we remove the one that costs context (listing) and keep the one that costs little (the adapter).
- **List the nine to legacy eras only, for good** (the scan's suggestion). Era says how new the client's protocol is, not how old the setup is; 2025-11-25 clients are current. Done in 0.14 for the modern era only, as a step.
- **Keep the nine as separate implementations.** Costs nothing now and keeps 0.8's exact text. It also keeps a second copy of every visibility rule, and 0.13.3 showed what that costs. Adapters keep the 0.8 text and have one implementation.
- **Rename parameters and break the old names.** Cleaner schemas. Agents carry the old names in skills and prompts; the skill file itself is copied into people's setups. Aliases cost one `or` per argument.
- **Advertise the aliases in the schema.** Easier to discover, but 20 or so extra properties in a 41 KB list that agents pay for every session. Not worth it.
- **Offset cursors everywhere.** Already there and simple. A page can repeat or skip a row when notes change between calls; agents page through `tasks` and `list` while editing. Keyset needs one optional field.
- **A generic `fields` parameter to trim output.** Would cut tokens further, but it is a feature and it grows every schema. Out of scope.
- **Cache the visibility answer per path across calls.** Faster again, but the cache must be invalidated on every policy, lock and file change, and a stale entry is a leak. A snapshot that lives for one call cannot be stale across a policy change.
- **Move listings into the index and drop `visible`.** Not possible: visibility depends on the caller, and the index is shared (until the per-agent views, which only cover ranking).

## 5. Compatibility

**Older devices on sync.** No vault file, no sync format and no wire message changes. 0.13.x and 0.14 sync as before. The tool surface is per device.

**Existing agent setups.**

- Every argument name that works today works after 0.14 (3.2). Every tool name that works today works (3.4). Two behaviours tighten, both on inputs that were wrong or unbounded: a bare integer time shorter than 13 digits is refused; `tasks` and `query_view` cap at 500 rows (they cut at 1,000 before) and now give a cursor.
- `read_note`, `list_notes` and `list_tags` become bounded (3.4.1). A note longer than about 60 KB is cut with a pointer to `view`. This is the one visible change for the nine.
- Modern clients stop seeing the nine in the list. A client that cached an old list and calls them still succeeds.
- Result objects only gain fields (`total`, `truncated`, `next_cursor`, `_meta`). Text output of the 0.9 tools gains a "N more" line only when a list was cut.
- The CLI: `--since` with a bare small integer now fails with a message.
- `docs/formats/mcp.md` (tokens, consent, approval keys) is not touched. No file format changes.

**Real-time collaboration later.** Nothing here assumes one writer.
- Tools are stateless; no tool keeps state between calls. The only state in a call is the snapshot, which dies with the call.
- Concurrency control is already optimistic: `expected_version` plus a rebase and a merge preview. The version becomes documented as opaque so a later operation-log layer can issue its own values (a vector or an operation id) without breaking agents. Cursors carry a fingerprint and a key, not a file offset into the vault.
- Keyset cursors tolerate rows appearing and disappearing between pages, which is what concurrent writers do.
- `Visibility` is rules and a fingerprint, not a copy of the vault, and takes no lock on it, so a collaboration layer under the index changes nothing here.

**Re-bless policy.** The sessions run `tools/list`, `search`, `view`, `str_replace`, `create`, a resource read and an unknown tool. `tools/list` carries every schema, so any schema change re-records all four files; that is expected and is not by itself a sign of a mistake. Rule: a bless is committed on its own, in the commit that causes it, and its diff must contain only these kinds of change, each named in the commit message:

1. Modern file: the nine tools gone from `tools/list` (exactly nine entries removed).
2. Older files: the nine entries' `description` (prefix) and `title`; the `instructions` sentence.
3. All files: the new properties of 3.3 (`max_tokens`, `limit`, `total`, `truncated`, `next_cursor`) in the entries of the tools that gain them; the `Unknown tool` text.
4. No change to the `result` of `search`, `view`, `str_replace` or `create` other than `total`/`truncated` fields where those tools gain them. A different `text`, `path`, `version`, `hits` or `outcome` is a bug until proven otherwise.

Whoever blesses reads the diff against this list. The 0.8 fixtures are never blessed; if `answers_0_8_clients_as_0_8_did` fails beyond the two relaxed fields, the code is wrong.

- **Agents:** every list an agent can ask for (`list`, `tasks`, `tags`, `properties`, `recent_activity`, `history`, `proposals`, `links`, `query_view`) now has a limit, a size cap and a way to continue, and says when it was cut. Before, `tasks` stopped at its limit without saying so.

- **Agents:** `list`, `tags`, `properties`, `tasks`, `links` and `vault_info` answer several times faster on large vaults; at 50,000 notes they took close to a second each. (A target; the figure is set once measured.)
- **Agents:** a time such as `since: "7"` with no unit is now refused with a message instead of meaning 1970.

## 9. Open questions for the owner

1. **Listing and removal of the nine names.** The architect's frame (rule 5) lists them to every client in 0.14, keeps them working through 0.15.x and removes them no earlier than 0.16. I differ in one place (3.4.3): stop listing them to modern-era clients already in 0.14, and to all in 0.15. Recommendation: my version, and removal at 1.0 (announced in the 0.15 and 0.16 changelogs). If you prefer the frame, step 6 changes one condition and G1 and G2 become 42 tools and about 42,500 bytes (my guess: today's 41,315 plus the new fields). Removal in 0.16 is possible but we cannot see who still uses the names: there is no telemetry and the ledger does not keep tool names.
2. **`replace_in_note` has no successor.** Recommendation: add `all: true` to `str_replace` (replace every occurrence), do not carry the regex form forward, keep the old name working until removal. The alternative is to leave `replace_in_note` alone and un-deprecate it, which leaves one 0.8 name in the list for good.
3. **Tag allow lists and `Visibility`.** For a client whose policy limits it to notes with certain tags, a listing uses the index's tags, which can lag the file by the watcher's debounce. `view` of the note is still fully checked. Recommendation: accept (the lag is a fraction of a second and the policy option is rare). The alternative is to read the tags from the file for those clients only, which keeps the per-note disk read for them.
4. **Lowering `tasks` and `query_view` maximums from 1,000 to 500.** Recommendation: yes. A caller that asks for 1,000 gets 500 and a cursor; `max_tokens` would have cut them well before 1,000 rows in any case (a task row is around 60-100 tokens by my estimate; a guess).
