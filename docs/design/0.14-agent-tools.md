# Quire 0.14: agent tools, one set with one convention

Status: current
Area: agents/MCP: the tool registry (`ToolRegistry`) shared by MCP, the agent panel and ACP agents
Code: `crates/quire-mcp/src/tools/{mod,common}.rs` (`legacy.rs` is deleted), `crates/quire-mcp/src/tools/read/*.rs`, `crates/quire-mcp/src/tools/write/{append,edit_section,str_replace}.rs`, `crates/quire-mcp/src/{bounds,server}.rs`, `crates/quire-agent/src/` (new `Visibility`, owned by this design as the architect's step T1), `crates/quire-assistant/src/runner.rs` (`ToolHost::defs`), `apps/quire-cli/src/commands/agent.rs` (`agent tools`), `packaging/perf-check.py` (budgets), `docs/agents.md`, `skills/quire/SKILL.md`; tests in `crates/quire-mcp/{src/tools/mod.rs,src/server/tests.rs,tests/visibility.rs}`

This note covers the agent-tool half of 0.14. It adds no tool. It does four things: it removes the nine 0.8 duplicate tools, it gives every tool the same parameter names (old names keep working), it bounds every listing, and it removes the per-note disk reads from listings. It keeps to the frame in `0.14-architecture.md` (section 4 for views, section 5 for budgets). Rule 5 of the frame's section 7 (a deprecation window for the nine names) is superseded by the owner's decision below; the frame needs that rule and its step T2 text corrected. `ask` and `search` take their view of the index from the per-agent index design (`0.14-agent-index.md`); section 3.9 says what the tools need from it.

## 1. The problem, as measured

Sources: the 0.14 performance scan (item 5), the 0.14 polish scan (items 3, 5 and 6), and the fixtures in `crates/quire-mcp/tests/fixtures/`.

**Nine duplicate tools.** `ToolRegistry::standard()` registers the 0.8 tools first (`legacy::tools()`), and `tools_list` offers them to every era. A client with a write grant sees 42 tools; nine are the 0.8 names in `legacy::NAMES`: `search_notes`, `read_note`, `list_notes`, `backlinks`, `ask_notes`, `list_tags`, `create_note`, `append_to_note`, `replace_in_note`. In `mcp-0.9-modern.jsonl` the `tools/list` result is 41,315 bytes (about 13,800 tokens by the estimate in `bounds.rs`, `ceil(bytes / 3)`). The nine take 3,045 bytes of that (about 1,000 tokens). The skill and `docs/agents.md` already tell agents to ignore them, yet agents spend context on them and sometimes pick them. The agent panel offers them too: `ToolHost::defs` lists every `Read` and `Write` tool, and only the "core" mode filters by `CORE_TOOLS`. A small on-device model in the full panel mode pays for them.

The nine are a second implementation of the same reads. The 0.13.3 leak (hidden notes taking source numbers in `ask` and `search`) was in `ask_notes` and `search_notes` as well. Each duplicate is another place where the visibility rule can be forgotten. Their gaps, from the polish scan: no `outputSchema`, one-line descriptions, no `expected_version`, `create_note` takes `title` + `folder` where `create` takes `path`, `append_to_note` has no `run`, `list_notes` takes any `limit` (default 200), `read_note` is unbounded, `ask_notes` and `search_notes` have no cursor.

**Names disagree.** The same idea has several names:

- A section is `view.section`, `edit_section.heading` and `append.under_heading`.
- A line range is `view.lines: [10, 40]` but the resource template is `?lines=10-40`.
- A result count is `limit` (most tools), `k` (`ask`) or `max_rows` (`query_view`).
- Folder and tag filters are `search.filters.{folder, tags[]}`, `list.{folder, tag}`, `tasks.{path, tag}`.
- A time is `search.modified_after`, `recent_activity.since`, `read_version.as_of`, `revert.since`, and each description spells the formats differently.
- `diff.from/to` are versions; `rename.from/to` are paths.
- `proposals.mine` (bool) against `recent_activity.actor` (string).
- `parse_time` (`common.rs:90`) reads any bare integer as Unix milliseconds, so `since: "7"` means 1970 and returns everything.

**Unbounded results.** Only `search`, `view`, `ask`, `read_version` and `canvas_read` take `max_tokens`. `tasks` (up to 1,000 rows), `query_view` (1,000), `recent_activity` (500), `tags`, `properties`, `proposals`, `history`, `neighbors`, `links`, `hierarchy` and `diff` return a whole list with no token bound and no `truncated`. `tasks` stops at `limit` without saying so, so an agent cannot tell "200 tasks" from "200 of 900" (`tasks.rs`: `if rows.len() >= limit { break; }`). `docs/agents.md` says the default bound is 4,000 tokens; `search` uses 2,000 (`search.rs`: `bounds::max_tokens(a, 2_000)`).

**Listings touch the disk once per note.** `list`, `tags`, `properties`, `tasks`, `links`, `vault_info`, `query_view` and the `where` filter call `common::visible` for every record. That calls `AgentStore::effective`, which for each note runs `resolve_in` (two `canonicalize` calls), `lock::folder_of` (two `exists()` per folder level) and `policy_state()` (reads and hashes the policy file). Timings from the scan (`quire-cli mcp`, p50 of 5 calls):

| Tool | 10k notes | 50k notes |
|---|---:|---:|
| `list` | 165 ms | 918 ms |
| `tags` | 165 ms | 742 ms |
| `properties` | 166 ms | 816 ms |
| `vault_info` | 162 ms | 812 ms |
| `links` | 154 ms | 886 ms |
| `tasks` | 188 ms | 807 ms |
| `query_view` (notes) | 156 ms | 796 ms |
| `search` (for comparison) | 28 ms | 140 ms |
| `backlinks` (for comparison) | 2.5 ms | 17 ms |

The perf job (`packaging/perf-check.py`) checks only `view` and `search`. `list` with `sort: modified` also calls `Storage::modified` for every note (`list.rs`), and the path and title sorts lower-case in every comparison.

**What 0.13.3 already fixed.** Output order no longer depends on hash order (`tasks`, `links`, `neighbors`, `properties` and `list` sort before they cut). A `where` condition is one line (`views::parse_where`) and runs only over visible notes (`views::run_over` with `visible`). This note keeps both and does not touch them.

### 3.2 The target convention

One table. "Accepted too" are old spellings. They are read by the handlers, kept out of the advertised schema (so the 41 KB list does not grow for them), and kept as long as the nine legacy names are (3.4.3): an alias costs one `or` in an argument reader. `docs/agents.md` lists them in one sentence.

| Idea | Canonical | Accepted too | Tools |
|---|---|---|---|
| A note | `path` (a title also resolves, as `existing()` does today) | | every per-note tool |
| Two notes | `from`, `to` (paths) | | `rename` |
| Two versions | `from_version`, `to_version` | `from`, `to` | `diff` |
| A section | `section` | `heading` (`edit_section`), `under_heading` (`append`) | `view`, `edit_section`, `append` |
| A line range | `lines`: `[10, 40]` or `"10-40"` | | `view`; the resource template's `?lines=` takes the same two forms |
| Row cap | `limit` | `k` (`ask`), `max_rows` (`query_view`) | every list |
| Size cap | `max_tokens` | | every list and every read |
| Paging | `cursor` in, `next_cursor` out | | every paged tool |
| Folder | `folder` (prefix) | `filters.folder` | `search`, `list`, `tasks`, `query_view` filters |
| Tags | `tags` (array; every tag must be on the note) | `tag` (one string), `filters.tags` | `search`, `list`, `tasks` |
| Property filter | `where` (one line) | `filters.where` | `search`, `list` |
| A time range | `since`, `until` | `modified_after`, `modified_before` (`search`), `filters.*` | `search`, `list`, `recent_activity`, `revert` |
| A point in time | `as_of` | | `read_version` |
| Whose changes | `actor` (an id; `"me"` means the caller) | `mine: true` (`proposals`) | `proposals`, `recent_activity`, `revert` |
| Optimistic lock | `expected_version` | | every edit of one note |
| Group of changes | `run` | | every write |
| Link types | `type` (array) | | `neighbors`, `links` |

Decisions that are not obvious:

- **Flat beats nested.** `search` keeps reading `filters{}` (it is on the 0.9 wire), but the advertised schema is flat, like `list`.
- **`list` gains `since` and `until`** (the same filter `search` has) so that "notes changed this week" is not a `search` with an empty query. This is the only new filter, and it exists because the old spelling is `modified_after`. It needs a modification time per note (3.5).
- **`tasks.path` stays** (one note, what it means today) and `tasks` gains `folder`. `tag` and `tags` both work.
- **Times.** One parser, one description string (`TIME_FORMATS`: "RFC 3339, YYYY-MM-DD, or a time back from now: 30m, 24h, 7d, 2w") used in every schema. `parse_time` rejects a bare integer shorter than 13 digits with `invalid_args`: "`since: 7` has no unit; write 7d or a date"; a ten-digit one says "looks like Unix seconds; send milliseconds, a date, or 7d" (guessing would be worse). Thirteen digits or more stays Unix milliseconds, as today, so nothing that works breaks. A time that cannot be parsed is `invalid_args` and names the argument.
- **`lines`** is accepted as an array or as `"10-40"` in the tool and in the resource template, because agents copy whichever form they last saw.
- **Results.** Every list keeps its array name (`notes`, `tasks`, `events`, ...). Each adds `total` (the count after filtering, when known), `truncated` and `next_cursor`. These are new fields on existing objects, so no client breaks.
- **`version` is opaque.** `docs/agents.md` says `sha256:` plus 32 hex digits. It will say: "compare versions for equality, never parse them". Today they are content hashes; a later layer may issue other values (section 5).

### 3.3 Bounds for every list

Two bounds, whichever is hit first: `limit` (rows) and `max_tokens` (size, estimated as `ceil(bytes / 3)`, hard maximum `HARD_MAX_TOKENS` = 20,000, `bounds::max_tokens` clamps to 100-20,000). A cut result has `truncated: true` and, if more can be fetched, `next_cursor`. `fit()` always keeps at least one row, so a single huge row cannot make an empty page that never advances.

| Tool | `limit` default / max | `max_tokens` default | Cursor | `total` | Changes from today |
|---|---|---:|---|:-:|---|
| `search` | 10 / 50 | 2,000 | offset | no | none. The docs are fixed to say 2,000 |
| `ask` | 6 / 20 (`limit`, `k` accepted) | 4,000 | none (one answer) | no | `truncated` added |
| `list` | 100 / 500 | 4,000 | keyset | yes | `max_tokens`, `total`, `truncated` |
| `tasks` | 200 / 500 (was 1,000) | 4,000 | keyset | yes | maximum lowered, `max_tokens`, cursor, `total`, `truncated` |
| `query_view` | 100 / 500 (was 1,000; `max_rows` accepted) | 4,000 | keyset when ungrouped | yes | same; a grouped view is cut by `max_tokens` and says `truncated` |
| `recent_activity` | 100 / 500 | 4,000 | keyset | yes | `max_tokens`, cursor, `total`, `truncated` |
| `history` | 20 / 200 | 4,000 | keyset | yes | same |
| `proposals` | 50 / 200 | 4,000 | keyset | yes | adds `limit`, the rest as above |
| `tags` | 200 / 1,000 | 4,000 | keyset on the tag name | yes | adds `limit`; sorted by tag name, counts are data (a count that changes between pages cannot make a row repeat) |
| `properties` | 100 / 500 keys | 4,000 | keyset | yes | adds `limit` |
| `outline` | 500 / 2,000 headings | 4,000 | keyset (line) | yes | adds `limit`, `max_tokens`, `truncated` |
| `neighbors` | 50 / 200 | 4,000 | none | yes | `max_tokens`, `total`, `truncated` |
| `links` | 100 / 500 | 4,000 | keyset | yes | `max_tokens`, cursor, `total` (it has `truncated`) |
| `hierarchy` | 200 / 500 | 4,000 | none | yes | `max_tokens`, `total` (it has `truncated`) |
| `diff` | n/a | 4,000 | offset (line) | no | `max_tokens`, `truncated`, `next_cursor` |
| `view`, `read_version` | n/a | 4,000 | offset (line) | n/a | none |
| `canvas_read` | n/a | 4,000 (200-20,000) | none | n/a | none (it cuts and says `truncated`) |
| `vault_info` | `zones` capped at 50 | n/a | none | n/a | `truncated` on `zones` |

Why two kinds of cursor:

- **Offset** (as `bounds::Cursor` is today: `{"o": offset, "v": version}`) stays for results that are one ranked list or one note's lines. A ranked list changes with the index, so `cursor_stale` is the honest answer when the question changed.
- **Keyset** for lists with a total order: the cursor carries the last sort key and path (`{"o": n, "v": fingerprint, "k": "<last key>"}`; `k` is a new optional field). The next page starts after that key. A note created or deleted between two pages then cannot make a page repeat or skip a row, which an offset allows. `Cursor::decode` still reads old cursors (no `k`), so a cursor in flight across the upgrade still works. The fingerprint is the arguments with `cursor` removed, as `list` does today. `since: "7d"` is resolved to a timestamp on the first call and the cursor carries that timestamp, so "7 days ago" does not move between pages.
- Keys: `list` (sort key, path), `tasks` (path, line), `recent_activity` (time, ledger position), `history` (time), `proposals` (created, id), `tags` (tag name), `properties` (key), `links` (direction, path), `outline` (line).
- `limit` above the maximum is clamped, not refused, and the result says `truncated` when more exist. `docs/agents.md` says this once. `total` costs one filter pass per page; that is inside the G5 budgets for every list except possibly `tasks` (200,000 tasks at 50k notes), which step 3 measures before the note promises `total` there.

A cursor for a changed fingerprint answers `cursor_stale`, as now. The page size when `max_tokens` is the limit varies by row size; the text of a cut result says how to continue, as `list` does today.

### 3.4 The nine 0.8 tools are removed

The owner decided that the nine names in `legacy::NAMES` go in 0.14. They are not unlisted and kept callable: most MCP hosts let a model call only listed tools, so "callable but not listed" would be removal for most clients anyway, and the nine are a second implementation of the visibility rule (section 1).

| 0.8 name | Use instead (0.9 tool) |
|---|---|
| `search_notes` | `search` (ranks sections, not notes; each hit has a line range for `view`) |
| `read_note` | `view` (`path`; long notes come in pages: `max_tokens`, `cursor`) |
| `list_notes` | `list` (`folder`, `tags`, `where`, `sort`, `limit`, `cursor`) |
| `backlinks` | `neighbors` with `direction: "in"` (each edge has the linking line as `context`), or `links` |
| `ask_notes` | `ask` |
| `list_tags` | `tags` |
| `create_note` | `create` (`path` is `folder/title.md`; it refuses to overwrite) |
| `append_to_note` | `append` |
| `replace_in_note` | `str_replace`, with `all: true` to replace every occurrence (there is no regex form) |

#### 3.4.1 What a client gets when it calls a removed name

A `tools/call` for one of the nine answers like any unknown tool, but the message names the replacement. It is an error result (`isError: true`) with code `not_found`, in every protocol era, over stdio and HTTP:

```
No tool called “search_notes”: it was removed in Quire 0.14. Use `search` instead
(see "Removed tool names" in docs/agents.md). Call tools/list for the names.
```

The structured content (eras that have it) is `{"error": "not_found", "removed": "search_notes", "use": "search"}`. Any other unknown name keeps the generic text "No tool called “{name}”. Call tools/list for the names." (the polish scan's wording; 3.10). The table is one constant, `REMOVED_TOOLS: &[(&str, &str)]` (old name, replacement and a short note), in `server.rs` next to the call that uses it. It is not a tool list: nothing lists it, `legacy::NAMES` no longer exists, and a test checks that every replacement it names is a registered tool. Recommendation: keep the table until 1.0 so an old setup gets an answer that says what to do, then drop it (the owner can drop it earlier; it costs one constant).

A removed tool is never offered, in any era: `tools/list` has the same 33 tools for the five protocol versions (older versions still get fewer fields: no titles or output schemas before 2025-06-18, as now).

#### 3.4.2 `str_replace` gets `all`

`replace_in_note` was the one tool with no 0.9 successor: it replaced every occurrence and could take a regex. `str_replace` gains `all: boolean` (default false). With `all: true` it replaces every occurrence of `old_str`; `no_match` if there is none; `not_unique` is not raised; the result says how many were replaced (`replacements`, a new field). `old_str` must still be non-empty. Everything else about it (`expected_version`, rebase, `run`, the policy route to a proposal) is unchanged, and the change goes through the same `AgentStore::submit` as one edit. The regex form is not carried forward.

### 3.5 No disk read per note

The cause is that `AgentStore::effective` answers one path at a time, and every answer re-derives things that depend only on the folder or on the whole call.

What a visibility answer depends on (`store.rs`: `effective`, `candidates`):

1. The policy state: one `Arc<PolicyState>`, valid until the policy file, the device state or the approvals change. Reading and hashing the file belongs to the call, not to the note.
2. The folder: zones, hidden folders (a segment starting with `.`), and locked folders (a key file in some folder above) are all decided by the folder prefix, not by the file. `lock::folder_of_with` already takes an existence test.
3. The file name: encrypted names and key files (`is_encrypted_name`, `is_key_file`), checked on the string.
4. For a client with an allow list (`c.limited()`): the note's tags (`tags_of`, which today stats the file for its cache stamp).
5. Symlinks. `resolve_in` follows them. The vault listing skips every symlinked note and folder (`storage.rs:193` and `:536`: "a symlinked note or folder is skipped"), so a path found by a walk is a regular file below regular folders, and `real == path`. That holds for the walk. It does not hold for `IndexMsg::Upsert`, which takes any path from any caller, so the design enforces it (below) instead of assuming it. The canonicalize calls stay for paths an agent names, which keep `guard()`.

The design follows the frame's section 4: **`quire_agent::Visibility`**, a value built from path-prefix rules with no filesystem call per note, plus a 32-byte fingerprint of those rules. This design owns it (the architect's step T1); the agent-index design uses it and must not build a second one.

- **What it holds.** The actor, the policy snapshot (1), the folder rules of (2) as prefixes (zones with their modes, hidden segments, the locked-folder set), the file-name rules of (3), and the allow-list rule of (4) when the client has one. API: `allows(&self, path: &NotePath) -> bool`, `allows_with_tags(&self, path, tags: &[String]) -> bool` (for a client with a tag allow list; other clients ignore the tags), `fingerprint(&self) -> [u8; 32]`, and `predicate(self: &Arc<Self>) -> Arc<dyn Fn(&NotePath, &[String]) -> bool + Send + Sync>`, which is what `quire-index` takes. The predicate takes the path and the record's tags (review B4), so a tag-limited client's view is rebuilt like any other when a note's tags change; `quire-index` cannot depend on `quire-agent`, and the agent-index design names this type.
- **A lock made by another process hides at once (review B1).** Today `candidates` calls `lock::folder_of` on every answer, so a folder the desktop app locks is hidden from a running `quire-cli mcp` or `serve` on the next call. That must stay true, and the watcher is not trusted for it. The locked-folder set is therefore not cached across calls and not taken from the manifest: at the start of each call, `AgentStore::visibility(actor, folders)` checks `lock::KEY_FILE` and `lock::UNLOCKING_FILE` once for each distinct folder prefix that holds indexed notes (`lock::folder_of_with`, with an existence test memoised for the call). With 40 folders that is at most 80 `exists` calls (about 120 with parent folders; OS-cached, microseconds each), none per note. The distinct folders come from the index paths in one pass of string work per call (a guess: a few milliseconds at 50k notes; if it shows in the perf job the index keeps the folder set up to date). The set is part of the fingerprint, so a lock changes the fingerprint and the agent-index design rebuilds the affected views. The rest of the rules (policy, zones) are cached.
- **A path that is not a regular file never reaches a listing (review B2).** One place enforces it: `run` in `quire-index/src/actor.rs` refuses an upsert whose path the manifest does not list (the manifest scan records regular files under regular folders only), logs it once per path, and does not index it. A vault with no manifest (in-memory vaults and tests) treats every path as regular, as before. The manifest's `note_written` for Quire's own writes must come before the upsert so that a new note is listed; I assume the index-startup design does this and ask it to confirm (guess). The property test in section 6 upserts a note reachable only through a symlinked folder and checks that no listing tool returns it.
- **One rule, written once.** `AgentStore::effective` and `Visibility::allows` call the same `fn decide(rules, actor, folder, name, tags)`. `Visibility` never has its own list of rules. A property test (section 6) checks `allows` against `effective_mode(.., Read)`.
- **When the cached part is rebuilt.** The cached part has the key (policy stamp, approvals generation). A call takes a clone of the current `Arc`, adds the call's locked-folder set, and rebuilds the cached part when the key changed, so a call checks a few integers and one hash, not the policy file per note. A call uses one `Visibility` from start to end, so a policy change during a call applies to the next call. Subscriptions keep their own URI check, asked again for every notification (`subs::Visibility`, a different type in `quire-mcp`; it will be renamed `UriVisibility` so the two names do not meet).
- **Fingerprint.** It covers everything that can change an answer of `allows`, and nothing else: which zones deny reading for the actor (not their other modes, so clients that differ only in `direct` or `propose` zones share a view, as the agent-index design asks), "AI off", "revoked", the client's allow list (the rule, not the tags), the hidden-segment rule, and the sorted locked-folder set. Two actors with equal fingerprints get equal answers for every path. A test builds random policies and paths and checks this one way (equal fingerprint, equal answers). The converse is not needed: unequal fingerprints may still agree, which only costs a view.
- **Use.** `ToolCx` gets `visibility: Arc<Visibility>` (taken once when the call starts, so a tool that never lists pays one clone and the lock check only if it lists; `ToolCx` builds it on first use). `common::visible(cx, path)` keeps its signature and calls `cx.visibility.allows(path)`; listing tools call `allows` directly. A human actor short-circuits as today (`actor.is_human()`).
- **Paths an agent names** (`existing()`, `guard()`) still go through `resolve_in` and the full check, with the canonicalize calls. `Visibility` is only for paths that came out of the index.

The tag allow-list case (4) uses the index record's tags, not the file's (decided). The index lags a file by the watcher's debounce, so for a client with a tag allow list a note whose tag was just removed outside Quire may be listed for that short time. `view` of it still runs the full guard, which re-reads the file. This is the one place `Visibility` is looser than `effective`. Clients with an allow list are rare (a policy option) and no other client is affected. The fingerprint of such a client does not include tags; the agent-index design (its 3.2) keys that client's view by the rule and uses each record's tags for membership, so a tag edit moves one note in or out of the view at the next index update, with the same lag.

What stays on the disk, and is bounded by the page or by the folder count, not by the vault:

- The lock check above: at most 2 `exists` per distinct folder, once per call.
- The `last_actor` column of the rows a call returns (a ledger lookup; at most `limit` rows, and `limit` is capped at 500).
- `modified` for every row and for `sort: modified`, `since` and `until`. Today `list` calls `Storage::modified` for every note and ignores what the index already knows. `Index::modified(p)` (and `set_modified`) keep "the file's time at load, the time of an update after" (`quire-index/src/index.rs`), in Unix milliseconds. `list`, `recent_activity` and `search` use it and fall back to `Storage::modified` only when it returns `None`. No new record field and no dependency on the index-startup design. With it `sort: modified` costs a sort and `modified` costs nothing.
- `vault_info`'s attachment count: today `storage().list()` and a guard per file. It keeps the one walk (one listing per call, as `vault_info` is called once per session) and counts with `Visibility`, so it makes no per-file call. The frame's manifest listing can replace the walk later; nothing here needs it.

Other costs found while reading, fixed in the same step because they dominate once the disk reads go:

- `list` sorts by path and title with `to_lowercase()` in every comparison; it will sort with `sort_by_cached_key`.
- `tasks`, `properties` and `tags` collect and sort every visible record by path on each call (the 0.13.3 fix for stable output). With keyset cursors they still sort once, then skip to the cursor, take `limit` and count the rest for `total`; the sort is cheap next to the disk reads it follows.
- `tasks` counts newlines from the start of the note for every task to get its line number (`matches('\n')` over `src[..offset]`). It will count only for tasks it returns.
- `query_view` (`views.rs:785`, `sort_rows`) allocates in every comparison; that is the performance scan's item 11, designed by the performance team. This note only passes `limit` and the cursor to it.

Expected result: the filesystem work in a listing goes from one `resolve` plus several `exists` per note to at most two `exists` per distinct folder. The time target is G5.

### 3.7 MCP spec compatibility

The server implements 2026-07-28 and four older versions (`protocol.rs`: `MODERN`, `LEGACY`). The next version is expected around March 2027. Nothing here depends on it, and nothing here blocks it.

- Everything in this note uses features of 2026-07-28 that are already in use: `inputSchema`, `outputSchema`, `structuredContent`, annotations, `resource_link`, `_meta`. The new fields are plain JSON in existing objects.
- The removal needs no spec feature: an unknown tool is an ordinary error result with a message and, where the version has it, structured content. It reads the same in every version.
- Pagination of `tools/list` itself is not needed (33 tools, about 40,000 bytes).
- Tool names use only lower-case letters, digits and underscores. A test asserts `^[a-z][a-z0-9_]{0,63}$` for every name, so a naming rule a later spec may adopt for tools is already met.
- Era handling stays in `protocol.rs` and `tool_result`; the tools produce `ToolOutput` and know nothing about eras. When a new spec arrives it is a new `Era` value and a new fixture, as 2026-07-28 was. The 0.9 note (section 4.7) asks for one recorded session per era; that stays.
- A guess, to be checked when the spec is published: a later spec may change how tools declare output or errors. The aliases live in the handlers and the registry, not in the wire layer, so the change would be in `tool_result` and `tools_list` only.

The panel is an actor (`panel:<provider>`), so it gets the same per-agent view as any other agent (3.9).

### 3.9 What `ask` and `search` take from the per-agent index

The leak fixed in 0.13.3 for tool results (hidden notes cannot take a place) leaves one in the statistics: IDF and the meaning model are built from every note (`0.14-health-gates.md`). The owner decided to fix it with a separate index per agent view. This note only fixes the seam. The names below are the frame's and `0.14-agent-index.md`'s:

- `ToolCx` today carries `index: &IndexService` (records, sources, links, search). `search` and `ask` call `search_sections_where(..., &|p| visible(cx, p))` and `retrieve_where`. The agent-index design (3.2, 3.7) replaces these with a handle: `cx.index.scope(cx.visibility.fingerprint(), cx.visibility.predicate())`, then `search_sections_in` and `retrieve_in` on it, without a `visible` closure, with the view's own statistics. Connections with the same fingerprint share one view (at most 4 are kept); a human actor never gets a view. Until a view's meaning model is fitted it answers by keyword with its own IDF, never with the whole-vault model (frame section 4); the closure form (`*_where`) ranks with whole-vault statistics and goes away for agents. A restricted view that is still being built answers by keyword, silently: the result carries no hint, because any such hint would tell the agent that notes are hidden from it (the agent-index design's question 2; that design decides this). `ToolHost` builds its `ToolCx` with the actor's `Visibility`, as the server does.
- Every other tool keeps reading records from the shared index and filtering with `Visibility`. A record list leaks nothing statistical: `tags` counts and `list` rows come only from notes the caller can see.
- `search` and `ask` keep their second guard, `hits.retain(|h| visible(cx, &h.path))`. The visibility test (section 6) keeps running every read tool, so a mistake in a view still fails it.
- The 0.13.3 tolerance in `tests/visibility.rs` (`RANKED` and `COUNTED`: they accept different `ask` and `search` rankings, as long as nothing hidden is named) is removed when the views land (the agent-index design's section 3.8 has the diff): with a view per agent the replies of the plain and the hidden-notes vault must be identical, scores included. Nothing in this note touches that test except that the new arguments (`cursor`, `max_tokens`, `since`, aliases) are driven by the same schema loop.

### 3.10 Errors that say what to do (small, same fixture)

Two texts the polish scan flagged change in the same step as the removal, because they re-bless the same fixtures:

- `READ_ONLY` ("Start the server with --allow-write"; it moves out of the deleted `legacy.rs`) is used for stdio only. Over HTTP the text for a connection that can only read already exists in `denied_message`; the HTTP branch must not fall back to the stdio text.

## 4. Alternatives considered

- **Keep the nine, unlisted or deprecated, as adapters or as they were.** This was the first version of this note, and the architect's frame. The owner chose removal: most hosts let a model call only listed tools, so "unlisted" is removal for most clients, and each kept name is a path to keep visibility-correct and view-aware. Not chosen.
- **Keep adapters for the seven that match their successor.** The review suggested it before the owner decided. Rejected with the rest: an error that names the replacement costs one constant instead of seven handlers and their fixtures.
- **Rename parameters and break the old names.** Cleaner schemas. Agents carry the old names in skills and prompts; the skill file itself is copied into people's setups. Aliases cost one `or` per argument.
- **Advertise the aliases in the schema.** Easier to discover, but 20 or so extra properties in a 41 KB list that agents pay for every session. Not worth it.
- **Offset cursors everywhere.** Already there and simple. A page can repeat or skip a row when notes change between calls; agents page through `tasks` and `list` while editing. Keyset needs one optional field.
- **A generic `fields` parameter to trim output.** Would cut tokens further, but it is a feature and it grows every schema. Out of scope.
- **Cache the visibility answer per path across calls.** Faster again, but the cache must be invalidated on every policy, lock and file change, and a stale entry is a leak. A snapshot that lives for one call cannot be stale across a policy change.
- **Move listings into the index and drop `visible`.** Not possible: visibility depends on the caller, and the index is shared (until the per-agent views, which only cover ranking).

## 5. Compatibility

**Older devices on sync.** No vault file, no sync format and no wire message changes. 0.13.x and 0.14 sync as before. The tool surface is per device.

**Existing agent setups.**

- Every argument name that works today on a 0.9 tool works after 0.14 (3.2). Behaviours that tighten, all on inputs that were wrong or unbounded: a bare integer time shorter than 13 digits is refused; `tasks` and `query_view` cap at 500 rows (they cut at 1,000 before) and now give a cursor.
- **The nine 0.8 tool names stop working.** A setup that calls one (a prompt, a script, a client with the name hard-coded) must switch to the 0.9 tool in the table of 3.4. It gets an error that names it. A setup that lists tools first needs no change. This is the one breaking change of this note, and the changelog says so in plain words.
- Result objects only gain fields (`total`, `truncated`, `next_cursor`, `_meta`). Text output of the 0.9 tools gains a "N more" line only when a list was cut.
- The CLI: `--since` with a bare small integer now fails with a message. `quire-cli agent tools` lists 33 tools.
- `docs/formats/mcp.md` (tokens, consent, approval keys) is not touched. No file format changes.

**Real-time collaboration later.** Nothing here assumes one writer.
- Tools are stateless; no tool keeps state between calls. The only state in a call is the `Visibility` it took at the start, which dies with the call.
- Concurrency control is already optimistic: `expected_version` plus a rebase and a merge preview. The version becomes documented as opaque so a later operation-log layer can issue its own values (a vector or an operation id) without breaking agents. Cursors carry a fingerprint and a key, not a file offset into the vault.
- Keyset cursors tolerate rows appearing and disappearing between pages, which is what concurrent writers do.
- `Visibility` is rules and a fingerprint, not a copy of the vault, and takes no lock on it, so a collaboration layer under the index changes nothing here.

## 6. Risks, and how each will be tested

| Risk | Test |
|---|---|

A second property test over random policies: equal fingerprints give equal answers for every path. | A removed name misleads or comes back. | `removed_names_answer_with_their_replacement` (3.4.3): all nine names, every era, over stdio and HTTP; the replacement is registered and listed. The registry tests of 3.4.3 prove that no tool of the 0.8 set is registered. |
| The registry changes by accident. | `every_0_9_tool_is_there_in_the_designs_order` compares all 33 by name and order, with the description-and-schema rule for every tool; `order_is_fixed_and_names_unique` is updated (3.4.3). A second run inserts and deletes a note between pages (keyset: still no repeat and no skip). |
| A listing reads the disk per note again. | A test `Storage` wrapper counts `exists`, `modified`, `read` and `canonicalize` calls. **Re-bless policy.** The sessions run `tools/list`, `search`, `view`, `str_replace`, `create`, a resource read and an unknown tool. `tools/list` carries every schema, so any schema change re-records all four files; that is expected and is not by itself a sign of a mistake. Rule: a bless is committed on its own, in the commit that causes it, and its diff must contain only these kinds of change, each named in the commit message:

1. All four files: the nine tools gone from `tools/list` (exactly nine entries removed in each).
2. All four files: the new properties of 3.3 and 3.4.2 (`max_tokens`, `limit`, `total`, `truncated`, `next_cursor`, `all`) in the entries of the tools that gain them; the generic unknown-tool text for the `nope` call.
3. Nothing else in `tools/list` (no description, title or annotation changes, no reordering of the 33).
4. No change to the `result` of `search`, `view`, `str_replace` or `create` other than `total`/`truncated` fields where those tools gain them. A different `text`, `path`, `version`, `hits` or `outcome` is a bug until proven otherwise.

Whoever blesses reads the diff against this list and puts it in the commit message. The deleted 0.8 fixtures are not re-recorded; they are removed.

## 7. What the user sees

Changelog bullets (at most two sentences each):

- **Agents (breaking):** the nine tool names from Quire 0.8 (`search_notes`, `read_note`, `list_notes`, `backlinks`, `ask_notes`, `list_tags`, `create_note`, `append_to_note`, `replace_in_note`) are removed. An agent, prompt or script that calls one must switch to the tool that replaced it (the table is in docs/agents.md); the error says which, and agents get about 1,000 tokens back.
- **Agents:** `str_replace` takes `all: true` to replace every occurrence of a text in a note.
- **Agents:** every list an agent can ask for (`list`, `tasks`, `tags`, `properties`, `recent_activity`, `history`, `proposals`, `links`, `query_view`) now has a limit, a size cap and a way to continue, and says when it was cut. Before, `tasks` stopped at its limit without saying so.
- **Agents:** the same idea has the same parameter name in every tool (`section`, `limit`, `since`, `tags`); the old spellings still work.
- **Agents:** `list`, `tags`, `properties`, `tasks`, `links` and `vault_info` answer several times faster on large vaults; at 50,000 notes they took close to a second each. (A target; the figure is set once measured.)
- **Agents:** a time such as `since: "7"` with no unit is now refused with a message instead of meaning 1970. `tasks` and `query_view` return at most 500 rows a page and give a cursor for the rest.
- **Agents:** a folder you lock in the app is hidden from a running MCP server on the next request; this already worked and is now covered by a test.

## 9. Open questions for the owner

None blocks the build. Two small ones remain:

1. **How long does `REMOVED_TOOLS` stay?** It is the table that turns a call to a removed name into a helpful error. Recommendation: until 1.0, then drop it (the cost is one constant and one test).

## 10. As built: steps 2 and 3

Steps 2 and 3 are built. Where the code differs from sections 3.3 and 3.5, or settles what they left open:

- **Two checks, not one.** `common::visible` keeps the full check (`effective_mode`, links followed) and stays for paths that did not come out of the index: a path an agent named, a ledger entry's, a proposal's, a canvas or citation an agent gave. Paths from the index or the vault listing use `ToolCx::visibility()` (or `visibility_in(&ix)` taken before a closure that runs under the index's read lock). `Visibility` assumes the path is the file it names, which holds only for those.
- **Symlinked folders.** `Visibility` hides a path below a folder that is a symlink, so a path that reached the index some other way never reaches a listing whether or not the index refuses it. That is one `symlink_metadata` per folder, on a vault on disk, besides the two `exists`: three file-system calls per folder, two of them through `Storage`. A symlinked note file is not caught here; the index's manifest check is the one place for it.
- **Tags.** For a client with a tag allow list, `ToolCx` gives `Visibility` the records' tags once per call (`with_tags`), so `allows(path)` works where a tool has no record at hand.
- **One rule set, cheaply.** `decide` hands each mode to a sink with a function that names its source: `effective` collects the reasons, `Visibility` keeps only the strictest mode (`Policy::modes_for_each` is `modes_for` without labels; `zone_matches` and `hard_rule` compare ASCII text without a copy). `Visibility::mode(path, op)` answers `vault_info`'s zone probes. `guard` resolves a path once instead of twice.
- **Keys.** As 3.3 says, with these exact keys: `links` (direction, path, type: one note can link twice with different types), `history` (time, file), `recent_activity` (time, actor, op, path, to, proposal, version; two entries with the same key are one), `tasks` (path, byte offset, which orders as the line does). `query_view`'s rows carry no sort key (the view's `sort:` decides), so its cursor holds the position: a keyset in form, an offset in effect. A grouped view is cut by `max_tokens` with no cursor. `since: "7d"` is not yet carried in the cursor as a timestamp (step 4, with `since` and `until`).
- **`total`.** `neighbors` walks to its full depth to count, then shows the first `limit` and the edges between the notes shown; `hierarchy`'s total is the ancestors, descendants and siblings found before the cut.
- **Open question 2.** `tasks` with `total` at 50,000 notes and 200,000 tasks: 61 ms for the first page and 67 ms for a later one (p50 of 5, opt-level 2, on the 2-CPU VM shared with another build; 86 to 95 ms in a busier run), under the 150 ms budget. `total` is on every page.
- **Speed (G5), same conditions.** At 10,000 notes (the perf job's vault, `quire-cli bench --suite mcp`): `list` 8 ms, `tags` 7, `properties` 10, `tasks` 8, `links` 6, `vault_info` 8, `query_view` 28. At 50,000 notes: 52 to 87 ms for all of them but `query_view`, 220 ms, whose sort allocates in every comparison (the performance scan's item 11, as 3.5 says; not part of this step).
- **G2.** `tools/list` for a write grant measured 43,327 bytes after step 3, of which the nine 0.8 tools take 3,054; `tool_contract.rs` holds both, and the step-5 target is (43,327 - 3,054) x 1.05.
- **Storage calls (G4).** `listing_cost.rs` runs every read tool of the registry that returns a list, and the two handshakes, on 2,000 notes in 40 folders: none per note, two per folder, 3 to 8 more per call. What a call does for a note it names or returns (`existing`, `search`'s second guard and trust label) is bounded by the page, as this section's list of disk work says, and is allowed 6 calls per such note. Before step 2 a listing made about 4,000 calls besides 100 per folder. The perf job's exact counts at 10,000 notes in 50 folders: 103 for most listing tools, 108 for `links` and `vault_info`.
- **The handshake** (`initialize`, `server/discover`) counts the caller's visible notes with `Visibility`, copying the index's paths and tags and counting without its lock; it resolves the caller without fixing an unverified client's name.
- **Re-bless.** The four recorded sessions were re-recorded in the commit that adds the new properties, as the policy of section 6 asks. The diff is the `tools/list` line only and holds only kind 2 of the list (the new properties, `cursor` among them), plus the two maximums 3.3 lowers.
